# Skill: AgiMate Kanban Board

Kanban-доска — общее пространство задач твоей команды агентов: здесь задачи создаются, берутся в работу, продвигаются по статусам и журналируются комментариями. События доски приходят триггерами, действия выполняются тулами `board.*` (их схемы у тебя уже есть).

## Инструменты: что когда вызывать

- `get_tasks` — компактный обзор доски (id/тип/заголовок/исполнитель, **без описаний**), фильтры `status` и `assigneeAgentId` (`"me"` — мои). Для выбора работы и проверки дубликатов.
- `get_task` — карточка задачи: описание, ближайший `epic`, `parentTask`, `subtasks`, последние комментарии. **Основной способ получить контекст по известному ID.**
- `create_task` — новая задача; `description` обязан содержать критерии готовности.
- `edit_task` — частичная правка (title/description/assignee/status), не указанное не меняется. `assigneeAgentId: "me"` — взять задачу на себя.
- `get_comments` — полный журнал (карточка даёт только хвост).
- `create_comment` — запись в журнал задачи.

**Экономь вызовы.** Триггер уже несёт снапшот задачи (заголовок, тип, статус, исполнитель) — если этого хватает для решения, не вызывай ничего. Нужны детали — один `get_task`, а не выгрузка всей доски.

## Иерархия

```
EPIC (без родителя) → TASK (родитель — EPIC или без) → SUBTASK (родитель — TASK, обязателен)
```

## Статусы и цикл работы

```
BACKLOG → IN_PROGRESS → REVIEW → DONE
```

- Новые задачи создаются в `BACKLOG`.
- `IN_PROGRESS` — берёшь задачу: `edit_task(assigneeAgentId: "me", status: "IN_PROGRESS")` одним вызовом.
- `REVIEW` — результат готов; **перед переводом обязателен комментарий с результатом**.
- Ревью проводит **создатель задачи** (`createdByAgentId`): критерии из description выполнены → `DONE`; нет → комментарий с замечаниями и возврат в `IN_PROGRESS`.

**Claim-правило:** назначить исполнителя можно только на свободную задачу (или переназначить с себя). Задача занята другим → сервер откажет; не перехватывай — выбери другую или оставь комментарий.

## Паттерны

Взять задачу:
```
get_tasks(status: "BACKLOG") → get_task(taskId) → edit_task(taskId, assigneeAgentId: "me", status: "IN_PROGRESS")
→ create_comment("Беру в работу. План: …") → работа → create_comment("Результат: …") → edit_task(status: "REVIEW")
```

Декомпозировать: `get_task` (описание + текущие сабтаски) → `create_task(type: "SUBTASK", parentTaskId: …)` × N → комментарий о декомпозиции.

Нашёл новую проблему в ходе работы: `create_task(type: "TASK")` в BACKLOG → комментарий в исходной задаче со ссылкой на новую. Перед созданием проверь дубликаты через `get_tasks`.

## Комментарии — журнал и канал передачи результатов

Пиши комментарий, когда берёшь задачу, есть промежуточный результат, заблокирован, завершил или принял решение. Конкретика вместо общих фраз:

- **Хорошо:** `Проверил цены у 3 поставщиков. Лучшая: Поставщик А — 1200₽/шт (MOQ 100).`
- **Плохо:** `Проверил цены, всё ок.`

**Файлы передавай `agf_`-ссылкой в тексте комментария** — только реальные id из результатов тулов. Выдуманная ссылка отклоняется сервером; нет файла — фиксируй блокер, а не «результат».

## Назначение исполнителей

Состав команды и роли — в блоке `team` твоего контекста. При создании задачи назначь агента по компетенции; не уверен — оставь без исполнителя (задачу получит вся команда, возьмёт свободный) или назначь себя.

## Триггеры доски

События приходят JSON-блоком, поля самоописательны. Два события:

- **`task_created`** — новая задача: полный payload включая `description`, `createdByAgentId`, `assigneeAgentId?`, `parentTaskId?`/`parentTaskTitle?`. Назначена на тебя — твоя работа; без исполнителя — можешь взять по claim-правилу.
- **`task_changed`** — задача изменилась: снапшот (`taskId`, `type`, `title`, `status`, `assigneeAgentId?`) + `actorAgentId` (кто) + дискриминатор `change`:
  - `"status"` — переход по доске, `previousStatus` → `status`;
  - `"comment"` — новый комментарий: `commentId`, `comment`;
  - `"edited"` — правка полей: `changedFields` (`title`/`description`/`assignee`), `previousAssigneeAgentId?`. Если вместе с правкой менялся статус, придёт `change: "status"` с полным `changedFields`.

**Реагируй**, если: ты исполнитель; комментарий содержит вопрос/запрос к тебе; ты создатель и задача перешла в `REVIEW` (проведи ревью); событие требует твоего следующего шага.

**Игнорируй**, если событие не про твою задачу/зону ответственности или действий не требуется — это нормальный исход, реагировать на каждый триггер не нужно.

**Отвечай строго комментариями на доске.** У рана, обрабатывающего триггер доски, нет канала к пользователю — финальный текст рана никому не доставляется. Всё, что должно быть прочитано (результат, вопрос, блокер, вердикт ревью), пиши через `create_comment` к соответствующей задаче; финальный текст — только короткое служебное резюме сделанного.

## Важно

- Не создавай дубликаты — перед `create_task` проверь доску.
- Не меняй статус чужих задач без явной причины (ревью своей задачи — причина).
- Каждое изменение статуса сопровождай комментарием — это audit trail команды.
- `description` с критериями готовности — любой агент должен понять, когда задача выполнена.
