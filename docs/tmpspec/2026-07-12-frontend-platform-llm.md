# Frontend: платформенная LLM-модель (fallback без привязки)

> Временная спека для фронтенда. Бэкенд добавил **платформенный LLM-провайдер**: агент без
> единой LLM-привязки теперь работает «из коробки» на платформенной модели (когда фича включена
> на инсталляции). Изменения **аддитивные**, breaking-изменений нет. Полные схемы —
> в `docs/services/control-api-manage-llm-providers.md` (раздел Platform provider).

---

## 0. TL;DR что поменялось

| Было | Стало |
|---|---|
| Агент без LLM-привязки — нерабочий (ран падает) | Работает на платформенной модели (если фича включена на инсталляции) |
| `AgentLlmResponse` без признака источника | НОВОЕ поле `source: "USER" \| "PLATFORM"` |
| `llmProviderId` всегда UUID | **nullable**: `null` у платформенной записи |
| Пустой список `llms` = «модель не настроена» | Пустой список = «модель не настроена И платформенный fallback недоступен» |

Никакие эндпоинты не удалялись и не переименовывались. Wizard-требование «сначала подключи
LLM-провайдера» можно снимать: шаг выбора модели становится опциональным.

---

## 1. Затронутые эндпоинты (только форма ответа)

- `GET /control/manage/agents/` — `AgentResponse.llms[]`
- `GET /control/manage/agents/{agentId}` — `AgentResponse.llms[]`
- `GET /control/manage/agents/{agentId}/llms/` — `AgentLlmResponse[]`

## 2. Изменённый DTO: `AgentLlmResponse`

```jsonc
// обычная (пользовательская) привязка — как раньше, плюс source
{
  "name": "main_model",
  "model": "gpt-4o",
  "llmProviderId": "018f...",        // UUID провайдера пользователя
  "llmProviderName": "My OpenAI",
  "providerType": "OPENAI",
  "source": "USER"                    // НОВОЕ
}

// синтетическая платформенная запись (агент без привязок)
{
  "name": "platform",
  "model": "gpt-5-mini",              // модель платформенного free-tier
  "llmProviderId": null,              // НЕ адресуема: провайдер системный
  "llmProviderName": "platform",
  "providerType": "OPENAI_COMPATIBLE",
  "source": "PLATFORM"                // НОВОЕ
}
```

Семантика `source`:
- `USER` — реальная строка `agent_llms`; редактируется/удаляется как раньше
  (`PUT/DELETE /manage/agents/{agentId}/llms/{name}`).
- `PLATFORM` — **виртуальная** запись, не существует в БД. Появляется в списках только когда
  у агента **ноль** привязок и платформенный провайдер включён на инсталляции. Пропадает сама,
  как только пользователь создаёт первую привязку (личная модель всегда побеждает fallback).

## 3. Правила для UI

1. **Не давать редактировать/удалять** запись с `source === "PLATFORM"`: не показывать
   кнопки Edit/Delete (попытка `DELETE /llms/platform` вернёт 404 — записи нет в БД).
2. **Бейдж «Платформенная модель»** вместо имени провайдера: `llmProviderName` у платформенной
   записи технический (`"platform"`), человекочитаемую подпись даёт фронт.
3. **Пустой `llms[]`** теперь означает «модель не настроена и платформенный fallback недоступен» —
   в этом состоянии агент запускаться не будет; уместен прежний warning «подключите LLM-провайдера».
   Если раньше warning показывался по `llms.length === 0` — логика не меняется, просто состояние
   стало реже.
4. **Селектор провайдера при создании привязки** не меняется: платформенный провайдер никогда
   не приходит в `GET /manage/llm-providers/` и его нельзя указать в `llmProviderId` (будет 404).
5. В карточке агента платформенную запись стоит показывать как «модель по умолчанию», а рядом —
   CTA «Подключить свой ключ» (создание привязки убирает агент с free-tier).

## 4. Что НЕ входит в это изменение

- Лимиты/квоты free-tier и отображение остатка токенов — следующий этап (появится
  `GET /manage/llm-usage/`, отдельная спека).
- Управление платформенным провайдером из UI — его нет и не планируется (конфигурируется
  окружением инсталляции + флагом в БД).
- Runtime-эндпоинт `/control/agent/llm/**` (внешние агенты) fallback **не** получил — там
  по-прежнему только реальные привязки.
