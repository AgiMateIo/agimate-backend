# Frontend: расход LLM-токенов и квоты

> Временная спека для фронтенда. Бэкенд добавил учёт расхода токенов (пишется всегда, для всех
> провайдеров) и квоты. Изменения **аддитивные**. Продолжение
> `2026-07-12-frontend-platform-llm.md` (там — платформенная модель и `source` в привязках).
> Полные схемы — `docs/services/control-api-manage-llm-providers.md`.

---

## 0. TL;DR

| Что | Как |
|---|---|
| Расход по провайдерам | НОВОЕ: `GET /control/manage/llm-usage/` — used/limit/remaining за текущие день и месяц (UTC) |
| Квоты на свой (BYOK) провайдер | НОВОЕ: `GET/POST/DELETE /control/manage/llm-providers/{providerId}/quotas/` |
| Агент упёрся в лимит | Ран завершается ERROR-сообщением с готовым человекочитаемым текстом — показывать как есть |

---

## 1. `GET /control/manage/llm-usage/`

Один элемент на провайдера. У BYOK — расход **всего провайдера**; у платформенного — расход
**текущего пользователя** (лимит free-tier персональный).

```jsonc
{
  "response": [
    {
      "llmProviderId": "018f...",     // null у платформенного (не адресуем)
      "providerName": "my-openrouter", // у платформенного технический "platform" — подпись даёт фронт
      "source": "USER",                // USER = свой провайдер | PLATFORM = платформенный
      "windows": [
        { "window": "DAY",   "windowStart": "2026-07-13", "usedTokens": 300,
          "requests": 7,   "limitTokens": 1000, "remainingTokens": 700 },
        { "window": "MONTH", "windowStart": "2026-07-01", "usedTokens": 4500,
          "requests": 120, "limitTokens": null, "remainingTokens": null }  // null = квоты нет
      ]
    }
  ]
}
```

Использование в UI:
- Карточка «Платформенная модель · осталось {remainingTokens} из {limitTokens} сегодня» —
  элемент с `source: "PLATFORM"`, окно `DAY`.
- Страница провайдера: прогресс-бары day/month; `limitTokens: null` → показывать только расход,
  без прогресс-бара.
- Токены — `input + output + cache_write`; `requests` — число LLM-вызовов (не сообщений).

## 2. Квоты BYOK-провайдера

`/control/manage/llm-providers/{providerId}/quotas/` (JWT, провайдер должен принадлежать юзеру):

- `GET /` → список `{ id, subjectKind, window, limitTokens }`
- `POST /` `{ "subjectKind": "TOTAL"|"AGENT", "window": "DAY"|"MONTH", "limitTokens": >=1 }`
  → `409` если квота на такую пару (субъект, окно) уже есть
- `DELETE /{quotaId}`

Семантика для подписи в UI:
- `TOTAL` — «потолок на весь ключ» (суммарно все агенты);
- `AGENT` — «лимит каждому агенту» (один сорвавшийся агент не сожжёт ключ);
- `USER` — валиден API, но для BYOK бессмыслен (провайдер и так одного юзера) — в UI не предлагать.

Изменение лимита = DELETE + POST (PATCH нет сознательно).

## 3. Поведение при исчерпании лимита

Ран агента завершается ERROR-сообщением в сессии с готовым текстом, например:
«Дневной лимит токенов платформенной модели исчерпан. Лимит обновится в 00:00 UTC.
Чтобы снять ограничение, подключите свой LLM-ключ в настройках.»

- Текст показывать как есть — он уже написан для человека.
- Рядом уместен CTA «Подключить свой ключ» (для платформенного) — тот же флоу, что в
  `2026-07-12-frontend-platform-llm.md` §3.5.
- Лимит проверяется перед каждым LLM-вызовом: агент останавливается быстро, «долгов» не копит.

## 4. Что НЕ входит

- Квоты платформенного провайдера через API — нет и не будет (сидируются платформой).
- Per-agent разрезы расхода в `/manage/llm-usage/` — enforcement их учитывает, но вью пока
  показывает только провайдер-уровень.
- История расхода по дням/графики — только текущие окна; появится позже при необходимости.
