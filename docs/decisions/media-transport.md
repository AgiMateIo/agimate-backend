# Транспорт медиа-вызовов: как выбирается диалект провайдера

Решение о том, каким способом media-коннектор разговаривает с провайдером при генерации
изображений. Принято в июле 2026 после того, как `gen_image` на Polza.ai начал возвращать 500 —
и выяснилось, что дело не в провайдере и не в нашем коде, а в том, что мы приняли конвенцию
одного вендора за стандарт.

Реализация: `controlapi.service.llm.media` (`MediaInferenceService`, транспорты), коннектор —
`connectors/internal/media`. Текущее поведение описано в [../connectors/media.md](../connectors/media.md).

## Что было

`MediaInferenceHttp` умеет ровно один диалект: `POST /chat/completions` с
`modalities: ["image","text"]`, картинка разбирается из `choices[0].message.images[].image_url.url`
как data-URI. Это **конвенция OpenRouter**, а не спецификация. На любом другом провайдере вызов
падает ошибкой самого провайдера — у Polza это `500 INTERNAL_ERROR` с `raw: "Unknown error"`,
потому что их шлюз не маршрутизирует image-модели через чат-пайплайн вовсе (генерация живёт на
`/v1/images/generations` и на собственном `/v1/media`).

Резолвер при этом не проверял, умеет ли выбранная модель отдавать изображение: `pickModel`
фильтрует строки реестра только по `UNAVAILABLE`, а `output_modalities` не смотрит.

## Ландшафт: две разные задачи

**Зрение (image → text) стандартизовано.** `chat/completions`, картинка частью user-сообщения
(`{"type":"image_url","image_url":{"url":"data:…;base64,…"}}`). Так делают OpenAI, OpenRouter,
Google через OpenAI-совместимый слой, xAI, Together, Fireworks, Mistral и все прокси-агрегаторы.
Выпадают только API со своей формой: GigaChat (загрузка в `/files` → `attachments`, **одна
картинка на сообщение**), Yandex AI Studio (OpenAI-слой только для текста), нативный Anthropic.
Для `read_image` одной ветки достаточно — здесь чинить нечего.

**Генерация (text → image) распалась на четыре семейства.**

| Семейство | Форма | Кто | Результат |
|---|---|---|---|
| **A. chat + modalities** | `POST /chat/completions`, картинка в `message.images[]` | OpenRouter и сквозные прокси к нему (ProxyAPI `/openrouter/v1`) | base64 data-URI |
| **B. `/images/generations`** | OpenAI Images API, синхронно | OpenAI (`gpt-image-2`), xAI (`grok-2-image`), Together, Fireworks, **Google через OpenAI-слой**, VseGPT, Polza (gpt-image/dall-e) | `b64_json` или `url` |
| **C. async-задача** | submit → poll/webhook → скачать | Polza `/v1/media`, OpenRouter `/api/v1/images`, YandexART (`imageGenerationAsync` → operations), FusionBrain/Kandinsky, fal.ai, Replicate | URL на CDN или base64 |
| **D. тул внутри чата** | модель сама зовёт встроенную функцию | GigaChat (`function_call: auto` → `<img src="uuid"/>` → `GET /files/{id}/content`), OpenAI Responses API | file id |

Ключевая асимметрия, из которой следует всё дальнейшее: **A и B — опубликованные спецификации,
которые копируют дословно; C — не спецификация, а силуэт.** «submit → poll → скачать» у Polza,
YandexART и FusionBrain выглядит одинаково и не совпадает ни в одной детали (форма тела, путь
статуса, форма результата, аутентификация). Общим у них может быть только каркас — цикл поллинга
с бюджетом, шаг скачивания, запись в файловый слой, — но не протокол.

Отсюда: **generic-стратегий ровно две.** Всё, что за их пределами, — вендорский код, и это
нормально, если он не притворяется generic.

Два факта, которые дополнительно закрывают вопрос «может, обойдёмся семейством A»:

- Google свои image-модели через `chat/completions` не отдаёт **вообще** — только через
  `/images/generations` на OpenAI-слое. То есть с текущим кодом не заработал бы и Gemini напрямую.
- OpenRouter сам уходит от A: у них появился отдельный `/api/v1/images` с `input_references`
  и своим листингом. Ставка только на A стареет.

## Что показали замеры (Polza, июль 2026)

Догадки о том, «как оно у Polza», проверены реальными вызовами — и часть выводов из таблицы выше для
этого провайдера пришлось поменять.

| Проба | Результат |
|---|---|
| `chat/completions` + `modalities`, модель с `output_modalities: ["image"]` (flux, seedream, qwen…) | **500** `INTERNAL_ERROR`, `raw: "Unknown error"` |
| то же, модель с `["image","text"]` (gemini-*-image) | **200 без картинки**: `content: ""`, `images` нет — **при `image_tokens: 1290` и `cost_rub: 2.90`** |
| `POST /images/generations` | **201 + `requestId`**, результат забирается через `GET /media/{id}` |
| `POST /media` с `async: false` | **200 синхронно**: `status: completed`, `data[0].url` |
| ссылка из ответа | публичный https, `image/png`, без авторизации |
| `input.images[]` | работает и как `{"type":"url"}`, и как `{"type":"base64"}` (голый base64, без `data:`-префикса), до 8 штук |
| тело только с `prompt` | **400** у части моделей: им нужны `aspect_ratio`, `quality`, `image_resolution` |
| флаги `required` в листинге | **ненадёжны**: `gemini-3.1-flash-lite-image` не помечает обязательным ничего и всё равно даёт 400 без `aspect_ratio`, не называя поле |

Три следствия:

1. **Второй случай опаснее первого.** 500 виден в логе, а «200 без картинки» выглядит как отказ
   модели рисовать — при полностью списанных деньгах. Тихая трата хуже громкой ошибки.
2. **Семейство B у Polza вырождено в C** — отдельного синхронного `/images/generations` там нет,
   поэтому транспорт `IMAGES_GENERATIONS` этому провайдеру ничего не даёт.
3. **Поллинг оказался фолбэком, а не архитектурой.** `async: false` отвечает в том же запросе, и
   «дорогая фаза C» из плана сжалась до одного запроса за байтами. Цикл ожидания остаётся только на
   случай, если провайдер всё-таки вернёт незавершённую задачу.
4. **Профиль параметров оказался не улучшением, а условием работоспособности.** Тело с одним
   `prompt` отвергается доброй половиной моделей, и вычислить набор по флагам `required` нельзя —
   они врут. Поэтому транспорт подставляет **всё объявленное** из `top_provider.parameters`
   (`default`, иначе первое допустимое значение), а не только обязательное.

Отдельно: **у Polza в листинге есть поле `type`** (`chat` 311, `image` 22, `video`, `tts`,
`embedding`) — и именно оно, а не модальности, отвечает на вопрос «эту модель зовут медийным
эндпойнтом». Модальностям тут верить нельзя: chat-модели `openai/gpt-5.2`, `gpt-5.1` и ещё две
объявляют `output_modalities: ["text","image"]`, ничего при этом не рисуя через наш путь. Поле
лежит в `raw_metadata` — читать его будет следующая фаза.

## Решение

**Диалект — в коде (две generic-стратегии). Маппинг «провайдер → диалект» — в данных.
Профиль модели — из реестра. Уточнение — в момент настройки, не в рантайме. Всё неизвестное —
внятный отказ, а не попытка угадать.**

Это разрешение основного противоречия: знание о транспорте должно быть в коде (иначе вызов
недетерминирован и неотлаживаем) и не должно быть в коде (иначе протухает и требует релиза на
чужое изменение). Разделяем по природе знания:

| Что | Где живёт | Почему именно там |
|---|---|---|
| Диалект (две спецификации) | код, `MediaTransport` | опубликован и стабилен, меняется раз в годы |
| Маппинг провайдер → диалект | данные: поле + таблица префиксов | меняется с каждым новым прокси, релиз не нужен |
| Профиль модели | реестр (`llm_provider_models`) | уже лежит в БД, обновляется дискавери сам |
| Коррекция | проба при настройке провайдера | единственный момент, когда ошибка бесплатна |

### 1. Две generic-стратегии в коде

```java
public interface MediaTransport {
    MediaTransportType type();
    GeneratedImage generate(GenerationRequest request);
}
```

- `CHAT_MODALITIES` — прежний код как есть (OpenRouter и прокси к нему);
- `MEDIA_ENDPOINT` — `POST /media` с `async: false` и модель-нативным `input` (диалект Polza).

**Стратегия возвращает байты, а не ссылку.** Тогда `MediaInferenceService` остаётся тем, чем был
(резолв модели → вызов → файловый слой → учёт), а вся разница между провайдерами заперта за
интерфейсом. Стратегия, которой провайдер ответил ссылкой, скачивает её сама — и вопрос «кому можно
ходить по внешнему адресу» решается один раз, в `RemoteImageFetcher`, а не расползается по коду.

Зрение через транспорты **не** идёт: картинка в чат-сообщении — единственное, что все
OpenAI-совместимые провайдеры читают одинаково, и заводить там развилку не под что.

Метода `supports(capability)` из первоначального наброска нет: оба реализованных транспорта умеют и
генерацию, и редактирование, и композицию, так что метод сейчас возвращал бы только `true`. Он
появится вместе с первым транспортом, которому есть что не уметь — например `IMAGES_GENERATIONS`,
где редактирование это multipart `/images/edits`, а композиции нет вовсе.

### 2. Маппинг — в данных

Порядок разрешения:

```
llm_providers.media_transport  →  дефолт CHAT_MODALITIES  →  отказ, если транспорта нет в сборке
```

**Явное поле — единственный источник истины на сегодня**, и по-другому не выйдет: OpenRouter и Polza
оба `OPENAI_COMPATIBLE`, то есть дефолт по типу провайдера их не различает в принципе. Пустое поле
значит «как было», поэтому существующие строки не требуют миграции данных.

Таблица префиксов `base_url` (`media_transport_presets`) **отложена**: при двух провайдерах на
установку она не окупается — выбрать значение руками дешевле, чем сопровождать сид. Когда до неё
дойдёт дело, ключом должен быть **полный префикс, а не хост** (у ProxyAPI `/openai/v1` и
`/openrouter/v1` — разные диалекты на одном хосте), и вместе с ней придётся написать **одно правило
нормализации**: схема и хост в нижнем регистре, хвостовой слэш отброшен (это уже делает
`MediaInferenceHttp`), сравнение по самому длинному совпавшему префиксу. Иначе таблица начнёт молча
промахиваться, и диагностировать это станет так же тяжело, как исходную 500-ку.

### 3. Профиль модели — из того, что уже есть

`llm_provider_models.output_modalities`, `supported_parameters` и `raw_metadata` заполняются
дискавери и до сих пор не читались никем. Модальности уже читает `MediaInferenceService`
(отказ до HTTP, если модель объявила выход без `image`), остальное — следующая фаза: «какими
параметрами её просить» (`aspect_ratio` против `size`, сколько референсов) и поле `type` из
`raw_metadata`. Новых колонок не требуется.

**Транспорт и профиль — разные оси.** Имя модели транспорт не определяет: `gpt-image-2` у OpenAI
это B, `openai/gpt-image-2` у OpenRouter — A. Транспорт задаётся провайдером, профиль — моделью.

Для провайдеров, которые параметров не объявляют, профиль пуст → шлём минимальное тело, как
сейчас.

### 4. Проба при настройке

Когда пользователь задаёт `purpose_priority[IMAGE]` или подключает провайдера, — один запрос,
различающий 404 (эндпоинта нет) и 400 (эндпоинт есть, тело не то), с записью результата в поле.
Ошибка в этот момент ничего не стоит; в момент пользовательского вызова она стоит денег и
доверия.

**Отложено вместе с таблицей префиксов** и по той же причине: при двух провайдерах проба дороже,
чем выбор значения руками. Замеры выше показывают и другую сложность — у Polza «неподходящий
транспорт» не всегда даёт код ошибки: одна модель отвечает 500, другая 200 без картинки. Проба
должна будет проверять **наличие картинки в ответе**, а не только статус.

### 5. Всё неизвестное — отказ

Ни один путь не заканчивается «попробуем и посмотрим». Не разрешился транспорт, профиль говорит
что модель не отдаёт изображения, стратегия не поддерживает композицию — `MediaInferenceException`
с текстом, адресованным человеку. Он и так уезжает агенту дословно.

## Что не выбрано и почему

Три отказа, которые важнее самого решения: без них эти идеи вернутся через полгода в том же виде.

### Конфиг-DSL для «полностью кастомной стратегии» — нет

Соблазн: администратор описывает в JSON эндпоинт, шаблон тела и путь к картинке в ответе — и любой
провайдер поддержан без релиза.

Почему нет: это мини-язык. Свой синтаксис подстановок, свой JSONPath, своя отладка, свои сообщения
об ошибках — и всё это надо сопровождать. Плюс адрес запроса начинает приходить из данных, то есть
мы своими руками строим примитив для SSRF и для отправки ключа пользователя на произвольный хост.

Кастомная стратегия — это **класс в коде**, по тому же образцу, что коннекторы: интерфейс,
реализация, регистр, резолв по коду.

Отдельно: **закрытая комбинаторика — это не DSL**. Разложить транспорт на оси
(`{суффикс пути} × {форма тела} × {где картинка} × {байты или ссылка}`) с фиксированными enum'ами
по каждой оси — законный ход: адрес по-прежнему собирается из `base_url` провайдера, тело собирает
наш код. Это **отложено, а не отвергнуто**: под два известных диалекта проектировать комбинаторику
рано. Когда стратегий станет три и в них обнаружится общий код сборки тела — они сами развалятся
на оси, и это будет рефакторинг под давлением фактов.

### Посредник (LiteLLM / one-api сайдкаром) — нет

Соблазн: поставить нормализующий прокси, говорить с ним одним диалектом, зоопарк — его забота.
Нашего кода почти ноль.

Почему нет — по предметной причине, а не по архитектурной: он снимает ровно ту часть зоопарка,
которая и так закрывается двумя генериками, и **не снимает ту, ради которой всё затевалось** —
Polza `/media` и GigaChat он не нормализует. Плюс через сторонний процесс идут ключи пользователей,
что противоречит направлению на per-user шифрование, и в деплой добавляется узел, который надо
обновлять вслед за чужими API.

### Перебор транспортов в рантайме — нет

Соблазн: не выбирать вовсе. Первый вызов пробует диалекты по очереди, успешный запоминается в
реестре. Ближе всех к «система выбирает сама».

Почему нет: **неудачная попытка может быть оплачена**. У OpenRouter явно написано «either completed
and billed in full, or it fails and is not billed», но такой гарантии нет ни у кого другого, и 500
после того, как модель отработала, — обычный сценарий. Перебор идёт на деньги пользователя, 5xx
неотличим от «уже списали», а первый вызов становится самым медленным и недетерминированным.

Информация из кодов ответа при этом ценная — поэтому она используется, но в пробе при настройке
(п. 4), где ошибка бесплатна.

### Семейство D (GigaChat) как транспорт — нет

Там генерация — побочный эффект чат-хода с function-calling: нужен триггер в промпте, модель сама
решает звать `text2image`, результат приходит file id внутри HTML-тега. Это не отображается на нашу
модель «тул зовёт модель» и тянет за собой чужую семантику. Если GigaChat понадобится — это
отдельный коннектор, а не ветка транспорта.

## Что сделано

1. **Чтение модальностей + fail-fast** — модель, объявившая выход без `image`, отвергается до
   HTTP-вызова (`MediaInferenceService.requireImageModality`). Пустой список — «не объявлено», а не
   «не умеет». Плюс 5xx от провайдера теперь несёт подсказку про транспорт, а не только чужое тело.
2. **`MediaTransport` + `MediaTransportRegistry`** — `CHAT_MODALITIES` (прежний код) и
   `MEDIA_ENDPOINT` (Polza), выбор по `llm_providers.media_transport`.
   Профиль параметров модели читается из `raw_metadata` и ложится под `extra_body`: настройка руками
   всегда бьёт значение из листинга. Форма `top_provider.parameters` — вендорская, поэтому её знает
   только вендорский транспорт, а `ResolvedLlm` носит сырую запись как есть.
3. **`RemoteImageFetcher`** — скачивание результата по ссылке: только https, без редиректов, без
   приватных и loopback-адресов, потолок 20 МБ по фактическому потоку, обязательный `image/*`.
4. **Поле в API управления** — `mediaTransport` в create/update/response провайдера.

`IMAGES_GENERATIONS` **не сделан**: ни одному из двух настроенных провайдеров он не нужен
(у Polza этот эндпойнт асинхронный, OpenRouter говорит на A). Появится вместе с провайдером
OpenAI-семейства.

## Открытые вопросы

- **Деньги за медийные вызовы нигде не учтены.** `llm_usage_log` считает токены, а `/media` берёт
  плату в рублях (`usage.cost_rub`); транспорт пишет цену в лог, но в счётчики и квоты она не
  попадает. Для платформенного провайдера с квотами это дыра — нужна отдельная фаза про стоимость
  в учёте.
- Формат ответа `/images/generations` (`url` против `b64_json`) в доках Together, Fireworks и
  VseGPT явно не описан — проверить перед реализацией `IMAGES_GENERATIONS`.
- Нужен ли per-model транспорт. У Polza `type` в листинге показывает, что chat- и image-модели
  живут на разных эндпойнтах одного провайдера; пока это лечится тем, что в `purpose_priority[IMAGE]`
  ставят image-модель, но проверять это должен код (следующая фаза, чтение `type` из `raw_metadata`).
- Разделение капабилити GENERATE/EDIT/COMPOSE: «умеет ли **эта модель** четыре референса»
  по-прежнему не знает никто (см. «Чего система не проверяет» в
  [../connectors/media.md](../connectors/media.md)).
