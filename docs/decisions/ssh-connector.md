# SSH-коннектор: команды на удалённом сервере

Даёт агенту инструмент **выполнять shell-команды на конкретной удалённой машине** через подключение,
которое пользователь создал и явно выдал агенту. Подключение адресует `username@host:port`, credentials
остаются в зашифрованном хранилище `control-api`, агент получает только тулу выбранного экземпляра.

Это четвёртый вид терминала рядом с уже разобранными, а не замена им:

| Исполнитель | Где выполняется команда | Что является границей доступа |
|---|---|---|
| ACP | IDE пользователя | живой ACP-канал и разрешение в IDE |
| [Terminal на устройстве](deferred/terminal-app.md) | приложение на машине пользователя | приложение, его песочница и локальные разрешения |
| [Terminal + sandbox-runner](deferred/terminal.md) | песочница платформы | изолированный workspace коннекшена |
| **SSH (этот документ)** | существующий удалённый сервер | права SSH-пользователя на этом сервере |

## Главное

- **Integration-коннектор `ssh`**: `BACKEND` + `STATIC`, несколько экземпляров у пользователя.
- **Одна тула `run_command`**, неинтерактивная. Один вызов = один SSH `exec` request; PTY и постоянного
  shell нет.
- **Исполнение в `control-api`** через отдельный `SshExecutor`. Worker protocol и формат DBOS
  checkpoints не меняются.
- **Проверка ключа сервера** по закреплённому SHA-256 fingerprint: ключ запоминается при создании
  подключения (TOFU) и дальше сверяется на каждом соединении; `AcceptAllServerKeyVerifier` не
  используется.
- **Apache MINA SSHD 2.x** как Java-библиотека. Внешний процесс `ssh`, `ssh-agent` и файлы `~/.ssh`
  машины `control-api` не используются.
- **At-most-once для команды.** Ни SSH-коннектор, ни платформенный DBOS replay не отправляет её повторно.
  После сбоя исход может быть неизвестен, но неизвестность не превращается в второй запуск.
- **Новых таблиц нет; нужна одна миграция `tool_call_logs`.** Для гарантии at-most-once добавляются
  служебные `dispatch_at` и `dispatch_deadline_at`. Подключения, секреты, привязки и ABAC используют
  существующую модель.

## Модель подключения

Одна строка `connections` = один SSH-пользователь на одном сервере:

| Поле формы | Хранение | Правило |
|---|---|---|
| `host` | `connections.params` | DNS-имя или IP, обязательно |
| `port` | `connections.params` | необязательно, по умолчанию `22`; диапазон 1–65535 |
| `username` | `connections.params` | обязательно, регистр сохраняется |
| `hostKeyFingerprint` | `connections.params` | не поле формы: записывается проверкой при создании, дальше только сверяется |
| `privateKey` | `secrets` | содержимое приватного ключа, не путь к файлу |
| `privateKeyPassphrase` | `secrets` | необязательная парольная фраза, только вместе с ключом |
| `password` | `secrets` | парольная аутентификация вместо ключа |

`privateKey` и `password` взаимоисключающи: заполнен ровно один. Пустая парольная фраза эквивалентна её
отсутствию. Попыток «сначала ключ, потом пароль» нет — поведение подключения должно быть видно из формы.

`sub_code = username@host:port` после нормализации хоста: trim, нижний регистр для DNS-имени, порт 22
подставляется явно. Две учётные записи на одном сервере — два разных экземпляра. `displayName` =
`SSH: username@host:port`, `allowsMultipleInstances = true`.

Открытая часть параметров позволяет навыку находить экземпляр существующим правилом `params @>` и не
содержит секретов: `host` и `port` хранятся в каноническом виде, который вернула проверка, — имя в
нижнем регистре, порт числом, — а `hostKeyFingerprint` дописывается той же проверкой при создании.
Fingerprint открыт намеренно: это идентификатор публичного ключа сервера, а не credential, дающий
доступ.

### Изменение подключения

`host`, `port` и `username` **неизменяемы**. Существующий `ConnectionService.updateSecret` требует, чтобы
результат валидации сохранил прежний `sub_code`; для SSH это становится явным продуктовым правилом.
Смена сервера или учётной записи = удалить старое подключение, создать новое и заново привязать его к
агентам. Старый `connectionId` и выданный доступ нельзя незаметно перенести на другую машину.

Обновление приватного ключа, пароля или passphrase использует существующую **полную замену**
credential-набора через `updateSecret`:

- клиент отправляет все открытые поля и новый секрет целиком; частичный набор отклоняется валидацией до
  `ConnectionCredentialStore.write`, поэтому `params` не затираются;
- секрет при редактировании вводится повторно: backend хранит его зашифрованным и не отдаёт для
  предзаполнения формы;
- `hostKeyFingerprint` не меняется обновлением: если проверка увидела другой ключ сервера, замена
  credentials отклоняется, а подключение пересоздаётся — отпечаток закрепляется только при создании;
- имя и `enabled` редактируются существующим отдельным `update` и credentials не затрагивают.

Частичный PATCH credentials и params-only update не заводим.

### Форма приватного ключа

`CredentialField.Type.SECRET` уже решает хранение, но не описывает многострочный ввод. Для ключа нужен
общий признак `multiline` у `CredentialField`, по умолчанию `false`; секретность и раскладка по
`params`/`secrets` от него не зависят. Фронт по этому признаку показывает многострочное поле без
эхо-вывода содержимого. Специального типа поля «SSH key» и ветки по имени `privateKey` на фронте не
заводим.

Принимаются OpenSSH/PEM private keys, включая зашифрованные с passphrase. PuTTY PPK, SSH certificates,
`keyboard-interactive`, аппаратные токены и локальный `ssh-agent` — вне первой версии. Устаревшие
алгоритмы не включаются ради совместимости молча; сервер, которому нужен `ssh-rsa` с SHA-1, не сможет
установить соединение и получит безопасную общую ошибку подключения или аутентификации — без отдельного
объяснения про алгоритм.

## Доверие к ключу сервера

Пользователь fingerprint не вводит. Работает TOFU, как в OpenSSH: при создании подключения платформа
сама запоминает ключ, которым сервер представился, и дальше требует именно его.

Порядок при создании подключения:

1. Проверить форму адреса и способ аутентификации; ключ разбирается до сетевого вызова.
2. Разрешить сетевой адрес по правилам раздела «Сеть».
3. Во время SSH-handshake принять представленный сервером публичный ключ и вычислить его
   OpenSSH-отпечаток `SHA256:…`.
4. Только после этого отправить credentials пользователя и выполнить аутентификацию.
5. Вернуть отпечаток в `derivedCredentials` — он записывается в `connections.params` рядом с
   `host` и `port`. Отпечаток публичного ключа секретом не является и виден владельцу в подключении,
   поэтому его можно при желании сверить независимым каналом уже после создания.

Дальше каждое подключение — штатный тест, выполнение команды — проверяет представленный ключ по
закреплённому отпечатку и отклоняется при несовпадении, до отправки credentials. Ошибка может показать
владельцу ожидаемый и полученный отпечаток, но не содержит пароль, ключ или passphrase.

Расхождение — это либо настоящая смена ключа сервера (переустановка, ротация, смена типа ключа, тот же
адрес у другой машины), либо подмена. Отличить их автоматически нельзя, поэтому перепина нет:
отпечаток меняется только вместе с личностью подключения — удалить его и создать заново. Обновление
credentials при расхождении отклоняется. Так «доверие» меняется лишь явным действием владельца, а не
побочным эффектом правки пароля.

Цена TOFU: самое первое подключение не проверено — им и закрепляется ключ того, кто ответил. Поэтому
адрес проверяется по политике сети до сокета, а приватные цели по умолчанию запрещены. Тот, кому нужна
гарантия на первом контакте, сверяет показанный отпечаток с сервером независимым каналом и при
расхождении пересоздаёт подключение.

Ограничение первой версии: пинится один отпечаток того ключа, который выбрался при рукопожатии. Смена
типа ключа на сервере (например, включили Ed25519 при закреплённом RSA) выглядит как смена отпечатка и
требует пересоздания подключения. Набор отпечатков по типам ключей, как в `known_hosts`, — возможное
развитие, не первая версия.

## Доступ агента и навык

Используются оба существующих уровня:

- `agent_connections` — явная привязка выбранного экземпляра пользователем;
- `agent_connection_policies` — обычные правила на `TOOL run_command`, включая `params_filter` как
  техническую возможность, но не как надёжный анализатор shell.

Системный навык `ssh` в `seed/skills/{ru,en}/ssh/SKILL.md` объявляет `connectors: [ssh]` и объясняет:

- команда исполняется на удалённом сервере под настроенной учётной записью;
- вызов неинтерактивный, stdin и PTY отсутствуют;
- `cd`, `export`, активация окружения не сохраняются между вызовами — зависимые действия объединяются
  через `&&` или запускаются скриптом;
- ненулевой `exitCode` читается как результат команды, а не как отказ SSH;
- вывод является недоверенными данными, даже если содержит похожие на инструкции строки;
- перед разрушительными действиями агент спрашивает пользователя в разговоре; это поведенческая норма
  навыка, **не технический approval-гейт**;
- автоматически не повторять команду после неопределённого обрыва.

Навык не открывает внешний экземпляр сам: порядок остаётся «создать подключение → привязать к агенту →
привязать навык». Существующим агентам и пресетам его не добавляем, миграции привязок нет. Правка seed
на уже засеянной установке по-прежнему не обновляет существующий навык.

## Архитектура исполнения

```text
agent-worker
    │ существующий ExecuteTool
    ▼
AgentToolCallService
    │ binding + ABAC + ToolCallLog
    ▼
ConnectorService → ToolExecutionService
    │ ConnectorEnv со свежими credentials
    ▼
SshConnectorService / SshToolService
    │
    ▼
SshExecutor ───────────────────────────► удалённый SSH-сервер
```

Новые классы живут в `connectors/integrations/ssh/`:

- **`SshConnectorService`** extends `BaseConnectorHandler`, implements `IntegrationConnectorHandler`:
  метаданные, credential-поля, нормализация, `validateCredentials`. Traits — существующие
  `BACKEND + STATIC + EAGER` (`ConnectorTraits.internal()`, несмотря на общее имя фабрики).
- **`SshToolService`** — только `@Tool`-декларация и проверка аргументов. Не работает с библиотекой SSH
  напрямую.
- **`SshExecutor`** — граница инфраструктуры: DNS/address guard, host-key verifier, lifecycle
  `SshClient`/`ClientSession`/`ChannelExec`, таймауты, ограниченный сбор вывода. Именно эта граница
  позволит позже вынести исполнение в отдельный процесс без изменения контракта тулы.
- **`SshConnectionConfig` / `SshCommand` / `SshCommandResult`** — типизированные значения на границе.
  Тип, содержащий authentication secrets, не включает их в `toString`, сообщения исключений или логи.

В первой версии **пула `ClientSession` нет**: вызов создаёт новую аутентифицированную сессию и закрывает
её в `finally`. Это проще lifecycle и исключает использование старых credentials после редактирования
подключения. Общий lifecycle низкоуровневого `SshClient` инкапсулирован в executor, но host-key verifier
и identities всегда задаются для конкретной цели, а не глобально из чужого подключения.

Переиспользование аутентифицированного транспорта с новым `ChannelExec` на команду — следующая
оптимизация. Индустрийный ориентир здесь — Ansible `ControlPersist`: разделяется SSH-транспорт, а не
состояние удалённого shell. На корректность первой версии пул не влияет.

## Контракт `run_command`

Аргументы:

| Аргумент | Правило |
|---|---|
| `command` | непустая строка до 64 КиБ; передаётся verbatim в SSH `exec` request |
| `timeoutSeconds` | необязательно; по умолчанию 60, допустимо 1…1800 |

Отдельных `host`, `username`, `connectionId`, `cwd`, `env`, `stdin` и `background` в аргументах нет.
Экземпляр выбран namespace/привязкой, а рабочий каталог и окружение при необходимости задаются внутри
самой команды. SSH-сервер интерпретирует строку shell'ом выбранной учётной записи; платформа не обещает
bash там, где его нет.

Результат содержит:

| Поле | Смысл |
|---|---|
| `stdout`, `stderr` | ограниченный текстовый вывод |
| `exitCode` | код завершения; `null`, если его не удалось получить |
| `timedOut` | истёк именно таймаут удалённой команды |
| `truncated` | хотя бы один поток вывода превысил лимит |
| `durationMs` | длительность выполнения после открытия канала |

Хинты: `readOnlyHint=false`, `destructiveHint=true`, `idempotentHint=false`, `openWorldHint=true`.
Схема строится штатной рефлексией, agent-facing имя образуется существующим namespace экземпляра.

**Ненулевой exit code — обычный результат тулы, не `ConnectorException`.** Ошибки валидации аргументов,
адреса, handshake, аутентификации и транспорта — `ConnectorException` с безопасным сообщением. Обрыв после
отправки `exec` формулируется как **неизвестный исход команды**, а не как «не выполнено».

## Выполнение, таймауты и отмена

Порядок одного вызова:

1. Проверить аргументы и получить permit исполнения.
2. Разрешить и проверить сетевой адрес.
3. Подключиться, проверить host key, аутентифицироваться.
4. Открыть `ChannelExec`, отправить команду один раз.
5. Одновременно читать stdout/stderr в ограниченные буферы и ждать exit status/закрытия.
6. Закрыть канал и сессию, отдать permit в `finally`.

Таймауты подключения, аутентификации и открытия канала — по 10 секунд каждый. Таймаут команды принадлежит
`SshExecutor` и не выводится из ожидания воркера. При его истечении executor прекращает ожидание, закрывает
канал и сессию и возвращает частичный вывод с `timedOut=true`, `exitCode=null`.

`@Tool(timeoutSeconds)` описывает только бюджет ожидания результата и задаётся по верхней границе команды
(30 минут). Основной агент после существующего grace перейдёт на detached path: результат приедет
триггером `tool_completed`, отдельных `background=true`, `check_command` и второго task API не заводим
([detached-tools.md](detached-tools.md)). Для внешнего MCP-вызова работает существующий task-механизм
`tool_call_logs`.

Остановка рана сохраняет текущую общую семантику ([run-cancellation.md](run-cancellation.md)):

- вызов, ещё не взятый в исполнение, не открывает SSH;
- уже идущая SSH-команда не убивается отменой рана немедленно — она завершится или достигнет своего
  таймаута, результат останется в `tool_call_logs`, доставка отменённому рану подавляется;
- рестарт `control-api` разрывает SSH-соединение, но не гарантирует остановку удалённого процесса;
- закрытие канала вообще не гарантирует завершение `nohup`, daemon и уже отделившихся дочерних процессов.

## At-most-once на платформенном replay

Запрета retry внутри `SshExecutor` недостаточно. `ToolCallDispatcher` сохраняет `toolCallId` между
реплеями, а `AgentToolCallService.processToolCall` сейчас повторно зовёт `pushToConnector` для
незавершённой строки: текущий общий принцип — «редкий дубль лучше потери вызова». Для SSH этот принцип
меняется осознанно: **потерянный или неизвестный исход лучше второго необратимого действия**.

### Политика исполнения

В `ToolProvider` появляется backend-only `executionPolicy(toolName, input)`:

- `REPLAYABLE` — дефолт, текущее поведение всех существующих тулов;
- `NON_REPLAYABLE` + обязательный конечный `executionTimeout` — политика `ssh.run_command`.

Это не MCP-аннотация и не часть `ConnectorToolSpec`: в proto воркера, наружный `/mcp` и схемы тулов
политика не попадает. SSH вычисляет таймаут как запрошенный `timeoutSeconds` плюс 60 секунд — 30 на
connect/auth/open и 30 запаса на запись результата. Отсутствие конечного таймаута у `NON_REPLAYABLE` —
ошибка конфигурации до обращения к серверу.

### Claim перед исполнением

Гейт стоит в `ToolExecutionService`, а не внутри коннектора, поэтому покрывает и worker dispatch, и
`executeWithTimeout` для MCP/вью:

1. Для `REPLAYABLE` гейт ничего не пишет и пропускает вызов как раньше.
2. Для `NON_REPLAYABLE` выполняется атомарный `UPDATE`:
   `SET dispatch_at = now, dispatch_deadline_at = now + executionTimeout, updated_at = now`
   `WHERE id = :toolCallId AND dispatch_at IS NULL AND finish_at IS NULL`.
3. Обновилась одна строка — этот вызов получил право исполнения. Ноль строк — это replay, дубль или уже
   финализированный вызов; коннектор **не вызывается**, второй результата и доставки не создаётся.
4. Перед самим обращением к коннектору дополнительно проверяется `finish_at`: recovery мог уже закрыть
   просроченный вызов, пока он стоял в очереди executor'а. Такой вызов не стартует.

`AgentToolCallService` может сохранить текущую ветку `Replay` с повторным `pushToConnector`: фактический
дубль поглощается гейтом. Воркер получает прежний `externalId` и продолжает читать результат той же
строки. Повторный MCP `executeWithTimeout` отвечает `StillRunning` либо сразу читает уже готовый
результат; второго выполнения нет. APP/LOOPBACK-пути и остальные BACKEND-тулы не меняются.

Два поля в `tool_call_logs`:

- `dispatch_at` — факт выигранного права на первое и единственное исполнение, не факт начала команды;
- `dispatch_deadline_at` — момент, после которого исполнение считается потерянным, а не повторяемым.

Индекс на `(dispatch_deadline_at)` — partial `WHERE dispatch_deadline_at IS NOT NULL AND finish_at IS NULL`.
Владелец узла и lease не нужны: повторять вызов запрещено всегда, а финализировать просроченную строку
может любой узел.

### Recovery с исходом `unknown`

Планировщик раз в 30 секунд читает по индексу пачку строк с истёкшим `dispatch_deadline_at` и
`finish_at IS NULL`. Для каждой:

- guarded-финализация по `id AND finish_at IS NULL` ставит `finish_at`, `updated_at` и безопасную ошибку
  «исполнение прервано или его исход неизвестен; внешнее действие могло выполниться»;
- победивший guarded UPDATE отправляет результат через существующий `AgentDeliveryService.deliverToolResult`:
  поллящий воркер получает `ERROR`, detached-вызов получает штатный `tool_completed`, MCP читает тот же лог;
- проигравший ничего не доставляет.

Второе окно recovery — результат detached-вызова, записанный в `tool_call_logs`, но не доставленный:
процесс умер после финализации, до отправки `tool_completed`. Планировщик доставляет хранящийся результат
через тот же `AgentDeliveryService`, а существующий `claimDelivery` не даёт доставить его дважды. Выборка
ограничена живым push-способным агентом и живым исходным раном (`run_id IS NOT NULL`, родитель не
отменён): у MCP-тасков `run_id` нет, а отменённый ран подавляет доставку намеренно, поэтому без фильтра
такие строки выбирались бы каждые 30 секунд бесконечно. `MCP` — единственный транспорт с
`supportsPush() = false`; будущий не-push тип обязан расширить это условие.

Запись результата SSH-исполнения и recovery использует одну CAS-финализацию. Поздний результат процесса,
пережившего deadline, не перезаписывает `unknown` и не доставляется вторым результатом. Для остальных
тулов их текущий путь записи не меняется.

Так закрываются оба сбоя:

- **воркер упал, `control-api` жив** — replay встречает `dispatch_at`, не исполняет команду повторно и
  забирает результат первого исполнения;
- **`control-api` упал после claim, до или во время SSH** — replay не запускает команду, а recovery после
  deadline завершает строку честной ошибкой неизвестного исхода.

Возможен и обратный край: процесс упал после claim, но до фактического `exec`; команда не выполнилась,
а пользователь получит «исход неизвестен». Это цена at-most-once, а не повод автоматически попробовать
снова. Перебор нескольких уже проверенных IP внутри **одного** claim допустим только на этапе установления
TCP-соединения; после начала аутентификации и тем более отправки `exec` повторная попытка запрещена.

## Вывод и параллелизм

- Лимит — **32 КиБ на stdout и 32 КиБ на stderr**. Избыток продолжает читаться и отбрасывается, чтобы
  удалённый процесс не встал на заполненном канале; `truncated=true`.
- Байты декодируются как UTF-8 с заменой повреждённых последовательностей. Пользовательской кодировки в
  первой версии нет; нельзя обрезать текст по символам до чтения байтового лимита.
- Потолки: **16 одновременных SSH-вызовов на узел `control-api`, 2 на `connectionId`**. Permit берётся до
  DNS и освобождается в `finally`.
- При насыщении вызов не ставится во внутреннюю бесконечную очередь, а получает безопасную ошибку
  «executor busy» / «connection busy». Потолок на узле, как и остальные ресурсные лимиты JVM; суммарный
  потолок флота намеренно не координируется.
- Потолок `connector_jobs` здесь не применяется: путь тулов его не проходит. Отдельной таблицы счётчиков
  нет, семафоры живут в памяти узла.

## Сеть и DNS

`PublicOnlyHttp` не покрывает raw SSH. Используется общий `PublicTargets`, но проверка встраивается в
фактическое подключение:

1. `PublicTargets.resolve(host)` возвращает адреса и проверяет **все** по текущей политике.
2. SSH-клиент подключается к выбранному уже проверенному `InetAddress`, а не повторно резолвит имя сам.
3. Исходное нормализованное имя остаётся в идентичности подключения и диагностике; host-key fingerprint
   не зависит от выбранного IP.

Так закрывается DNS rebinding между отдельной предварительной проверкой и вторым резолвом в библиотеке.
Флаг `app.net.allow-private-targets` имеет прежний смысл: по умолчанию приватные, loopback, link-local,
CGNAT и остальные непубличные цели запрещены; `true` отключает guard целиком для локальной разработки.
Нового SSH-only обхода и скрытого разрешения `127.0.0.1` нет.

На multi-tenant установке глобальное включение `allow-private-targets` не считается решением для доступа
в частные сети: оно снимает guard и у других исходящих вызовов. Отдельный allowlist или выделенный
executor появится только вместе с таким требованием.

Системный HTTP-прокси из [egress-proxy.md](egress-proxy.md) на SSH не распространяется. SOCKS-прокси,
jump hosts/bastion и port forwarding в первую версию не входят. Egress-политика кластера остаётся вторым
рубежом и должна разрешать исходящий TCP от `control-api` к целевым SSH-портам.

## Секреты, аудит и граница безопасности

- Credentials читаются только существующим `ConnectorEnvFactory`/`ConnectionCredentialStore`; в worker,
  proto, DBOS checkpoint, tool arguments и `PromptBlock` они не попадают.
- Локальные identity-файлы, `~/.ssh`, SSH-agent и agent forwarding не используются. Разрешены только
  credentials конкретной строки `connections`.
- Application logs содержат только `connectionId`, `toolCallId`, `runId`, код/класс исхода и длительность.
  Команда, stdout/stderr, пароль, ключ и passphrase туда не пишутся.
- Стандартный `tool_call_logs` сохраняет команду и результат — это аудит и источник tool-result, а не
  application log. Пользователь должен понимать, что секрет, напечатанный удалённой командой, окажется и
  там, и в контексте модели. Автоматической «маски секретов» не обещаем.
- Привязка `run_command` означает право выполнить **произвольную команду** без подтверждения каждого
  вызова. Общего cross-channel approval-механизма в платформе пока нет; ACP permission к этому пути не
  применим.
- Основная граница — права SSH-пользователя. Рекомендация установки: отдельная непривилегированная
  учётная запись, отдельный ключ только для AgiMate, минимальные права на файлы и сервисы, без root и
  неограниченного passwordless sudo.
- Regex/ABAC `params_filter` по `command` не является безопасным запретом опасных действий: эквивалентные
  команды, shell expansion, scripts и encoding делают такой фильтр обходимым. Его можно использовать как
  дополнительную организационную политику, но не как песочницу.

## Выбор Java-библиотеки

**Берём актуальную стабильную Apache MINA SSHD 2.x**, версия фиксируется в Gradle; milestone-линейку 3.x
не используем. Библиотека даёт `SshClient`, `ClientSession`, `ChannelExec`, отдельные stdout/stderr,
настраиваемые verifier'ы и несколько сессий у клиента
([официальный client setup](https://github.com/apache/mina-sshd/blob/master/docs/client-setup.md)).

Дефолтный `AcceptAllServerKeyVerifier` непригоден и заменяется обязательным per-target verifier'ом.
Перед посадкой делается небольшой технический spike на Java 25: OpenSSH key + passphrase, проверка
fingerprint, exit status, раздельные потоки, таймаут и обрыв. Spike не становится второй реализацией
коннектора.

Рассмотренные альтернативы:

- **SSHJ** — рабочий клиент с более компактным API, оставляем запасным вариантом. Аргумента «MINA всегда
  быстрее» нет: переход Apache NiFi на MINA мотивирован сокращением площади сопровождения и основой для
  connection reuse, а не опубликованными замерами
  ([NIFI-14720](https://issues.apache.org/jira/browse/NIFI-14720)).
- **`mwiede/jsch`** — поддерживаемый форк для существующего JSch-кода. У нас такого кода нет, поэтому
  новый API и конфигурационное наследие без необходимости не приносим.
- **Оригинальный JCraft JSch** — не рассматривается для нового кода.
- **Внешний OpenSSH CLI** — отвергнут: зависимость от бинарника и домашнего каталога контейнера, сложнее
  ограничить identities/config, таймауты и потоки, нельзя удержать единый Java-контракт executor'а.

## Почему не другие архитектуры

| Вариант | Почему не выбран сейчас |
|---|---|
| Постоянный shell/PTY в `control-api` | Другой продукт: маркеры завершения, FIFO, ANSI, владение живым каналом, reconnect и уборка. Не нужен для большинства разовых административных команд |
| Отдельный `ssh-executor` с первой версии | Новый сервис, mTLS и передача секретов между процессами. Оправдан изоляцией сети или нагрузкой, которых пока нет; локальный `SshExecutor` сохраняет путь к нему |
| Выполнение в `agent-worker` | Потребовало бы выдать credentials воркеру и расширить протокол; сегодня integration tools и секреты принадлежат `control-api` |
| APP/ACP на машине пользователя | Требует живого клиента и решает другой сценарий: доступ в его сеть и к его ключам. Не заменяет автономный серверный коннектор |
| Универсальный MCP-over-SSH | Требует отдельного MCP-сервера на удалённой стороне и не нужен для выполнения shell-команды |

## Отложено сознательно

- Пул `ClientSession` с keepalive и invalidation по lifecycle-событиям.
- Двухшаговый TOFU с отдельным probe и подтверждением показанного fingerprint: сейчас ключ
  закрепляется молча, а владелец при желании сверяет его в подключении задним числом.
- PTY/shell-сессии, stdin, интерактивные программы, `tmux`/`screen`.
- SFTP/SCP и связь удалённых файлов с `agf_`.
- Jump hosts, SOCKS, port forwarding, SSH certificates, keyboard-interactive/2FA, PPK.
- Выделенный `ssh-executor` с mTLS и request-scoped credentials.
- Cross-channel подтверждение отдельных команд человеком.
- Немедленная отмена уже идущей удалённой команды и попытка завершить её process group.
- Отдельные allowlist приватных SSH-сетей для multi-tenant установки.

## Проверка

Unit-тесты без Spring context и внешней инфраструктуры:

- нормализация `sub_code`, обязательные поля, XOR способов аутентификации, passphrase только с ключом;
- неизменяемость `host`/`port`/`username`, полный credential-набор при update, отсутствие затирания
  `params` неполным набором;
- проверка без отпечатка запоминает представленный ключ и возвращает его в `derivedCredentials`;
  закреплённый отпечаток сверяется до аутентификации, а его расхождение при обновлении credentials
  отклоняется;
- адрес для сокета берётся из проверенного `PublicTargets.resolve`, повторного свободного резолва нет;
- ненулевой exit code не становится transport error;
- таймаут возвращает частичный вывод и закрывает ресурсы; retry отсутствует;
- claim `NON_REPLAYABLE` выигрывается один раз при последовательных и параллельных replay; повторный
  `executeTool`/`executeWithTimeout` не доходит до коннектора; `REPLAYABLE` сохраняет прежнее поведение;
- recovery финализирует только просроченную незавершённую строку и доставляет ровно один `unknown`;
  записанный, но не доставленный detached-результат доставляется один раз, а поздний фактический
  результат не перезаписывает `unknown`;
- stdout/stderr ограничены байтами, избыток дренируется, флаг `truncated` выставляется;
- потолки узла/подключения и освобождение permit при всех исходах;
- секреты не попадают в `toString`, безопасные сообщения и application logs;
- стандартные `ConnectorTextsTest` и `ToolSafetyHintsTest` проходят для нового коннектора.

Живой прогон на выделенной тестовой VM, без боевых credentials в репозитории:

1. Создание подключения по Ed25519-ключу с passphrase; отдельно — по паролю.
2. Неверный fingerprint и смена ключа сервера отклоняются; credentials не отправляются до проверки.
3. Успешная команда, stderr, ненулевой exit code, большой вывод и timeout.
4. Команда дольше grace отцепляется и возвращается через `tool_completed`.
5. Недоступный/приватный адрес отклоняется при выключенном `allow-private-targets`; локальный стенд
   работает при осознанно включённом.
6. Агент видит только явно привязанный экземпляр и не может сменить сервер аргументом.
7. Остановка рана, DBOS replay и рестарт `control-api` не порождают повторной команды; после сбоя
   исполнителя recovery доставляет один честный `unknown`.
8. Обновление credentials полным набором работает; смена `host`/`username` отклоняется, неполный набор
   не затирает открытые параметры.
9. В application logs нет команды, вывода и секретов; `./gradlew build` зелёный.
