# Matrix-коннектор: аккаунт на каждого агента (отложено)

Разбор августа 2026. Отправная точка — «сделать коннектор мессенджера Matrix, чтобы у каждого агента
там был свой аккаунт, с учётом того, что мы можем держать свой сервер». Документ фиксирует, почему
транспортом должен быть application service, что при этом придётся поменять в общем коде (три из
четырёх пунктов — не про Matrix), и какой инфраструктурой это оплачивается. Кода не написано ни
строки.

## Зачем это вообще

Matrix даёт то, чего нет ни у одного текущего канала: **идентичность агента бесплатна**. В телеграме
агент — это отдельный бот, заведённый руками у BotFather, с токеном в кредах
(`TelegramConnectorService.getCredentialFields` → `token`). На своём Synapse через application
service (AS) мы получаем целый неймспейс пользователей и право действовать от имени любого из них без
паролей: «у каждого агента свой аккаунт» перестаёт быть настройкой и становится побочным эффектом
создания агента.

Честно про аудиторию: как **пользовательский** канал для prosumer/SMB Matrix мёртв — там телеграм.
Окупают его два других сценария:

- **on-prem-инсталляции**, где телеграм запрещён политикой, а свой Element уже стоит;
- **комната как рабочее место команды агентов**: несколько агентов и людей в одном руме, у каждого
  агента имя и аватар. Пересекается с [agent-to-agent-internal.md](agent-to-agent-internal.md), но с
  другой стороны: там канал общения агентов внутренний и невидимый, здесь — обычная комната, в
  которой сидит и человек.

Если ни один из двух не является целью — браться не стоит: протокол дороже своей пользы.

## Транспорт: application service, а не бот-аккаунты

| | AS (свой сервер) | Аккаунт на агента + `/sync` |
|---|---|---|
| Идентичности | неограниченно, из неймспейса, без паролей | по аккаунту руками, хранить токен каждого |
| Входящий | сервер сам пушит транзакции на наш HTTP | N долгоживущих long-poll, по одному на агента |
| Чужой homeserver | нельзя (нужна правка `homeserver.yaml` + рестарт) | можно |
| Масштаб | один эндпойнт на всех агентов | слот джобы на агента, как телеграмный polling |

**Делать только AS-режим.** Второй — это ровно `TelegramToolService.longPoll` со всеми его болями
(409 Conflict, оффсеты в памяти), помноженный на число агентов, и главного — бесплатных
идентичностей — он не даёт. Присоединение к чужому серверу обычным аккаунтом останется отдельным
режимом на будущее, если появится клиент со своим Matrix.

**Ключевое следствие AS.** Регистрация AS — это файл в `app_service_config_files` плюс **рестарт
Synapse**. Значит:

1. AS создаётся **один на инсталляцию**, а не на пользователя. Динамически завести новый нельзя.
2. URL AS-эндпойнта постоянен — `connectionId` в пути невозможен. Эндпойнт фиксированный
   (`/control/matrix/appservice/...`), а connection определяется по `hs_token` из заголовка.

## Как ложится на модель коннекторов

- **Connection = один homeserver-AS.** Integration-коннектор `matrix`, credential-поля
  `homeserverUrl`, `asToken`, `hsToken`, `localpartPrefix`; `sub_code` — хост сервера.
- **Channel = аккаунт агента.** Триплет `(agent, matrix, connection)` уже уникален среди активных —
  «у агента ровно один mxid на этом сервере» выражается существующим партиальным индексом, новых
  сущностей не нужно. В `channels.config` — `localpart`/`mxid`, `autoJoinInvites`, `allowedRooms`,
  `defaultRoomId` (симметрия телеграмному `defaultChatId` для проактивных ответов по `time.due`).
- **Identity scope = AGENT.** Тул `matrix.send_message` не получает «от кого»: mxid выводится из
  `env.agentId`, как память выводит своё пространство. Ложится на ось, описанную в
  [connectors.md](../../architecture/connectors.md), без новых полей в `ConnectorEnv`.
- **Новая таблица одна** — `matrix_room_members (connection_id, room_id, agent_id, mxid, joined_at)`,
  уникально по `(connection_id, room_id, agent_id)`. Без неё входящее событие некуда маршрутизировать.
  Заполняется по `m.room.member` с `state_key` из нашего неймспейса.

## Что придётся поменять в общем коде

Три пункта из четырёх — общие долги, которые Matrix просто вскрывает первым.

**1. Одна транзакция → много триггеров.** Контракт сейчас — `normalizeInbound(env, rawBody) → Trigger`
(ровно один), а Synapse шлёт `PUT …/transactions/{txnId}` с массивом событий по всем комнатам и всем
агентам сразу. Нужен `default List<Trigger> normalizeInboundBatch(...)` в
`IntegrationConnectorHandler` (дефолт — обёртка над одиночным) и цикл на вызывающей стороне. Плюс
тонкий `MatrixAppserviceController`: generic-эндпойнт `POST /webhook/{connectionId}` не подходит ни
методом, ни путём — HS сам дописывает `/_matrix/app/v1/transactions/{id}` и отдельно зовёт
`/users/{mxid}` и `/ping`. Валидация переиспользуется как есть: `hs_token` в `Authorization: Bearer`
против `env.webhookSecret()`.

**2. Кому адресовано событие.** У вебхука нет `TriggerContext`, и ABAC разошлёт сообщение из комнаты
всем агентам, привязанным к connection. Ответ уже есть в модели: коннектор при нормализации
заполняет `TriggerAudience.targetAgentIds` агентами из `matrix_room_members`, и `findRecipients`
сужает сам. Побочно снимается ограничение, честно записанное в
[channels-and-triggers.md](../../architecture/channels-and-triggers.md) («у вебхука снаружи контекста
нет»): Matrix — первый вебхук, который свою аудиторию знает.

**3. Сессия сейчас одна на канал по TTL.** `AgentSession` внешнего ключа не имеет,
`findOrCreateActive` берёт последнюю живую за 12 часов. Для агента в пяти комнатах это смешанная
история **и**, что хуже, общий `sessionId` — то есть общий ключ партиции очереди `agent_exec`: пять
независимых разговоров выстроятся в один поток. Нужен `agent_sessions.external_key` (для Matrix —
`roomId` или `roomId#threadId`) и резолв «по ключу, иначе TTL». Телеграм выигрывает от этого ровно
так же (сейчас все его чаты в одном канале сливаются), а `ChannelInfo.messageId`, зарезервированный
«под треды и реплаи», наконец получает потребителя.

**4. Провижининг аккаунта — lifecycle-хук, которого у `ChannelHandler` нет.** При создании канала
надо зарегистрировать `@<prefix>_<slug>:hs` (`m.login.application_service`), проставить displayname и
аватар из карточки агента, при `defaultRoomId` — вступить; при удалении — выйти или деактивировать.
Сейчас хендлер умеет только `validateConfig`. Вешать регистрацию на валидацию — ложь про имя метода;
нужен `onChannelCreated`/`onChannelDeleted`.

## Тулы и обратный путь

Хендлер `matrix` объявляет `supportsOutboundAttachments()` и `deliverProgress()`, и здесь Matrix
заметно лучше телеграма: прогресс — не поток сообщений, а `m.typing` во время размышления плюс **одно
сообщение, редактируемое по месту** (`m.replace`); `messageId` для идемпотентности уже есть в
`OutboundDispatch`. Вложения: `agf_` → upload в `mxc://`; входящие `mxc://` скачиваются на ингесте в
`parts`, как это делает `TelegramMediaService`, — файловый слой не меняется вовсе.

Тулы (`MatrixToolService` + диспатч `BaseConnectorHandler`): `send_message` (markdown →
`formatted_body`), `send_file`, `edit_message`, `redact_message`, `react`, `set_typing`,
`create_room`, `invite`, `leave_room`, `set_profile`. Триггеры: `message_received`, `media_received`,
`invited_to_room`, `mention_received`, `reaction_received`.

**Дефолт ответа в групповой комнате — только на упоминание или реплай**, в DM — на всё. Иначе трое
агентов в одной комнате устроят бесконечный диалог. Оттуда же защита от эха: события с sender'ом из
нашего неймспейса игнорируются, если агент не упомянут явно.

## Инфраструктура

**Поднимать нужен ровно один новый сервис — Synapse.** Homeserver — это отдельный продукт (комнаты,
состояние, права, ключи, медиа, федерация); мы к нему клиент и приложение. **Портов в control-api не
добавляется**: AS-эндпойнт — новый HTTP-путь на текущем 8080, требующий только записи в security
filter chain.

```
Element (клиент)  ──► ingress ──► synapse:8008                              (единственное публичное)
synapse           ──► control-api:8080 /control/matrix/appservice/…         (внутри кластера)
control-api       ──► synapse:8008 /_matrix/client/v3/… с as_token          (внутри кластера)
```

| Компонент | Порт | Публично |
|---|---|---|
| synapse | 8008 (client-server API) | да, через ingress |
| synapse | 8448 (федерация) | только если федерацию открываем |
| control-api | 8080 (уже есть) | как сейчас |

Путь AS окажется доступен снаружи заодно со всем `/control/*` (он аутентифицирован `hs_token` и
проходит `InboundRateLimiter`, как телеграмный вебхук) — но внешним клиентам он не нужен, поэтому
закрыть его на ингрессе стоит.

**Локальный стек:** новый профиль `matrix` в `ops/compose.yaml` (synapse + опционально Element Web),
своя БД `am_matrix_db` в `ops/postgres/init-databases.sh` — Synapse требует для неё `LC_COLLATE=C`,
`LC_CTYPE=C`; `ops/dev-init.sh` генерит `as_token`/`hs_token` и рендерит `registration.yaml` +
`homeserver.yaml` из `ops/templates/` (ровно тот же ряд, что JWT/Centrifugo/worker-ключи); в
`ops/caddy/Caddyfile` — хост `matrix.agimate.lc` и раздача `/.well-known/matrix/{client,server}`.
Testcontainers с Synapse не заводить: старт ~40–60 с, дешевле мок AS-транзакций (обычный JSON) плюс
ручной smoke.

**Прод (`agimate-infra`, ArgoCD):** Deployment/StatefulSet Synapse (1 реплика; workers — отдельный
проект, если упрёмся), БД, PVC или свой S3-бакет под медиа (`synapse-s3-storage-provider`; наш
файловый слой Synapse не переиспользует), Ingress с увеличенным `proxy-body-size` (дефолтный 1 МБ
убьёт вложения) и `proxy-read-timeout` ≥ 180 с (клиенты держат long-poll `/sync`), раздача
`/.well-known`.

**Ловушка с реальным IP.** Synapse считает свои rate-limit'ы (`rc_login`, `rc_message`) по IP, а SNAT
балансировщика в нашем кластере адрес клиента съедает — сервер увидит один адрес на всех, и первый же
всплеск заблокирует всех разом. Значит для этого ingress'а нужен PROXY protocol и `x_forwarded: true`
на listener'е Synapse, не сломав текущее правило `use-forwarded-headers: false` для остальных путей.
Правки ingress-nginx живут вне ArgoCD и теряются при `helm upgrade` — это самая неприятная часть.

**Эксплуатация.** Это первый stateful-компонент помимо Postgres: ~1–2 ГБ RAM минимум, растущая БД
(state groups требуют периодического сжатия), апгрейды со схемными миграциями, свой формат логов (не
наш ECS-JSON), свой бэкап.

## Решения, которые потом не отменить

- **`server_name`** вшит в каждый mxid и в события; смена после запуска — миграция всего сервера.
  Брать сразу целевое (`agimate.ru` с делегацией на `matrix.agimate.ru`), иначе адреса агентов
  навсегда останутся `@agent:matrix.agimate.ru`.
- **Неймспейс AS** (`exclusive: true`) — менять больно; закладывать сразу с запасом: под агентов и,
  если решим, под людей.
- **Федерация.** Закрытая (`federation_domain_whitelist: []`) — ни спама, ни репутации, ни порта
  8448, но и никакого «клиент со своего корпоративного Matrix пишет нашему агенту». Открыть позже
  можно, закрыть обратно — уже нет: комнаты успеют федерироваться. Начинать закрытыми.
- **`url_preview_enabled: false`.** Иначе Synapse ходит по любым ссылкам из комнат изнутри кластера —
  это SSRF по внутренней сети, выданный наружу через чат.

## E2EE — не в первой итерации

Шифрование для AS технически возможно: Synapse поддерживает MSC3202 (device masquerading +
transaction extensions) с 1.63, до 1.141 — через `experimental_features`. Но на стороне бота это
полный крипто-стек (device keys, one-time keys, megolm, cross-signing, key backup), а живых
реализаций на JVM нет — всё живое это Rust/Go/Python (matrix-rust-sdk, mautrix). Значит E2EE = ещё
один сервис-сайдкар, то есть отдельный проект, а не хендлер.

Первая итерация — нешифрованные комнаты на своём сервере, с явным гашением шифрования по умолчанию
через `/.well-known/matrix/client`:

```json
{ "io.element.e2ee": { "default": false, "force_disable": true } }
```

Element Web это уважает, Element Android — нет (известный баг). На практике DM с агентом и так
останется открытым: Element включает шифрование в DM, только если у собеседника загружены ключи, а у
наших AS-пользователей их не будет. В комнате с включённым шифрованием агент обязан ответить открытым
текстом «не умею читать шифрованное», а не молчать.

## Прочие ловушки

- **Идемпотентность транзакций.** HS ретраит транзакцию до 200; падение посередине означает, что
  половина событий уже уехала в раны. Дедуп по `event_id` в `trigger_logs.external_id` — проверить,
  наложена ли уникальность по `(connection_id, external_id)`, и наложить.
- **Обратное давление.** Отвечать 200 после постановки в очередь, а не «приняли и разберёмся»: это
  единственный способ притормозить HS.
- **Приглашения как вектор спама.** Пригласить агента в комнату может кто угодно из федерации.
  `autoJoinInvites` по умолчанию — только от своего сервера или из белого списка.

## Открытые вопросы

1. **Hosted или только self-hosted?** От этого зависит всё остальное: при self-hosted креды AS вбивает
   админ, hosted тянет за собой платформенную connection (как платформенные LLM-ключи), квоты и
   модерацию. Скорее всего нужны оба режима, и признать это надо до кода.
2. **Заводим ли аккаунты людям на нашем HS?** Инфраструктурно дешёвый путь — не поднимать OIDC, а
   выдавать людям аккаунты тем же AS (`POST /_matrix/client/v3/login` с
   `type: m.login.application_service`): кнопка в UI выдаёт токен, Element логинится без пароля.
   Альтернатива — делать user-api полноценным OIDC-провайдером, это работа не на день.
3. **Чиним ли `agent_sessions.external_key` сразу?** Я за: иначе Matrix придётся переделывать через
   месяц, а телеграм так и останется со слипшимися чатами.
4. **Добавляем ли `onChannelCreated`/`onChannelDeleted` в `ChannelHandler`** или провижининг живёт в
   `validateConfig` (не живёт).

## Фазы, когда вернёмся

- **Фаза 0** — решения выше, без кода.
- **Фаза 1** — AS-коннектор и канал: регистрация аккаунта агента, DM и групповые комнаты, текст,
  вложения, typing + edit как прогресс, аудитория из `matrix_room_members`. Самодостаточно:
  «пригласи агента в Element».
- **Фаза 2** — треды как сессии, реакции и редактирование от агента, несколько агентов в одной
  комнате с правилами упоминаний.
- **Фаза 3, только по спросу** — E2EE-сайдкар; подключение к чужому homeserver'у обычным аккаунтом.
