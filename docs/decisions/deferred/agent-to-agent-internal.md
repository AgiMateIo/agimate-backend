# Общение агентов внутри платформы (отложено)

Дизайн коннектора, через который агенты одного пользователя разговаривают друг с другом. Отправная
точка обсуждения июля 2026 — идея тулы `ask_agent(id, prompt)`. Первая редакция документа
фиксировала, что запрос-ответ требует «pending tool-result» в ядре исполнения тулов и потому дорог.
Августовская тройка — [стиринг](../steering.md), [отложенные тулы](../detached-tools.md),
[сессии агента](../agent-sessions.md) — построила этот механизм для всех долгих тулов сразу, и
оценка изменилась: задача стала коннектором по шаблону с одной небольшой правкой в ядре. Отложена
теперь по приоритету, а не по цене.

**Это не A2A.** Внешние агенты по протоколу A2A — отдельный трек, см.
[a2a-external-agents.md](a2a-external-agents.md). Здесь обе стороны — наши агенты, наши раны, наша
история; ни AgentCard, ни сетевого протокола не возникает. Пересечение только в рисках
(петли, стоимость, инъекции) и в том, что оба трека однажды могут закрыть один и тот же
пользовательский сценарий «делегируй эксперту».

## Как `ask_agent` ложится на отложенные тулы

Ран агента B — отдельный DBOS-воркфлоу, синхронного ответа в цепочке
тула → триггер → `agent_runs` → воркер → `SaveMessage(ANSWER)` нет нигде. Раньше отсюда следовала
развилка «блокировать поток control-api или строить pending-результат»; теперь ответ один — путь
детача, уже существующий для любого долгого вызова:

1. Тула `ask_agent` создаёт триггер для B и **не возвращает результата из своего потока**.
2. Ран B — целая LLM-последовательность, grace 10 с он не переживает практически никогда, так что
   вызов детачится: A получает interim `{"status":"detached","task_id":...}`, договаривает
   («спросил, сообщу») и завершается. Партиция сессии A свободна — пользователь получает ответы,
   пока B думает.
3. Ответ B (его `ANSWER`) записывается в pending-строку `tool_call_logs` вызова A, дальше работает
   воронка `AgentDeliveryService.deliverToolResult`: триггер `tool_completed`, новый ран той же
   сессии A, адресация провенансом. Бегущий main заберёт его стирингом, свободная сессия отработает
   обычным порядком.

Дедуп (`delivered_at` claim-first), гашение по `cancel_requested_at` родителя, кап ~20К на данные
триггера, direct-родитель без каналов — всё наследуется от механики отложенных тулов без единой
строки. Несколько ответов разных агентов в одну сессию при живом main сольются стирингом в один ран.

Семантика при этом не «A ждёт и продолжает ход», а «ответ возвращается следующим раном» — та же
UX-модель, что у любого детачнутого тула, пользователь её уже видит.

### Что всё-таки остаётся сделать

- **Запись ответа B в вызов A.** Паттерн — app-тулы: результат приходит извне
  (`ToolCallLogService.recordOutputFromApp`), потом воронка. A2a-канал в `handleOutput` пишет
  `ANSWER` B в pending-строку и зовёт `deliverToolResult`. Id `tool_call_log` едет в данных
  триггера B (их формирует наш код) — **per-message, не per-thread**: у каждого `ask` свой вызов.
- **Одна правка в ядре.** `ToolExecutionService.executeAndRecord` записывает результат из возврата
  метода коннектора всегда; нужен способ для тулы сказать «результата из этого потока не будет»
  (sentinel/`ToolPending`), чтобы строка дождалась детача и внешней записи. На порядок меньше
  прежней оценки, но не ноль.
- **Финал B без `ANSWER`.** `FAILED`-ран B оставил бы pending-строку A висеть вечно: на такой финал
  писать error-результат в вызов, плюс TTL/сметатель по образцу MCP-тасков. Отложенные тулы
  сознательно не решали «политики реакции на ERROR» — здесь минимум решить придётся.

## Набор тулов

**`list_agents()`** — обязательна. Адресация по UUID для LLM бессмысленна; агент должен видеть, *кому*
и *зачем* писать: имя, описание, навыки. Скоуп — не «все агенты пользователя» (это уже есть в
platform-коннекторе как `list_agents` для мета-агента), а те, на кого у агента есть binding.

**`ask_agent(agent, prompt, thread_id?)`** — запрос-ответ. `thread_id` не декорация: без него каждый
вопрос стартует B с чистой историей, и «уточни предыдущий ответ» невозможно. Thread — сессия
a2a-канала: `agent_sessions` формализовал сессии у каждого рана, ран B получает свою по ключу
канала (как чаты у telegram-канала — канал один, сессий много), история и партиционирование
достаются от канального слоя. Собственная таблица переписки не нужна.

**`tell_agent(agent, message)`** — fire-and-forget. Отдельная тула, а не флаг у `ask_agent`:
уведомление не занимает вызов в `tool_call_logs` и семантически другое («я закончил свою часть» ≠
«ответь мне»). После детача разница с `ask` только в том, ждёт ли вызов записи результата.

**Триггер `message_received`** — как B вообще просыпается. Без него коннектор нерабочий: тула только
пишет, будит агента триггер.

**`handoff(agent, context)`** — передача *разговора с пользователем*: ответ уходит пользователю
напрямую, инициатор ничего не ждёт и из разговора выходит. Единственный сценарий, который не
покрывается ни `ask_agent`, ни доской (агент-диспетчер → профильный агент). Во вторую фазу, но
заложить в модель канала сразу — иначе `Channels` придётся переделывать.

## Что не делать

**`broadcast(team, message)`** — N ранов одним вызовом LLM, без обратной связи и с непредсказуемым
счётом. Источник шторма; если понадобится «оповестить команду» — это задача доски или отдельного
события, а не тулы.

**`delegate_task(agent, task)`** — уже есть: `board` с assignee и триггерами
`task_created`/`task_changed`. Для долгой работы доска строго лучше: состояние, история, отмена,
видимость пользователю. `ask_agent` остаётся для коротких «спроси и получи ответ», и **это надо
написать прямо в SKILL.md** — иначе LLM будет висеть на `ask_agent` там, где нужна задача.

**Отдельная `reply`** — не нужна: ответ B это `ANSWER` его рана в a2a-канал, проекция уже есть в
`MessageLogService`.

## Механика: где неочевидное

**Кто кому пишет.** Новых сущностей не нужно: binding через скилл + `agent_connection_policies` с
`params_filter` по аргументу-адресату. Механизм фильтрации аргументов на месте вызова уже применяется
(`AgentToolCallService`), список разрешённых собеседников выражается им без единой новой таблицы.

**Trust.** Текст от другого агента — **untrusted**. B мог начитаться внешних данных (Telegram, MCP,
веб), и его сообщение — вектор инъекции ровно как входящее письмо. Никакого `presentation=PROMPT` в
`ContextDirectives`; только untrusted-блок с явным указанием автора. (Guard в `ConnectorBootstrap`
разрешает PROMPT internal-коннекторам — a2a внутренний, так что запрет здесь дисциплинарный, а не
механический: зафиксировать в коде и ревью.)

**Циклы.** A→B→A зациклится с гарантией. Нужен счётчик глубины в цепочке (в данных триггера, которые
формирует наш код, а не модель), запрет self-call и потолок порядка 3.

**Стоимость.** Один `ask` = ран A + ран B + ран доставки ответа (сольётся стирингом, только если
main A ещё жив) — минимум две, обычно три LLM-последовательности на вопрос. Для prosumer-тарифа с
платформенными ключами лимит глубины не только про петли, но и про деньги.

## Развилки, которые определяют объём фазы 1

Две развилки первой редакции закрылись архитектурой: «`ask` сразу или сначала `tell`» — обе тулы в
фазу 1, `ask` больше не требует работы в ядре сверх `ToolPending`; «где живёт thread» — сессия
a2a-канала. Остаются:

1. **Скоуп адресации** — вся команда (`agentic_team`) или явный binding на конкретных агентов.
2. **Кто платит за глубину** — лимит на пользователя, на агента-инициатора или на цепочку.
3. **Форма error-результата при `FAILED`-ране B** — что именно видит A и когда срабатывает TTL.

## Ключевые файлы (проверено 2026-08-29)

- `connectors/core/execution/ToolExecutionService.java` — `executeAndRecord` записывает результат из
  возврата метода; точка, куда встаёт `ToolPending`.
- `service/AgentDeliveryService.java`, `service/delivery/DetachedToolResultDelivery.java` — воронка
  `deliverToolResult` и превращение результата в `tool_completed`-ран; a2a переиспользует как есть.
- `service/tool/ToolCallLogService.java` — `recordOutputFromApp`: образец записи результата извне.
- `service/channel/MessageLogService.java` — проекция `SaveMessage` в каналы; здесь ответ B
  превращается в доставку.
- `service/channel/handler/ChannelHandler.java` — SPI канала; a2a-канал реализует `handleInput`
  (сообщение → `InboundMessage`) и `handleOutput` (ответ → запись в вызов A).
- `service/trigger/TriggerRouterService.java`, `service/trigger/TriggerAudience.java` — адресная
  доставка триггера конкретному агенту (образец — `time.fire`).
- `connectors/internal/platform/PlatformAgentToolService.java` — существующий `list_agents` (мета-агент,
  другой скоуп).
- `connectors/internal/board/` — альтернатива для делегирования долгой работы.
