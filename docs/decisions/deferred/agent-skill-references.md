# Навык и подключение на агенте: что видит агент и пользователь (отложено)

После [skills-for-connection.md](../skills-for-connection.md) требование навыка находит своё
подключение правилом: код совпадает, и открытая часть подключения содержит `params` требования. Модель
«правило по умолчанию, ссылка — когда пользователь выбрал» уже работает: требование без строки
`agent_skill_connections` разрешается правилом. Документ о том, что вокруг этой модели не доделано, и о
том, как доделать это без смены модели и без ломающих изменений.

Отложено: ни один из пунктов не мешает работать сейчас, и ни на один нет жалобы. Первым стоит взять
то, что исправляет ошибку, — правила навыка у требований, разрешённых правилом.

## Что есть сейчас

- `agent_skill_connections(agent_skill_id, connector_key) → connection_id`. Строку пишет привязка
  навыка (`AgentSkillService.storeConnections`): для внешнего требования — подключение, которое
  пользователь выбрал в карте `connections`; для внутреннего — строку-режим, которую сервер создаёт сам
  (`ensureModeConnection`). Внешнее требование без выбора строки не получает.
- Гейт (`resolveInstances`): ссылка есть — решает она; нет — привязанные к агенту подключения, которые
  подходят по правилу; у требования без `params` — все привязанные подключения кода. Агент из пресета с
  единственным подходящим подключением получает навык без мастера.
- `key` требования по умолчанию равен коду, а когда код повторяется, обязан быть явным и уникальным
  (`ConnectorRequirements.normalize`). Он нужен: навыку может понадобиться несколько подключений
  одного коннектора — «программист» с MCP документации и MCP GitHub, или перенос между двумя
  аккаунтами одного сервиса, где `params` совпадают и развести требования может только ссылка.

Чего не хватает:

1. **Агент не знает, какие тулы относятся к какому навыку.** Каталог `<skills>` несёт только
   `connector_codes`; тело навыка автор пишет, не зная, как у пользователя назовётся подключение; тулы
   приходят плоским списком `{full_code}.{tool}` по всем подключениям удовлетворённых навыков. С двумя
   подключениями одного сервера агент видит два одинаковых набора с разными префиксами и выбирает по
   префиксу наугад — даже когда ссылка указывает на одно из них: о ссылке агенту ничего не сообщается.
2. **Правила навыка не ложатся на подключения, найденные правилом.** `applyPolicies` проходит только по
   ссылкам. У агента из пресета `allow`/`deny` навыка не пишутся никогда, хотя навык работает.
3. **Ссылка на удалённое подключение застревает.** Подключения удаляются мягко, внешний ключ строку не
   уносит, `detachConnection` её не трогает. Требование навсегда в `NOT_BOUND`, хотя подходящее
   подключение у агента может быть.
4. **Пользователь не видит неоднозначности.** Подходят несколько подключений — навык получает все, и
   статус показывает первое. Часть подходящих сломана — `OK`, и сломанные отбрасываются молча.
5. **Лишние строки у внутренних коннекторов.** Строка-режим одна на пользователя, выбирать нечего, а
   ссылка пишется — и вместе с ней `ensureModeConnection` в привязке навыка.

## Решение

Модель, ключ, таблица, состояния требования и запросы привязки не меняются. Ответы только
дополняются.

### Агент видит подключения своих навыков

Строка навыка в каталоге `<skills>` получает подключения, которые гейт отдал навыку, — префиксы тулов и
имена, данные пользователем:

```
- skill_id: …
  name: tinvest
  connector_codes: mcp
  connections: mcp_tinvest (T-Invest MCP)
```

- Префикс — namespace из имени тула (`RunCatalog.namespaceOf`: `full_code` у внешних, код у
  внутренних); имя в скобках — `connections.name`, если задано и отличается от префикса.
- Когда у навыка несколько требований одного кода, подключения перечисляются по требованиям, с
  подписью требования (`title`, иначе ключ):
  `connections: docs → mcp_context7 (Context7); github → mcp_github (GitHub)`.
- Подключений у требования несколько (нет ссылки, подходят несколько) — перечисляются все, и агент
  видит, что выбор за ним. Со ссылкой — одно, даже если тулы второго у агента есть из-за другого
  навыка: так ссылка начинает работать и в рантайме, а не только в гейте.
- Данные уже есть: гейт считает подключения навыка (`SkillGate.satisfied`), `full_code` и `name` лежат
  в загруженных `connections`. Нового запроса нет.
- Имя подключения пишет владелец агента, как и его инструкции; в каталоге оно проходит той же
  очисткой, что и остальные строки, без переводов строк.

### Правила навыка — одной функцией от разрешения

`SkillPolicySync.resync(agentId, skillId)`: снять строки этого навыка на агенте (`source = skill:<id>`)
и записать заново на подключения, которые даёт разрешение навыка, — ссылку, иначе подходящие по
правилу. Вызывают её все события, которые сейчас пишут правила, и одно новое:

- привязка навыка, смена ссылок, `refresh` — как сейчас, но через `resync`;
- **выдача агенту доступа к подключению** — `resync` навыков агента, которым это подключение
  подходит. Агент из пресета получает навык раньше подключения, и без этого шага правила не легли бы
  никогда;
- отвязка подключения — правила уходят вместе со строкой доступа (`removeBinding`), как сейчас.

Источник у правил один — `resolveSkills`, тот же, что у гейта, поэтому разъехаться им нечему.
Правило, которое пользователь отредактировал, теряет `source` и в снятие не попадает — как сейчас при
`refresh`.

Цена: у навыка со списком `allow` правило уровня привязки — `DENY` на всё, кроме перечисленного. Без
ссылки и с двумя подходящими подключениями ограничены оба, и вне навыка тоже. Замечание
`MULTIPLE_MATCHES` делает это видимым, ссылка — исправляет.

### Ссылка на удалённое подключение не читается

- Гейт пропускает ссылку, чьё подключение удалено, и требование разрешается правилом.
- Удаление подключения (`ConnectionService.delete`, удаление приложения) снимает его ссылки.
- Миграция удаляет уже висящие ссылки.

### Ссылки у внутренних коннекторов не пишутся

Гейт разрешает внутреннее требование правилом: строка-режим у агента одна. Привязка навыка перестаёт
писать ссылку и звать `ensureModeConnection` — строку-режим создаёт выдача доступа (`bindInternal`),
как и сейчас при ручной привязке. Миграция удаляет существующие ссылки внутренних коннекторов;
поведение не меняется, потому что правило даёт ту же строку-режим.

### Замечания в статусе требования

В `SkillConnectorStatus` добавляются поля, существующие не трогаются:

- `connectionIds` — все подключения, которые получает требование; `connectionId` и `connectionName`
  остаются и показывают первое, как сейчас;
- `pinned` — подключение выбрано ссылкой, а не правилом;
- `notices: [{code, connectionIds}]` — замечание навык не отключает, блокирует ли требование, говорит
  `state`. `policyConflicts` остаётся отдельным полем.

Коды — только те, что считаются из данных, которые план и список навыков агента уже загружают
(разрешение навыка и `statusContext` с подключениями пользователя):

| Код | Когда | Что предложить |
|---|---|---|
| `MULTIPLE_MATCHES` | нет ссылки, работают несколько подходящих подключений агента | выбрать одно (ссылка) или отвязать лишнее |
| `SOME_UNUSABLE` | нет ссылки, подходят несколько, часть не работает | переавторизовать или отвязать |
| `SAME_CONNECTION` | два требования одного кода получили одно и то же подключение | выбрать за требованиями разные подключения |
| `OTHER_INSTANCE_BOUND` | требование не удовлетворено, а к агенту привязано подключение того же кода с другими `params` | создать нужное или выбрать это, если это зеркало сервера |

Гейт и состояния не меняются: замечания считаются только там, где строится статус.

## Отвергнутое

- **Ссылка только по выбору пользователя как новая модель, с удалением ключа и переводом ссылок на
  код.** Модель «правило по умолчанию, ссылка по выбору» уже работает; удаление ключа теряет навыки с
  двумя подключениями одного коннектора, ради которых ключ заведён.
- **Убрать таблицу совсем; сузить навык — только отвязкой.** Не работает, когда второе подключение
  нужно этому же агенту для другого навыка или канала.
- **Новые значения и новый смысл состояний** (`NOT_CHOSEN` — «нет подходящего у пользователя»,
  `NOT_BOUND` — «есть, но без доступа»). Лишний запрос в гейте и ломающее изменение ради различия,
  которое мастер уже видит в `matches[].boundToAgent`.
- **Замена `connectionId` списком и перенос `policyConflicts` в `notices`.** Ломает клиентов, ничего не
  давая сверх добавленных полей.
- **`DECLARED_TOOLS_MISSING`** (тулы из `tools.allow`, которых у подключения нет) и **`PARAMS_HIDDEN`**
  (URL с ключом хранится в секрете, сопоставить нельзя). Первое требует сверки с `connection_tools`,
  второе — редкий случай; оба — до первой встречи на практике.
- **Блокирующее состояние `AMBIGUOUS`** и **выбор «основного» подключения сервером.** Навык, который
  работал бы с обоими подключениями, перестал бы работать; сервер подключение за пользователя не
  выбирает.

## Что может лечь в таблицу потом

Таблица описывает тройку «агент, навык, подключение»; сюда идут только данные, которые зависят от всех
трёх (от пары «агент, подключение» — в `agent_connections.settings`, от пары «агент, навык» — в
`agent_skills`). Пользователя ни у одного кандидата нет:

- настройки навыка для подключения — счёт по умолчанию в T-Invest, чат для отчётов, проект на
  MCP-сервере, когда два навыка работают с одним подключением по-разному;
- согласие на доступ стороннего публичного навыка к подключению, с версией навыка;
- раскрытие тулов по навыку через `skill-loader`: ссылка тогда отделяет тулы, а не только подпись;
- правила, действующие только в рамках навыка, — требует, чтобы вызов тула знал свой навык.

## Следствия

- **Правила появятся там, где их не было** — на подключениях, найденных правилом, при первом `resync`.
  Это исправление, но у агента со списком `allow` в навыке подключение сузится и вне навыка.
- **Каталог `<skills>` меняется при переименовании подключения** — префикс кеша промпта сбрасывается,
  как и при любом изменении каталога.
- Ломающих изменений для веба и Android нет: им нужно только показать новые поля, когда захочется.
