# Коннектор-сценарист: `run_workflow(spec)`

Разбор идеи: внутренний коннектор с одной тулой `run_workflow(wf_spec.yaml)`, где спека на диалекте
[Open Workflow](https://open-workflow-specification.org/) (бывш. Serverless Workflow, переименован в
июне 2026, текущая версия DSL 1.0.3) описывает, какие *другие* тулы дёрнуть, в каком порядке и какие
сделать преобразования данных. Модель пишет спеку один раз — платформа исполняет её без обращений к
модели на каждом шаге.

**Статус — отложено.** Форму фазы 1 перебивает code mode, а предпосылка для него уже
спроектирована; разбор ниже сохранён целиком, потому что его половина про ABAC переносится туда
дословно. Подробности — в ревизии сразу за этим абзацем.

**Короткий вывод разбора от 2026-09-11.** Идея упирается не в ABAC — ABAC ложится почти бесплатно
и даже становится строже, чем сегодня. Она упирается в две вещи: (1) одноразовая спека, написанная моделью вслепую,
окупается примерно с пятого шага, а до того агентный цикл дешевле; (2) вся настоящая ценность — в
*сохранённом* сценарии, который запускается триггером и вообще без модели, а это уже не «одна тула»,
а сущность, редактор и место в продукте. Развилку между этими двумя надо решать до кода: они дают
разный объём работы и разную пользу.

## Ревизия 2026-09-12: отложено, и вот чем перебито

Вчерашний разбор сравнивал идею с агентным циклом и проверял её на ABAC. Обе проверки она прошла —
и обе были не теми сравнениями. Правильное сравнение — **code mode**, которого я не проверил; после
проверки оно выигрывает.

**Что такое code mode.** Одна тула вместо каталога: модель пишет не спеку, а код (TypeScript или
Python), тулы внутри песочницы выглядят обычным API. Промежуточные данные остаются в песочнице,
модель читает только итог. Cloudflare выкатил это в сентябре 2025, Anthropic описал в ноябре 2025 —
у них рабочий сценарий похудел со 150 000 токенов до 2 000. Это ровно наша задача: N обращений к
модели схлопнуть в одно и убрать промежуточные результаты из контекста.

**Почему код бьёт наш YAML.** Аргумент Cloudflare эмпирический и неприятно точный: «LLM видели много
кода. Тул-вызовов они видели мало». Самодельный диалект попадает в ту же категорию — модель пишет
на нём первый раз в жизни, тогда как на Python пишет всю жизнь. Наш ответ на это — парный навык,
объявляющий грамматику, — по их же метафоре есть «месячные курсы мандаринского для Шекспира». А
проблема слепого сочинения никуда не девается: модель пишет всю цепочку, не видя форм промежуточных
данных. Бенчмарки структурного вывода показывают ровно такую форму отказа — структура выходит
валидной, а значения внутри неё неверны; для jq-выражения это означает спеку, которая разберётся,
запустится и сделает не то.

**Чем мы оправдывали DSL — и почему оправдание протухло.** Единственный настоящий довод за
интерпретируемую грамматику был «нам негде исполнять код»: `run: shell` и контейнеры мы запретили
сами, потому что песочницы нет. Но она **спроектирована** — [terminal.md](terminal.md),
`sandbox-runner` на gVisor, и там прямым текстом: «весь dispatch/gRPC/ABAC/listing — без изменений».
Цепочка получается такая:

1. DSL — правильный ответ, **если песочницы не будет никогда**.
2. Песочница спроектирована и стоит в roadmap. Как только она появится, code mode — это
   сгенерированный клиент к собственным тулам агента внутри неё, а каждый вызов из неё возвращается
   тем же путём `gRPC → AgentToolCallService`, что и сегодня.
3. Значит интерпретатор сейчас — это худший ответ, построенный ровно перед тем, как приедет
   предпосылка для лучшего. И машинерии в нём больше, чем в code mode.

### Возражение: «код может вызвать что угодно» — и как код вообще зовёт наши тулы

Возражение очевидное и его стоит разобрать до конца, потому что ответ на него — это половина
аргумента за code mode.

**Две разные модели безопасности.** Наш DSL защищает **невыразимостью**: запрещённое нельзя
написать, парсер отказывает. Песочница защищает **недостижимостью**: написать можно что угодно,
дотянуться не до чего. Вторая модель сильнее, и [terminal.md](terminal.md) уже её выбрал —
`egress по умолчанию deny` («LLM-bash + сеть = экфильтрация и SSRF во внутреннюю сеть»), никаких
секретов в env песочницы, лимиты CPU/mem/pids/disk и wall-clock, gVisor, отдельная VM вне кластера.
Код в такой коробке может написать `fetch("https://evil.com")` — сети нет; может полезть в
`/etc/passwd` — есть только свой workspace с path-конфайнментом; может искать ключ провайдера — его
там нет по правилу.

У грамматической защиты есть известный способ отказать: **грамматика растёт**. `run: shell` попал в
Open Workflow ровно так. Наше подмножество безопасно ровно до первого «ну добавь только
`call: http`, очень надо». У песочницы этого свойства нет: она остаётся безопасной при любом
изменении набора тулов, потому что безопасность лежит не в грамматике.

**Как код зовёт тулы.** Один новый переход, остальное — существующее:

```
песочница (сети нет)
   │  единственный сокет наружу — не интернет, а runner
   ▼
sandbox-runner   приклеивает личность (agentId, runId, sessionId) из задачи, которую ему дали
   │  TLS + token
   ▼
control-api: AgentToolCallService   binding → правило → params_filter → строка tool_call_logs
   │
   ▼
ToolExecutionService   ровно как сегодня для воркера
```

Три свойства, которые и закрывают возражение:

1. **Клиент генерируется из `ConnectorToolSpec`** — из того же источника, из которого сегодня
   строится `inputSchema` (`ToolSchemaReflector`), и только из тулов, доступных этому агенту после
   ABAC-листинга. Запрещённого тула в сгенерированном клиенте попросту нет.
2. **Код не заявляет, кто он.** Личность приклеивает runner из контекста задачи — тот же принцип,
   по которому `ConnectorEnv` собирается только в `ConnectorEnvFactory`, а не из аргументов вызова.
   Соврать про `agentId` нельзя, потому что код его не передаёт; обойти сгенерированный клиент и
   постучаться в сокет руками можно, и попадёшь в ту же точку с той же личностью.
3. **ABAC тот же и на каждый вызов.** `params_filter` по посчитанным аргументам, строка на шаг,
   отмена, ссылка на родителя — весь разбор ниже применяется дословно.

Итог: **для тулов возражение неверно** — код не может вызвать запрещённое, потому что вызов идёт
через ту же единственную точку принуждения. Что код действительно может, а спека нет, — сжечь
процессор, уйти в бесконечный цикл, съесть память. Это лимиты, и они нужны в обоих дизайнах: потолок
на время jq-выражения мы уже записали себе сами.

**Где возражение право, и это я вчера недооценил.** Размер доверенной базы. Парсер закрытой
грамматики — тысяча строк, которые читаются глазами. Песочница — gVisor плюс рантайм контейнеров
плюс отдельный привилегированный сервис плюс выделенная VM; `terminal.md` сам признаёт, что
control-api не должен держать докер-сокет. Побег из gVisor — не гипотетика. Это честная цена, и она
несопоставима с ценой парсера.

Поэтому развилка формулируется не так, как я написал выше, а короче: **не «DSL или code mode», а
«заводим ли мы песочницу вообще»**. Заводим — тогда code mode, и ABAC не страдает ни в чём.
Не заводим — тогда и DSL слаб: его собственная беда (модель пишет вслепую на диалекте, которого не
видела) никуда не девается, и честный ответ — не строить ни того, ни другого и жить агентным циклом,
пока не появится пользователь, которому детерминированная цепочка нужна по-настоящему.

**Третий вариант, который напрашивается и не годится**: встроить интерпретатор JS или Lua прямо в
control-api — «код без песочницы». Получаем непредсказуемость кода вместе с отсутствием изоляции, в
одном процессе с базой и секретами; внутрипроцессные песочницы на JVM исторически плохи, а
`SecurityManager` удалён. Худшее из обоих.

**Что из разбора не пропадает.** Весь раздел про ABAC переносится в code mode дословно: точка
принуждения та же, `params_filter` так же применяется к **посчитанным** аргументам, строка на шаг в
`tool_call_logs` так же появляется, отмена так же требует проверки между шагами, а ссылка на
родительский вызов так же нужна, иначе шаги — сироты. Устарела ровно одна посылка — «песочницы не
будет».

**Что показала разведка по чужим решениям.**

| Кто | Что делает | Отношение к нашей идее |
|---|---|---|
| Code mode (Cloudflare, Anthropic) | Одна тула, модель пишет код, тулы — API внутри песочницы | Перебивает форму фазы 1 целиком |
| n8n / Zapier через MCP | Агент зовёт **готовый** сценарий как тулу | Это наша развилка 2, и она коммодити: спрос подтверждён, новизны нет |
| Open Agent Spec, декларативный LangGraph | Декларативное **описание агента**, пишет человек | Другая задача: конфигурация, а не исполнение по требованию |
| Сочинение Open Workflow агентом на лету | Не нашлось | Отсутствие здесь — не пустая ниша, а след того, что нишу занял code mode |

**Решение.** Фаза 1 (`run_workflow(spec)` с сочинением спеки на лету) — отложена; вернуться, когда
появится `sandbox-runner`, и тогда решать уже не «DSL или нет», а «code mode на нашей песочнице».
Развилка 2 (сохранённые детерминированные сценарии по расписанию) от этого решения **не зависит**:
спрос на неё подтверждён чужими продуктами, и она остаётся настоящим продуктовым пробелом — но это
сущность, триггер и редактор, а не «одна тула», и на roadmap она заслуживает собственной строки.

Ниже — разбор от 2026-09-11 без изменений.

## Где здесь ABAC и почему он почти бесплатный

Точка принуждения политик у нас одна и она не там, где кажется. `ToolExecutionService` **ничего не
проверяет** — он доверяет строке `tool_call_logs`, которую ему дали. Проверяет
`AgentToolCallService.evaluate`: binding агент↔коннекция, правило `agent_connection_policies`,
`params_filter` по аргументам вызова. Стоит движку сценария позвать
`ToolProvider.executeTool` напрямую — политики исчезают целиком, и тула `run_workflow` становится
дырой, через которую агент дотянется до любого коннектора, к которому не привязан.

Отсюда **инвариант, вокруг которого строится всё остальное**:

> Каждый шаг сценария входит в исполнение через `AgentToolCallService` с личностью **инициировавшего
> агента**, а не от имени движка.

Личность уже вся есть в `ConnectorEnv`: `userId`, `agentId`, `runId`, `agentSessionId`, `channelId`.
Движок не добывает ничего нового — он переиспользует контекст своего собственного вызова.

Что достаётся из этого инварианта даром:

- **Гейт binding'а и правила.** Шаг к коннектору, к которому агент не привязан, отказывается тем же
  «Connector instance is not bound to the agent», что и обычный вызов.
- **`params_filter` по *посчитанным* аргументам.** Фильтр применяется к тому, что получилось после
  jq-преобразования, а не к тому, что написала модель. Это строже сегодняшнего: сегодня модель
  сочиняет аргументы сама, и фильтр — единственная преграда; здесь преграда та же, но данные в неё
  приходят из предыдущего шага, а не из головы модели.
- **Аудит.** Каждый шаг — отдельная строка `tool_call_logs` с `access_effect`. Сценарий не становится
  чёрным ящиком: в журнале видно ровно то же, что видно от агентного цикла. Но связи с вызовом
  `run_workflow` у этих строк нет — для читателя журнала (и для сметателя) они выглядят вызовами
  верхнего уровня с загадочными `external_id`. Чтобы утверждение об аудите было правдой, нужна
  ссылка на родителя в схеме.
- **Отмена — наполовину.** `executeAndRecord` перечитывает `cancel_requested_at` рана-родителя перед
  каждым вызовом, так что остановленный ран больше не сделает ни одного побочного эффекта. Но отказ
  приходит **обычным error-результатом**, а спека с `try` вокруг шага его поймает и пойдёт дальше —
  сценарий переживёт отмену, отказывая шаг за шагом. Движок обязан проверять
  `isCancelRequested(runId)` сам между шагами и трактовать отмену как необрабатываемый обрыв,
  отличный от ошибки тулы.
- **Секреты.** Креды расшифровываются в `ConnectorEnvFactory` внутри штатного пути исполнения и в
  движок не попадают вовсе. Это надо записать как инвариант: в DSL не должно существовать способа
  сослаться на кред.
- **Идемпотентность.** `external_id` шага чеканит движок (`wf:<runId>:<step>:<attempt>`), и защита
  от дублей из `AgentToolCallService` работает на реплее так же, как на вызовах модели.

То есть ABAC — не проблема этой задачи. Проблема — исполнение.

## Что придётся поправить в ядре

Немного, но не ноль — как и в [agent-to-agent-internal.md](../agent-to-agent-internal.md).

1. **Слой.** `AgentToolCallService.processToolCall` принимает `ToolCallRequest` из
   `controller/agent/dto`, а коннекторному слою запрещено зависеть от `controller/**`. Интерфейс
   `IToolCall` в `service/dto` уже есть, но объявляет только `id/connectorCode/connectionId/name/input`
   — `agentSessionId` и `runId` читаются с конкретного класса. Нужна сервисная запись (или
   дорасширение `IToolCall`) и перегрузка.
2. **Исключения.** `processToolCall`/`authorizeToolCall` бросают `ForbiddenStatusException` и
   `ConflictStatusException` — исключения HTTP-границы, ловить их внутри коннекторного слоя значит
   нарушить собственное правило о слоях. Нужен неброскающий вход, возвращающий решение: сценарию
   отказ шага — это событие, которое ловит `try/catch` спеки, а не аварийное завершение.
3. **ThreadLocal.** `BaseConnectorHandler.invoke` делает `ConnectorEnvHolder.set(env)` и
   `clear()` в `finally`. Если `run_workflow` исполнит шаг синхронно на своей нити, вложенный
   `invoke` в `finally` сотрёт **чужой** env — свой собственный. Либо env захватывается один раз на
   входе и дальше не читается из холдера, либо — лучше — шаги уезжают на `toolExecutor` через
   `executeWithTimeout`: там своя нить со своим ThreadLocal, а исход `StillRunning` и есть нужный
   примитив «шаг ещё бежит».
4. **Разные виды исполнения шага.** `executeAndRecord` возвращает результат только для `BACKEND`.
   `APP` уезжает в канал приложения и результата не возвращает вовсе (он придёт извне,
   `recordOutputFromApp`), `LOOPBACK` вообще нельзя отправить на исполнение — его исполняет
   вызывающий агент. Единственная модель, покрывающая все три, — «выдать вызов и ждать `finish_at` в
   `tool_call_logs`», ровно то, что делает воркер через `GetToolResult`. Ждать так внутри
   control-api — значит держать поллинг собственной базы; это работает, но это уже не «тула,
   исполняющая спеку», а маленький планировщик, и это главный аргумент второй развилки.

Даром при этом достаётся долгое исполнение: `run_workflow` — обычная тула, и сценарий длиннее grace
(10 с) отцепляется по [detached-tools.md](../detached-tools.md), а результат приезжает триггером
`tool_completed`. Механика ожидания долгого результата уже построена, изобретать её не надо.

## Развилка 1: где живёт движок

**В control-api, внутри коннектора.** Просто и укладывается в SPI без изменений формы. Расплата —
недолговечность: control-api — производитель DBOS, но не исполнитель, durable-шагов у него нет, а
`connector_jobs` — планировщик, а не машина шагов, и рестарт пода теряет сценарии в полёте. Для одноразовой спеки на 5–10 шагов это приемлемо, если
объявить явно: сценарий короткий, ограниченный, падение равно ошибке тулы.

**В agent-worker, отдельным видом рана.** Здесь обнаруживается главный аргумент всего разбора:
примитив шага **уже написан**. `ToolCallStep` выдаёт вызовы через `ExecuteToolAsync` и ждёт их
поллингом `GetToolResult` — то есть покрывает все виды исполнения разом (`BACKEND`, `APP`), умеет
детач, бюджет, отмену и реплей, и всё это durable-шагом DBOS с чекпоинтом из id и статусов. Движку
сценария нужен ровно такой шаг. Путь вызова — тот же gRPC, значит ABAC приходит бесплатно и без
правок ядра из предыдущего раздела. Расплата — правка протокола, новый вид рана и вопрос очереди:
`agent_exec` партиционирована сессией (single-writer), и долгий сценарий либо запрёт сессию, либо
требует своей очереди.

Различающий вопрос ровно один: **должен ли сценарий переживать рестарт?** Разовая спека внутри хода
агента — нет. Сохранённый сценарий по расписанию — обязан, иначе ночной запуск тихо не состоится.
Ответ на развилку 2 отвечает и на эту.

## Развилка 2: где на самом деле ценность

Честная оценка одноразовой спеки: **она даёт меньше всего**. Модель пишет YAML с jq вслепую — не
видя промежуточных результатов, не зная, что вернёт третий шаг. Ошибка в выражении стоит хода на
переписывание, и для цепочки из трёх шагов это дороже, чем просто вызвать три тулы: агентный цикл
**уже** является движком сценариев, где поток управления — модель, и у него есть то, чего у
декларативной спеки нет, — возможность посмотреть на результат и передумать.

Порог окупаемости — примерно с пяти шагов, и не по длине, а по признакам:

- **детерминированная передача данных** (id из шага 1 в шаг 4 не галлюцинируется — jq не ошибается
  в UUID, а модель ошибается);
- **параллель, которую модель не выразит** (`fork`/`for` по пятидесяти карточкам доски: выдать
  несколько вызовов одного хода разом воркер умеет и сейчас, но столько `tool_use`-блоков в одном
  ходе модель не пишет);
- **цикл по коллекции** (`for` по письмам — сегодня это N ходов модели с полной историей в каждом);
- **повтор без хода модели** (`try`/`retry` на сетевой ошибке).

Настоящая же ценность — **сохранённый сценарий**: запускается триггером или расписанием, модели не
требует вовсе, стоит ноль токенов, повторяем. Это форма n8n/Zapier, и она бьёт в главный названный
разрыв с конкурентами. Но это уже не «одна тула»: нужна таблица сценариев, привязка к агенту, тулы
`save_workflow`/`list_workflows`/`run_workflow(name)`, вход из `TriggerRouterService` и когда-нибудь
редактор во фронте. Против исходной формулировки «с одним лишь методом» — но именно здесь лежит то,
ради чего это стоит делать.

Промежуточная ступень, которая мирит обе: **одноразовая спека в первой фазе, но с самого начала
адресуемая по имени** — `run_workflow(spec)` для отладки и `run_workflow(name, input)` для
сохранённого. Тогда вторая фаза добавляет хранилище и триггер, не переписывая исполнение.

## DSL: что берём и что запрещаем сразу

Из двенадцати типов задач Open Workflow нам ложатся: `do`, `set`, `switch`, `for`, `fork`, `try`,
`raise`, `wait`. Выражения — jq, как требует спека; на JVM это `jackson-jq` (чистая Java, Jackson 2
— та же генерация, на которой стоит `JsonUtils`, так что в нашу двойную джексоновскую границу
ложится без конфликта).

Запрещается на разборе, а не на исполнении:

- **`call: http` / `openapi` / `grpc` / `asyncapi`** — обход ABAC по построению. Агент получил бы
  произвольный исходящий запрос от имени нашего сервера мимо binding'ов; гард
  [outbound-http.md](../../architecture/outbound-http.md) защитил бы внутреннюю сеть, но не защитил бы
  от «выложить содержимое памяти на чужой адрес». Единственный разрешённый `call` — в тулу агимейта.
- **`run: container` / `script` / `shell`** — исполнение чужого кода на нашем сервере; это отдельный
  продукт ([terminal.md](terminal.md)), а не побочный эффект коннектора.
- **`listen` / `emit`** — своей событийной шины у нас нет, а изображать её триггерами значит
  случайно построить вторую систему маршрутизации рядом с `TriggerRouterService`.
- **`run: workflow`** — вложенность откладывается до появления сохранённых сценариев; до тех пор она
  только даёт рекурсию.

То есть от спеки берётся **поток управления и преобразования**, и не берётся **ввод-вывод**: весь
ввод-вывод — это наши тулы, а они уже под политиками. Это и есть формулировка, которая делает
задачу безопасной.

Реализация парсера/валидатора: у спеки есть Java SDK (7.x, требует JDK 17) с эталонным движком —
координаты `io.serverlessworkflow:serverlessworkflow-api` относятся к релизам до июньского
переименования, после него их надо перепроверить. Брать ли SDK целиком или только модель+валидатор, а
исполнение писать своё — вопрос ревизии: движок SDK рассчитан на `call: http` и прочий ввод-вывод,
и вопрос в том, позволяет ли он белый список типов задач или его проще обойти. Свой интерпретатор
разрешённого подмножества — это, по грубой прикидке, не самая большая часть работы; большая часть —
именно шов с исполнением шага.

## Парный навык: он объявляет грамматику, а не описывает её

Коннектор без навыка здесь нерабочий, и это не тот случай, когда навык — вежливая документация. У
модели **уже есть** представление об Open Workflow из обучения, и оно шире нашего: она напишет
`call: http`, `run: shell`, `listen` — ровно то, что мы отказываем. Без навыка каждая первая спека
разбивается о парсер, агент уходит в цикл переписывания, и тула обходится дороже, чем её отсутствие.
Навык — единственное место, где сужение спеки становится известно тому, кто спеку пишет.

Что в теле обязательно:

- **Разрешённые ключевые слова дословно**, с явным «в этом диалекте больше ничего нет». Перечислить
  то, чего нет, важнее, чем то, что есть: модель дополняет список сама.
- **Форма `call: agimate`** и как назвать тулу — под `llm_name`, тем же именем, которым модель зовёт
  её напрямую. Иначе она изобретёт `function`, `service` или URL.
- **jq на примерах передачи данных между шагами.** Ради этого сценарий и пишется; примеры — на
  настоящих тулах платформы, потому что форму модель копирует из примера, а не из описания.
- **Порог.** «От пяти шагов, параллель, цикл, детерминированные идентификаторы» — и прямо
  сформулированное «на две тулы сценарий не пишут». Урок `ask_agent` против доски: без этой фразы
  модель начнёт писать YAML там, где достаточно двух вызовов.
- **Что делать с отказом шага** (`try` ловит запрет политики — это штатный исход, а не авария) и
  **что сценарий длиннее grace отцепляется**: иначе агент пообещает пользователю мгновенный ответ и
  замолчит на десять минут.

Frontmatter — `name: workflow`, `disclosure: lazy` ([progressive-disclosure.md](../progressive-disclosure.md)):
тело большое, а нужно оно только тогда, когда сценарий действительно пишется. Объявляется в
`connectors` **только сам `workflow`**, хотя сценарий зовёт тулы чужих коннекторов. Соблазн написать
`[workflow, board, telegram]` есть, и он неверен: гейт удерживает навык целиком, пока все объявленные
коннекторы не разрешатся в удовлетворённые экземпляры, — навык просто никогда не доехал бы до
агента без телеграма. Доступность чужих тулов — вопрос binding'ов агента, а не деклараций навыка.

**Ловушка, которая здесь дороже обычного.** Системные навыки сеются по ключу `(userId, name)`
**только если их нет**: после первого засева classpath перестаёт быть источником истины, и правка
`SKILL.md` на поднятой среде не делает ничего. С доской это пережили; тут расхождение навыка с
парсером означает спеки, написанные по устаревшей грамматике и отказанные — то есть сожжённые ходы.
Отсюда требование к первой фазе: **сообщение об отказе парсера само перечисляет разрешённые
ключевые слова** и называет то, которое не прошло. Тогда отставший навык деградирует в «модель
исправилась со второй попытки», а не в «агент не может пользоваться тулой». Механизма обновления
системных навыков у нас нет, и заводить его ради этой задачи дороже, чем сделать отказ
самоописательным.

## Неочевидные места

**Имена тулов в спеке.** Модель знает тулы под `llm_name` (`platform__agent_list`), который считает
бэкенд, а исполнение адресуется парой `connectionId` + голое имя. Движок обязан переиспользовать то
же разрешение имени, что и воркер, включая случай двух экземпляров одного коннектора
(`mcp_context7` против `mcp_notion_work`), а не заводить свой поиск. Иначе первая же вторая
коннекция того же типа разъедется.

**Постепенное раскрытие против спеки.** Тула с `disclosure = LAZY` модели не видна, пока не
загружена, — значит и сослаться на неё в спеке модель не может. Это скорее хорошо: сценарий пишется
из того, что агент реально видит. Но отсюда следует дешёвая и полезная вещь — **предполётная
проверка**: до исполнения первого шага прогнать каждый шаг через `ConnectorToolSpec.inputSchema` и
`ConnectionAccessEvaluator`, и отказать всей спеке целиком с внятным перечнем проблем. Половина
ошибок модели ловится до того, как сценарий сделает первый побочный эффект, и стоит это один проход
по спеке.

**`params_filter` на самой `run_workflow` бессмысленна.** Фильтровать YAML-строку нечем, так что
политика на этой туле — только разрешить/запретить. Фактическое ограничение даёт фильтр на тулах
шагов, и это надо написать в документации коннектора: запрет на `telegram.send_message` продолжает
работать внутри сценария, потому что проверяется на шаге.

**Рекурсия и петли.** `run_workflow` внутри спеки запретить (см. выше). Когда появятся сохранённые
сценарии — счётчик глубины в контексте исполнения и потолок, как у a2a.

**Потолки.** Число шагов, общее время, размер контекста между шагами, время одного jq-выражения
(jq умеет зациклиться), размер вывода шага. Обрезка вывода на 64 000 символов, которую делает
воркер, **внутри движка не действует** — это цифра его шва, а не платформенная.

**Доверие.** Вывод тула, детерминированно уезжающий в следующий шаг, безопаснее сегодняшнего: между
ним и решением нет модели, которую можно уговорить. Исключение — шаг, который сам является вызовом
модели (медиа-тулы): там в промпт уезжает недоверенный текст, ровно как сегодня.

**«Два способа сделать одно и то же».** Сценарий встаёт рядом с обычными вызовами, доской и
`ask_agent`, и выбор между ними модель делает сама. Единственное место, где этот выбор можно
объяснить, — тело навыка; см. раздел о парном навыке выше.

## Что это даёт

- **Токены и латентность.** Цепочка из десяти шагов — один ход модели вместо десяти, и ни один
  промежуточный результат не занимает контекст.
- **Точность передачи данных.** Id, суммы, даты переезжают между шагами выражением, а не пересказом.
- **Параллель за пределами хода.** Вызовы одного хода воркер и сегодня выдаёт разом и ждёт вместе
  (`ToolCallStep`), так что «параллели нет» сказать нельзя. Чего нет — параллели, не выраженной
  моделью: пятьдесят ветвей `fork` — одна строка спеки и ни одного лишнего `tool_use`-блока.
- **Повторяемость.** Один и тот же сценарий даёт один и тот же порядок вызовов — то, чего от модели
  нельзя требовать и на чём ломаются продажи «автоматизации».
- **Прозрачность.** Спеку видно и можно прочитать до запуска; агентный план — нет.

## Что не делать

- **Не давать движку прямой доступ к `ToolProvider`.** Единственная по-настоящему опасная ошибка в
  этой задаче — вся остальная работа только вокруг неё.
- **Не делать «универсальный движок workflow» как продукт.** Мы делаем способ агенту описать
  детерминированную часть своей работы, а не конкурента n8n с нулём интеграций.
- **Не пускать `http`/`shell` даже «для своих».** Один флаг «только для внутренних сценариев»
  переживёт своё обоснование и станет дырой.
- **Не хранить спеку в `agent_runs`/чекпоинтах DBOS.** Правило про минимизацию данных в чекпоинтах
  никто не отменял; спека живёт в своей таблице (или в аргументах вызова), в чекпоинт едет id.

## Порядок работ, если первая фаза принимается

- [ ] Решить развилку «где движок» (ответ следует из «нужны ли сохранённые сценарии в первой фазе»)
- [ ] Ревизия `serverlessworkflow-api` 7.x: годится ли модель+валидатор без эталонного исполнения
- [ ] Сервисный вход в `AgentToolCallService` без DTO контроллера и без исключений HTTP-границы
- [ ] Разрешение имени шага (`llm_name` → `connectionId` + голое имя) общим кодом с воркером
- [ ] Предполётная проверка спеки: схемы аргументов + `ConnectionAccessEvaluator` по каждому шагу
- [ ] Интерпретатор подмножества (`do`, `set`, `switch`, `for`, `fork`, `try`, `raise`, `wait`) + jq
- [ ] Ссылка на родительский вызов в `tool_call_logs` (миграция) — иначе шаги в журнале сироты
- [ ] Отмена как обрыв, а не ловимая `try` ошибка шага
- [ ] Потолки: шаги, время, размер контекста, время выражения, размер вывода шага
- [ ] Самоописательный отказ парсера: перечислять разрешённые ключевые слова в тексте ошибки
- [ ] Коннектор `workflow` + парный навык `workflow` (`disclosure: lazy`, `connectors: [workflow]`):
      грамматика дословно, форма `call: agimate`, jq на настоящих тулах, порог и детач
- [ ] `docs/connectors/workflow.md` и строка в `docs/architecture/connectors.md`
