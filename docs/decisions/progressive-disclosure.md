# Постепенное раскрытие контекста: навыки и схемы тулов

Сейчас в системный промпт рана уезжают **тела всех** привязанных навыков и **схемы всех**
доступных тулов. И то и другое фиксируется один раз, при сборке рана, и не зависит от того, что
агент на самом деле будет делать. Документ о том, как перевести обе части на раскрытие по мере
надобности, и почему это один механизм, а не два.

Ревизия 2026-09-08 (сверка с кодом и с документацией провайдеров) поменяла два допущения, на
которых стояла первая редакция: рост списка тулов внутри рана не дешёв, а отдельного состояния
«что раскрыто» не нужно. Оба разобраны ниже, в «Ограничениях» и в «Механике». Тем же днём принят
транспорт: внутренний коннектор со строкой-режимом, подключаемый к агенту так же, как
`persist-memory` — через навык. Разбор трёх отвергнутых вариантов — в «Транспорте раскрытия».

Уточнения при составлении плана (тем же днём, после обсуждения):

- раскрывающих коннекторов **два**, по одному на ось — `skill-loader` (`load_skill`) и `tool-loader`
  (`load_tools`); первая редакция сводила их в один `system`. Оси независимы, и один коннектор
  не давал включить половину;
- ось `disclosure` переопределяется и на отдельном туле (`@Tool`), а не только на коннекторе;
- LLM-имя тула (`platform__agent_list`) вычисляет control-api и присылает в спеке (`llm_name`).
  Это то имя, которое стоит в листинге, в аргументах `load_tools` и в ledger'е, поэтому раскрытое
  множество сопоставляется с каталогом рана по имени, без полей маршрутизации в записях ходов;
- все сидовые навыки `lazy`, кроме `persist-memory` и `media`: это поведенческая дисциплина
  (когда сохранять заметку, как итерировать картинки), которую модель не загрузит сама, потому что
  не подозревает, что она ей нужна.

## Проблема в цифрах

Замер по сидовым пресетам и `@Tool`-декларациям (сентябрь 2026):

| Агент | Навыки | Тулы |
|---|---|---|
| personal-assistant (`time`, `persist-memory`) | 10 КБ ≈ 3.5k токенов | 11 тулов ≈ 2k |
| health-diary (`sheets`, `media`, `time`, `persist-memory`) | 24 КБ ≈ 9k | 27 тулов, 56 параметров ≈ 5k |
| platform-admin (`platform`) | 17 КБ ≈ 6k | **79 тулов, 163 параметра ≈ 15–20k** |

Два вывода, оба против интуиции «проблема в навыках»:

1. **Схемы тулов — бо́льшая половина.** У platform-admin они весят втрое больше тела навыка.
   Решать только навыки — значит снять треть проблемы у самого тяжёлого агента.
2. **Пресеты привязывают 1–4 навыка, а не девять.** Худший реальный случай по навыкам — 9k токенов,
   а не 15k, как выходит, если сложить весь каталог. Экономия есть, но она не «губительная»
   сама по себе — губительна сумма.

Внутри тула тоже неоднородно: «вывеска» (имя + короткое описание) — это ~30–40 токенов, а
«начинка» (`inputSchema`, собранная `ToolSchemaReflector` из `@ToolParam` с примерами) — основные
150–250. Дробить надо по этой границе. Оговорка: это верно для **своих** тулов, где описание не
длиннее 85 символов. У MCP описание не ограничено ничем (`ConnectionTool.description` — TEXT, через
`ConnectionToolMapper` уезжает в спеку как есть), и там «вывеска» без вычисленного короткого текста
съедает экономию целиком.

Ориентиры из документации Anthropic по tool search: точность выбора тула падает после 30–50
доступных, отложенную загрузку советуют от 10 тулов или от 10k токенов определений. Platform-admin
с 79 тулами выше обоих порогов; у OpenAI мягкая рекомендация — «до 20 тулов на старте хода».

## Что уже есть в коде

Половина механики существует — важно не изобретать её заново:

- `RunContextService.skillsBlock()` уже выдаёт список навыков `skill_id / name / description /
  connector_codes`. «Перечисление вместо тел» — это уже реализованный блок, новое только «не класть
  тела».
- `ContextSpec.SkillBodies.MATCHED` — детерминированный отбор тел по коннектору события. То есть
  идея «отбирать до рана, а не спрашивать модель» в проекте уже принята, просто для триггеров.
- `AgentSkillService.satisfiedSkillInstances()` — гейт «навык доезжает только если его коннекторы
  разрешаются в живые инстансы».
- `ToolRegistry` в воркере уже держит полный маппинг `sanitized → (connectorCode, name,
  connectionId)`; `ToolDef` — отдельный список, который передаётся в `llmCaller.call(messages,
  toolDefs)` на каждом ходу.
- `ConnectorTraits` — тип-уровневый дескриптор коннектора, объявляемый в коде и засеваемый в таблицу
  `connectors`. Готовое место для оси «раскрытия».
- `RunHistoryAssembler.assemble()` загружает **все** ходы окна истории (20 ранов, до 300 ходов) до
  того, как режет их на выдачу. Всё, что модель вызывала в окне, уже лежит в памяти сборщика в момент
  сборки контекста — из этого выводится раскрытое множество, см. ниже.
- `TurnLog.record()` пишет в `agent_run_turns` **каждый** ход цикла, включая ходы тулов, независимо
  от того, кто тул исполнил. Видимость в ledger'е не зависит от транспорта раскрытия.
- Внутренний коннектор со строкой-режимом — готовый путь в ран: строка материализуется в
  `ConnectionBindingService.ensureModeConnection` при привязке навыка, доступ открывает пользователь
  или пресет, тулы попадают в `requiredConnections` через удовлетворённые навыки, ABAC гейтит по
  привязке, вызов ложится в `tool_call_logs`. `persist-memory` живёт ровно так.
- `ConnectorToolSpec._meta` (`@Tool(meta = @ToolMeta(...))`) доезжает до воркера: `RunContextMapper`
  копирует карту в proto. Готовый канал для маркера «результат этого тула — дельта контекста».
- Реплей шага `tool_calls` перечитывает результат по id из `tool_call_logs.output` через
  `GetToolResult` (`ToolCallDispatcher.reread`). Всё, что тул вернул, уже долговечно на бэкенде.

## Ограничения, которые задают форму решения

Шесть фактов из кода и документации провайдеров, каждый из которых обрубает какой-то из очевидных
путей.

**1. Тул — структурный контракт, а не текст.** Навык действует, как только его текст попал в
контекст. Тул — нет: модель не может вызвать то, чего нет в списке тулов запроса. Значит одного
описывающего метода мало. Либо посредник (`tool_call(name, args)` со свободным JSON внутри строки) —
и тогда теряется валидация аргументов провайдером, модели заметно хуже попадают в схему, и это
противоречит нашему же `TOOL_CALL_GUIDANCE`; либо **состав видимых тулов меняется по ходу рана**.

**2. Состав видимых тулов менять можно.** «Тулы фиксируются на ран» — неточность: `GetRunContext`
вызывается один раз за ран (`ContextMaterialsFetcher`), но `AgiMateAgent` передаёт `toolDefs` в
каждый ход отдельно. Фиксируется доставка спецификаций, а не то, что видит модель. Правка —
изменяемость одного поля в воркере, не форма протокола.

**3. Раскрытие не имеет права попасть в DBOS-чекпоинт.** Вызовы тулов — durable-шаг
(`ToolCallDispatcher` → `dbos.runStep(..., "tool_calls")`), но его результат намеренно тощий:
`ToolCallStep.Outcome(toolCallId, status, error)`, без содержимого — содержимое живёт в ledger'е
бэкенда и на реплее перечитывается через `GetTurn` (решение «только id в чекпоинтах»). Класть
раскрытые спеки в чекпоинт нельзя дважды: это protobuf (Jackson давится дескрипторами) и это
раздувание чекпоинта.

Из этого следует форма долговечности: **источник истины по раскрытому — ledger в control-api**, а
набор `ToolDef` в воркере — производная. `GetRunContext` вызывается вне шага
(`ContextMaterialsFetcher`), то есть на восстановлении рана выполняется заново — и возвращает как
`EAGER` то, что раскрыли **завершённые** раны окна. Раскрытия самого упавшего рана в окно ещё не
попали; они возвращаются вместе с реплеем вызовов мета-тулов: чекпоинт шага `tool_calls` говорит
«вызов завершился успешно», содержимое перечитывается по id из `tool_call_logs` через
`GetToolResult`, и воркер применяет ту же дельту заново (см. «Транспорт»). Drain при выкатке не
нужен: ни один чекпоинт формы не меняет.

**4. `RunHistoryAssembler.TOOL_JSON_CONTEXT_CAP = 4 КБ`.** Результат тула обрезается при сборке
истории (вторая точка обрезки — воркер, 64 000 символов внутри рана; тело в 17 КБ её проходит).
Тело `sheets` (8 КБ) или `platform` (17 КБ), приехавшее результатом `load_skill`, на следующем ране
пришло бы обрубком — агент тихо забыл бы навык посреди разговора. Любое решение обязано сказать, что
происходит с телом на следующем ране.

**5. Кэш префикса: тулы стоят первыми.** У обоих провайдеров порядок кэшируемого префикса один:
`tools → system → messages`, и любое изменение слева сбрасывает кэш всего, что правее
(Anthropic: «adding, removing, or reordering a tool invalidates the entire cache»; OpenAI: изменения
имён, описаний, схем и порядка тулов ломают совпадение префикса). Первая редакция документа считала,
что «рост в хвосте дешевле перетряхивания префикса». Для **тел навыков**, приходящих результатом тула
в хвост сообщений, это так. Для **схем тулов** — нет: каждое дораскрытие среди рана переписывает
префикс целиком. Отсюда правила, которые дальше держатся как инварианты:

> **Внутри рана раскрытое множество меняется пачкой и как можно раньше. Между ранами оно выводится
> из окна истории до сборки контекста.**

Единичный сброс на ран терпим, сброс на каждое дораскрытие — нет. На границе рана префикс всё равно
собирается заново, и там раскрытие по окну истории бесплатно.

**6. Провайдер не развернёт схему за нас.** У Anthropic tool search вставляет определение
найденного тула в позицию сообщения, а массив `tools` не трогает — схему провайдер знает из запроса.
Наш воркер ходит через OpenAI-совместимый API, где тул обязан быть в `tools`; нативный
`defer_loading` через шлюзы не гарантирован (в Claude Code он отключается при стороннем
`ANTHROPIC_BASE_URL`). Поэтому раскрытие — наш механизм, а не настройка провайдера, и ограничение 5
остаётся в силе.

## Как это решено у других: Claude Code, OpenCode, deepseek-harness

Тот же класс задачи в трёх системах. Claude Code и API Anthropic — по документации; OpenCode — по
документации и исходникам (ветка `dev`, коммит d6855b6b, 2026-09-08); deepseek-harness — по
документации и исходникам (ветка `master`, коммит c389f96b, 2026-09-07).

**Anthropic и Claude Code.** Все определения едут в каждом запросе, на нечастых
`defer_loading: true`; в контексте отложенных нет вообще — ни имени, ни описания, модели советуют
абзац «доступны тулы для Slack, GitHub, Jira». Поиск серверный (regex или BM25) по именам,
описаниям и аргументам. Найденное **вставляется в историю** как `tool_reference` и разворачивается
API на месте — массив `tools` не меняется, префикс цел. **Отдельного состояния «что раскрыто» нет**:
тул виден, пока сообщение с его обнаружением есть в истории, и пропадает только с компакцией.
Claude Code с 2.1.69 держит встроенные тулы отложенными (ядро Bash, Read, Edit — сразу; контекст
встроенных тулов сжался с 14–16k токенов до ~1k), MCP отложены по умолчанию; порог
`ENABLE_TOOL_SEARCH=auto:N` — доля окна модели, по умолчанию 10 %; через сторонний
`ANTHROPIC_BASE_URL` не работает. Пороги из документации: точность выбора падает после 30–50 тулов,
отложенная загрузка — от 10 тулов или 10k токенов, 3–5 самых частых держать неотложенными.

**OpenCode.** Все схемы — встроенные и все MCP — собираются на **каждом шаге** цикла
(`SessionTools.resolve`) и уходят в каждый вызов; тул скрывается из схемы только правилом
`"*": deny` на агенте, точечный deny оставляет схему и режет на исполнении. Отложенной загрузки нет.
Единственное исключение — экспериментальный code mode: все MCP-тулы сворачиваются в один тул
`execute`, в описании которого каталог с **бюджетом 2000 токенов**, заголовок COMPLETE или
PARTIAL «N из M», и `$codemode.search` с постраничной выдачей полных сигнатур. Каталог навыков
(имя + описание + путь) идёт в системный промпт и перегенерируется каждый шаг — в коде комментарий,
что подробный список в системном промпте работает лучше, чем в описании тула. Тело навыка —
результатом тула `skill` в `<skill_content>`. Обрезка вывода любого тула: 2000 строк или 50 КБ,
**полный текст в файл** с подсказкой «Grep или Read с offset». Pruning старых результатов за
пределом 40k токенов, но `PRUNE_PROTECTED_TOOLS = ["skill"]` — результат загрузки навыка от pruning
защищён (от компакции нет). Точки кэша на первых двух системных сообщениях и двух последних
несистемных; на массив тулов ничего, только сортировка по алфавиту.

**deepseek-harness.** Все схемы в каждом запросе, в README прямо: «Schema tokens repeat on every
request. Restricting a tool removes its entire schema cost for that agent» —
`ctx.tools.restrict({allow, deny})` на скоупе агента, пресет задаёт тулы, промпт и навыки на сессию.
Свёртка в код — режим PTC: один тул `run_code` и секция промпта с типами `declare const tools`.
Каталог навыков **не в системном промпте**: долговечное user-сообщение `<system-reminder>` на первом
шаге, только имя + описание, описание обрезано до 500 символов; перед каждым шагом считается дайджест
каталога, изменился или скрыт компакцией — вставляется полная замена. Причина названа явно: динамику
держат вне системного промпта, чтобы префикс system + tools был байт-в-байт стабилен под неявный
кэш DeepSeek. Тело навыка — результатом тула `skill`, без своей защиты. Обрезка в три слоя: bash
64 КБ хвоста со сбросом в файл; результат больше 50 000 байт целиком в файл, модели голова и хвост
плюс путь; под давлением компакции ретроактивный middle-pruner (порог 8192). Явных точек кэша нет;
сводка компакции переигрывает тот же system + tools, чтобы не терять тёплый префикс — вариант
«убрать tools из запроса на сводку» отвергнут с формулировкой «схемы тулов — часть кэшируемой
последовательности».

| | Anthropic / Claude Code | OpenCode | deepseek-harness | Наше решение |
|---|---|---|---|---|
| Схемы тулов в запросе | Только неотложенные; отложенные без имён | Все, каждый шаг | Все, каждый запрос | EAGER полностью, LAZY вывеской |
| Раскрытие среди рана | Поиск → ссылка в истории, префикс цел | Нет | Нет | `load_tools` пачкой, один сброс префикса |
| Ответ на большой каталог | Поиск, до 10 000 отложенных | Code mode: один тул, каталог 2000 токенов, поиск | PTC: один `run_code`, типы в промпте | Открыто: строка на коннектор + `load_tools(query)` |
| Каталог навыков | Описание в контексте | Системный промпт, каждый шаг | User-сообщение по дайджесту | Системный блок `skills` |
| Тело навыка | По требованию | Результат тула `skill` | Результат тула `skill` | Результат тула `load_skill` |
| Судьба тела в истории | До компакции | Защищено от pruning | Обычный результат | Не режется на 4 КБ, предел 32 КБ |
| Предел описания | Нет | Навык 1024 | Каталог 500 | Вывеска тула 160 |
| Обрезка вывода тула | Контекстное редактирование | 2000 строк / 50 КБ, полный в файл | 50 000 байт, полный в файл | 64 000 символов с маркером; история 4 КБ |
| Субагент с урезанным набором | Agent tool | Есть, deny «*» | Есть, фильтр на экземпляр | Идея C, отложена |

Что из этого переносится:

- **Тело навыка результатом тула** — единогласно. `load_skill` в общей колее.
- **Не резать результат загрузки навыка** — прецедент `PRUNE_PROTECTED_TOOLS = ["skill"]` в OpenCode.
  Наше освобождение от 4 КБ по флагу на строке ledger'а — то же правило, объявленное на строке, а не
  на имени.
- **Предел на описание в каталоге** — deepseek режет до 500, OpenCode валидирует до 1024. `summary`
  до 160 для тулов — из того же ряда; на описание навыка предела нет, добавить тестовый.
- **Модель-управляемое раскрытие схем есть только у Anthropic.** Оба открытых харнесса отвечают на
  большие каталоги иначе: урезать набор на агента заранее или свернуть каталог в один исполняющий
  тул с бюджетным списком и поиском. Для нас это два готовых элемента: прогрев на границе рана (уже
  в решении) и форма ответа на «сотни тулов MCP» — каталог с бюджетом, заголовок «N из M», поиск.
- **Схемы тулов — часть кэшируемого префикса** подтверждает третий источник. Ограничение 5 стоит.
- **Динамика вне системного промпта.** У нас это уже есть — эфемерные user-блоки для заметок памяти.
  Каталог навыков в системном блоке, как у OpenCode; менять не надо, пока список навыков агента
  стабилен внутри сессии.
- **Полный вывод тула в файл** вместо маркера обрезки — у обоих харнессов. У нас есть `agf_`-ссылки,
  механика ляжет на них. Вне этого решения — в `docs/roadmap.md`.

## Три идеи

### Идея A. Раскрытие по требованию (принята за основу)

Два мета-тула — `load_skill(names[])` и `load_tools(names[])`, тулы внутренних коннекторов
`skill-loader` и `tool-loader`. Вызовы пишутся в `agent_run_turns` как любые другие (`TurnLog` не различает исполнителя)
и в `tool_call_logs`, как любой вызов через бэкенд. Ответ на вызов, кроме текста для модели, несёт
**раскрытые спеки**, которые воркер применяет к своему реестру: LAZY-тул становится вызываемым со
следующего хода, с валидацией аргументов на стороне провайдера. Тела навыков едут текстом результата
`load_skill`.

Ключевая деталь, снимающая возражение «лишний обход бэкенда ради того, что и так лежит в воркере»:
**LAZY-тулы едут в `GetRunContext` без `inputSchema` и с явным флагом `disclosure`** — только имя,
короткое `summary`, маршрутизация. Схема физически появляется в воркере только после
`load_tools`. Обход не избыточен, он и есть работа.

Состояние — одно на обе половины, и оно **не хранится отдельно**: раскрытое множество выводится из
окна истории при сборке следующего рана (см. «Механика»). Внутри рана оно только растёт, пачкой.

- Плюсы: единообразие (всё через тулы, всё в ledger), одно правило на два вида содержимого, ошибка
  отбора исправима внутри рана, никаких новых таблиц и зависимостей.
- Минусы: цена раскрытия — лишний ход модели (латентность в диалоге) и один сброс кэша префикса на
  ран; изменяемый реестр в воркере; правка сборщика истории.

### Идея B. Только детерминированный отбор, без мета-тулов

Никаких `load_skill`/`load_tools`. Что раскрыто, целиком решает control-api при сборке рана: по
каналу, по коннектору события (`MATCHED` уже так делает), по «недавно использованному» из ledger
и — новое — по дешёвому предварительному отбору (эмбеддинги описаний навыков и тулов против текста
входящего сообщения, либо маленькая модель-классификатор).

- Плюсы: **ноль лишних ходов**, кэш идеален (набор фиксирован до рана), нет риска «модель не
  догадалась загрузить», в воркере и протоколе не меняется ничего. Поведенческие навыки не
  страдают — они и так всегда в промпте.
- Минусы: ошибка отбора **неисправима внутри рана** — агент просто отвечает «у меня нет такого
  инструмента», и пользователь видит деградацию без объяснения. Классификатор — новая зависимость и
  латентность перед раном, качество надо мерить. Отладка тяжёлая: почему тул не приехал, видно
  только по логам отбора.
- Годится как **дополнение**, не как единственный механизм: детерминированный прогрев EAGER-набора
  разумен в любом варианте, а после ограничения 5 он ещё и главный способ не платить сбросом кэша.

### Идея C. Фасад тяжёлого коннектора (вложенный ран)

Не раскрывать по одному, а спрятать тяжёлый коннектор целиком за один тул — `platform(task: string)`,
который запускает **вложенный ран** со своим контекстом, где видны все 79 тулов и тело навыка.
Переход в надсистему: не сжимаем контекст, а делим работу.

- Плюсы: главный контекст мал постоянно, без вытеснения; вложенные вызовы — свои
  `agent_run_turns`, то есть видно даже лучше; ложится на существующие сущности (`AgenticTeam`,
  сессии со `scope`).
- Минусы: вложенный ран стоит целого системного промпта и заметной латентности; суб-агент не видит
  разговора, поэтому задачу надо формулировать текстом (потеря контекста и источник ошибок); ошибки
  и артефакты надо транслировать наружу. Для health-diary с его 27 тулами — из пушки по воробьям.
- Область применения узкая, но точная: `platform` (79 тулов) и MCP-инстансы с большими каталогами.

### Что взято

**A как основу**, из B — детерминированный прогрев (EAGER-набор считается до рана: ось, окно истории,
коннектор события), C — отложить до момента, когда появится второй коннектор масштаба `platform`.
A и C не конфликтуют: фасад — это просто ещё один EAGER-тул.

## Механика

### Ось раскрытия объявляется в коде

Свойство коннектора с переопределением на туле: `ConnectorTraits` получает третью ось `disclosure`
(`EAGER | LAZY`), засеваемую бутстрапом в таблицу `connectors` — значит позже её можно переопределить
на установке, не трогая код. `platform`, `mcp` и `sheets` — `LAZY`; остальные (`time`,
`persist-memory`, `board`, `media`, `astro`, `divination`, `acp`, коннекторы каналов) — `EAGER` до
замера. Ось ставится на хендлере, не в фабрике `dynamicIntegration()`: `app()` тоже DYNAMIC, а
тулы приложений не отложены. Отдельный тул переопределяет ось коннектора необязательным атрибутом
`@Tool(disclosure = …)` (по совету «3–5 самых частых — неотложенные»); по умолчанию атрибут
наследует ось коннектора. Эффективная ось считается в одном месте, на `RunTool`. У динамических
тулов MCP переопределения нет — их нечем объявить.

Две оси независимы и управляют разным: ось навыка — **телом инструкции**, ось коннектора —
**схемами тулов**. Навык `lazy` при коннекторе `eager` — «инструкцию покажем по требованию, тулы
видны сразу»; навык `eager` при коннекторе `lazy` — «дисциплина всегда в промпте, схемы по
требованию». `load_skill` не открывает тулы LAZY-коннектора — см. ниже.

У навыка то же самое во фронтматтере `SKILL.md`: `disclosure: eager|lazy`, по умолчанию `eager`
(пользовательские навыки через `SkillService` — тоже). Сидовые навыки — `lazy`, кроме трёх:
поведенческих `persist-memory` (когда сохранять заметку) и `media` (дисциплина работы с
картинками) и `time` — за ним тянется почти каждый ран, и отложенное тело стоило лишнего хода
модели на «который час» (первый живой прогон, 2026-09-08). Модель никогда не загрузит то, о чём
не подозревает, что ей это нужно; процедурные навыки (`platform`, `sheets`, `board`, `astro`,
`divination`, `acp`) такой проблемы не имеют — их описание в листинге и есть маршрут.
Навыки-инструкции раскрывающих коннекторов (`skill-loader`, `tool-loader`) — `eager` по
определению.

Ось навыка — умолчание, а не приговор: **привязка переопределяет её** (`agent_skills.disclosure`,
`NULL` — наследовать). Один и тот же навык у одного агента лежит в промпте, у другого грузится по
требованию; выставляется при привязке (`POST …/skills/`) и меняется потом
(`PATCH …/skills/{skillId}`, тристейт `INHERIT | EAGER | LAZY` — `null` в PATCH уже значит
«не трогать», а пустой строки у enum нет). Эффективная ось считается в одном месте,
`AgentSkillService.resolveSkills`, и оттуда её читают и ран, и листинги. Переопределение —
явный выбор владельца, как запрет `load_tools` политикой: без `skill-loader` в скоупе оно, как
и сама ось, не читается.

**Ось действует только там, где есть кому раскрывать.** Мета-тулы приносят два коннектора,
`skill-loader` и `tool-loader`, а их к агенту подключают, как память, — через навык. У агента без
раскрывающего LAZY-тул раскрыть некому, и единственная разумная семантика — фолбэк, по осям:

> Если в `requiredConnections` рана нет коннекции `skill-loader`, тела всех навыков едут `EAGER`;
> если нет `tool-loader` — все спеки едут `EAGER`, как сегодня. Ось `disclosure` читается только
> при наличии своего раскрывающего.

Два условия в `RunContextService`, вычисляются после гейта навыков. Следствие продуктовое, и оно
принято сознательно: раскрытие — функция по выбору на агента, причём каждая половина отдельно.
Пресеты с тяжёлыми коннекторами (`health-diary`, `platform-admin`) получают обе через навыки
`skill-loader` и `tool-loader` (см. «Транспорт»), существующие агенты не меняют поведения, пока
пользователь их не подключит. Для замера это даёт контроль, для цели «токены — расходы платформы»
это минус: у агента, собранного не из пресета, функция выключена. Включать ли её по умолчанию у
новых агентов — открытый вопрос, после замера.

Ловушка: `SystemSkillBootstrap` и `SystemPresetBootstrap` — seed-only-if-missing. На засеянных средах
правка `SKILL.md` и `PRESET.md` ничего не изменит: миграция ставит `disclosure` навыкам по имени у
системного владельца, дописывает новые навыки в списки пресетов и правит текст навыка `platform`
через `replace()` в обоих языках — фраза «их схемы у тебя уже есть» под LAZY становится ложью.

### LAZY-спека: явный флаг и вывеска

Сигналом «тул отложен» служит **явное поле** `disclosure` в `ConnectorToolSpec`, а не отсутствие
схемы: `ToolRegistry.parseToolSchema` превращает пустую схему в `EMPTY_OBJECT_SCHEMA`, и спека без
схемы сегодня становится вызываемым тулом без аргументов. В proto это enum, у которого
`UNSPECIFIED` читается как `EAGER` — так старый control-api не ломает новый воркер. LAZY-спека
**не входит в `toolDefs`** — живёт только в маршрутной карте реестра и в листинге для модели; в
карту она попадает сразу при сборке, чтобы суффиксы разрешения коллизий имён не зависели от порядка
раскрытия.

Там же едет `llm_name` — имя, под которым тул видит модель (`platform__agent_list`). Его вычисляет
control-api, вместе с разрешением коллизий после санитизации; воркер берёт имя как есть и держит
собственную санитизацию только фолбэком на время выкатки против старого control-api (правило одно и
то же, результат совпадает). Причина переноса: имя должно быть одним и тем же в листинге вывесок, в
аргументах `load_tools` и в ledger'е, а листинг собирает бэкенд.

В листинг LAZY-тула едет не `description`, а `summary` — первое предложение, жёсткий предел около
160 символов, вычисляется в одном месте control-api при сборке спеки. Полное описание приезжает
вместе со схемой по `load_tools`. Для EAGER-тулов ограничение не рантаймовое, а тестовое, как
`ConnectorTextsTest`: описание своего тула не длиннее порога. Тем же тестом — описание навыка в
`SKILL.md` (у OpenCode предел 1024, у deepseek каталог режется до 500).

Порядок выкатки: **сначала воркер**. Новый воркер против старого control-api видит все тулы EAGER —
нормально. Старый воркер против нового control-api у агента с подключённым `tool-loader` увидел
бы 79 безаргументных тулов и не сумел бы применить дельту; у остальных агентов фолбэк EAGER, и
разницы нет.

### Раскрытое множество выводится из окна истории

Отдельной таблицы нет. `RunHistoryAssembler` уже загружает все ходы окна; правило одно:

> **Тул, который в окне истории вызывался или описывался, раскрыт для этого рана. Навык, который в
> окне загружался, — тоже.**

Это не только проще таблицы с `disclosed_at`/`last_used_at` — это единственно согласованный вариант.
История отдаётся модели как нативные `tool_use`; если тул из истории не в списке, модель повторит
вызов по образцу и получит «unknown tool» от `ToolCallDispatcher`. Таблица с правилом «не
использовался N ранов» обязана была бы держать N не меньше окна.

Две детали:

- Вывод идёт по окну **после** обрезки `withinTurnBudget` — по тем ранам, что модель увидит.
  Следствие для `RunContextService.build()`: история загружается **до** `collectTools`, сегодня она
  последний шаг.
- Ledger хранит имя в виде, который видит модель (`platform__agent_list`). Это же имя control-api
  вычислил сам (`llm_name`), поэтому обратное отображение — поиск по каталогу рана: имя из хода →
  `RunTool`. Ни полей маршрутизации в `ToolCallRec`, ни дублирования санитизации. Тул, чьё имя в
  каталоге не нашлось (коннекция отвязана), просто не раскрыт — что и требуется. Для
  `load_tools` имена лежат в аргументах вызова, среди них бывают промахи, поэтому сборщик
  читает **результат**: компактный JSON с разрешённым списком `llm_name` — тот самый, который воркер
  отдал модели. Какой результат читать, говорит вид «материала контекста» на `ToolResultRec`
  (`TOOLS | SKILL`), выставляемый воркером при `SaveTurn`.
- Строки ledger'а, записанные до выкатки, вида не несут, а имена в них совпадают с нынешними — так
  что вызовы из старых ходов сопоставляются, а результаты старых `load_skill` не встречаются вовсе.
  Переходного окна нет.

### Тело навыка на следующем ране

Результат `load_skill` **не режется** на 4 КБ при сборке истории. Тело остаётся в истории, история
входит в префикс следующего рана так же, как системный блок; заглушки, таблицы и второго
представления нет, а модель видит тело там, где его загрузила, в порядке разговора.

Освобождение от 4 КБ — не проверка имени в сборщике: воркер помечает результат при `SaveTurn` видом
«материала контекста» (`SKILL`) в `ToolResultRec`, сборщик читает его со строки ledger'а. Так
работает при любом транспорте раскрытия. Предел остаётся — 32 КБ: «бюджет важнее полноты» никуда не
делся. От накопления копий при перезагрузке навыка сборщик держит только новейший результат
`load_skill` на навык; старшие режутся, как обычный результат.

Что теряется: инструкция в результате тула весит меньше, чем в системной позиции. Для LAZY-навыков
это приемлемо — они процедурные (какие тулы, в каком порядке). Поведенческая дисциплина остаётся
EAGER и в системном блоке.

### Вытеснение

Окно истории и есть вытеснение. Поверх него — байтовый бюджет на раскрытые схемы и тела в префиксе
рана: константа рядом с `MAX_HISTORY_TURNS`, 96 КБ, лишнее вытесняется по давности в окне.
Производная от окна модели — потом; у Claude Code порог включения — 10 % окна, правило того же вида
можно взять как критерий «есть ли смысл в LAZY для этой модели».

Стиринг: на шве поглощения **не сжимать**. Ран ограничен пятью сбросами бюджета, а сжатие рвёт префикс
так же, как рост.

### Транспорт раскрытия: коннекторы `skill-loader` и `tool-loader`, подключаемые как память

Принято 2026-09-08; тем же днём один коннектор `system` разделён на два, по одному на ось.
`skill-loader` (`load_skill`) и `tool-loader` (`load_tools`) — внутренние коннекторы со
строкой-режимом, «Режим, владелец: агент» в матрице `docs/architecture/connectors.md`, рядом с
`persist-memory`, `time` и `sheets`: пользователь идентичность экземпляра не приносит, тул выводит
всё из вызывающего (`env.runId`, `env.agentId`). Каждый подключается через свой сидовый навык того
же имени (`disclosure: eager`, `connectors: [skill-loader]` и `[tool-loader]`), тело которого и
есть инструкция: как читать листинг вывесок, когда звать `load_skill`, что `load_tools` берёт
пачку. Два навыка, а не один на оба коннектора: гейт держит по инстансу, и навык с двумя
объявленными коннекторами не доехал бы к агенту, у которого подключён один. Внутренние коннекторы в
UI подключаются только через навык, поэтому навык обязателен, а не опционален. Тулы раскрывающих
попадают в ран тем же путём, что тулы памяти, — через `requiredConnections` удовлетворённых
навыков; в `collectTools` особой ветки нет.

Почему два, а не один. Оси независимы: ось навыка управляет телами, ось коннектора — схемами, и
агенту с малым набором тулов и тяжёлыми навыками нужна одна половина, а не обе. С одним коннектором
включить половину было нельзя, а фолбэк EAGER был общим на обе оси. Цена — второй класс-фасад и
второй навык, оба крошечные.

**Дельта контекста — обычный результат тула.** `load_tools` возвращает в `output_json` спеки
(`llm_name`, полное описание, `inputSchema`, маршрутизация), `load_skill` — тела. Какой результат
воркер разбирает как дельту, говорит маркер в `_meta` спеки (`@Tool(meta = ...)`), а не жёстко
зашитый код коннектора. `ToolGateway` не меняется: `output_json` и так непрозрачные байты. Модели
воркер отдаёт не полный ответ, а компактный JSON с разрешённым списком `llm_name` (и промахами
отдельно) — тот самый, который `RunHistoryAssembler` читает из записи результата в ledger'е (см.
«Раскрытое множество выводится из окна истории»); схемы уходят в массив `tools`, не в сообщения.
Для `load_skill` содержимое — тело навыка: оно должно остаться в истории, воркер отдаёт его модели
как есть. Два следствия по коду:

- разбор — из сырого `output`, **до** обрезки `truncateOutput` (64 000 символов): схемы
  platform-admin весят около 60 КБ;
- реплей бесплатен: `reread` вернёт тот же `output_json` из `tool_call_logs`, воркер применит ту же
  дельту. Ничего дополнительно хранить не надо.

**Скоуп считает бэкенд, внутри тула.** `load_tools` и `load_skill` пересчитывают каталог рана по
`env.runId` тем же кодом, что `GetRunContext` (сборка тулов и гейт навыков выносятся из
`RunContextService` в общий каталог рана). Так держится требование протокола «бэкенд не доверяет
воркеру в правах»: воркер не может выпросить схему тула, к которому агент не привязан. Цикла бинов
нет — `ConnectorRegistry` собирает хендлеры лениво ровно ради таких зависимостей (прецедент
`platform → AgentService → ConnectorRegistry`).

**Цена, принятая сознательно.**

- *Полсекунды на ход раскрытия.* `ToolCallStep.run` опрашивает результат раз сразу после выдачи и
  дальше каждые 500 мс; тул на 10 мс обходится в полсекунды. Лечится разгоном первых опросов
  (50 → 100 → 200 → 500 мс) — общая правка, ускоряющая и `time.now`, и `persist-memory`; в плане.
- *Вне рана тулы работают грубее.* `McpToolCatalog` и manage-листинг идут по привязкам, значит у
  агента с раскрывающими коннекторами их тулы видны MCP-клиентам и в редакторе политик. `env.runId` там пуст, тул
  считает каталог на уровне агента, а не рана. Честно и безвредно.
- *Пользователь может запретить `load_tools` политикой* и получить агента, у которого LAZY-тулы
  недостижимы. Тот же класс, что запрет `update_memory`: выбор владельца, не защищаем.

**Отвергнуто.**

- *RPC `Disclose` на `AgentContext` с двумя воркерными тулами.* Заводит категорию «тул, который
  исполняет воркер», которой по контракту `tool_gateway.proto` не существует, оставляет вызов без
  строки в `tool_call_logs` и добавляет в `ToolDispatcher` ветку «мета или бэкенд». Аргументы за него
  из первой ревизии — «`ContextDelta` в ответе `ToolGateway`», «дельту надо хранить для реплея»,
  «строка-режим требует миграции и INSERT в read-only `RunContextService`» — по коду не подтвердились:
  дельта едет в `output_json`, реплей читает `tool_call_logs`, строка-режим создаётся при привязке
  навыка, как у памяти.
- *Раскрывающий коннектор без экземпляра* (тулы платформы без строки в `connections` и без
  привязки, доступны каждому рану с LAZY). Меньше всего кода, но третий вид строки в модели коннекторов с тремя
  читателями (исключение в ABAC, guard в `ConnectionBindingService`, фильтр каталога
  `/manage/connectors/`) и «функция включена у всех» без права пользователя её выключить. Вариант
  со строкой-режимом ложится в существующую матрицу без новой клетки.
- *Воркер-локальное раскрытие* (LAZY-схемы и тела едут в `GetRunContext` с флагом «не показывать»,
  мета-тулы переносят их из придержанной карты в `toolDefs`). Ни RPC, ни обхода, ни латентности,
  около 200 КБ на ран для MCP на двести тулов — байты, не токены. Проигрывает там же, где RPC:
  воркер исполняет тулы сам, строки в `tool_call_logs` нет, скоуп не пересчитывается на бэкенде.

### Что происходит на первом ходу

Модель видит: список навыков с «когда применять», список тулов «имя + summary», плюс `load_skill` и
`load_tools` раскрывающих коннекторов. Листинг вывесок собирает `RunContextService`, а не
`PromptBlockProvider` коннектора: блоки коннекторов получают env без `runId`, а листинг зависит от
скоупа рана. Имя в листинге — то самое `llm_name` (`platform__agent_list`), которым модель потом
вызовет тул и которое передаёт в `load_tools`; никакой второй формы имени модель не видит.
Оба мета-тула принимают **массив имён** — это требование, а не удобство: раскрытие пачкой стоит
одного сброса префикса, по одному — сброса на каждый.

`load_skill` приносит **только тело**, схем не раскрывает: иначе на platform-admin загрузка навыка
немедленно вернула бы в контекст те самые 79 схем, ради которых всё и затевалось. Тело навыка называет нужные тулы поимённо, поэтому дальше идёт один вызов
`load_tools` пачкой. Это два лишних хода на первом использовании в сессии, не на каждом ране —
дальше раскрытое выводится из окна. Возможный срез позже: `tools:` во фронтматтере навыка, чтобы
`load_skill` раскрывал названные тулы одним ходом (навык уже источник истины для `connectors:`);
сейчас не нужно.

Guidance, зависящий от состава тулов (абзац про `untrusted_tool_output`, `detachedToolGuidance`),
решается по **полному** известному множеству, включая LAZY, а не по выставленному на момент сборки:
MCP-тул, раскрытый среди рана, должен получить не только обёртку от диспетчера, но и объяснение к ней.

### Триггерные раны раскрываются заранее

В `SYSTEM_TRIGGER`-ране лишний ход — чистые потери: там нет пользователя, ждущего ответ, а отбор уже
детерминированный. Правило: в триггерном ране `MATCHED`-навыки и тулы коннекторов события
раскрываются сразу, независимо от оси. Это обязательно, а не желательно: история берётся из сессии
канала (`Channels.sessionIdOf`), и у триггерного рана в CONNECTION-сессии окна, из которого можно
вывести раскрытое, нет. Место для этого в `ContextSpec` уже есть — там же, где `SkillBodies`.

## Открытые вопросы

Закрыты ревизией 2026-09-08 (номера — из первой редакции):

- **1. Гранулярность оси.** Коннектор с переопределением на `@Tool`, оба с первого шага (уточнение
  при составлении плана); какие тулы переопределять — по замеру. Динамические тулы MCP — только ось
  коннектора.
- **2. Бюджет.** Константа на раскрытые схемы и тела рядом с `MAX_HISTORY_TURNS`, 96 КБ; тело
  навыка в истории — до 32 КБ; `summary` — 160 символов; описание навыка — тестовый порог 500.
  Производная от окна модели потом.
- **3. Стиринг.** На шве не сжимать.
- **4. Промах по имени в `load_tools`.** Ошибка с перечнем ближайших имён того же namespace, как
  уже делает `ToolCallDispatcher` для неизвестного тула. Угадывать за модель не надо, у неё есть
  листинг.
- **7. MCP-агенты.** `McpToolCatalog` собирается отдельно от `RunContextService`, ось его не касается:
  MCP-клиент получает полные схемы, как сегодня. Тулы раскрывающих коннекторов он увидит у агента с
  подключённым коннектором — см. «Цена» в «Транспорте». При реализации подтвердить тестом. Замер
  той же стоимости со стороны MCP-клиента есть в issue #2 репозитория на GitHub (автор — внешний
  контрибьютор): 79 тулов ≈ 73 КБ; эта половина issue решением сознательно не покрыта.
- **Транспорт раскрытия.** Коннекторы `skill-loader` и `tool-loader` со строкой-режимом, см.
  «Транспорт раскрытия».

Остаются:

- **Раскрытие по умолчанию.** Функция по выбору на агента; включать ли навыки `skill-loader` и
  `tool-loader` каждому новому агенту, а не только пресетам, — после замера.
- **Маршрутный текст навыка** (5). `description` сейчас — каталожное описание для UI, а «когда
  применять» — другая фраза. Новое поле фронтматтера `when` или правило «`description` пишется как
  маршрутный текст»? Не зависит от механики, решается после первого замера.
- **Видимость для пользователя** (6). Показывать ли в UI, что открыто в сессии, и давать ли закрепить
  навык принудительно. Тоже после замера.
- **Каталоги в сотни тулов.** Для MCP-сервера с двумя сотнями тулов даже вывески — 6k токенов.
  Anthropic для этого вообще не перечисляет отложенные тулы, а даёт поиск по тексту; OpenCode в
  code mode сворачивает каталог в бюджет 2000 токенов с заголовком «N из M» и поиском. Для нас это
  `load_tools(query)` поверх имён и одна строка на коннектор в листинге, когда тулов больше
  порога. Порог — из замера, не заранее. Промежуточная единица между коннектором и тулом —
  модуль: у `platform` их пять (`Platform*ToolService`), и issue #2 предлагает отбор именно по
  ним. В SPI такого понятия нет, и заводить его ради одного коннектора рано; если листинг
  придётся сворачивать, модуль — кандидат на строку листинга.
