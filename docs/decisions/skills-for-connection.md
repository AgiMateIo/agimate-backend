# Навыки для подключения: открытые параметры подключения и селектор навыка

На странице подключения фронт показывает навыки, которые с ним работают, двумя запросами:
`/manage/skills/?connectorCode=mcp&scope=MINE` и то же с `scope=PUBLIC`. Фильтр смотрит только на код
коннектора, поэтому на странице MCP-сервера T-Invest оказывается и навык Excalidraw, хотя
`RunContextService` их никогда не сведёт: у навыка объявлен другой сервер. Документ о том, как
сделать связь «навык ↔ подключение» запросом к данным, а не вычислением в коде коннектора, и одним
правилом для листинга, рантайма и мастера привязки.

## Что есть сейчас

- Требование навыка (`ConnectorRequirement` в `skills.connectors` JSONB) несёт `code`, `key` и
  `params` — значения полей формы подключения. Поля `SECRET` в `params` запрещены
  (`SkillService.validateConnectors`).
- У подключения все поля формы, открытые и секретные вместе, лежат одной картой в зашифрованном
  секрете. Открытой копии нет, поэтому сравнить `params` навыка с подключением в SQL нельзя.
- Сравнение идёт в коде: `IntegrationConnectorHandler.identifierOf(params)` вычисляет из `params`
  будущий `sub_code` (у MCP — URL через `McpUtils.toServerConfig`), и он сравнивается с
  `connections.sub_code`. Правило записано в `AgentSkillService` дважды (`resolveInstances` и
  `matches` в `/plan`), а листинг (`SkillSpecs.hasConnector`) и тул `platform` знают только его
  половину — совпадение кода.
- `toServerConfig` собирает полную конфигурацию сервера, включая `auth_token`, OAuth-токен и
  `headers`. Функция, которая работает на каждой сборке контекста, без нужды проходит по секретам.
- `scope=MINE` и `scope=PUBLIC` пересекаются: свой публичный навык приходит в обоих ответах.

## Решение

### Две части учётных данных по объявлению коннектора

Что секретно, решает коннектор — объявлением полей в `getCredentialFields()`, как и сейчас:

- поля `SECRET` хранятся в зашифрованном секрете, как сейчас;
- остальные — в новой колонке `connections.params` (`JSONB NOT NULL DEFAULT '{}'`), открыто;
- поля, которые вычислила проверка (`derivedCredentials`: OAuth-метаданные, токены), — в секрете.
  Пользователь их не вводил, автор навыка их не знает, сопоставлять по ним нечего.

Коннектор получает склейку двух частей — одну плоскую карту, как сегодня. Ключ поля лежит ровно в
одной части, поэтому склейка однозначна и правило приоритета не нужно. SPI коннекторов не меняется:
`validateCredentials`, `ConnectorEnv` и OAuth-хранилище видят ту же карту, что и раньше.

Чтение и запись идут через одно место — хранилище учётных данных подключения: `read(connection)`
отдаёт склейку, `write(connection, credentials)` раскладывает карту по объявлению полей. Сейчас
секрет подключения читают напрямую пять мест: `ConnectorEnvFactory`,
`ConnectionService.revealCredentials`, `McpToolDiscoveryService`, `McpOAuthStore` и
`ConnectionService.updateSecret`/`create` на запись. Все они переходят на хранилище; прямой
`secretService.reveal` по секрету подключения после этого — ошибка.

Для MCP это значит: `headers` объявляется `SECRET`. В заголовках обычно лежит авторизация, и
раз коннектор не может поручиться за их содержимое, решает он в пользу секрета. Открытая часть MCP —
`{url}`. У Telegram единственное поле `token` секретное, открытая часть пуста.

### Нормализация при записи, по типу поля

Сравнивается строка со строкой, поэтому `https://x/mcp` и `https://x/mcp ` должны стать одним
значением до записи — с обеих сторон. Нормализация привязана к типу поля из `CredentialField`
(`URL` — `trim()`, как сейчас в `McpUtils.toServerConfig`; `TEXT` — тоже `trim()`) и живёт в одном
месте ядра коннекторов. Её зовут запись подключения и `validateConnectors` навыка; конкретный
коннектор ничего для этого не реализует.

### Сопоставление: открытая часть содержит `params` требования

Требование подходит подключению, когда `connector_code` совпадает с `code`, а открытая часть
подключения содержит все пары `params` требования. В SQL это `connections.params @> requirement.params`.

- Пустые `params` у требования — «подойдёт любой экземпляр кода»: `@> '{}'` истинно всегда. Тот же
  смысл, что у короткой формы `- telegram`, и тот же путь для внутренних коннекторов — у их
  строк-режимов `params` пустые.
- `params` — плоская карта строк по построению: секретные поля в неё не попадают, остальные типы
  полей скалярные. Поэтому в Java то же правило — одна строка (`entrySet().containsAll`), и
  `resolveInstances`, который уже держит загруженные подключения агента, не ходит за этим в базу.
  Две записи одного правила стерегут общие случаи: в Java — табличный тест, в SQL — тот же набор,
  прогнанный руками на клоне базы (интеграционных тестов в репозитории нет).
- `IntegrationConnectorHandler.identifierOf` удаляется из SPI вместе с реализацией в MCP: вычислять
  больше нечего. Вопрос «как назвать идентичность» снимается вместе с ней.
- `sub_code` остаётся тем, чем был, — ключом экземпляра, который возвращает проверка (URL у MCP,
  имя бота у Telegram), для уникальности и `full_code`. Сопоставление навыка его не читает.

Обратный запрос — навыки для подключения — пишется по JSONB навыка, без отдельной таблицы:
SQL-функция `skill_fits_connection(connectors, connector_code, params)` с
`EXISTS (... jsonb_array_elements(connectors) r WHERE r->>'code' = connector_code AND params @> coalesce(r->'params', '{}'))`,
заведённая миграцией, потому что `jsonb_array_elements` из criteria API не позвать, а функцию —
можно (как `jsonb_contains` в `hasConnector`). Индекса нет, по той же причине, что у `hasConnector`:
таблица навыков маленькая, фильтр листинговый.

### Листинг

`GET /manage/skills/` получает:

- `connectionId` — подключение пользователя (чужое или удалённое — 404). Отбирает навыки, которым
  оно подходит, функцией выше. Вместе с `connectorCode` — 400: код уже задан подключением.
- `scope=ALL` — свои навыки и публичные в каталоге языка запроса одним условием `OR`, поэтому свой
  публичный навык приходит один раз. `MINE` и `PUBLIC` остаются.

Страница подключения делает один запрос: `?connectionId=…&scope=ALL`. По `connectors[].params` в
ответе фронт отличает навык, написанный под этот сервер (`params` непустые), от навыка, которому
подходит любой экземпляр.

Тул `platform` (`PlatformAgentToolService`) переходит на тот же spec.

### Что меняется в ответах

- `ConnectionResponse` получает `params` — открытую часть. Секретных значений в ответе по-прежнему
  нет, и теперь это следует из места хранения, а не из аккуратности сериализатора.
- `SkillConnectorStatus.identity` удаляется: мастер видит `params` требования, а `matches` сервер
  уже посчитал. Это ломающее изменение для веба и Android — идёт в `tmpspec/`.

## Отвергнутое

- **Вычисляемый `sub_code` требования и проекция `skill_requirements`.** Требования раскладывались в
  таблицу, `sub_code` в ней вычислялся `identifierOf` при записи навыка, стартовая сверка
  пересчитывала строки после смены нормализации. Работало бы, но это производная таблица ради
  значения, которое можно просто хранить, и вычисление в коде каждого коннектора, которое трогало
  секреты.
- **Фильтр в Java поверх кандидатов по коду** (`GET /manage/connections/{id}/skills/`). Без
  пагинации и с тем же вычислением в коде коннектора.
- **`sub_code` в ответе и фильтр на клиенте.** Правило в трёх кодовых базах, страница из 100 после
  фильтрации может прийти пустой, тул `platform` остаётся с прежним фильтром.
- **Таблица связей «навык × подключение», поддерживаемая событиями.** Каждый публичный навык
  размножался бы на подключения всех пользователей, а пересчёт нужен при пяти событиях с двух сторон.
  Предвычисленные связи оправданы, когда сопоставление дорогое; у нас это сравнение строк.
- **Приложение (сервер) как сущность каталога**, на которую ссылаются и требование, и подключение.
  Самая чистая связь — равенство внешних ключей, но это новый каталог, сидинг серверов и переразметка
  подключений ради задачи, которую закрывает селектор по `params`. Остаётся путём на будущее —
  ради витрины серверов, а не ради связки.
- **Секретность поштучно для каждого заголовка.** Склейка по вложенным ключам, флаг на каждой строке
  формы, запретный список имён. Секретность — решение коннектора на уровне поля; у MCP оно `SECRET`
  для `headers` целиком.

## Вне рамок

- `ConnectorRequirement.key` и ссылка `agent_skill_connections.connector_key`. Во всех засеянных
  навыках ключ лишь даёт имя MCP-требованию, двух требований одного кода нет нигде. Убрать его стоит,
  но это вопрос ссылки из привязки, а не сопоставления, и он решается отдельно.
- Неявная связь на агенте: требование без строки `agent_skill_connections` разрешается правилом, а
  не ссылкой. Правило становится запросом к данным, но сам фолбэк остаётся, как и записано в
  `CLAUDE.md`.

## Следствия и ловушки

- **Миграция существующих подключений.** Открытые поля сейчас внутри зашифрованного секрета, и
  Liquibase их не расшифрует. Нужен разовый раннер: прочитать секрет, разложить по объявлению,
  записать обе части. Порядок: сначала код, который читает склейку (с пустыми `params` она
  совпадает со старым поведением), потом раннер. `headers` существующих подключений после смены
  объявления остаются в секрете — там, где и лежали.
- **`updateSecret` заменяет карту целиком** и по-прежнему требует того же `sub_code`. Теперь он
  пишет обе части через хранилище, и `params` обновляется в той же транзакции.
- **OAuth-хранилище переписывает секрет целой картой** (`McpOAuthStore`, `OAuthCredentials`). Через
  хранилище открытые поля из неё уйдут в `params` и не задвоятся в секрете.
- Новый коннектор, объявляя поле не-`SECRET`, соглашается, что значение лежит в базе открытым
  текстом и видно в ответе API. Это и есть смысл объявления, и его стоит прямо сказать в javadoc
  `CredentialField.Type`.
