# Коннектор `web`: поиск в интернете и чтение страниц

Агент сегодня не может ничего узнать за пределами своих коннекторов: ни курса, ни новости, ни цены
конкурента на маркетплейсе. Для нашей аудитории — prosumer и SMB в рунете — это самый заметный
пробел, и закрывать его надо поиском, который **хорошо ищет по-русски**.

## Какие варианты рассматривались

| Вариант | Рунет | Из РФ (оплата, сеть) | Почему не он |
|---|---|---|---|
| **Yandex Search API** | лучший | да | — выбран |
| SERP-агрегаторы (XMLRiver и подобные) | как у Яндекса | да | скрейпинг выдачи, без SLA — годится как «свой ключ», не как платформенная зависимость |
| Serper / SerpApi / Brave | средне (Google с `gl=ru`) | нет | оплата из РФ, прокси; у Brave слабый индекс по рунету |
| Tavily / Exa / Jina / Perplexity Sonar | слабо | нет | англоязычные индексы |
| SearXNG у себя | плавает | да | скрейпинг с IP датацентра упирается в капчу |
| Поиск на стороне модели (плагин `web` OpenRouter, `web_search` OpenAI) | слабо | зависит | мимо тулов: нет ABAC, лога вызовов, недоступен сабагентам и джобам |
| Существующий MCP-коннектор | слабо | нет | ничего «из коробки», настройка на пользователе |

Поставщик выдачи — заменяемая деталь (см. ниже), поэтому выбор Яндекса не закрывает остальные: любой
из них добавляется реализацией, а не переделкой.

## Решение

Internal-коннектор `web` с двумя тулами. Одного поиска мало: сниппет — две-три строки, и по ним
модель додумывает. Поэтому пара — «найти» и «прочитать».

### `web_search(query, limit?, region?)`

Возвращает `[{title, url, snippet, date?}]`. `limit` — по умолчанию 10, не больше 20; `region` —
числовой код региона Яндекса, по умолчанию 225 (Россия). Кодов модель не знает, поэтому ходовые
перечислены прямо в описании параметра: 213 — Москва, 2 — Санкт-Петербург. Фильтр свежести в первую версию не входит: у API
для него есть поле `period`, но заводить параметр до первой просьбы незачем.

**Yandex Search API v2**, синхронный вызов:

```
POST https://searchapi.api.cloud.yandex.net/v2/web/search
Authorization: Api-Key <key>
{ "query": {"searchType": "SEARCH_TYPE_RU", "queryText": "…", "familyMode": …, "page": 0},
  "groupSpec": {…}, "region": "225", "l10n": "LOCALIZATION_RU", "folderId": "…",
  "responseFormat": "FORMAT_XML" }
→ { "rawData": "<base64 от XML>" }
```

XML разбирается по `group/doc` (`url`, `title`, `passages`, `modtime`), подсветка `<hlword>`
снимается. `queryText` ограничен 400 символами — длиннее тул отвечает ошибкой, а не обрезает молча.

**Ключ платформенный**, из конфига оператора: `app.connectors.web.yandex.api-key`,
`app.connectors.web.yandex.folder-id`. Ключ API выпускается на сервисный аккаунт с ролью
`search-api.webSearch.user` в том же каталоге, что `folder-id`. Своих ключей у пользователя в первой
версии нет — это строка-режим connection, когда о ней попросят. Свойства выбора поставщика тоже нет,
пока он один (см. «Заменяемость»).

**Без ключа** (self-hosted, локалка) коннектор не прячется: `web_fetch` работает всегда, а
`web_search` отвечает агенту `ConnectorException` «поиск не настроен оператором». Прятать коннектор
целиком значило бы лишить агента чтения страниц без всякой причины. Тул при этом остаётся в листинге,
поэтому навык прямо говорит: после такой ошибки поиск больше не звать.

**Суточный лимит** на пользователя, `app.connectors.web.search.daily-limit-per-user`. Каждый запрос
стоит платформе денег, а агент в цикле может сделать их сотни. Считаем по `tool_call_logs`
(`connector_code = 'web'`, `name = 'web_search'`, `user_id`, `created_at` за последние сутки) —
индекс `idx_tool_call_logs_user_id_created_at` там уже есть, новой таблицы не нужно. Две тонкости:

- строка вызова фиксируется **до** диспетчеризации (`AgentToolCallService.evaluate` → `createLog`),
  так что текущий вызов уже в подсчёте и порог сравнивается через `>`;
- в подсчёт идут только `access_effect = 'ALLOW' AND error IS NULL`: запрещённые политикой вызовы,
  отказы самого лимита и ошибки Яндекса денег не стоили и квоту не съедают.

Настоящие квоты — вместе с персональной квотой LLM, отдельной работой.

### `web_fetch(url, maxChars?)`

Возвращает `{url, title, content, truncated}`, где `content` — markdown основного текста страницы.

- **Сеть — только через `PublicOnlyHttp`**: SSRF-защита и исходящий прокси там уже есть. Клиент
  редиректы не выполняет намеренно, поэтому тул проходит по ним сам — до 5 переходов. Приватный
  адрес не пропустит резолвер `PublicOnlyHttp` на соединении; на каждом переходе тул сам собирает
  абсолютный `Location` и проверяет схему — `http` или `https`, без `httpsOnly`: в рунете хватает
  сайтов на http.
- **Общий дедлайн на вызов** — около 20 секунд на все переходы вместе, а не только таймаут чтения
  на запрос: воркер по умолчанию ждёт результат 60 секунд, и пять редиректов с отдельными
  таймаутами легко выходят за них.
- Берём `text/html` и `text/plain`; тело — не больше нескольких МБ, лимит считается потоково по
  **распакованным** байтам (httpclient5 сам снимает gzip — лимит по сжатому пропустит бомбу) и до
  парсинга. PDF и прочие файлы в первой версии отклоняются понятной ошибкой.
- **Тело читается байтами**, кодировка — `charset` из `Content-Type`, затем BOM, затем
  `<meta charset>`. Для рунета это не формальность: старые сайты до сих пор в `windows-1251`, а
  строка без charset читается как ISO-8859-1.
- **Страница антибот-проверки** (капча, JS-челлендж) распознаётся и возвращается ошибкой «сайт не
  пускает автоматические запросы», а не пересказом капчи.
- Содержимое страницы — недоверенный ввод, канал для prompt injection, и выдача поиска тоже.
  Отдельного механизма не нужно: оба тула объявлены с `openWorldHint = true` (он и так по
  умолчанию), и воркер оборачивает их вывод в `<untrusted_tool_output>` с нейтрализацией
  закрывающего тега (`ToolCallDispatcher.wrapUntrusted`), а смысл обёртки модели объясняет
  системный абзац.

**Маркетплейсы — по мере возможности.** Ozon отдаёт адресам датацентров антибот-проверку, WB —
SPA с данными из отдельного API. Фикстура карточки в тестах проверяет разбор JSON-LD, но не то,
что живой маркетплейс вообще отдаст страницу; что реально читается, покажет живой прогон, и
обещать агенту (и пользователю) больше этого нельзя.

### Как HTML становится markdown

Четыре шага, каждый со своей ответственностью:

1. **Байты → DOM.** jsoup, `Jsoup.parse(InputStream, charset, baseUri)`.
2. **Основной текст отдельно от обвязки.** Сначала вырезается очевидный шум (`script`, `style`,
   `nav`, `header`, `footer`, `aside`, `form`, `[hidden]`, `role=navigation|banner|contentinfo`),
   затем выбирается основной блок: `<article>`, иначе `<main>`, иначе `[role=main]`, иначе блок с
   наибольшей долей текста к ссылкам. Метаданные — `meta description`, `og:*`, JSON-LD —
   собираются всегда: у статьи там дата и автор, у маркетплейса цена, наличие и рейтинг. Если
   основного текста почти не осталось (SPA без серверного рендера), тела нет вовсе и ответ состоит
   из заголовка и метаданных.
3. **DOM → markdown.** Заголовки, абзацы, списки, цитаты, код — как есть; ссылки — абсолютными
   (`javascript:` и якоря выкидываются); картинки — только `alt`; таблицы — GFM, а при объединённых
   ячейках или вложенных блоках — текстом построчно; пробелы и пустые строки нормализуются.
4. **Обрезка** до `maxChars` (по умолчанию около 20k) на границе абзаца или заголовка, с
   `truncated: true`. Дочитывание по `offset` — когда понадобится.

Шаги 2 и 3 — своя реализация поверх jsoup, без Readability4J и flexmark: это одна новая
зависимость и около 250 строк, которые целиком под нашим контролем и проверяются на страницах
рунета. Если своя эвристика заметно проиграет на новостях, её заменит Readability4J — ради этого
шаги и разнесены по интерфейсам.

Страницы, которые рендерятся только JavaScript'ом, вне первой версии: им нужен headless-браузер или
внешний сервис вроде Jina Reader.

### Заменяемость: стратегии, а не утилиты

Поставщик выдачи, извлечение текста и конвертер — **интерфейсы с реализациями-бинами**, не
`@UtilityClass`. Статический вызов заменяется только правкой всех мест вызова и не мокается в тестах;
бин заменяется одним новым бином.

```
connectors/internal/web/
  WebConnectorService, WebToolService   — фасад и тулы
  search/
    WebSearchBackend        (interface)  — search(WebSearchQuery) → List<WebSearchHit>
    YandexSearchBackend     (@Component)
  page/
    WebPageReader           (@Component) — HTTP, кодировка, лимиты, порядок шагов, обрезка
    ContentExtractor        (interface)  — Document → ExtractedContent
    HeuristicContentExtractor (@Component)
    MarkdownConverter       (interface)  — Element → String
    JsoupMarkdownConverter  (@Component)
    ExtractedContent        (record)     — title, body (Element, null — тела нет), metadata
```

`ExtractedContent` держит тело как `Element`, а не как текст: метаданные — не кусок DOM, и
конвертеру их не передать. Поэтому ответ собирает `WebPageReader`: markdown тела от конвертера плюс
блок метаданных, при `body = null` — только блок.

- `WebPageReader` — единственное место, которое знает порядок шагов. Реализации шагов — чистые
  функции без состояния и I/O, тестируются через `new`, без Spring-контекста.
- Граница между шагами — типы jsoup (`Document`, `Element`). Это сознательная зависимость: jsoup —
  стандарт де-факто, на нём же Readability4J, а flexmark принимает `element.outerHtml()`.
- Пока у интерфейса одна реализация — никаких свойств выбора, у поиска тоже. Вторая приходит
  вместе со свойством `@ConditionalOnProperty` (для поиска — `app.connectors.web.search.provider`);
  стороннему разработчику достаточно своего бина с `@Primary`.

### Как агент получает коннектор

Через seed-навык `web` («ищи, затем прочитай два-три источника, отвечай со ссылками»; «поиск не
настроен» — больше не звать, «сайт не пускает» — взять другой источник), ленивый, как
большинство, и через пресеты. Всем агентам подряд, как `sessions`, — нет: поиск стоит денег, а
лишний тул мешает слабым моделям.

## Что показала реализация (2026-09-30)

Прогон `web_fetch` на живых страницах (без поиска — ключа ещё нет):

- Статьи Хабра, Ленты, РИА, КонсультантПлюс читаются: заголовок, дата и автор в метаданных, текст
  статьи в markdown. Главные страницы СМИ отдают ленту ссылок — это честный результат для такой
  страницы.
- **Ozon, Wildberries и главная РБК** — антибот-стена уже с адреса разработчика. У WB статус 498 и
  ресурсы `antibot`, у РБК пустая страница на 401; распознаются обе, агенту уходит «сайт не пускает».
  Маркетплейсы через `web_fetch` в первой версии фактически недоступны — это стоит учитывать в
  пресетах для селлеров.
- **JSON-LD новостных сайтов — в основном шум** (логотипы, картинки, реквизиты издателя) и съедал
  бюджет раньше текста. Поэтому у статей из него берутся только дата и автор, служебные типы
  (сайт, организация, хлебные крошки) пропускаются, у данных вырезаются картинки, ссылки и отзывы.
- **Ссылки с трекинговыми хвостами** (Яндекс Маркет — больше 1000 символов) выводятся только текстом,
  если адрес длиннее 300 символов.
