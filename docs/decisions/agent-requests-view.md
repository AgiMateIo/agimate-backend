# Просмотр поручений между агентами команды

Доска команды видна пользователю целиком: `GET /manage/boards/{boardId}/tasks/` отдаёт канбан, события
`board.task.*` в `user:{userId}` двигают карточки без перезагрузки. Поручения между агентами
([agent-to-agent-internal.md](agent-to-agent-internal.md)) были видны только изнутри одного разговора:
`GET /manage/sessions/?parentSessionId=` и `GET /manage/runs/?originRunId=`. Кто кому что поручил
в команде за день, что сейчас в работе, чем закончилось — собрать было негде. Здесь — какие данные для
этого нужны, откуда они берутся и как они показаны.

Из трёх набросков интерфейса выбран вариант «переписка»: список веток слева, диалог ветки в
середине. Сделаны эндпойнты списка и ветки и живое событие; агрегат по парам агентов (вариант
«связи») не делается, пока его никто не показывает.

## Единица показа — поручение

Пользователь думает не сессиями и не ранами, а поручением: «Менеджер попросил Юриста проверить
договор». В базе это ветка — строка `agent_sessions` с `connector_code = agents`. Всё остальное к ней
приводится:

| Что показать | Откуда | Примечание |
|---|---|---|
| Кому | `agent_sessions.agent_id` | адресат — владелец ветки |
| От кого | `agent_id` родительской сессии (`parent_session_id`) | join на вторую `agent_sessions` в том же запросе |
| Заголовок | `agent_sessions.title` | заголовок первого поручения (`createChild`) |
| Где родилось | родительская сессия: `title`, `connector_code` | «Telegram · Клиент Ромашка» — и куда ушёл ответ |
| Команда | `agents.agentic_team_id` адресата | у сессии нет `team_id`; фильтр — join на `agents` |
| Сколько поручений в ветке | раны ветки с триггером `request_received` | первое `mode = new`, дописанные `append` |
| Текст поручения | `trigger_logs.input` этих ранов | `title`, `instructions`, `context`, `mode`, `fromAgentId`, `fromAgentName` |
| Отчёт | `agent_runs.result` или `error` рана ветки | в списке — превью, в деталях — целиком |
| Отчёт доставлен | `agent_runs.reported_at` | null при ответе без отчёта — известное ограничение, показываем честно |
| Идёт работа | живой ран в сессии ветки | одно мнение с чатами: `AgentRunQueryService.liveSessionIds` |
| Прервано | `cancel_requested_at` или статус `CANCELLED` последнего рана | `/stop` в разговоре или отмена его сессии |
| Ветка закрыта | `agent_sessions.closed_at` | дописать уже нельзя |
| Что делал адресат | `GET /manage/runs/{runId}/turns/` по `runId` рана ветки | уже есть, ссылка из деталей |

Дети разговора бывают и субагентскими (`connector_code = subagents`); их в выборку не берём —
это работа того же агента, не общение. Новых колонок и таблиц нет: всё выводится из того, что уже
пишется.

Читаются только `agent_sessions`, `agent_runs`, `trigger_logs` и `agents`. `channel_session_messages`
не нужны: `trigger_logs.input` — то же поручение до рендера в XML, `agent_runs.result`/`error` — тот
же ответ, и обе колонки есть даже у рана, который не успел ничего записать в историю.

### Статус

Один вычисляемый признак вместо машины состояний (`AgentRequestStatus`); считает
`AgentRequestQueryService` по ранам ветки, в этом порядке:

| Статус | Когда |
|---|---|
| `CANCELLED` | у последнего рана стоит `cancel_requested_at` или статус `CANCELLED` |
| `WORKING` | сессия ветки жива: идёт ран или ждёт доставки отложенная тула |
| `DONE` | последний ран `DONE` |
| `FAILED` | последний ран `FAILED` |
| `STALLED` | поручено, но ничего не идёт: ран застрял в `ENQUEUED` дольше окна живости или его нет вовсе |

Порядок — часть смысла. Отмена сильнее живости: прерванный ран ещё мгновение выполняется, и
показывать работу тому, кто её остановил, нельзя. Живость сильнее законченного рана: ответ, данный
при ожидающей отложенной туле, — промежуточный, ветка продолжает работать.

`STALLED` не было в наброске. Это честное имя для дыры, которую уже знает
[agent-to-agent-internal.md](agent-to-agent-internal.md): при сбое постановки в очередь ран остаётся
`ENQUEUED`, сметатель берёт только `RUNNING`, и поручение не выполняется никогда. Выдавать это за
«в работе» — врать в единственном месте, где пользователь мог бы заметить проблему.

Поглощённые стирингом раны (`steered_at`) в свёртке пропускаются: такой ран ничего не говорил и
ничего не ответит — отвечает тот, кто забрал его сообщение. Поручением он при этом считается, и в
ветке помечен `absorbed`.

Отдельно `reportedAt` у отчёта: `DONE` без `reportedAt` — ответ есть, в разговор он не дошёл.

## Эндпойнты

Владелец — команда, как у доски, поэтому ресурс живёт под ней
(`ManageAgentRequestController`, путь под `ManageAgenticTeamController.PATH`). Команда проверяется
на принадлежность пользователю до любого чтения.

1. `GET /manage/agentic-teams/{teamId}/requests/` — страница поручений команды, свежие сверху.
   Фильтры: `agentId` (любая сторона), `fromAgentId`, `toAgentId`, `since` (по `last_activity_at`),
   `page`, `size`. Элемент — `AgentRequestResponse`: `id` (= `threadId`), `title`,
   `from {agentId, agentName}`, `to {agentId, agentName}`,
   `origin {sessionId, title, connectorCode}`, `status`, `requestsCount`,
   `lastReport {status, preview, at, reportedAt}` или null, `createdAt`, `lastActivityAt`, `closedAt`.
   Текстов поручений в списке нет — они длинные и нужны только в деталях.
2. `GET /manage/agentic-teams/{teamId}/requests/{threadId}` — `{request, exchange[]}`: шапка как в
   списке плюс ходы ветки по времени — `{kind: REQUEST, at, runId, mode, title, instructions,
   context, absorbed}` и `{kind: REPORT, at, runId, status, text, reportedAt}`. `runId` — ран
   адресата, по нему открываются его ходы.

**Фильтра по статусу нет**, хотя в наброске он был. Статус вычисляется по ранам; чтобы фильтровать им
в SQL, пришлось бы повторить правило вторым выражением — и оно бы разошлось с первым. Клиент
фильтрует страницу у себя, а «кто сейчас работает» и так видно по `status` каждой строки.

Живое обновление — как у доски: событие `agent.request.*` в `user:{userId}` с тегами
`entity=agent.request`, `teamId`; типы `started`, `appended`, `reported`, `cancelled`, полезная
нагрузка — `AgentRequestResponse` той же формы, что в списке. Публикует `AgentRequestEventPublisher`,
точки вызова: `AgentsToolService` (started/appended), `SubagentReportListener` после доставки отчёта
(reported, только для веток `agents` — отчёт субагента ничьей строкой не является),
`RunCancellationService` (cancelled, только по веткам, которые в этот момент работали). Сбой
публикации никогда не роняет то, из-за чего она случилась.

## Три варианта интерфейса

Отличались принципом организации, а не раскладкой; все три кормились одним списком.

| | А. Лента | Б. Связи | В. Переписка |
|---|---|---|---|
| Организация | по времени: день → карточки поручений | по отношению: агенты — узлы, поручения — рёбра | по содержанию: список веток → диалог ветки |
| Вопрос пользователя | что произошло сегодня | кто кого грузит, где узкое место | что именно спросили и что ответили |
| Эндпойнты | 1 + события | агрегат + 1 по паре | 1 + 2 + ходы рана |
| Слабое место | длинные ветки разворачиваются в ленте неудобно | содержания не видно, нужен второй экран | нет общей картины за день |

Выбран **В**: единица интерфейса совпадает с единицей данных, детали открываются без
эндпойнта-агрегата, и отсюда один шаг до ходов рана «что делал адресат». Лента (А) — те же данные в
другом порядке, её уместно добавить виджетом «сегодня» на странице команды. Канбан по статусам не
предлагался нарочно: он повторил бы доску, а `agents` и `board` — независимые коннекторы с разными
единицами.

## Что не делаем

- Не заводим таблицу поручений и колонку `team_id` у сессии: всё выводится из существующих строк,
  а команда агента может смениться — считать надо по текущему составу.
- Не отдаём `instructions`/`context` в списке.
- Не показываем субагентские ветки в этом ресурсе — им место рядом с разговором.
- Не отдаём `reportRunId` (ран отчёта в разговоре): в разговор ведёт `origin.sessionId`, а факт
  доставки — `reportedAt`.
