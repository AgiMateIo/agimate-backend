# Интерпретатор Python для агента: два продукта под одним словом

Разбор идеи «тула, исполняющая Python-код агента». Главный критерий — **изоляция исполняемого
кода**: модель пишет код, которого никто не читал, и он исполняется на нашей инфраструктуре.

**Короткий вывод.** Под «интерпретатором Python» скрываются два разных продукта с разной
изоляцией, разной инфраструктурой и разной ценой:

| | A. Код-режим | B. Интерпретатор данных |
|---|---|---|
| Что пишет модель | оркестрацию своих же тулов: циклы, фильтры, передача id между шагами | анализ данных: pandas, matplotlib, openpyxl |
| Что нужно от Python | подмножество языка, `json`/`re`/`datetime`, никаких пакетов | полный CPython и сторонние пакеты |
| Ввод и вывод | аргументы и результаты тулов | файлы `agf_` внутрь, файлы и картинки наружу |
| Состояние между вызовами | нет | нужно: DataFrame живёт между ячейками |
| Изоляция | интерпретаторная (Monty) **плюс** процесс без сети и секретов | только уровня ОС: gVisor, egress deny |
| Инфраструктура | один headless-под, никакого докер-сокета | `sandbox-runner` из [terminal.md](deferred/terminal.md), VM вне кластера |
| Прототипы снаружи | Anthropic programmatic tool calling, Cloudflare Code Mode, Pydantic Monty | OpenAI Code Interpreter, E2B, Jupyter-ядро в контейнере |

A можно делать сейчас, и он не ждёт песочницы. B — это terminal с Python-образом и ядром Jupyter,
своей задачи у него нет; делать его отдельно от `sandbox-runner` значит построить тот же runner
второй раз. Рекомендация — A первым, B вместе с terminal.

Ревизия [workflow-connector.md](deferred/workflow-connector.md) от 2026-09-12 отложила код-режим
«до появления `sandbox-runner`» и отвергла «интерпретатор в процессе» как код без изоляции. Обе
посылки пересматриваются здесь: изоляция у интерпретаторной песочницы есть по построению, а в
процессе control-api ей всё равно не место. Разбор ABAC и правок ядра из того документа переносится
сюда без изменений.

## Почему это два продукта

Прототипы снаружи разошлись по той же линии:

- **Programmatic tool calling** (Anthropic, ноябрь 2025) и **Code Mode** (Cloudflare, сентябрь
  2025): одна тула, модель пишет скрипт, тулы внутри выглядят функциями, промежуточные данные не
  доходят до контекста. Anthropic приводит 37% экономии токенов на исследовательских задачах.
- **Code Interpreter** (OpenAI) и **E2B**: ядро Jupyter в контейнере, файлы внутрь и наружу,
  графики через MIME-вывод, состояние переживает вызовы.

Общего у них только слово Python. У первого код короткий и без библиотек, у второго — полный
CPython c pandas. Первому нужна изоляция от собственных тулов и ресурсов, второму — от ядра ОС.

Наш опыт указывает туда же. [workflow-connector.md](deferred/workflow-connector.md) хотел
детерминированную цепочку шагов без хода модели на каждый — это A. А `sheets` уже принимает
`xlsx` по `agf_`-ссылке и строит графики; следующий запрос пользователя «посчитай по этому файлу
то, чего в sheets нет» — это B.

## Изоляция: что от чего защищаем

Три угрозы, разные для A и B:

1. **Выход к хосту**: файлы, сеть, env, секреты платформы.
2. **Выход к соседу**: данные другого пользователя, исполняющиеся рядом.
3. **Выход за полномочия**: вызвать тул, который агенту не разрешён, или назваться другим агентом.

### A. Интерпретаторная изоляция плюс пустой процесс

[Monty](https://github.com/pydantic/monty) (Pydantic, февраль 2026) — интерпретатор подмножества
Python на Rust, написанный ровно под эту задачу. Файловой системы, сети и переменных окружения
внутри **не существует**: код достаёт до хоста только через функции, которые хост явно передал.
Лимиты на время, память, аллокации и глубину рекурсии встроены в VM. Есть проверка типов `ty` до
запуска, снимок состояния в байты и возобновление, синхронные и асинхронные внешние функции.
Биндинги — Python, JS, Rust; на сентябрь 2026 проект **до V1**, и авторы честно пишут: «никто
пока не сломал, но настоящая прочность приходит со временем». Поддерживаются функции, классы,
датаклассы, замыкания, comprehensions, `try/except`, f-строки, `async/await`; из stdlib —
`json`, `re`, `datetime`, `math`, `collections`, `itertools`, `functools`, `base64`, `typing`,
`asyncio`; сторонних пакетов не будет никогда. Для A этого достаточно, для B — нет.

Тезис про интерпретаторную изоляцию сам по себе слаб: «до V1» и «никто не сломал» — не
доказательство. Поэтому Monty — не единственный слой, а первый из трёх:

| Слой | Что даёт | Что остаётся при пробое |
|---|---|---|
| Monty | нет fs/сети/env по построению, лимиты ресурсов | код исполняется как хост-процесс |
| Хост-процесс на задачу | процесс без секретов и без egress; на соседей не дотянуться | процесс в поде без сети |
| Транспорт «control-api → под» | под не ходит наружу вообще; единственный канал — входящий стрим от control-api | можно только отвечать в этот стрим |

Последняя строка и есть главный аргумент. Под с кодом **не имеет исходящих соединений**, даже к
control-api. control-api сам открывает к нему gRPC-стрим, шлёт код и держит стрим открытым; когда
код зовёт тул, запрос уходит **вверх по тому же стриму**, control-api исполняет его с личностью
задачи и возвращает результат вниз. Личность код не передаёт и передать не может — она у стрима,
как `ConnectorEnv` собирается только в `ConnectorEnvFactory`, а не из аргументов вызова.

Отсюда следствие, которое стоит записать явно: **полный пробой Monty даёт злоумышленнику ровно
полномочия самого агента**. Взломанный процесс может лишь попросить control-api вызвать тул от
имени того же агента, той же сессии, с тем же ABAC и `params_filter` — то есть то, что модель
может и без взлома. Радиус поражения при отказе изоляции равен радиусу поражения агента, а его
ABAC уже ограничивает. Ни секретов, ни соседей, ни сети в поде нет по построению.

Что для этого нужно от пода:

- egress закрыт NetworkPolicy целиком, включая DNS; ingress — только control-api (TLS + токен,
  контур P0-харденинга);
- контейнер non-root, read-only rootfs, seccomp по умолчанию, лимиты cgroup;
- **процесс на задачу**: хост-сервис форкает воркер под каждый запуск (единицы миллисекунд),
  два пользователя никогда не делят один процесс интерпретатора;
- никаких платформенных секретов в env; токен для ingress — только у control-api.

Ступень выше — тот же образ внутри `sandbox-runner` на gVisor, когда runner появится ради
terminal. Контракт стрима от этого не меняется. Слабый вариант — Monty в процессе control-api —
не рассматривается: там база, секреты и все пользователи разом, и никакая интерпретаторная
граница этого не оправдывает.

### B. Только изоляция ОС

Ядро Jupyter — это **обычный процесс CPython с сохраняемым пространством имён**: `os`,
`subprocess`, сокеты, всё на месте. Никакой изоляции ядро не даёт; его дают контейнер и ядро ОС
вокруг. Поэтому B целиком наследует [terminal.md](deferred/terminal.md): gVisor (`runsc`),
выделенная VM вне кластера, egress deny, лимиты CPU/mem/pids/disk, никаких секретов в env,
symlink-guard на fs-полосе, лестница gVisor → Kata/Firecracker при ужесточении threat model.

Отличия от terminal — не в изоляции, а в единице состояния:

- **ядро на сессию**, а не workspace на агента. Terminal сознательно выбрал stateless `exec`;
  для данных это плохо, потому что агент перечитывал бы CSV в каждом вызове. Ядро держит
  DataFrame между вызовами. Ключ — `ConnectorEnv.sessionId()`: сессия сериализует ходы, ядро
  сериализует ячейки, параллельные сессии одного агента не топчут друг друга;
- **ядро стоит памяти.** pandas с данными легко занимает сотни мегабайт; нужен idle-TTL, рестарт
  по OOM и честное сообщение модели «ядро перезапущено, переменных больше нет»;
- **файлы только через `agf_`.** Durable workspace не нужен: входные файлы разворачиваются в
  контейнер по id перед запуском, выходные и MIME-вывод (`image/png` от matplotlib) промоутятся в
  `files` через `FileStorageService.store` и возвращаются как `{"file": {"id","mime","size"}}` —
  модель прикладывает их `[[attach:agf_…]]`. Это фаза 4 terminal, здесь она обязательна с первого дня;
- **прерывание бесплатно**: канал `control` ядра стыкуется с `cancel_requested_at` без убийства
  процесса.

Если terminal доедет первым, B — второй образ и протокол ядра на том же runner'е. Если B нужен
раньше terminal, runner всё равно строится по terminal.md, только без workspace-полосы и без
`AppWorkspaceController`.

## A. Код-режим: как выглядит

### Тула

Коннектор `code`, internal, `ConnectorTraits.internal()`; одна тула `run_code(code)`, для модели —
`code__run_code`. Описание тулы короткое: «твои тулы доступны как функции с теми же именами и
аргументами; верни значение через `result`; промежуточные данные в контекст не попадают».
`openWorldHint = true` остаётся: код пишет модель, но данные в нём приходят из тулов, часть
которых открытые, и вывод должен ехать в `<untrusted_tool_output>` как сегодня.

`timeoutSeconds` — под бюджет всей цепочки, а не одного шага; цепочка длиннее 10 с отцепляется
по [detached-tools.md](detached-tools.md), результат приезжает `tool_completed`. Ничего нового
для этого не нужно.

### Заглушки: API для кода — это тот же каталог, что модель уже видит

Внешние функции Monty объявляются стабами:

```python
def board__create_task(title: str, description: str | None = None) -> dict: ...
```

Стабы генерируются из `ConnectorToolSpec.inputSchema` — из того же источника, что `inputSchema`
для провайдера (`ToolSchemaReflector`), — по ABAC-листингу агента, без `internal`, без `@Job`,
без самой `run_code` (guard «не сам себя», как у `platform`). Имена — `llm_name`, посчитанный бэкендом: модель зовёт
функцию тем же словом, каким звала бы тул напрямую, и второй экземпляр одного коннектора
(`mcp_context7` против `mcp_notion_work`) разъезжается так же, как в прямом вызове.

Из этого следуют две дешёвые вещи:

- **отдельного prompt-блока «вот твой API» не нужно**: стаб — механическое преобразование того,
  что модель уже читает в списке тулов;
- **предполётная проверка достаётся даром**: `ty` внутри Monty проверяет код против стабов до
  первого вызова. Опечатка в имени или типе аргумента возвращается моделью ошибкой, и ни один
  побочный эффект не случился. Это та самая «предполётная проверка», которую workflow-документ
  собирался писать руками.

**Открытый вопрос — `LAZY`-тулы.** Раскрытое множество нигде не хранится: control-api выводит его
из окна истории при сборке контекста рана ([progressive-disclosure.md](progressive-disclosure.md)),
а в момент исполнения `run_code` пересчитывать его пришлось бы заново, включая `load_tools` этого
же рана. Простой вариант — стабы по полному каталогу без фильтра по раскрытию: модели стабы не
показываются, а незагруженный тул она знает по вывеске (`llm_name` и `summary`) и, назвав его в
коде, получит сигнатуру из ошибки `ty`. Это дешёвое раскрытие в обход `load_tools`; годится ли оно
дисциплине постепенного раскрытия — решить до генератора.

Что вызывать можно: только тулы с `ExecutionKind.BACKEND`. `APP` уезжает в канал приложения и
результата не возвращает, `LOOPBACK` исполняет сам вызывающий агент — внутри кода их ждать нечем.
Это не потеря: для APP-тулов у модели остаётся прямой вызов.

### Хост-сервис `code-runner`

Headless-сервис по образцу `agent-worker`: Python-процесс с `pydantic-monty` (или Rust-бинарь,
контракт тот же). Один gRPC-метод, bidi-стрим:

```
control-api ──► Run { code, stubs, limits }
control-api ◄── ToolCall { seq, name, args }        # код позвал функцию
control-api ──► ToolResult { seq, result | error }  # или Abort — отмена рана
control-api ◄── Done { result, stdout, error, calls, elapsed }
```

Runner форкает процесс на `Run`, кормит Monty стабы и код, каждую внешнюю функцию превращает в
`ToolCall` вверх по стриму и ждёт `ToolResult`. Разрыв стрима — kill процесса. Никакого состояния
между запусками, никакого хранилища, никакого egress.

Со стороны control-api `CodeToolService.run_code` — клиент этого стрима на нити `toolExecutor`
(виртуальная, блокировать можно). На каждый `ToolCall` он идёт в единственную точку принуждения
политик: `AgentToolCallService.evaluate` → `tool_call_logs` → `ToolExecutionService.executeAndRecord`
с личностью из своего `ConnectorEnv`. Инвариант workflow-документа дословно:

> Каждый шаг входит в исполнение через `AgentToolCallService` с личностью инициировавшего агента,
> а не от имени движка.

`params_filter` применяется к **посчитанным** аргументам, а не к написанным моделью, — строже
сегодняшнего. Отказ политики возвращается в код обычным исключением Python: `try/except` его
ловит, это штатный исход. Отмена рана — не исключение, а `Abort`: код её не поймает.

### Что придётся поправить в ядре

Список из [workflow-connector.md](deferred/workflow-connector.md), проверенный по коду:

1. **Сервисный вход без DTO контроллера.** `AgentToolCallService` принимает `ToolCallRequest` из
   `controller/agent/dto`, а коннекторному слою зависеть от `controller/**` нельзя. `IToolCall` в
   `service/dto` не несёт `runId`/`agentSessionId` — расширить и дать перегрузку.
2. **Неброскающий вход.** `authorizeToolCall` бросает `ForbiddenStatusException` и
   `ConflictStatusException` — исключения HTTP-границы. Коннектору нужно решение как значение,
   чтобы превратить отказ в исключение Python, а не ловить `*StatusException` в домене.
3. **ThreadLocal.** `BaseConnectorHandler.invoke` ставит и чистит `ConnectorEnvHolder` в `finally`,
   а `executeAndRecord` исполняет тул на нити вызывающего — шаг, запущенный им прямо из `run_code`,
   стёр бы env самой `run_code`. Шаги уезжают через `executeWithTimeout`: он отправляет
   `executeAndRecord` на `toolExecutor`, и у шага своя нить со своим holder'ом; env `run_code`
   захватывается один раз на входе и из holder'а больше не читается.
4. **Ссылка на родителя в `tool_call_logs`** (миграция): иначе шаги в журнале — сироты с
   загадочными `external_id`, а сметатель отложенных вызовов их не отличит. `external_id` шага
   чеканит control-api: `code:<toolCallId>:<seq>`, защита от дублей работает как на реплее.
5. **Отмена между шагами.** `executeAndRecord` перечитывает `cancel_requested_at` перед вызовом
   и отказывает шаг ошибкой; `run_code` обязан сам проверять отмену и слать `Abort`, иначе код с
   `try` переживёт остановку рана, отказывая шаг за шагом.

### Потолки

Время всей цепочки, память и аллокации VM (встроены в Monty), число вызовов тулов на запуск,
размер результата (64 000 символов режет воркер, ~20 000 — если отцепилось), rate-limit запусков
на пользователя рядом с `InboundRateLimiter`. Обрезка воркера **внутри** кода не действует: тул
вернул мегабайт — он весь ушёл в переменную, и это нормально; в контекст уезжает только `result`.

### Навык

`code`, `disclosure: lazy`, `connectors: [code]` — и **только** `code`, хотя код зовёт чужие тулы:
гейт удерживает навык целиком, пока все объявленные коннекторы не удовлетворены. Тело — порог
(«от трёх шагов с передачей данных между ними; на один вызов код не пишут»), форма `result`,
что отказ политики — исключение, что длинная цепочка отцепляется. Ловушка seed-only-if-missing
здесь мягче, чем у workflow-документа: грамматика — Python, её навык не описывает, а ошибку
типов модель читает из вывода `ty`.

## B. Интерпретатор данных: как выглядит

Коннектор `python`, тула `run_python(code, file_ids?)`:

- перед запуском файлы по `file_ids` разворачиваются в `/data/<name>` контейнера (через
  `FileStorageService.open`, ownership проверен), код видит пути;
- исполнение — `execute_request` в ядро сессии; `stream`, `execute_result`, `error` собираются в
  текст, `display_data` с `image/png` и файлы из `/output` промоутятся в `files`
  (`origin = python:run`, `sessionId` даёт `file_references`);
- результат: `{"stdout", "result", "error", "files": [{"id","mime","size","name"}]}`; тула
  просит модель приложить нужное `[[attach:agf_…]]`;
- `reset` — отдельная тула или параметр: модель должна уметь начать заново после OOM.

Всё остальное — runner из terminal.md. Ядро в контейнере на gVisor, per-session, idle-TTL,
reaper по `deleted_at` коннекции и по TTL сессии.

## Что не делать

- **Monty в процессе control-api.** Интерпретаторная граница не отменяет того, что рядом база и
  секреты всех пользователей.
- **Исходящий канал из пода с кодом.** Как только под сам ходит в control-api, появляется
  standing-токен в поде, и пробой Monty превращается в доступ к чужим задачам. Стрим сверху
  закрывает это по построению.
- **Прямой доступ runner'а к `ToolProvider`** в обход `AgentToolCallService`. Единственная
  по-настоящему опасная ошибка задачи.
- **Один хост-процесс на всех.** Процесс на задачу стоит миллисекунды и убирает целый класс угроз.
- **Ось «разрешён из кода» на туле** (аналог `allowed_callers`) в первой фазе: ABAC уже гейт,
  BACKEND уже фильтр; заводить третий переключатель без пользователя — YAGNI.
- **B без runner'а**: «просто `subprocess.run("python")` в поде» — это полный CPython с сетью в
  нашем кластере.

## План

Фаза A — код-режим:

- [ ] Сервисный вход в `AgentToolCallService` без DTO контроллера и без исключений HTTP-границы
- [ ] `parent_tool_call_id` в `tool_call_logs` (миграция, сметатель, `external_id` шага)
- [ ] Решить, фильтровать ли стабы по раскрытию `LAZY` (см. открытый вопрос)
- [ ] Генератор стабов из `ConnectorToolSpec` по ABAC-листингу; исключить `run_code`, `internal`, не-BACKEND
- [ ] `code-runner`: bidi-стрим `Run/ToolCall/ToolResult/Abort/Done`, процесс на задачу, лимиты Monty, `ty` до запуска
- [ ] Под: egress deny (включая DNS), ingress только control-api, non-root, read-only rootfs, cgroup-лимиты
- [ ] Коннектор `code` + `CodeToolService` (клиент стрима на `toolExecutor`), отмена как `Abort`
- [ ] Потолки: вызовы на запуск, время цепочки, rate-limit на пользователя
- [ ] Навык `code` (`disclosure: lazy`), `docs/connectors/code.md`, строка в `docs/architecture/connectors.md`
- [ ] Замер на настоящей цепочке: токены и ходы против прямых вызовов

Фаза B — интерпретатор данных, после `sandbox-runner` из terminal.md:

- [ ] Образ с ядром Jupyter и пакетами данных; протокол ядра в API runner'а
- [ ] Ядро на сессию, idle-TTL, рестарт по OOM с сообщением модели
- [ ] `run_python(code, file_ids)`: файлы внутрь по `agf_`, MIME-вывод и `/output` наружу через `FileStorageService`
- [ ] Отмена через канал `control` ядра
