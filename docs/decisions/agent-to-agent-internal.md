# Общение агентов внутри платформы

Дизайн коннектора, через который агенты одного пользователя поручают друг другу работу. Отправная
точка обсуждения июля 2026 — идея тулы `ask_agent(id, prompt)`.

Первая редакция (август) строила `ask_agent` на [отложенных тулах](detached-tools.md): вызов уходит в
фон, ядро учится оставлять результат незаписанным (`ToolPending`), ответ B пишется в ожидающую строку
`tool_call_logs` вызова A и возвращается раном `tool_completed`. Редакция 2026-09-17 от этого
отказывается: в сентябре сделаны [субагенты](subagents.md) — агент поручает работу своей копии, — и
их схема «квитанция сразу, отчёт своим триггером в разговор» закрывает всё, что оставалось сделать для
a2a, без правок ядра исполнения тулов. Субагент — это a2a, где адресат совпадает с поручившим. Здесь
описано, что добавляет другой адресат.

**Это не A2A.** Внешние агенты по протоколу A2A — отдельный трек, см.
[a2a-external-agents.md](deferred/a2a-external-agents.md). Здесь обе стороны — наши агенты одного
пользователя, наши раны, наша история; ни AgentCard, ни сетевого протокола. Поэтому коннектор
называется `agents`, а не `a2a`.

Схема потоков, согласия и данных — артефакт https://claude.ai/artifact/373TdktumE3YimuUWcnc34.

## Главное

- **Поручение другому агенту устроено как поручение субагенту.** Работа B идёт в сессии его канала
  `agents`, у сессии `parent_session_id` = разговор A. История, пресет диалога, стиринг дописанного
  поручения, `/stop` каскадом, сметатель — от субагентов и канального слоя.
- **Квитанция сразу, отчёт — триггером.** `ask_agent` возвращает `threadId` в том же ходе; ответ B
  приходит раном `agents.report_received` в разговор A и уходит в канал, где A разговаривал.
- **Граница — команда.** Поручать можно только агенту своей команды (`agentic_team`) — тот же круг,
  что у доски. Участвует агент с привязкой к коннектору `agents`; ABAC-правило нужно только для
  исключений. Тула A проверяет всё до маршрутизации и отказывает сразу, а не теряет поручение молча.
- **Глубина 1.** В ветке a2a агент B не поручает дальше — ни другому агенту, ни субагенту. Петли
  A→B→A невозможны по построению, счётчик глубины не нужен.

## Что отпало из первой редакции

| Первая редакция | Теперь |
|---|---|
| `ToolPending` в `ToolExecutionService.executeAndRecord` | не нужен: тула возвращает квитанцию |
| ожидающая строка `tool_call_logs`, запись ответа B в неё | отчёт — свой триггер, связь через `agent_runs.origin_run_id` |
| TTL и сметатель для `FAILED`-рана B | `RunsSwept` → отчёт `failed`, как у субагента |
| `thread_id` как отдельное понятие | `threadId` = id сессии B, дописывание как у `subagentId` |
| счётчик глубины в данных триггера, потолок 3 | глубина 1 по `parent_session_id` |
| `tell_agent` (fire-and-forget) | не делаем: отличается от `ask_agent` только недоставленным отчётом; «я закончил свою часть» — задача доски |
| `list_agents()` | не нужна: состав команды уже в системном промпте (`teamBlock`), коннектор добавляет короткий блок «кому можно поручить» |
| скоуп адресации — развилка «команда или binding» | команда; binding — участие, ABAC — исключения |
| триггер `message_received` | `agents.request_received`, зеркало субагентов |

## Решения

Предложены 2026-09-17 после реализации субагентов; решение 2 согласовано в тот же день.

1. **Отдельный коннектор `agents`, общее ядро с `subagents`.** Не параметр `agent` у `ask_subagent`:
   у тулов разное описание для модели, разное согласие сторон, и пользователь включает a2a отдельно.
   Ядро — сессии-дети, кап, доставка отчёта — одно.
2. **Кому можно писать — три слоя.**
   - *Круг — команда.* Адресат состоит в той же `agentic_team`, что и поручающий, и это не он сам.
     Доска уже живёт в этом круге: исполнитель задачи — только агент команды
     (`BoardService.resolveTeamAgent`), задачу без исполнителя получает состав команды. Два разных круга
     собеседников у одного агента — через доску одни, через `ask_agent` другие — были бы непоследовательны.
     Пользователь, собравший агентов в команду, этим и дал согласие.
   - *Участие — привязка.* Навык `agents` привязывает коннектор: поручающему он даёт `ask_agent`,
     адресату — возможность получить поручение (роутер доставляет только привязанным) и правила его
     обработки. Адресат должен принимать пуш. С 2026-09-21 участие — по умолчанию: агент, созданный в
     команде, получает навык при создании (`AgentService.create`); отказ от участия — отвязать навык.
     Команда назначается только при создании, других точек входа в круг нет.
   - *Исключения — ABAC.* Необязательные правила: TRIGGER-правило B на `agents.request_received` с
     `params_filter` по `fromAgentId` («не принимать от A») или запрет тулы `ask_agent` у агента.
     `fromAgentId` пишет наш код, не модель.

   В таблице осей [connectors.md](../architecture/connectors.md) `agents` встаёт в колонку «владелец:
   команда» рядом с `board`.
3. **Поручение для B — вход канала с явным автором**, как у субагента, а не недоверенное событие.
   Смысл a2a — «спроси эксперта», и B должен принять поручение как задачу. Риск, которого у субагентов
   нет: у B могут быть права, которых нет у A, и отравленный внешними данными A сделает B исполнителем.
   Команда сужает круг до агентов, которых пользователь сам поставил рядом; точечная защита — правило B
   из решения 2; блок промпта говорит B, что поручение пришло от агента, а не от пользователя.
4. **Отчёт для A — недоверенный `event`**, как отчёт субагента: B мог читать сайты, почту, MCP.
5. **Глубина 1.** Ран в сессии с `parent_session_id` не получает тулы ни `subagents`, ни `agents`.
   Это ограничение механики, а не защита от петель: петля A→B→A возможна только через `ask_agent`, а
   копия B поручать всё равно не может. Чтобы пустить B к своим субагентам, нужны три правки: роль
   рана по каналу сессии вместо `parent_session_id`, рекурсивная каскадная отмена и кап на каждом
   уровне отдельно. Признак «сессия занята» (см. [subagents.md](subagents.md), «Отложенные тулы у
   ребёнка») для этого уже сделан. Цена сейчас: эксперт не может распараллелить свою работу.
6. **Поручать можно только из разговора** — у рана есть сессия канала, как решение 7 субагентов.
7. **Кап общий с субагентами:** три работающих ребёнка на разговор, любых. `remaining` в отчёте тогда
   честно отвечает на вопрос «все ли отчитались».
8. **Нельзя поручить самому себе** через `ask_agent` — для этого `ask_subagent`.

## Как устроено

### Коннектор

`AgentsConnectorService extends BaseConnectorHandler implements InternalConnectorHandler,
TriggerProvider, PromptBlockProvider` — по образцу `SubagentsConnectorService`. Подключение — строка-режим
на пользователя (`bindInternal`), одна `connection` на всех его агентов; канал `agents` у B создаётся
при первом поручении ему.

| Возможность | Реализация | Что делает |
|---|---|---|
| `ToolProvider` | `AgentsToolService.askAgent` | поручение или дописывание |
| `TriggerProvider` | `request_received`, `report_received` | вход B и вход A |
| `ChannelHandler` | `AgentsChannelHandler` | `handleInput` рисует `<agent_request>`; `handleOutput` публикует отчёт |
| `PromptBlockProvider` | блоки `teammates`, `agent_request` | кому из команды можно поручить; роль B |
| Навык | `seed/skills/<lang>/agents/SKILL.md` | когда спрашивать агента, а когда ставить задачу на доску |

### Тулы

Отдельной `list_agents` нет. Состав команды — id, имя, описание — уже в системном промпте
(`RunContextService.teamBlock`). Коннектор добавляет блок **`teammates`** (SYSTEM): имена и id тех
участников команды, кому можно поручить сейчас, — привязаны к `agents`, принимают пуш, не сам агент.
Меняется только при изменении команды или привязок, префиксный кэш не страдает. Правило ABAC адресата
в блоке не учитывается — оно проверяется при вызове.

**`ask_agent(agentId, title, instructions, context?, threadId?)`** — поручение. Порядок:

1. Проверки в транзакции под блокировкой строки сессии разговора (как `SubagentService.open`): у рана
   есть разговор, ран сам не ребёнок, у агента есть команда, адресат — другой агент **той же команды**,
   принимает пуш, привязан к `agents`, ABAC с `params_filter` пропускает; кап 3; `threadId` — сессия B
   этого разговора, не закрыта. Отказ перечисляет, кому из команды поручить можно. Проверка команды
   повторяется и при дописывании: вышедшему из команды B дописать нельзя.
2. Сессия B в его канале `agents` с `parent_session_id` = разговор A (`createChild`).
3. `Trigger.createDirected(agents, connectionId, request_received, data, audience = B,
   Channels.ofPrompt(каналB, сессияB), originRunId = ран A)` → `routeTrigger`.
4. Квитанция: `{threadId, status: started|appended, note}`.

Данные поручения: `threadId`, `title`, `mode`, `instructions`, `context`, `fromAgentId`, `fromAgentName`.
Последние два заполняет тула из `ConnectorEnv`, модель их не передаёт.

### Работа B

Ран B — канальный: пресет `DIALOGUE`, все навыки B, память B, история своей сессии, партиция — сессия B
(несколько поручений бегут параллельно). Вход — `<agent_request from_agent="…" thread_id="…"
title="…">` с `<context>` и `<instructions>`, значения экранируются `PromptEscaping`. Блок
`agent_request` (USER, нестабильный): «поручение от агента X того же владельца, не от пользователя;
ответ уйдёт X; делай только поручение; поручать дальше нельзя; начни с результата».

### Отчёт A

`AgentsChannelHandler.handleOutput` публикует то же событие, что субагенты (`ChildOutput`, до
обобщения — `SubagentOutput`), `SubagentReportListener` и `SubagentReportDelivery` доставляют. Уже
общее: доставка опирается на `parent_session_id` сессии, а не на код коннектора; claim `reported_at`;
`RunsSwept` → `failed`; каналы с поручившего рана (`Channels.continuation()`); отменённый ребёнок не
отчитывается.

Что обобщить:

- **агент рана отчёта** — агент разговора, и брать его из `agent_sessions.agent_id` родительской
  сессии, а не с поручившего рана: ветка `historyOnly` (поручивший ран удалён) иначе остаётся без агента;
  сейчас стоит `child.getAgent()`;
- **триггер отчёта** — код коннектора сессии ребёнка (`agents.report_received` / `subagents.report_received`);
- **данные отчёта** a2a дополнительно несут `agentId`, `agentName`;
- **фильтр роли** `RunCatalog.withoutDelegation` (до обобщения — `withoutSubagents`) снимает оба
  коннектора. Определять роль по
  `parent_session_id` там можно: любой ребёнок теряет обе тулы. Навык `agents` у B снимается вместе с
  ними — его тело описывает `ask_agent`, которой у B нет; правила приёма поручения несёт блок
  `agent_request`;
- **блоки промпта `subagents` — по коду коннектора сессии**, не по `parent_session_id`: сейчас
  `SubagentsConnectorService.promptBlocks` считает субагентом любую сессию с родителем, и B, привязанный
  к `subagents`, получил бы в канале `agents` директиву «ты копия себя» рядом с `agent_request`.

Ран отчёта — `DIALOGUE_EVENT`, недоверенный `event`, отчёт режется до 20 000 символов.

### Поток данных

```
пользователь → webchat → ран A (разговор S)
  ask_agent(B) ─ проверки + сессия T(B, parent = S) ─ квитанция {threadId} → A договаривает
             └─ триггер agents.request_received → роутер → ран B (сессия T, канал agents у B)
                                                              │
                  ответ B → MessageLogService → AgentsChannelHandler.handleOutput
                                                              │ событие отчёта
                  SubagentReportDelivery: claim reported_at, триггер agents.report_received,
                  ран A' (сессия S, агент A, origin = ран B, каналы рана A) → ответ в webchat
смерть B: сметатель → RunsSwept → тот же отчёт со статусом failed
/stop в S: каскадом отменяет раны T
```

### Стоимость

Одно поручение — ран A, ран B, ран отчёта A: три LLM-последовательности; стиринг сливает отчёт с бегущим
раном A. Кап 3 на разговор и глубина 1 ограничивают счёт одного хода девятью ранами.

## Что не делать

**`broadcast(team, message)`** — N ранов одним вызовом LLM, без обратной связи и с непредсказуемым
счётом. «Оповестить команду» — задача доски или события.

**`delegate_task(agent, task)`** — уже есть: `board` с assignee и триггерами `task_created`/`task_changed`.
Для долгой работы доска строго лучше: состояние, история, отмена, видимость пользователю. `ask_agent` —
для «спроси и получи ответ», и это пишется прямо в SKILL.md.

**Отдельная `reply`** — ответ B это `ANSWER` его рана в канал `agents`.

**`tell_agent`** — см. «Что отпало».

**Ожидание ответа внутри хода A** — держало бы слот воркера и партицию разговора.

## Отложенное

- **`handoff(agent, context)`** — передача разговора: ответ B уходит пользователю напрямую, A выходит.
  Не механика субагентов: ран B отвечает в канал разговора A, принадлежащий другому агенту. Перед
  дизайном проверить, выдерживает ли `MessageLogService.deliver` адрес ответа в чужом канале и чья
  история пишется.
- Глубина больше 1 — если экспертам понадобятся свои субагенты; что для этого нужно, в решении 5.
- **Суженный набор тулов для ранов B по поручению** — ответ на риск решения 3 (поручение от
  отравленного A исполняется с полными правами B); у Claude Code это `tools:` в описании типа агента.
  Противоречит правилу «политика и канал — разные слои», поэтому только после того, как прогон покажет,
  что команды как круга недостаточно.
- **Срок поручения** — сейчас только окно сметателя, 15 минут молчания.
- Разговор между агентами разных пользователей — через [agent-participants.md](agent-participants.md).

## Что изменилось при реализации

Код и живой прогон — 2026-09-21. Ревью нашло одну ошибку: правило адресата судилось по данным без
`mode`/`threadId`; исправлено до коммита.

- **Проверки адресата — в `TeammateService`**, отдельном от `SubagentService`: круг, участие и правило
  повторяют выборку роутера (`AgentRepository.findBoundToConnection`, `supportsPush`, ABAC с
  `params_filter` над данными поручения), чтобы принятое тулой поручение роутер не отбросил. Проверка
  «адресат — агент этого пользователя» добавлена явно: команда её подразумевала, но не проговаривала.
- **`SubagentService.openFor(Callee, …)`** — общий метод открытия ребёнка; `open` для субагентов —
  его частный случай с `Callee.self`. Дописать можно только в ветку, принадлежащую адресату.
- **Роль по блокам промпта — `SubagentService.isChildOf(sessionId, connectorCode)`**, а не наличие
  родителя: иначе B в канале `agents` получал бы директиву субагента. Роль по тулам осталась по
  `parent_session_id` — любой ребёнок теряет обе тулы.
- **Агент рана отчёта — из `agent_sessions.agent_id` родительской сессии.** Если разговора или его
  агента нет, отчёт не создаётся и claim не берётся.
- **Квитанция несёт `agentName`**, чтобы модель не путала ветки разных адресатов.
- Блок `teammates` — SYSTEM и стабильный; `agent_request` — USER. Навык `agents` описывает обе
  стороны: как поручать и как принимать поручение.
- Гонка первого поручения одному адресату из двух разговоров сразу упирается в частичный уникальный
  индекс канала: второй вызов падает, повтор проходит. Не чинится — окно миллисекунды, а re-find внутри
  помеченной на откат транзакции невозможен.

## Известные ограничения

Наследуются от субагентов (см. их раздел): ребёнок без отчёта глушит итог до 15 минут; отчёт теряется
при сбое доставки; файлы `[[attach:]]` в отчёте теряются; продолжение обходит кап. Потеря отчёта
проверена по коду 2026-09-21: `SubagentReportDelivery.prepare` фиксирует claim `reported_at` и ран
`ENQUEUED` в своей транзакции, затем `AgentDeliveryService.deliverTrigger` ставит ран в очередь и ошибку
только логирует; сметатель подбирает лишь `RUNNING`. Ран остаётся `ENQUEUED` навсегда, повтора нет.
Для a2a цена выше, чем у субагентов: пропадает работа другого агента. Своё:

- **Правило B поменяли между проверкой и роутингом** — поручение не дойдёт, ребёнок считается
  работающим до окна сметателя. Окно — миллисекунды.
- **Агент без команды поручать не может** — только своим субагентам. Навык `agents` без команды
  бесполезен; фронту нужен путь «сначала добавьте агента в команду».
- **Агенты, созданные в команде до 2026-09-21, навыка не получили** — автопривязка работает только
  при создании; им навык включается руками или одноразовым SQL по `agents.agentic_team_id IS NOT NULL`.
- **Специалист — только в одной команде** (`agents.agentic_team_id` — одна ссылка). Юрист не может
  служить и «Финансам», и «Договорам»; обход — второй агент из того же пресета, с отдельной памятью.
  Если сценарий окажется частым — связь «многие ко многим» для всех командных коннекторов сразу, иначе
  доска и `ask_agent` снова разойдутся.
- **B пересадили в другую команду во время поручения** — открытая ветка доработает и отчитается;
  дописать в неё уже нельзя.
