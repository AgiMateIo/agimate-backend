# Администрирование платформы через MCP и мета-агента

Решение о том, что внутренний коннектор `platform` покрывает **весь** дашбордный
(`/manage/**`) функционал: MCP-клиент (Claude Desktop/Code, Cursor) и чат с мета-агентом
умеют то же, что веб-панель. Принято в августе 2026. Действующее поведение —
[../connectors/platform.md](../connectors/platform.md). Рабочий спек PR хранился вне репозитория
и по мерже не требуется: этот документ и platform.md фиксируют решения и контракт.

## Что было до

Коннектор `platform` (см. [../connectors/platform.md](../connectors/platform.md)) давал
мета-агенту 15-16 тулов: листинги, создание/правку агентов, авторство навыков, deep-link
подключений. Каналы (входящий роутинг), ручные ABAC-политики, LLM-провайдеры,
delete/regenerate, команды — были намеренно вне коннектора (YAGNI). Весь остальной
админ-функционал был доступен только через REST `/manage/**` под JWT в дашборде.

## Решение

Коннектор `platform` расширяется до полной дашбордной поверхности в согласованных границах: **79 тулов** (13
существующих без изменения поведения + 3 расширенных — `create_agent`, `update_agent`,
`get_agent` — + 63 новых), сгруппированных в пять тул-сервисов
(`PlatformAgentToolService`, `PlatformConnectionToolService`, `PlatformLlmToolService`,
`PlatformWorkspaceToolService`, `PlatformObservabilityToolService`) плюс статические хелперы
(`PlatformToolsSupport`). Один фасад `PlatformConnectorService` передаёт все модули в
`BaseConnectorHandler`, который меняется минимально: конструктор принимает
`Object... toolServices` с детекцией дублей `@Tool(name)` между сервисами (остальные
девять коннекторов компилируются без правок — varargs принимает один аргумент).

Читающая часть — из репозиториев, пишущая — через существующие service-layer команды;
там, где сервис принимает controller-DTO (команды агентов — исключение, для них
командные record уже есть), добавляются перегрузки: `AgenticTeamService.create/patch`,
`LlmProviderService.create/update` (+ командные record в `service/dto/llm`),
`AgentLlmService.create/replace`, `LlmUsageQueryService.usageForUserSnapshot`,
`ChannelService.listHandlersFlat`. Список — в спеке, раздел «Flags summary».

Ключевые решения по границам:

- **Секреты остаются write-only.** `webhookAuthHeader` и `apiKey` провайдеров принимаются
  на вход, наружу не возвращаются никогда (`hasWebhookAuth`, `apiKeyMask`). Подключения —
  по-прежнему deep-link: креды через LLM не идут.
- **Ключ агента выдаётся только через UI.** `create_agent` и `regenerate_agent_key` возвращают
  `keyUrl` на страницу агента `/dashboard/agents/<id>`, где ключ показывается один раз; в ответе
  тула секрет не приходит. Тем самым восстановлена исходная договорённость «ключ не возвращается
  тулом» — отменена предыдущая отмена этого правила.
- **PATCH-семантика одна на все update-тулы**: параметр не прислан (`null`) = не трогаем,
  пустая строка/пустой объект = очистить. Тул сам резолвит «не трогаем» через текущее
  значение записи, где сервис не умеет null-семантику. Исключения: enum-параметры
  (`update_agent.type`, `update_policy.effect`) — пустое значение = не прислано; name —
  пустая строка это ошибка либо «не трогаем» (`update_connection`).
- **Охрана «не сам себя»** — на тулах, управляющих агентом с `agentId`; `list_agent_skills`
  и `list_agent_connections` — read-only исключения, поэтому листинг собственного агента разрешён.
  Guard стал null-safe и распространён на мутации ABAC-политик: агент не может
  создавать/менять/удалять политики, чей субъект — он сам (иначе DENY владельца на мета-агента
  был бы самоустранимым).
- **Граница досок.** Мета-агент конфигурирует платформу, а работу на доске выполняет коннектор
  `board`: остаются только `list_boards` (краткие сведения без задач) и `create_board`. Поэтому
  первичное наполнение доски команды — двухшаговый поток: создать доску через `platform`, затем
  привязанный коннектор `board` создаёт задачи и ведёт их.
- **Усечённые листинги явны.** Все листинги владельца (22: agents, skills, files, connectors,
  connections, connection_tools, connection_agents, agent_connections, channels, policies,
  llm_providers, llm_provider_models, llm_quotas, agent_llms, runs, sessions, tool_call_logs,
  trigger_logs, webhook_deliveries, teams, boards, connector_jobs) ограничены 100 первыми записями
  и возвращают `{items, truncated}`, чтобы клиент не считал результат полным; статические каталоги
  (`list_channel_handlers`, `list_llm_provider_catalog`, `list_presets`) и `get_run_turns`
  (объявлено в описании тула) не капятся.
- **ADMIN-поверхность (`/manage/admin`) вне коннектора**: в `ConnectorEnv` нет роли,
  ключ агента не доказывает ADMIN. Единственное исключение из «всё, что может дашборд»,
  мотивированное не транспортом, а правами.

## Почему не иначе

**Отдельный эндпоинт `/admin-mcp` под JWT.** Отвергнут: второй контур аутентификации с
той же ABAC-логикой, дубль каталога тулов и политик, и непонятно, кто там владелец
операций. Расширение коннектора выигрывает потому, что контур один (ключ агента),
ABAC уже гейтит (`agent_connections` + `agent_connection_policies`), MCP-сервер уже
существует (`/mcp`, ревизия 2026-07-28), а `env.userId` выводится из владельца агента
— ровно та модель, что у существующих тулов.

**Второй коннектор (`platform-admin-advanced`).** Отвергнут: два набора тулов
пересекались бы по смыслу, навык `platform-admin` пришлось бы плодить, а листингу —
объяснять, почему у одного агента два «админских» namespace. Один коннектор, один
навык, одна точка расширения.

**Оставить как есть (YAGNI).** Отвергнут: пользователь явно запросил полную
дашбордную поверхность; включение механически безопасно, потому что все операции —
тонкие адаптеры поверх уже существующих, проверенных сервисов.

**Ключ агента возвращать в ответе тула.** Отвергнут после пересмотра: `create_agent` и
`regenerate_agent_key` возвращают deep-link на страницу агента в UI, где ключ показывается
владельцу один раз. Так секрет не проходит через MCP/LLM, а внешний клиент настраивается
пользователем после перехода по ссылке.

## Границы

- **ADMIN-раздел** (роль в JWT, `manage/admin/**`) — вне коннектора, документировано.
  Сюда же: платформенный LLM-провайдер, create/update пресетов, системные навыки.
- **Приложения (`/manage/apps`)** — жизненный цикл устройства (ключ бесполезен до
  паринга на физическом устройстве); YAGNI.
- **Webchat send/start/contacts, centrifugo-токен** — разговор агента с самим собой или
  токены UI; наблюдение покрывают листинги сессий.
- **Загрузка файлов** — multipart не влезает в JSON-аргументы тула; upload остаётся в UI.
- **Креды подключений** (create с секретом, updateSecret, oauth-complete) — секреты через
  LLM не ходят; deep-link остаётся.
- **Перевод агента в команду** (`update_agent(teamId)`) — в manage-API вообще нет такой
  операции (команда задаётся только при создании), сервисного метода нет.
- **Правка/удаление досок, сообщения сессий, per-connector маппинг навыка,
  per-model extra_body** — нет эндпоинтов либо YAGNI; см. «Отложено».

## Механика

- Модули получают ровно свои репозитории/сервисы (таблица в спеке §1.1); DTO разнесены
  по файлам на модуль (один общий `PlatformDtos` с `OperationResult`), чтобы параллельные
  задачи не правили один файл.
- `BaseConnectorHandler` держит `Map<Method,Object> ownerByMethod`; диспатч по имени не
  меняется; дубль имени тула между модулями — `IllegalStateException` на конструкторе.
- Все мутации — через `PlatformToolsSupport.domain(...)` (трансляция `*StatusException`
  в `ConnectorException`); листинги владельца возвращают `{items, truncated}` и ограничены
  `MAX_LISTING = 100`, без пагинации.
- **Раскатка сидов.** Seed-only-if-missing сохраняется: на уже засиденных окружениях новое тело
  `SKILL.md` попадает к агентам через существующий manage API (`update_skill` +
  `mark_skills_installed`) либо одноразовый ops SQL. Версионированная доставка сидов — отдельная
  будущая задача.
- Rate-limit не добавляется: действует общий MCP-лимитер вызовов.

## Решения ревью (2026-08-29)

- **Отмена ранов — осознанное исключение из «только человек отменяет».** `cancel_run`/`cancel_session`
  исполняются от имени владельца агента (`env.userId` — та же личность, что у `/manage`), поэтому
  отменяет владелец, а не агент; javadoc `RunCancellationService` переписан под это исключение.
- **`create_agent(skillIds)` открывает внутренние коннекторы навыков вторым шагом** (как UI-флоу
  `openAgentAccess` + bind): навык — декларация, `agent_connections` — грант, и платформа разделяет
  эти шаги намеренно (docs/architecture/connectors.md). Шаг гранта не атомарен с созданием агента;
  при его сбое агент уже существует — повторный `bind_skill` идемпотентно дооткроет коннекторы.
- **Очистка `description` политики** — по канону `/manage` (пустая строка = очистить): исправлено в
  `AgentConnectionPolicyService.update` (раньше пустая строка сохранялась буквально).
- Проверка принадлежности задачи адресованной доске была добавлена до сужения поверхности; после
  исключения task-инструментов из `platform` это ограничение остаётся ответственностью коннектора
  `board`.

## Ревью GLM-5.3 (opencode, zai-coding-plan) — 2026-08-29

- **Секреты в обход редактирования закрыты**: `get_run_prompt` (история сессии в промпте) и
  `list_runs`/`get_run` (финальный ответ рана) теперь прогоняют текст через `redactKeys` —
  модель, процитировавшая ключ в ответе, больше не отдаёт его через эти тулы.
- **Очистка каналов/провайдеров по канону**: пустой `config` канала = очистить (null), пустое
  имя провайдера = 400.
- Досочные task-инструменты и их листинговые ограничения исключены из `platform` при уточнении
  границы: задачи и комментарии обслуживает коннектор `board`.
- **Согласованы статусы логов с фильтром**: ERROR = есть error (включая refused-DENY-строки).
- **Fail-fast** `BaseConnectorHandler` на пустой/null список tool-сервисов; валидация scope
  листинга навыков; динамический список допустимых типов агента.
- `cancel_session` для connection-scope сессии отвечает осмысленной ошибкой; не-channel сессии
  останавливать нельзя.

## Ревью дельты (opencode, zai-coding-plan/glm-5.3) — 2026-08-29

- **Редактирование ключей стало тотальным**: паттерны переведены с `\b` на lookaround
  (`-` не word-символ, ключ с хвостовым `-` из base64url проходил мимо); списки tool-calls/results
  и `error` логов редактируются тем же паттерном; `redactSecrets` обходит вложенные объекты/массивы.
- **Единый кап `MAX_LISTING`** для всех листингов владельца (connections/channels/teams/boards/
  tasks/providers); комментарии доски капятся новейшими (иначе ASC+limit молча терял свежие).
- **`cancel_session`**: владелец проверяется по сессии до scope-проверки (чужая строка — «not
  found», без раскрытия существования).
- Blank enum-фильтры (status/accessEffect) трактуются как «не прислан».

## Отложено сознательно

Per-connector маппинг инстансов привязанного навыка (`set_skill_connections`), история
сообщений сессии, `list_connection_triggers`, правка досок (эндпоинтов нет), app-тулы,
OAuth-завершение. Первые три — механические добавления, если понадобятся; досочные
правки — сначала в manage-API.
