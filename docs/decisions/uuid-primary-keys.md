# Один UUID-ключ вместо пары `Long id` + `pub_id`

Решение о том, чем адресуются сущности control-api. Принято и выполнено в июне 2026, до первого
прода. Документ был написан как план исполнения; после исполнения от него оставлено решение и то,
чем реальность от него отличается.

## Что было

У каждой сущности жило два идентификатора: `Long id` — `BIGSERIAL`-ключ для внутренних связей, и
`UUID pubId` (`UUIDUtils.generateUUIDv8()`) — то, что уезжает наружу. Это требовало постоянного слоя
резолва `pubId → Long` и породило три несовместимые конвенции внешних ключей одновременно: `Long`-
скаляр (`channel_id`), `UUID *_pub_id` (`agent_pub_id`) и JPA-связь по `Long`. В нативном SQL это
выглядело так: в одном запросе `a.pub_id = p.agent_pub_id`, в соседнем — `a.id = b.agent_id`. Около
406 упоминаний `pubId` в 81 файле.

## Решение

Единственный ключ — `UUID id`, он же внешний идентификатор; `pubId` исчезает, колонки `*_pub_id`
переименовываются в `*_id`. Значение генерирует **база**: `DEFAULT uuidv7()` (PostgreSQL 18, RFC
9562) и на сущности `@Generated(event = INSERT) @ColumnDefault("uuidv7()")` — Hibernate делает
`INSERT … RETURNING id`.

Исключения, принятые сразу: `Connector` остаётся с натуральным ключом `code TEXT`; `user_id` —
кросс-сервисная ссылка в user-api и генерируется там; `connector_code` — обычный текстовый FK.

## Почему генерация в БД, а не в приложении

| | БД, `uuidv7()` | Приложение, `generateUUIDv8()` |
|---|---|---|
| Стандарт | RFC 9562 | самодельный v8 (CRC + зашитая строка `"agimate"`) |
| Монотонность | сквозная по всем инстансам | только в пределах JVM (синхронизированный счётчик) |
| `save()` | id пуст до вставки → Spring Data честно зовёт `persist()` | id заполнен → `merge()` и лишний SELECT на каждую вставку |
| Цена | жёсткая зависимость от PG18 | нет |

Решающим был второй столбец целиком: самописный генератор уходил с пути первичного ключа, а
`merge()`-ловушка не возникала вовсе — без неё `BaseEntity` не пришлось делать `Persistable<UUID>`
ради флага `isNew`. `UUIDUtils` остался для того, чем и был помимо ключей: идентификаторы запросов
(`RequestIdFilter`), внешние идентификаторы user-api.

## Чем реальность отличается от решения

Аудит, на который опиралось решение, утверждал: **ни одному месту в коде не нужен id до вставки**.
Это оказалось верно для 37 сущностей из 40 и неверно для двух (третья — `Connector` с его текстовым
ключом):

- **`Connection`** — id коннекшена адресует строки во всех нижележащих таблицах и для `APP`-коннекторов
  обязан совпадать с `app.id`. Значение приходит извне, а не из базы;
- **`StoredFile`** — id уезжает наружу как `agf_<uuid>` и входит в ключ блоба в хранилище
  (`user_id/agf_<id>`), то есть нужен раньше, чем строка вставлена.

Обе получают id приложением (`UUIDUtils.generateUUIDv8()`) и платят за это ровно тем, что описано в
таблице выше — лишним SELECT'ом на вставке, потому что `Persistable` так и не понадобился остальным
38. Правило, которое из этого следует: **ключ генерирует база; приложение — только когда id не
просто ключ строки, а адрес чего-то ещё.**

## Почему нет миграции перехода

База на тот момент нигде не была развёрнута, поэтому changelog'и правились **на месте**, а не
дописывались миграцией: `initial/` сразу описывает `UUID`-ключи с `defaultValueComputed="uuidv7()"`.
Диффом это дешевле для ревью и не оставляет мёртвого шага в истории миграций, которого никто никогда
не исполнит. Обратная сторона — воспроизвести старую схему из репозитория нельзя; она осталась
только в git.
