# Платформенные назначения и источник моделей агента

Назначение — ось выбора модели, но до конца эта ось доведена только на уровне агента:
`agent_llms` хранит упорядоченную цепочку пар «провайдер + модель» на каждое назначение, а
платформенный запас остался одной строкой `llm_providers` с картой «назначение → список моделей».
Отсюда два предела: все платформенные назначения делят один аккаунт — ключ, адрес, транспорт,
`extra_body` и квоту, — а второй платформенный провайдер выразить нечем.

Решение состоит из двух осей, которые внедряются **одним заходом**: одна миграционная
последовательность, один релиз control-api, один релиз фронта.

1. `platform_llms` — платформенные назначения как упорядоченные цепочки, зеркало `agent_llms`.
2. `agents.llm_source` — явный режим агента: `PLATFORM` или `BYOK`.

Разделение на оси описательное: резолвер, миграции и тесты одни. Флаг без первой оси решает только
половину задачи — платформа осталась бы однопровайдерной; первая ось без флага оставила бы
эмерджентное правило «есть привязки — свои, нет — платформа».

Предшественник — [agent-llm-purpose-chain.md](agent-llm-purpose-chain.md): там цепочка введена для
агента, а платформенный уровень явно оставлен отдельным решением. На проде предшественник ещё не
выкачен: в `agent_llms` нет `priority`, последняя запись `databasechangelog` — 2026-10-26. Поэтому
первый шаг — смержить `feature/agent-llm-purpose-chain` и раскатать её; две оси этой спеки идут
следующим релизом control-api. Очистка `purpose_priority` — отдельным, неоткатываемым релизом
после окна отката.

## Как сейчас

| Уровень | Единица настройки | Хранение |
|---|---|---|
| Провайдер (BYOK и платформа) | список моделей на назначение | `llm_providers.purpose_priority` (JSONB) |
| Агент | цепочка «провайдер + модель» на назначение | `agent_llms(purpose, priority, llm_provider_id, model)` |
| Платформа | **одна строка** системного пользователя с картой назначений | `llm_providers` при `user_id = SYSTEM_USER_ID`, имя `platform` |

Политика резолвера (`LlmCredentialsResolver.chainFor`):

| Назначение | Порядок |
|---|---|
| явные привязки агента | закрытое множество: платформа не подставляется |
| `CHAT` без привязок | `purpose_priority[CHAT]` платформенного провайдера |
| `IMAGE`, `VISION`, `AUDIO_*` без привязок | списки назначения chat-провайдеров → список платформенного провайдера |
| `ROUTINE` без привязок | списки `ROUTINE` chat-провайдеров → модель `CHAT` агента; платформа — только если chat-привязок нет |

Платформенный провайдер — синглтон: имя `platform` форсируется, второе создание отвечает 409,
переименование и удаление запрещены (`PLATFORM_PROVIDER_NAME`, `findUsablePlatformProvider`).
Смысл `[]` у провайдера двоится: у BYOK это «выключено у меня, иди к следующему», на платформенном
шаге — «закрыть цепочку» (`platformEmptyStops`).

## Ось 1. `platform_llms`

### Схема

```sql
CREATE TABLE platform_llms (
    id              UUID PRIMARY KEY DEFAULT uuidv7(),
    created_at      TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at      TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    llm_provider_id UUID NOT NULL REFERENCES llm_providers(id) ON DELETE RESTRICT,
    model           TEXT NOT NULL,
    purpose         TEXT NOT NULL DEFAULT 'CHAT',
    priority        INTEGER NOT NULL DEFAULT 0,
    CONSTRAINT uq_platform_llms_purpose_priority UNIQUE (purpose, priority)
);
CREATE INDEX idx_platform_llms_llm_provider_id ON platform_llms(llm_provider_id);
```

`RESTRICT`, а не `CASCADE`: удаление провайдера, на которого ссылаются назначения, запрещено, и это
правило должно держаться и при прямом SQL, и в гонке с вставкой. Сервис отвечает 400 «сначала
снимите назначения»; внешний ключ — backstop, его нарушение маппится в тот же 400.

Таблица глобальная, без `user_id`: платформенные назначения не принадлежат пользователю.
Платформенный провайдер — любая строка `llm_providers` с `user_id = SYSTEM_USER_ID`; `isPlatform()`
уже проверяет владельца, а не имя, поэтому множественность строк не требует нового признака.

### Сервис

`PlatformLlmService`: плоский список, `replaceChain(purpose, bindings)`, `delete(purpose)`.
Правила зеркалят `AgentLlmService`:

- потолок пять привязок на назначение;
- дубль `(провайдер, модель)` в одной цепочке запрещён;
- модель проверяется по реестру провайдера (`validateModelsKnown`; пустой реестр — разрешить);
- провайдер обязан быть системным (`isPlatform`) — иначе админская опечатка привяжет пользовательский
  ключ и квоту к платформе;
- замена цепочки — удаление и вставка в одной транзакции с `flush`; гонка ловится unique и отвечает
  409, а не уходит ошибкой из метода после коммита.

Отдельный `append` не заводится: платформенная конфигурация редкая, `PUT` целиком закрывает сценарий.
Миграция обрезает существующие списки до пяти (см. «Миграция»); потолок остаётся правилом сервиса.

### API

- `POST /manage/llm-providers/platform` — создать платформенного провайдера: добавляется `name`
  (уникально среди системных), убирается `purposePriority`, строка создаётся выключенной.
- `GET /manage/admin/platform-llms/` — плоский список привязок в порядке назначений и `priority`.
  Строки самодостаточные: `llmProviderId`, `providerName`, `providerType`, `purpose`, `priority`,
  `model` — админской странице не нужен отдельный join.
- `PUT /manage/admin/platform-llms/{purpose}` — заменить цепочку списком привязок; `[]` равносилен
  `DELETE`, на пустом назначении с непустым списком создаёт цепочку.
- `DELETE /manage/admin/platform-llms/{purpose}` — снять назначение; на пустом назначении — 404, как
  в `AgentLlmService.delete`.

`/manage/admin` целиком закрыт ролью ADMIN в `SecurityConfig`, поэтому `@PreAuthorize` не нужен.
Создание провайдера остаётся на существующем пути со своим `@PreAuthorize`.

### Резолв

Платформенный шаг — чтение `platform_llms[purpose]` и те же кандидаты, что у явных привязок агента,
дальше общий `firstEligible`. Исчезают `platformEmptyStops` и особый смысл `[]` на платформенном
шаге: нет строк — нет шага. `chatProviders()` перестаёт возвращать платформенного провайдера при
отсутствии chat-привязок — платформа становится отдельным шагом и работает только для
PLATFORM-агентов.

`ROUTINE`: цепочка `platform_llms[ROUTINE]` → цепочка `platform_llms[CHAT]`, как у агента
`ROUTINE` → `CHAT`. Медиа: у PLATFORM-агента — цепочка `platform_llms[purpose]`; у BYOK-агента —
списки назначения его chat-провайдеров, платформенный шаг не подставляется вовсе.

Тип отказа при всех выключенных провайдерах меняется. Раньше `findUsablePlatformProvider`
отфильтровывал выключенного: у `CHAT`/`ROUTINE` отказ был `NotFoundStatusException`, у медиа —
`NoCapableModelException`. Теперь выключенные провайдеры — кандидаты, и `firstEligible`
классифицирует «все выключены» как `LlmProviderDisabledException` (`FAILED_PRECONDITION`) для всех
назначений. Для чата воркер подменяет текст своим шаблоном; для медиа текст уходит агенту; у BYOK
медиа-отказ дополняется «или переключите агента на платформу».

BYOK без CHAT — штатное состояние: `CHAT` не находит кандидатов и отдаёт `NotFoundStatusException`,
воркер показывает `notice.no-model` («агенту не настроена модель… подключи LLM-провайдера и выбери
модель в настройках агента»). `ROUTINE` — джоба компакции, пользователю не показывается.

### Жизненный цикл платформенного провайдера

- Имя свободное, уникальное среди системных; переименование разрешено. Проверка уникальности при
  переименовании идёт по `provider.getUserId()`, а не по `userId` вызывающего: у платформенной
  строки владелец системный, и текущий код проверил бы чужое пространство имён.
- Удаление — только когда на провайдера не ссылается ни одна строка `platform_llms`; иначе 400
  «сначала снимите назначения». С `ON DELETE RESTRICT` правило держится и в гонке, и при прямом SQL;
  сервисная проверка нужна для дружелюбного 400.
- `purposePriority` у платформенных строк запрещён: создание его не принимает, обновление отвечает
  400. Иначе админ правит поле, которое никто не читает.
- `enabled`, квоты, `mediaTransport`, `extraBody`, ротация ключа — без изменений.
- До чистящего релиза строку с именем `platform` не переименовывать и не удалять: старые инстансы
  ищут её по имени. После раскатки — аудит (см. «Риски и проверки»).

### Чтение и учёт

- `listForUser(admin)` показывает все системные строки, а не одну по имени.
- Листинг привязок PLATFORM-агента показывает эффективную конфигурацию. `GENERIC` — все
  платформенные назначения; внешние (`MCP`, `WEBHOOK`, `CENTRIFUGO`) — только медиа (`IMAGE`,
  `VISION`, `AUDIO_IN`, `AUDIO_OUT`), потому что их мозг снаружи и `CHAT`/`ROUTINE` у них не работают
  как модель агента. Неактивные пользовательские привязки показываются в том же ответе с
  `active = false`, чтобы данные не терялись и их можно было удалить. У платформенных строк
  `llmProviderId = null`, `priority` — фактический, `source = PLATFORM`.
- У BYOK-агента без CHAT листинг показывает только активные строки; отсутствие CHAT — нормальное
  состояние, интерфейс должен предложить добавить модель.
- `LlmUsageQueryService` показывает по субъекту на каждый включённый платформенный провайдер; в ответе
  появляется несколько строк `PLATFORM`. `llmProviderId` у них остаётся `null` (провайдер не адресуем
  пользователем), различаются именем. Текст исчерпанной квоты называет платформенного провайдера, а
  не «платформенную модель» в единственном числе.
- `get_llm_usage` платформенного коннектора — текст во множественном числе, форма ответа та же.

### Миграция

1. Создать таблицу с `ON DELETE RESTRICT`.
2. Перенести `purpose_priority` существующих системных строк в строки `platform_llms`. Приоритет —
   `ROW_NUMBER() OVER (PARTITION BY purpose ORDER BY provider.created_at, provider.name, model_ord) - 1`:
   это сохраняет порядок единственной строки один в один и не падает, если в базе окажется вторая.
   После нумерации оставить `rn <= 5` — тот же потолок, что у сервиса; дубли `(провайдер, модель)` и
   ключи вне `LlmPurpose` отбросить. На проде сейчас `CHAT`/`IMAGE`/`VISION` по одной модели, так что
   обрезка ничего не тронет.
3. Поле `purpose_priority` **не очищать** в этой же миграции. Иначе старые инстансы control-api во
   время раскатки потеряют платформенный запас: они читают только это поле. Очистка — отдельным
   релизом после того, как весь флот на новом коде и окно отката закрыто. Новый код у платформенных
   строк поле не читает и не отдаёт (`purposePriority = null` в ответе).
4. Миграции этой спеки идут после `30-00-agent-llm-priority.xml` предшественника: новый код
   использует `agent_llms.priority`, а на проде этой колонки ещё нет.

На свежей установке переносить нечего: таблица пуста, админ настраивает назначения заново.

### Следствия

- Квоты остаются по провайдеру: несколько платформенных провайдеров означают несколько независимых
  бюджетов. Общего лимита «на все вендоры» нет; если он понадобится, это отдельная функция.
- `[]` перестаёт быть частью платформенной модели: выключение назначения — отсутствие строк.
- Смысл `purpose_priority` у платформенных строк исчезает; у BYOK-провайдеров он сохраняется
  (неявная маршрутизация медиа и `ROUTINE`).

## Ось 2. `agents.llm_source`

### Схема и значения

```sql
ALTER TABLE agents ADD COLUMN llm_source TEXT NOT NULL DEFAULT 'PLATFORM';
ALTER TABLE agents ADD CONSTRAINT chk_agents_llm_source CHECK (llm_source IN ('PLATFORM', 'BYOK'));
```

Колонка, check-констрейнт и backfill — один changeset, чтобы между ними не было окна. Значения —
`PLATFORM` и `BYOK`. Поле появляется в сущности `Agent`, в ответе агента и в переключении режима.
Новые агенты создаются только как `PLATFORM`; пресеты источник не задают. Отдельного значения
`MIXED` нет: переход резкий, старая политика не сохраняется.

### Резолв

```java
chainFor(agent, purpose):
    if (agent.llmSource == PLATFORM)
        return platformChain(purpose);
    return byokChain(agent, purpose);
```

- `PLATFORM` — только `platform_llms`; привязки агента не используются.
- `BYOK` — только привязки агента и списки назначения его chat-провайдеров; платформа не подставляется.

`ResolvedLlm.platformFallback` становится `source == PLATFORM`; `runsOnPlatformModels` —
`type == GENERIC && source == PLATFORM` (признак карточки, а не фильтр листинга).

### Инварианты

- Привязки PLATFORM-агента сохраняются, но неактивны; листинг показывает их с `active = false`.
- Manage API: добавление и замена привязки PLATFORM-агенту — 400 с указанием переключить режим.
  Удаление неактивной привязки разрешено, `PUT []` — тоже: это уборка, она не меняет платёж.
- `set_agent_llm` платформенного коннектора с непустой цепочкой на PLATFORM-агенте — исключение: он
  атомарно переключает агента в BYOK и ставит цепочку. Пустой список на PLATFORM — уборка. Manage-
  эндпойнты этим исключением не пользуются: интерфейс меняет режим явно.
- BYOK без CHAT — допустимое состояние. Удаление последней CHAT-привязки и `PUT CHAT []` разрешены;
  переключение в BYOK без CHAT разрешено. Отказ по чату — штатный и понятный (см. «Резолв»);
  интерфейс должен вести к привязке.
- Переключение `BYOK` → `PLATFORM` не удаляет привязки: они становятся неактивными.
- Удаление BYOK-провайдера разрешено: каскад может оставить агента без CHAT, это допустимое
  состояние, а не ошибка. Защита остаётся только у платформенного провайдера (ссылки из
  `platform_llms`).

### Переключение режима

`PUT /manage/agents/{agentId}/llm-source` — способ сменить режим из интерфейса. Тело: `{source}`;
ответ — агент с новым `llmSource`.

- `source = PLATFORM` — привязки становятся неактивными, больше ничего не меняется.
- `source = BYOK` — привязки становятся активными; если CHAT-привязки нет, это допустимое состояние:
  агент ответит понятным отказом, пока модель не добавят. Никакого `chatBinding` в запросе нет.
- Создание агента источник не принимает: новый агент всегда `PLATFORM`.
- Единственное исключение — `set_agent_llm` платформенного коннектора (см. «Инварианты»), чтобы
  мета-агент мог завершить настройку BYOK одним вызовом.

### Миграция

Резкий переход. `BYOK` — если у агента есть **любая** привязка; иначе `PLATFORM`.

Почему любая, а не только CHAT: явная привязка — это уже выбор пользовательских ключей; при
`CHAT`-only правиле IMAGE/ROUTINE-привязки стали бы неактивными, и медиа молча ушло бы на платформу.
Обратная сторона — агент только с медиа-привязкой остаётся без чата до добавления CHAT; это принято
как допустимое состояние с понятным отказом. На проде таких агентов нет (0 из 49), так что
фактической миграции это не меняет.

Следствия:

- агент с CHAT + IMAGE → BYOK, медиа больше не падает на платформу;
- агент только с IMAGE → BYOK, его IMAGE-привязка остаётся активной, чат отказывает до добавления
  CHAT, платформа за картинки не платит;
- агент с CHAT без медиа → BYOK, медиа работает, только если у его chat-провайдера есть список
  назначения; иначе ошибка с текстом «или переключите агента на платформу».

Во время раскатки есть короткое окно, когда старые инстансы ещё подставляют платформу, новые — уже
нет. Старые инстансы не читают `llm_source`, поэтому данные они не портят; окно закрывается первым
же полным перезапуском флота.

### API, интерфейс, коннектор

- Поле `llmSource` в ответе агента; переключатель в настройках агента. Для внешних агентов
  (`MCP`, `WEBHOOK`, `CENTRIFUGO`) переключатель выглядит и работает так же, как у `GENERIC`; у них
  он определяет источник медиа-моделей, потому что цикла чата у них нет.
- Листинг привязок PLATFORM-агента: `GENERIC` — все платформенные назначения; внешние — только медиа
  (`IMAGE`, `VISION`, `AUDIO_IN`, `AUDIO_OUT`). Плюс неактивные пользовательские строки с
  `active = false`. У платформенных строк `llmProviderId = null`, `priority` — фактический.
- `llmProviderId` в учёте для платформенных строк остаётся `null`.
- `set_agent_llm` платформенного коннектора на PLATFORM-агенте с непустой цепочкой переключает его в
  BYOK; с пустой — уборка. `delete_agent_llm` разрешён; `list_agent_llms` показывает эффективную
  конфигурацию и признак активности строк. В `AgentDetail`/`AgentBrief` добавляется `llmSource`:
  иначе мета-агент не увидит причину отказа и не объяснит её пользователю. `update_agent` источник
  не меняет.
- Внешний `GET /agent/llm/` и `GET /agent/llm/{purpose}` отдают только активные BYOK-привязки. Для
  PLATFORM-агента это пустой список и 404 соответственно: внешний мозг не должен видеть неактивные
  строки и не должен ходить к платформенной модели, к которой у него нет ключа. Описания эндпойнтов
  и `docs/contracts/api-keys.md` обновляются.

### Следствия

- Смешанные конфигурации исчезают: платформенный агент не тратит пользовательские ключи, BYOK-агент
  не тратит платформенные.
- BYOK-агент с неполной конфигурацией падает, а не деградирует на платформу; BYOK без CHAT — тоже
  допустимое состояние. Интерфейс должен вести к привязке CHAT/медиа-модели или переключению на
  платформу.
- Платформенные назначения обслуживают только PLATFORM-агентов; зона ответственности админа ясна.

## Совместная политика резолва

| Режим | Назначение | Порядок |
|---|---|---|
| `PLATFORM` | `CHAT` | `platform_llms[CHAT]` |
| `PLATFORM` | `IMAGE`, `VISION`, `AUDIO_IN`, `AUDIO_OUT` | `platform_llms[purpose]` |
| `PLATFORM` | `ROUTINE` | `platform_llms[ROUTINE]` → `platform_llms[CHAT]` |
| `BYOK` | `CHAT` | `agent_llms[CHAT]` |
| `BYOK` | `IMAGE`, `VISION`, `AUDIO_IN`, `AUDIO_OUT` | `agent_llms[purpose]` → списки `purpose_priority` chat-провайдеров агента |
| `BYOK` | `ROUTINE` | `agent_llms[ROUTINE]` → списки `ROUTINE` chat-провайдеров → модель `CHAT` агента |

## Принятые решения

| Вопрос | Решение |
|---|---|
| Миграция действующих агентов | резкий переход: `BYOK` при любой привязке, иначе `PLATFORM` |
| Привязки PLATFORM-агента | остаются в базе, неактивны (`active = false`) |
| Manage API на PLATFORM-агенте | добавление и замена — 400; удаление и `PUT []` — уборка |
| `set_agent_llm` коннектора на PLATFORM-агенте | непустая цепочка переключает в BYOK атомарно; пустая — уборка |
| Переключение в BYOK без CHAT | разрешено; без CHAT агент отвечает понятным отказом |
| BYOK без CHAT | допустимое состояние; удаление последней CHAT-привязки и `PUT CHAT []` разрешены |
| Переключение BYOK → PLATFORM | привязки остаются неактивными |
| Внешние агенты | тот же переключатель, что у `GENERIC`; источник медиа-моделей |
| Листинг PLATFORM-агента | `GENERIC` — все платформенные назначения; внешние — только медиа; неактивные пользовательские строки с `active = false` |
| `llmProviderId` в учёте | `null` для платформенных строк |
| Внешний `/agent/llm` | только активные BYOK-привязки; PLATFORM — пустой список/404 |
| Удаление платформенного провайдера | 400, если на него ссылаются платформенные назначения; в схеме `ON DELETE RESTRICT` |
| Удаление BYOK-провайдера | разрешено; агент может остаться без CHAT |
| Новые агенты и пресеты | `PLATFORM`; создание агента источник не принимает |
| `update_agent` платформенного коннектора | источник не меняет; `llmSource` виден в `AgentDetail`/`AgentBrief` |
| Очистка `purpose_priority` | отдельным неоткатываемым релизом после окна отката |
| Строка `platform` до чистящего релиза | не переименовывать и не удалять; после раскатки — аудит |

## Почему не иначе

**Один платформенный провайдер с картой назначений (как сейчас).** Отвергнут: все назначения делят
один ключ, адрес, транспорт и квоту; второй вендор не выражается.

**Несколько платформенных провайдеров с общим порядком и их `purpose_priority`.** Проще схема, но
порядок провайдеров общий для всех назначений: нельзя предпочесть одного вендора для картинок, а
другого для чата, если оба объявили оба назначения.

**Скрытый платформенный агент или строки `agent_llms` с `user_id = 0000`.** Отвергнут: `agent_id`
обязателен и связан внешним ключом с `agents`, поэтому нужен либо скрытый агент, протекающий во все
агентские выборки, либо ослабление схемы. Неявный дискриминатор `user_id = 0000` помнит каждый запрос.

**Одна общая таблица привязок со `scope` (`AGENT`/`PLATFORM`).** Честнее скрытого агента, но требует
переделки горячей таблицы и ослабления FK на `agents`. Оправдана, только когда появится третий
уровень (команда, организация); сейчас это YAGNI.

**Правило «есть хоть одна привязка у пользователя — платформу не отдавать».** Отвергнут: оно
глобально на пользователя, поэтому одна привязка у одного агента закрывает бесплатный уровень всем
остальным агентам.

**Переключатель на каждое назначение.** Это не упрощение, а текущее правило, сделанное явным: «есть
строки — BYOK, нет — платформа». Сохраняет гибкость, но добавляет состояние на каждое назначение и не
убирает смешанные цепочки.

**Переходный режим `MIXED`.** Отвергнут: сохранил бы старую политику для действующих агентов, но
оставил бы третью ветку в резолвере и двойную семантику на неопределённый срок. Выбран резкий
переход; поведение смешанных агентов меняется осознанно.

**Запрет BYOK без CHAT и 409 на удаление последнего провайдера.** Отвергнут: состояние допустимо и
даёт понятный отказ; guard добавил бы гонку с удалением привязки и запретил бы легальную уборку.
По той же причине убрано требование `chatBinding` при переключении в BYOK: режим — это плательщик, а
не полнота конфигурации.

**Показывать в карточке внешнего агента все платформенные назначения.** Отвергнут: строка `CHAT` у
агента с чужим мозгом — ложь; внешним показываем только медиа, которые платформа действительно
исполняет за него.

## Границы

- Явные привязки агента остаются закрытым множеством внутри BYOK: все непригодны — отказ, а не
  платформа. BYOK без CHAT — допустимое состояние с тем же отказом, а не нарушение инварианта.
- Платформенный агент не тратит пользовательские ключи, BYOK-агент не тратит платформенные.
- `LlmPurpose` не меняется. Новые назначения появятся как значения enum вместе с потребителем.
- Протокол воркера (`GetLlmCredentials`) не меняется: воркер по-прежнему получает одну модель на
  вызов; смена модели между вызовами — следствие цепочки.
- Квоты и учёт остаются по провайдеру; цепочка лимиты не суммирует. Общего лимита на несколько
  платформенных вендоров нет.
- Платформенные назначения настраиваются только администратором в UI; коннектор не получает этих
  тулов и не вызывает сервис платформенных назначений. Режим агента коннектор меняет только через
  `set_agent_llm` с непустой цепочкой; отдельного тула переключения нет.
- Внешний `/agent/llm` отдаёт только активные BYOK-привязки; платформенная конфигурация наружу не
  выходит.
- `purpose_priority` у BYOK-провайдеров сохраняет прежний смысл неявной маршрутизации медиа и
  `ROUTINE`; у платформенных строк поле мертво и очищается отдельным релизом.

## Риски и проверки

- **Предшественник не на проде.** В `agent_llms` нет `priority`, последняя миграция — 2026-10-26.
  Первый шаг — смержить `feature/agent-llm-purpose-chain` и выкатить; проверить колонку и
  `databasechangelog`. Без этого новый код не стартует.
- **Очистка `purpose_priority` неоткатываема.** На проде платформенный CHAT использовал 31 агент
  (2492 вызова); всего по платформе — 2947 вызовов и 45,4 млн токенов за всё время, 992 вызова и
  23,4 млн за 30 дней. Откат после очистки оставит эти агенты без модели. Очистка — отдельный релиз
  после закрытия окна отката.
- **Переименование/удаление строки `platform`.** Старые инстансы ищут её по имени. После раскатки,
  до чистящего релиза, проверить: исходный `id` и `name = 'platform'` на месте и включён;
  `platform_llms` ссылается на тот же `id`; в `llm_usage_log` нет провала по часам окна; в логах нет
  всплеска `no usable chat model` / `No CHAT model available`. При расхождении — инцидент, не
  чистить.
- **Медиа у BYOK-агентов.** На проде у 2 агентов на `deepseek.com` провайдер без IMAGE/VISION-
  списков (у одного есть явная VISION-привязка); у 3 на `proxyapi.ru` есть VISION, но нет IMAGE.
  Под BYOK IMAGE у них упадёт, если его вызвать; VISION работает через список или явную привязку.
  Фактического использования платформенных медиа у BYOK-агентов нет. Интерфейс должен вести к
  привязке медиа-модели или переключению на платформу.
- **Обрезка до пяти.** На проде все списки по одной модели — no-op. На клоне проверить списки длиннее
  пяти, дубли, `NULL`, `[]` и неизвестные `purpose`: миграция должна их пережить.
- **`RESTRICT` и 400.** Проверить на клоне: удаление провайдера со ссылками падает в FK и маппится в
  400; гонка вставки назначения с удалением провайдера не теряет строку молча.
- **Контракты ломаются:** создание платформенного провайдера теперь с именем, `purposePriority`
  уходит, появляется `llmSource`, признак `active`, тип-aware листинг, внешний `/agent/llm` больше не
  отдаёт неактивные строки, `set_agent_llm` коннектора меняет режим. Фронт выкатывается вместе;
  порядок — бэкенд, затем фронт, в окне админ не создаёт платформенных провайдеров старым фронтом.
- **Живой прогон:** два платформенных провайдера (чат и картинки), PLATFORM-агент без привязок и
  BYOK-агент; проверить, что первый не трогает пользовательские ключи, второй — платформенные;
  отдельно — PLATFORM-агент с сохранёнными неактивными привязками: `/agent/llm` пуст, листинг
  показывает `active = false`, `set_agent_llm` переключает режим.
- **Клон PostgreSQL:** SQL миграций и оба unique-констрейнта — интеграционных тестов в репозитории
  нет, констрейнты проверяются на живой базе.
