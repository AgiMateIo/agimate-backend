# Расписание в навыке: кто объявляет фоновую задачу агента

Фоновые задачи сегодня заводит **коннектор**: метод, помеченный `@Job`, попадает в `getJobs(env)`, и
при материализации экземпляра `ConnectorIdentityListener` пишет строку `connector_jobs`
(`kind=SYSTEM`, одна на `connection_id`). Есть и второй путь — агент сам вызывает `time.schedule`, и
появляется строка `kind=AGENT` с промптом в `args`.

Ни один не отвечает на вопрос «навык «Финансовый отчёт» хочет будить агента каждый понедельник».
Коннектор про такое не знает: расписание принадлежит не `sheets` и не `time`, а сценарию, который
написал автор навыка. Агент бы вызвал `time.schedule` — но только если догадается, и ровно один раз,
а при перепривязке навыка заведёт вторую такую же задачу.

## Ревизия: первый разбор ошибся в двух местах

Первая версия документа предлагала автоматическую материализацию: навык объявляет `jobs:`, сервер
заводит строки при привязке, зеркально `SkillPolicySync`. Разбор кода после этого перебил её дважды.

**Раз: развилка «куда отвечать» не открыта, она уже закрыта.** Разбор считал главным препятствием то,
что у объявленной задачи нет снапшота канала (`channel_id == null` → `ChannelResolution.direct()` →
финальный текст никуда не уходит). Но это не неопределённость, а **документированная конвенция** —
seed-навык `time` прямым текстом: «если чата не было — финальный текст никому не доставляется:
результат передавай инструментами». То есть задача без канала — рабочий, описанный режим: агент
просыпается и отдаёт результат тулом (сообщение в телеграм, комментарий на доске). Выбор канала —
улучшение, а не предпосылка.

**Два: автоматическая материализация противоречит собственному принципу платформы.**
[skill-connector-requirements.md](skill-connector-requirements.md) формулирует его прямо: «Навыки
никогда не привязывают и не отвязывают подключения — они только объявляют, что им нужно… доступ
выдаёт человек. Мастер — это и есть человек, с подсказками». `SkillPolicySync` выглядит исключением,
но им не является: он пишет **советующие** строки поверх привязки, которую человек уже сделал, и до
первого действия агента они ничего не меняют. Фоновая задача — это ран модели по таймеру, то есть
деньги на токенах, повторяющиеся без участия человека. Побочный эффект сильнее, чем у привязки
коннекции, а согласия при этом меньше. Асимметрия не оправдана.

Дальше — решение, которое из этих двух наблюдений следует.

## Идея распадается на два разных запроса

**A. Разбудить агента промптом по расписанию** — дайджест, обзор, напоминание. Механизм есть целиком:
строка `connector_jobs` → планировщик → скрытый `time`/`fire` → триггер `time.due`, адресованный
агенту. Не хватает только объявления и способа завести строку.

**B. Выполнить тулу коннектора вхолостую по расписанию** — `sheets.aggregate` каждую ночь, без модели.
`executeJob` умеет вызвать любой `@Tool`, но результату **некуда деться**: SYSTEM-джобу потребляет сам
коннектор, он же поднимает триггер, если есть о чём сообщить. Для объявленного прогона нужен путь
доставки — по форме подходит воронка `tool_completed` из [detached-tools.md](detached-tools.md), но
это своя работа.

**Документ про A.** B откладывается: выглядит соседним пунктом, стоит как отдельная фича, и без
первого не нужен.

## Пресеты — нет

Пресет композирует навыки через `skill_names`, инструкции копирует, навыки привязывает по ссылке.
Пресет, которому нужно расписание, везёт **навык, который его объявляет**. Иначе одна сущность
получает два языка объявления и два места, где они разъедутся. Значения по умолчанию (час, зона) тоже
не пресетные: тот же навык на втором агенте — другая задача с другим временем.

## Решение: навык предлагает, строку создаёт человек

Навык объявляет расписание во frontmatter. План привязки отдаёт объявленное как **предложение** с
подставленными значениями. Строку создаёт `POST /manage/connector-jobs` — с видом **`USER`**, который
в `ConnectorJobKind` уже зарезервирован ровно под это: «created by a user through the manage API
(creation is not implemented yet, the value is reserved)».

```
SKILL.md  jobs:  →  GET /manage/agents/{id}/skills/plan  →  человек правит час/зону/канал
                 →  POST /manage/connector-jobs (kind=USER)  →  существующий планировщик
```

### Почему это дешевле

Исполнять уже нечего делать: `JobExecutionService.buildEnv` для внутреннего коннектора собирает
контекст из `row.getUserId()/getAgentId()/getChannelId()/getSessionId()` **не глядя на `kind`** — строка
`USER` с заполненным `agent_id` исполнится ровно тем же путём, что и `AGENT`. Значит от работы
остаётся: блок `jobs:` в разборе frontmatter, предложения в плане привязки, один POST — и всё.

Из плана автоматической материализации при этом **выпадает целиком**:

| Что не нужно | Почему |
|---|---|
| `ConnectorJobKind.SKILL` | `USER` уже есть и означает именно это |
| колонка `connector_jobs.agent_skill_id` | идентичность строки — её собственный `id`, как у любой пользовательской |
| частичный уникальный `WHERE kind='SKILL'` | нет бизнес-ключа — нет и индекса под него |
| `SkillJobSync` и четыре шва в `AgentSkillService` | никто ничего не пересобирает |
| ворота по `satisfiedSkillInstances` | человек не создаст задачу для навыка, который ещё не работает; а если создаст — увидит результат |
| пере-материализация при возврате удовлетворённости | нечего материализовать |
| фаза 2 «переопределение расписания на привязке» | форма создания **и есть** переопределение |

### Формат объявления

```yaml
---
name: weekly-report
connectors: [sheets, time]
jobs:
  - name: weekly-digest
    title: Еженедельная сводка расходов
    cron: "0 0 9 * * MON"
    zone: Europe/Moscow      # значение по умолчанию, человек меняет
    prompt: >
      Собери сводку расходов за прошлую неделю и пришли её пользователю одним сообщением.
---
```

| Поле | Смысл |
|---|---|
| `name` | ключ предложения внутри навыка — по нему план отличает «уже создано» от «предлагается» |
| `title` | подпись в мастере; в строку не едет |
| `cron` \| `intervalSeconds` | ровно одно; форма та же, что у `time.schedule` |
| `zone` | IANA-идентификатор, по умолчанию `UTC` |
| `prompt` | с чем агент просыпается — то, что ляжет в `args.prompt` |

`ONETIME` в объявлении не нужен: «один раз после привязки» — это не расписание, а инструкция в теле
навыка, и агент сделает это сам в первом же разговоре.

**Коннектор `time` объявляется явно** — навык с `jobs:` обязан указать его в `connectors:`. Это не
стилистика: `fire` поднимает триггер с аудиторией из одного агента, а
`TriggerRouterService.findRecipients` начинает с `findBoundToConnection(userId, connectionId)` — без
привязки агента к экземпляру `time` у `time.due` **нет получателя**, и задача тикает вхолостую.
Проверять это надо **и на POST** (400, если агент не привязан к `time`), а не только при разборе
документа: строку можно создать и без навыка.

### Как план отличает созданное от предложенного

Предложение — не строка, а вычисление: план навыка сравнивает объявленные `jobs[].name` с уже
существующими задачами агента. Связь нужна только для этого сравнения — nullable-колонка
`connector_jobs.source TEXT` со значением `skill:<id>/<name>`, дословно по образцу
`AgentConnectionPolicy.source`. Ни индекса, ни констрейнта: это подсказка мастеру, а не инвариант.

Класть метку в `args` было бы соблазнительно (JSONB уже есть, миграции не надо), но неверно: `args` —
это **аргументы метода**, которые `buildMethodArgs` разбирает по параметрам `fire(prompt)`. Лишний
ключ там сегодня молча игнорируется, то есть сломается не сразу, а когда у `fire` появится параметр
`source`. Одна строка миграции дешевле такой мины, и прецедент `source` — именно колонка.

### Что человек теряет и почему это правильно

- **Отвязали навык — задача осталась.** Так и надо: строку создал человек, промпт продолжает
  работать, задача видна в `/manage`. Автоматически удалять то, что пользователь завёл явно, —
  как раз неожиданное поведение.
- **Новая версия навыка сама до задачи не доедет.** Ровно как сегодня с `connectors:`: план
  предложит новое, человек решит. Молча переписать расписание, которое пользователь настроил под
  себя, было бы хуже.
- **Пока нет формы — ничего не появляется.** Это честная цена, и она не блокирующая: см. ниже.

### Первый потребитель — мета-агент, а не фронт

`POST /manage/connector-jobs` полезен раньше мастера. Коннектор `platform` уже даёт мета-агенту
`create_connection`, `create_channel`, `create_policy` — задача того же ряда: пользователь говорит
«хочу сводку по понедельникам в 9 утра», мета-агент создаёт строку. То есть бэкенд шьётся и
проверяется независимо от фронта, а мастер приходит, когда дойдёт очередь до него вместе с двумя
другими пунктами roadmap, которые его ждут.

## Отвергнутые варианты

- **Автоматическая материализация при привязке (первая версия документа).** Отвергнута по разделу
  «Ревизия»: повторяющийся расход модели без участия человека — более сильный побочный эффект, чем
  привязка коннекции, которую навык делать не вправе. Плюс `kind=SKILL`, колонка, индекс, сервис
  синхронизации и четыре шва — всё это цена именно за автоматизм.
- **`TimeConnectorService.getJobs(env)` объявляет навыковые задачи сам** — первое, что придёт в голову
  читателю диффа, раз появился по-экземплярный хук. Не работает: экземпляр `time` один на
  пользователя, агентов много, и бизнес-ключ SYSTEM-строк `(connector_code, connection_id, name)`
  схлопывает их все в одну — `name` у всех `fire`, потому что это имя метода диспетчеризации.
- **Промпт-инструкция «вызови `time.schedule`».** Статус-кво: недетерминированно (модель может не
  вызвать), дубли при перепривязке, ничего не видно в плане.
- **Новая таблица `skill_jobs`.** Строка всё равно обязана попасть в `connector_jobs`, иначе её не
  увидит планировщик; вторая таблица была бы источником для первой.
- **Джобы в пресете.** Второй язык объявления той же сущности.

## Зависимости: чего эта работа ждёт

Ревизия открытых задач по джобам (13.09) показала, что документ нельзя реализовывать первым.

- **[connector-job-concurrency.md](connector-job-concurrency.md) — предпосылка, а не сосед.**
  Решение `accepted`, план не начат, семафора в коде нет. Оно родилось из заморозки control-api
  10.09, где «веер джоб на суточном кроне выбрал всю кучу», — а объявленное расписание производит
  ровно эту нагрузку: `JobSchedule.nextCron` возвращает точный тик без разброса, так что все, кто
  принял предложение с дефолтным `0 0 9 * * MON`, получают `next_run_at` на **одну и ту же
  секунду**. Без потолка это воспроизведение того же отказа по построению; с потолком — очередь,
  которая рассосётся по сроку. Отсюда же требование к формату: у предложения в мастере зона и час
  должны реально различаться от пользователя к пользователю, а не оставаться дефолтом автора.
- **Уведомление об упавшей джобе** — то, что отличает «работает» от «можно доверять». Сегодня
  упавшая итерация пишет `last_error` и молчит; для SYSTEM-строк (опрос коннектора) это терпимо, для
  строки, которую **завёл человек и ждёт от неё письма по понедельникам**, — нет. Шов уже есть:
  [push-notifications.md](push-notifications.md) отложил это сознательно, «тот же вызов реле, но
  другое условие врезки и другой payload». `kind=USER` — первый вид строк, ради которого это стоит
  достать из отложенных.
- **Пересечение с «сохранёнными сценариями»** — развилка 2 в
  [deferred/workflow-connector.md](deferred/workflow-connector.md). Это та же продуктовая
  поверхность: объявленная повторяющаяся работа. Там она без модели и с шагами, здесь — промптом и
  раном. Проектировать этот документ как одиночку не надо: тула создания задачи и хранение
  расписания у них общие.

## Следствия и ловушки

- **`time.scheduled_tasks` покажет задачу, которую агент не сможет отменить.**
  `findActiveByAgent` фильтрует по `(connector_code, user_id, agent_id)` **без учёта `kind`**, а
  `deleteOwned` требует `kind = AGENT`. Любая USER-строка с заполненным `agent_id` попадёт в листинг,
  и `cancel_scheduled` ответит «Scheduled task not found». Чинится до первой такой строки: либо
  сузить листинг до `AGENT`, либо показывать USER-строки помеченными как неотменяемые. Склоняюсь ко
  второму — агент должен видеть, что уже разбудит его в понедельник, иначе заведёт своё дубликатом.
- **Промпт задачи приходит агенту как доверенный текст.** `time.due` объявлен с
  `presentation = PROMPT`, и `RunContextService.triggerMainBlock` кладёт `data.prompt` в
  `RunBlock.trusted` — с оговоркой в коде «the text is authored by the agent or the platform». Для
  `AGENT` (сам себе) и для `USER` через manage API (владелец) это так и есть. Для тулы в `platform`
  это новое: **одна модель пишет текст, который попадает в доверенный блок другого агента**.
  Мета-агенту нужен тот же guard «не сам себя», что уже стоит в остальных его тулах, и стоит
  подумать, не должна ли пометка различаться по `kind` — «твоя отложенная задача» против
  «задача, заведённая владельцем». Директивы задаются только кодом, так что это правка
  `ContextDirectives`, а не данных.
- **Seed-only-if-missing.** Блок `jobs:`, дописанный в засеянный SKILL.md, не доедет до установки,
  пока не поднимется `skills.version` и человек не примет обновление. На `board` это уже срабатывало;
  здесь последствие тише — не «текст устарел», а «предложение не появилось».
- **DBOS ни при чём.** `connector_jobs` — собственный pull-планировщик control-api; ни дренажа, ни
  совместимости чекпоинтов работа не требует.
- **Стоимость расписания.** Задача раз в пять минут — это ран агента раз в пять минут, то есть
  реальные деньги. Минимальный интервал (не чаще раза в час) надо ставить **в `JobSchedule`**, а не на
  POST: `time.schedule` сегодня принимает любой положительный `intervalSeconds`, и ограничение на
  одном входе агент обойдёт через другой. Одно место, два вызывающих.
- **`run-now` уже есть** — `POST /manage/connector-jobs/{id}/run-now`, так что проверить созданную
  задачу можно не дожидаясь понедельника.

## План

Две фазы, и граница между ними не косметическая: фаза 1 шьётся и проверяется целиком без фронта,
фаза 2 заводит таблицу под потребителя, которого сегодня нет, и потому едет вместе с мастером.

**Фаза 1 — задача по расписанию как пользовательская сущность**

- [ ] `POST /manage/connector-jobs`: создание `kind=USER` (агент, коннектор `time`, промпт,
      cron/интервал, зона, канал), проверка привязки агента к `time`
- [ ] Минимальный интервал в `JobSchedule` — общий для POST и `time.schedule`
- [ ] `findActiveByAgent` без фильтра по `kind`: пометка неотменяемых в `time.scheduled_tasks`
      (сейчас листинг их покажет, а `cancel_scheduled` ответит «not found»)
- [ ] Миграция: nullable `connector_jobs.source TEXT`
- [ ] Тула `create_scheduled_job` в коннекторе `platform` — первый потребитель, независимый от фронта;
      guard «не сам себя» и решение по пометке доверенного промпта в `ContextDirectives`

**Фаза 2 — объявление в навыке**

- [ ] `SkillFrontmatterParser`: блок `jobs:` с проверками формы (ровно одно из `cron`/`intervalSeconds`,
      валидность выражения и зоны, обязательный `time` в `connectors`)
- [ ] Миграция: `skills.jobs JSONB`; модель `SkillJob`
- [ ] Предложения в `GET /manage/agents/{agentId}/skills/plan`: объявленное против существующего по
      `source`
- [ ] Системный навык с еженедельной сводкой — первый потребитель формата
- [ ] Мастер на фронте: шаг расписания после шага коннекторов (вместе с
      [`tmpspec/skill-wizard-frontend.md`](../tmpspec/skill-wizard-frontend.md))
- [ ] Документация: раздел Skills в `CLAUDE.md`, `architecture/connectors.md`, `roadmap.md`
