# Навыки подключения и их пользовательские копии

Приложение может принести не один навык, а несколько: отдельные инструкции для скриншотов,
буфера обмена, файлов. Текущая схема `app-skills` выражает ровно один: уникальный
`skills.origin_connection_id`, один JSONB `apps.skill` и один блок `skill` в линковке. Этот документ
заменяет одно-навыковую часть [app-skills.md](app-skills.md): объявления переезжают в
`connection_skills` рядом с `connection_tools`/`connection_triggers`, а в `skills` остаются
пользовательские копии, связанные с конкретным объявлением через `connection_skill_id`.

## Решение в одном абзаце

**`connection_skills` — каталог навыков, объявленных подключением; `skills` — пользовательская
копия каждого объявления.** Приложение присылает при линковке карту `skills`; бэкенд целиком
заменяет каталог `connection_skills` этого подключения и для каждого объявления создаёт или
обновляет копию в `skills`. Копия остаётся пользовательским объектом: её можно править, привязывать
к агентам и удалять; пока `updated_by = APP`, приложение обновляет её текст, стартеры и описание,
после первой правки — нет. Связь копии с объявлением — `skills.connection_skill_id` вместо
`origin_connection_id`; подключение выводится из объявления. Раскрытие — `LAZY`, стартеры
копируются в копию, поэтому `AgentStarterService` и `load_skill` не меняют свой путь.

## Почему не один навык и не origin

- У одного экземпляра приложения естественно несколько независимых инструкций. Один
  `origin_connection_id` не может сказать, какое из объявлений породило копию: при обновлении
  нельзя отличить «этот навык изменился» от «добавился второй».
- `apps.skill` — один JSONB на приложение; он не даёт ни идентичности отдельного навыка, ни
  точечного обновления, ни удаления одного из набора.
- `connection_skills` повторяет форму `connection_tools`/`connection_triggers`: каталог принадлежит
  подключению, заменяется целиком и не смешивается с пользовательским каталогом. Копия в `skills`
  остаётся потому, что продукт хочет владение, правку, привязку и стартеры — то, чего у чистой
  капабилити нет.
- `connection_skill_id` — стабильная идентичность объявления. Ключ `(connection_id, uri)` не
  годится как ссылка из копии: при переименовании или повторном объявлении он может измениться;
  id строки переживает и то, и другое.

## Схема

### `connection_skills`

| Колонка | Зачем |
|:--|:--|
| `id` | `uuidv7()`; на него ссылается копия |
| `connection_id` | Владелец каталога; FK на `connections(id)` |
| `uri` | Идентичность объявления: для приложения `app://<connectionId>/<key>`, для MCP — URI навыка у сервера |
| `name` | Ключ приложения (kebab-case) или имя навыка у MCP-сервера |
| `title` | Человекочитаемое название; у копии — fallback |
| `description` | Обязательное описание для приложения: lazy-навык показывается в каталоге им |
| `starters` | `text[]`; подсказки приложения |
| `language` | Язык тела — метаданные; у копии `skills.language` остаётся `NULL` |
| `frontmatter` | JSONB: объявление как пришло (для MCP — frontmatter сервера) |
| `content` | Тело `SKILL.md`; у приложения хранится сразу, у MCP — кэш до первой загрузки |
| `content_digest`, `content_size` | `sha256:<hex>` и размер байт; у приложения считаются при линковке, у MCP проверяются после `resources/read` |
| `manifest` | JSONB: файлы и дайджесты; у приложения `NULL`, у MCP — манифест |
| `discovered_at` | Когда объявление последний раз подтверждено (линк или discovery) |
| `deleted_at` | Мягкое удаление: каталог заменяется целиком, история остаётся |

Ограничения:

- `uq_connection_skills_connection_id_uri` — `(connection_id, uri)` **включая soft-deleted**: если
  приложение убрало навык и потом вернуло тот же ключ, строка оживает, а не создаётся вторая.
- `idx_connection_skills_connection_id` — выборка каталога подключения.
- `fk_connection_skills_connection` — на `connections(id)`, `ON DELETE RESTRICT`: объявление нельзя
  удалить, пока на него ссылается копия, даже soft-deleted. Уборка — только мягкая.

### Смысл колонок зависит от источника

Таблица общая с будущим входящим MCP ([mcp-skills.md](mcp-skills.md)), но колонки в двух режимах
значат разное, и читатель обязан фильтровать по виду коннектора:

- `uri` — идентичность **навыка**, не сервера. У каждого навыка MCP-сервера свой URI; у приложения
  он строится из `connectionId` и ключа.
- `content` у приложения — авторитетное тело, записанное при линковке; у MCP — кэш, который может
  быть пуст до первой загрузки.
- `deleted_at` у приложения означает «каталог заменён, ключа больше нет»; у MCP пропажа из
  `skills/list` не удаление — только `-32602` от `skills/get` убирает капабилити.
- `description` обязателен для приложения и может отсутствовать у MCP.
- App-ран читает копии в `skills`, а не `connection_skills`; MCP-фаза 2 читает
  `connection_skills` напрямую. Общий читатель не должен смешивать эти два режима.

### `skills.connection_skill_id`

- Новая nullable-колонка `UUID` + FK `fk_skills_connection_skill` на `connection_skills(id)`.
- `uq_skills_connection_skill_id` — уникальность **включая soft-deleted**: у объявления одна копия,
  и удаление копии пользователем не воскрешается следующей линковкой.
- `origin_connection_id` и его уникальность удалены contract-миграцией; единственный указатель —
  `connection_skill_id`.
- `updated_by` остаётся: `APP` — текст обновляется при линковке, `USER` — нет.

### `apps`

`apps.skill`, `apps.tools` и `apps.triggers` удалены contract-миграцией: источник каталога —
`connection_skills`/`connection_tools`/`connection_triggers`. `apps` хранит только
`code`/`title`/`version`, `description`, `deviceId`/`info`, ключи и состояние. Читатели
`UserAppDetailResponse`, `GET /manage/apps/{id}/tools|triggers` и
`AgentService.buildToolDefinitionMap` переведены на нормализованные таблицы.

## Синхронизация

Все записи `connection_skills` и копий идут через один идемпотентный `ConnectionSkillSync`; других
писателей у этих строк нет. Он используется линковкой и удалением приложения и делает следующее:

1. Блокирует строку `apps` (как сейчас) и читает объявления из запроса.
2. Обновляет `connection_skills` по ключу `(connection_id, uri)` **включая soft-deleted**: строка
   оживает, id сохраняется, копия остаётся связанной.
3. При полной замене (`skills`) soft-delete'ит ключи, которых нет в карте. Копии этих объявлений
   **не удаляет** — они замораживаются (см. «Жизненный цикл»).
4. Для каждого живого объявления ищет копию по `connection_skill_id` **включая soft-deleted**:
   - копии нет — создаёт;
   - копия жива и `updated_by = APP` — обновляет title/description/тело/стартеры, `version++`;
   - копия жива и `updated_by = USER` — не трогает;
   - копия soft-deleted — не воскрешает: удаление пользователем окончательное.
5. При удалении приложения проходит по всем объявлениям подключения и удаляет их копии, **пропуская
   уже soft-deleted**. `SkillService.delete` на удалённой строке отвечает 404, поэтому вызов
   подряд без проверки откатил бы всю транзакцию удаления приложения.

Инвариант: каждая копия подключения имеет `connection_skill_id`; origin-колонки в схеме больше
нет.

## Линковка

`POST /app/registration/link` получает карту `skills` рядом с `tools`/`triggers`:

```json
{
  "deviceId": "…",
  "app": { "code": "desktop", "title": "AgiMate Desktop", "version": "1.4.2" },
  "skills": {
    "screenshot": {
      "title": "Screenshots",
      "description": "Снимает экран и отдаёт файл.",
      "body": "…",
      "starters": ["Сделай скриншот"],
      "language": "ru"
    },
    "clipboard": {
      "description": "Читает и пишет буфер обмена.",
      "body": "…"
    }
  },
  "tools": { "…": { "…": "…" } },
  "triggers": { "…": { "…": "…" } }
}
```

Правила:

- Ключ карты — `key`: kebab-case, до 64 символов, уникален внутри подключения. Он входит в `uri` и
  в имя копии. Ключей не больше **32**; превышение — `400`, чтобы багованный клиент не создал
  тысячи пользовательских навыков.
- `description` и `body` обязательны; `title`, `starters`, `language` — нет. Ограничения прежние:
  описание ≤ 2000, тело ≤ 32768, стартеров ≤ 5 (`StarterTexts`).
- `skills` — **полная замена** каталога: ключи, которых нет в карте, получают `deleted_at`;
  копии при этом не удаляются (см. «Жизненный цикл»). `"skills": {}` очищает каталог.
- `skills` отсутствует или равен `null` — каталог не меняется. Это **осознанное расхождение** с
  `tools`/`triggers`: у них отсутствие поля очищает каталог, потому что `syncAppCatalog` сначала
  делает `deleteByConnectionId`, а вставляет только при non-null. Для навыков «отсутствует» значит
  «не трогать»: иначе частичный или старый клиент стёр бы навыки.
- Legacy-блок `skill` (один объект без ключа) принимается как объявление ключа `default` и
  **обновляет только его**, не трогая остальные ключи. Так старый клиент не стирает навыки,
  объявленные новым. `skill` и `skills` в одном запросе — `400`.
- `skills.default` — обычное объявление ключа `default`; legacy-колонок, куда бы оно
  дополнительно писало, в текущей схеме нет.
- Контракт клиента: **ключи стабильны**. Первая версия клиента, переходящая с `skill` на `skills`,
  обязана прислать `default` вместе с новыми ключами; иначе старое объявление исчезнет, а его
  копия `app-<code>` заморозится и останется рядом с новыми — дубль. Переименование ключа
  (`screenshot` → `screenshots`) — это новый навык; старое объявление и копия замораживаются.
- Блок `skill`/`skills` без блока `app` — `400`: имя копии строится из кода приложения.
- Невалидный элемент блокирует линковку целиком: приложение не должно молча остаться без навыка.

Синхронизация идёт в той же транзакции, что `apps`/`connections`; строка `apps` по-прежнему
блокируется на время линковки, поэтому две одновременные линковки одного приложения не создают
дублей.

## Копия

Для каждого объявления бэкенд создаёт копию в `skills`:

| Поле | Значение |
|:--|:--|
| `name` | `app-<code>-<key>`; для legacy-ключа `default` — прежнее `app-<code>` |
| `title` | `connection_skills.title`, иначе `app.title`, иначе для `default` — `app.code`, для остальных — `key` |
| `description` | `connection_skills.description` |
| `md_content` | `connection_skills.content` |
| `starters` | `connection_skills.starters` |
| `connectors` | принудительно `[app]` |
| `category` | `PLATFORM` |
| `disclosure` | `LAZY` |
| `language` | `NULL` — владелец видит копию в любом каталоге |
| `is_public` | `false` |
| `user_id` | владелец приложения |
| `connection_skill_id` | id объявления |
| `updated_by` | `APP` |

Имя с суффиксом: если `app-<code>-<key>` совпадает с другим навыком пользователя, добавляется
`-2`, `-3`; суффикс остаётся на всю жизнь копии. Ключ объявления при этом не меняется.

## Жизненный цикл

| Сценарий | `connection_skills` | Копия `skills` |
|:--|:--|:--|
| Первый линк с `skills` | Строки создаются | Создаётся по копии на объявление, `updated_by=APP` |
| Повторный линк, ключ есть | Обновляется объявление и `discovered_at` | При `APP` обновляются title/description/тело/стартеры, `version++`; при `USER` не трогается |
| Ключ исчез из `skills` | `deleted_at` | **Остаётся живой и замороженной**: приложение её больше не обновляет, пользователь может удалить |
| Ключ вернулся | Строка оживает (`deleted_at = NULL`) | Живая копия снова обновляется при `APP`; удалённая пользователем не воскрешается |
| Пользователь правил копию | Не меняется | `updated_by = USER`; приложение пишет только объявление |
| Пользователь удалил копию | Не меняется | Soft-delete; следующая линковка копию не создаёт |
| Приложение удалено | Все строки подключения soft-delete | Копии удаляются через `ConnectionSkillSync`; **уже soft-deleted копии пропускаются**, иначе `SkillService.delete` ответит 404 и откатит удаление приложения |

Почему копия не удаляется вместе с исчезнувшим ключом: копия — пользовательский объект. Приложение
убрало объявление, но пользователь мог её привязать к агенту и править; молча удалять его работу
нельзя. Замороженная копия продолжает работать, **пока подключение приносит хотя бы один тул или
триггер**: `connection_skill_id` ссылается на soft-deleted строку, подключение живо, требование
`[app]` разрешается. Если приложение тем же линком убрало и последний тул, DYNAMIC-подключение
попадает под `broughtNothing` и копия придёт агенту как `NO_CAPABILITIES` — это не ошибка
заморозки, а общий гейт. Если приложение хочет убрать навык совсем, он удаляется вместе с
приложением.

## Origin: от копии к подключению

`connection_skill_id` — не только происхождение, но и селектор экземпляра:

- `Skill.connectionSkillId` → `connection_skills.connection_id`; строка объявления читается
  **включая soft-deleted**, иначе замороженная копия потеряла бы подключение.
- `AgentSkillService.resolveInstances`: ветка выбирается по `connectionSkillId != null`, а не по
  тому, удалось ли вывести origin. Если объявление или подключение не найдены, кандидатов нет —
  ветка «любое подключение кода» не должна срабатывать.
- `AgentSkillService.resolveConnection`: ссылка привязки форсируется на это подключение; чужой id
  в запросе — `400`.
- `SkillSpecs.fitsConnection`: копия с `connection_skill_id` матчится только через объявление;
  пользовательский навык без него — с любым подходящим подключением, как раньше.
- `matches` мастера: если `connectionSkillId != null`, список сужается до выведенного подключения;
  иначе работает прежнее правило кода и params. Копия от приложения A не появляется на странице B.
- `SkillOriginResponse` получает `connectionSkillId` и `key`; остальные поля (`connectionId`,
  `code`, `title`, `version`, `deviceName`) считаются как раньше.

**Привязка копии не открывает подключение.** `agent_skill_connections` хранит ссылку «навык означает
это подключение», но `app` — внешний экземпляр: доступ к тулам даёт только отдельная привязка
`agent_connections`. Без неё копия приходит агенту как `NOT_BOUND` — это существующее правило
`skill-binding-opens-internal-connectors.md`, и оно не меняется.

Contract-миграция оставляет только путь через `connectionSkillId`; `originConnectionId` в коде и
БД больше нет.

## Ран

- Копия — обычный навык: `LAZY`, каталог показывает имя и описание, тело выдаётся `load_skill`,
  если в скоупе есть `skill-loader`; без него действует прежнее правило раскрытия.
- Стартеры копируются в `skills.starters`; `AgentStarterService` не меняется — он по-прежнему
  читает привязанные и удовлетворённые копии. Правка стартеров пользователем — такая же правка,
  как и тела: `updated_by = USER`, приложение их больше не перезаписывает.
- Тулы приложения остаются тулами подключения. Привязка копии добавляет ссылку
  `agent_skill_connections`, но доступ даёт только `agent_connections`; несколько копий одного
  приложения дают несколько наборов инструкций к одному набору тулов.
- ABAC-правила на подключение одни. Две копии одного приложения не могут иметь разные правила на
  один и тот же тул: `SkillPolicySync` вернёт конфликт и не запишет второе правило, а удаление
  выигравшей копии не переприменяет правила второй. Это ограничение модели, а не баг; копии
  изолируют инструкции, но не права.

## Миграция и обратная совместимость

Миграция — expand/contract, выполнена в одном выпуске: expand добавил и заполнил новые колонки,
contract сразу удалил legacy. Ниже — история обеих фаз.

### Expand (выполнен)

1. Создать `connection_skills`.
2. Добавить `skills.connection_skill_id` (nullable) и FK; уникальность пока не добавлять.
3. Backfill **идёт от копий и от приложений**: для каждого различного `connection_id`, у которого
   есть origin-копия или `apps.skill`, создать одну строку `connection_skills`:
   - `uri = 'app://' || connection_id || '/default'`, `name = 'default'`;
   - `title`/`description`/`starters`/`language`/`content` — из `apps.skill`, иначе из копии;
   - `frontmatter` — снимок объявления;
   - `content_digest`/`content_size` — по `content`, формат digest `sha256:<hex>` как в
     `McpSkillCatalog`; если SQL-функция недоступна, digest остаётся `NULL` и считается при
     следующем линке (формат не должен разъехаться с MCP);
   - `discovered_at = apps.updated_at` (или `updated_at` копии).
4. Проставить `skills.connection_skill_id` **всем** строкам с `origin_connection_id`. Инвариант:
   после этого не остаётся origin-копии без `connection_skill_id`; миграция проверяет это
   утверждением, иначе contract превратит сбой данных в неограниченный `[app]`-навык.
5. Добавить `uq_skills_connection_skill_id` (включая soft-deleted). Старую
   `uq_skills_origin_connection_id` и `apps.skill` оставить.
6. Новый код пишет `connection_skills` и копии; для legacy-блока `skill` и для `skills.default`
   дополнительно пишет `apps.skill` и `origin_connection_id` у копии `default` — чтобы старые
   клиенты и одно-навыковый сценарий пережили выпуск. Копии остальных ключей
   `origin_connection_id` не заполняют. Откат на старый код после появления multi-skill не
   поддерживается: старый код увидит такие копии как навыки без origin и сможет разрешить их в
   любое `app`-подключение. Это осознанная цена; откат безопасен только для приложений с одним
   legacy-навыком.

### Contract (выполнен)

- Удалены `uq_skills_origin_connection_id`, FK и колонка `skills.origin_connection_id`.
- Удалены `apps.skill`, `apps.tools`, `apps.triggers` и модель `AppSkill`: источник каталога
  подключения — `connection_skills`/`connection_tools`/`connection_triggers`.
- Перед удалением повторно добиты `connection_skills` из `apps.skill`/origin-копий, а
  `connection_tools`/`connection_triggers` — из JSONB там, где у подключения ещё нет живых строк.
- Читатели JSONB переведены на нормализованные таблицы: `UserAppDetailResponse`,
  `GET /manage/apps/{id}/tools|triggers` и `AgentService.buildToolDefinitionMap`.
- Legacy-ветка чтения origin убрана из `AgentSkillService`/`SkillSpecs`/`SkillService`.
- Старый код после contract не откатывается; legacy-блок `skill` в запросе остаётся alias'ом на
  `default` и продолжает работать со старыми клиентами.

### Совместимость

- Старые клиенты присылают `skill`; он обновляет только `default`. Имя legacy-копии не меняется —
  `app-<code>`, поэтому привязки, правила и упоминания в промптах не ломаются.
- Новые клиенты присылают `skills`. Старый экземпляр control-api **молча проигнорирует** это поле:
  Spring Boot 4/Jackson 3 не падает на неизвестных свойствах, `LinkDeviceRequest` их не запрещает,
  и старый сервер ответит `200 success`. Это известное ограничение, а не ошибка: multi-skill
  включается только после выката control-api, клиенты выпускаются после сервера. Отдельного эха
  принятых ключей или проверки версии в протоколе нет — сознательно не усложняем; цена — молчаливая
  потеря навыков при линковке на старый сервер, которую ловит порядок выката, а не ответ.
- **Обратная совместимость — для клиентов, не для отката кода.** Старый клиент с `skill` продолжает
  работать: блок превращается в объявление `default`. Откат на старый код после contract
  невозможен — колонок `origin_connection_id`, `apps.skill`, `apps.tools` и `apps.triggers` больше
  нет. Перед выкатом нужен дамп.
- `skills.connection_skill_id` — единственный источник истины; `connection_*` — единственный
  каталог подключения.

## Альтернативы

- **Капабилити без копий.** `connection_skills` и никаких `skills`; привязка подключения даёт
  навыки и тулы, текст не редактируется. Плюс: нет `updated_by`, каталога копий и жизненного цикла.
  Минус: пользователь теряет владение, правку и стартеры; это меняет продуктовую модель
  `app-skills`, поэтому отвергнуто.
- **`origin_key` на `skills`.** Снять уникальность origin и добавить ключ. Не даёт места для
  объявления (кроме `apps.skills` JSONB), не даёт стабильного id для копии и оставляет разбор
  «кто кого обновляет» на паре строк. Отвергнуто в пользу `connection_skill_id`.
- **`apps.skills` JSONB.** Хранить массив объявлений в `apps`, копии — в `skills`. Проще миграция,
  но нет нормальной идентичности, FK, выбора одного навыка и будущего переиспользования для MCP.
  Отвергнуто.
- **Удалять копию при исчезновении ключа.** Приложение — источник каталога, но не владелец копии;
  удаление потеряло бы пользовательскую правку и привязки. Оставлено мягкое замораживание.
- **Структурный ответ линковки с эхом принятых навыков.** Закрывал бы молчаливую потерю на старом
  сервере, но усложняет протокол ради переходного окна; порядок выката решает ту же задачу.
  Отвергнуто по простоте.

## Открытые вопросы

- Имя для ключа: `app-<code>-<key>` может оказаться длинным; при необходимости усечём с хвостом-хешем
  так же, как в `McpSkillCatalog`.
- Реэкспорт копий наружу через `/mcp` уже работает сам собой: копия — обычный пользовательский
  навык. Отдельных решений не требует.
- MCP-фаза 2 использует ту же `connection_skills` без копий; общие поля (`uri`, `frontmatter`,
  `manifest`, `content_digest`) уже заложены. Смысл колонок зависит от источника — см. выше.
  Если MCP понадобится другой набор метаданных, он добавит колонки, не ломая app-часть.
