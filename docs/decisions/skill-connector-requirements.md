# Требования навыка к коннекторам: экземпляр, параметры, правила доступа

Навык сегодня объявляет только **коды** коннекторов (`connectors: [mcp, persist-memory]`). Этого
хватало, пока внешний коннектор был один и у пользователя был один его экземпляр. Навык «программист»
хочет **два** MCP-сервера — документацию библиотек и GitHub, — по конкретным адресам и не со всеми их
тулами. Из кода `mcp` этого не вывести: мастер подключения на фронте не знает, какой сервер
предложить, какие поля заполнить и что из тулов ограничить. Документ о том, как навык описывает
свои требования точно, и что из этого бэкенд отдаёт мастеру.

Что должно получиться на фронте: пользователь привязывает навык к агенту, и мастер по очереди
показывает, что навыку нужно, — «нужен MCP-сервер Context7 по такому-то адресу: у вас он уже есть,
привязать?» или «создайте: адрес подставлен, введите токен» — а в конце ставит на привязку правила
доступа, которые автор навыка счёл нужными.

## Что есть сейчас и где не сходится

- `skills.connector_codes text[]` — список кодов. Ссылка навыка `agent_skill_connections` уникальна по
  `(agent_skill_id, connector_code)`: модель строилась под **один экземпляр на код**, и именно это
  больше не подходит — два MCP-сервера в одном навыке в неё не помещаются.
- Параметров у объявления нет. У MCP-экземпляра идентичность — `sub_code` = URL сервера
  (`IntegrationValidationResult.identifier`), поля формы описаны `CredentialField` (`url`
  обязательный, `auth_token` секрет, `headers` JSON). Мастер мог бы подставить адрес, но навык его не
  сообщает.
- Правил доступа навык не несёт. ABAC (`agent_connection_policies`) живёт на привязке агента к
  коннекции, дефолт-allow, и колонка `source` там есть **с рождения, но не пишется нигде** — как раз
  под происхождение правила.
- «Навык удовлетворён» = у каждого кода выбран экземпляр и он привязан к агенту. Это остаётся: меняется
  только то, по какому ключу выбирается экземпляр. (Позже, 2026-09-13, признак расширен состоянием
  экземпляра — живая авторизация и непустой набор тулов у DYNAMIC, — и у неудовлетворённого требования
  появилась причина: `AgentSkillService.RequirementState`. См. «Почему навык не доехал» ниже.)

## Решение

### Формат объявления

Элемент `connectors` — либо строка (как сегодня, короткая форма), либо объект:

```yaml
---
name: coder
connectors:
  - persist-memory
  - code: mcp
    key: context7
    title: Context7 — library documentation
    params:
      url: https://mcp.context7.com/mcp
    tools:
      allow: [resolve-library-id, query-docs]
  - code: mcp
    key: github
    title: GitHub
    params:
      url: https://api.githubcopilot.com/mcp/
    tools:
      deny: [delete_repository]
  - code: mcp
    key: tracker
    params:
      url: https://mcp.example.com/tracker
    tools:
      allow: [search_issues, { name: create_issue, params: { owner: "agimate" } }]
---
```

| Поле | Смысл |
|---|---|
| `code` | код коннектора; обязателен |
| `key` | ключ требования внутри навыка; по умолчанию равен `code`, уникален в навыке. Именно на него ссылается `agent_skill_connections` |
| `title` | подпись требования для мастера; по умолчанию — `key`, если он задан, иначе имя коннектора |
| `params` | **несекретные** значения полей формы интеграции (`CredentialField`), которыми мастер предзаполняет создание экземпляра; у внутреннего коннектора формы нет, и `params` там — ошибка. Секретов в SKILL.md не бывает: поле типа `SECRET` отвергается при сохранении навыка |
| `tools`, `triggers` | правила доступа: ровно одно из `allow`/`deny` (оба сразу — ошибка разбора). Элемент `deny` — имя; элемент `allow` — имя или `{name, params}`, где `params` — `params_filter` строки |
  
Короткая форма `- mcp` эквивалентна `{code: mcp, key: mcp}` — старые навыки и старые ссылки
(`connector_code` = код) остаются верными без миграции данных. Парсер проверяет только форму
(`allow` xor `deny`, уникальность `key`); что `code` существует, что `params` есть только у интеграции,
только из её `CredentialField` и без `SECRET`-полей, знает лишь реестр коннекторов, поэтому эта проверка
живёт в `SkillService` — там, где сегодня проверяются коды. Сидер системных навыков идёт через ту же
проверку: ошибка в seed-файле роняет сидинг одного навыка с записью в лог, как любое исключение там.

Правила переводятся в строки ABAC буквально, в существующей модели: `allow: [a, b]` — binding-wide
`DENY` (`name IS NULL`) плюс `ALLOW` на `a` и `b`; `deny: [x]` — `DENY` на `x`; `params` элемента —
`params_filter` его строки. Одна строка на элемент, режим решает только про binding-wide `DENY`. Новой
семантики у правил нет: `ConnectionAccessEvaluator` и листинг доступного не меняются, навык лишь
добавляет строки в таблицу, которую они и так читают. Это и есть довод, что механизм один. Имена
тулов при сохранении навыка не проверяются: у MCP набор известен только у подключённого экземпляра.

### Хранение

`skills.connector_codes text[]` заменяется на `skills.connectors JSONB` — нормализованный массив
объектной формы (короткая форма разворачивается при разборе). Объявление — документ: приходит из
frontmatter целиком, редактируется целиком, версионируется вместе с `skills.version`; резать его на
таблицу `skill_connectors` (строка на требование, JSONB для правил внутри) — значит держать реляционную
оболочку вокруг того, что всё равно JSONB.

- `connectorCodes` в ответах API остаётся как производное (уникальные `code`) — клиенты, которым нужен
  только список кодов, не меняются.
- Фильтр `SkillSpecs.hasConnector` (листинг навыков и тул `platform`) переходит с `text[] @>` на
  containment `connectors @> '[{"code": ?}]'`, записанный функцией `jsonb_contains`, — оператор из
  criteria API не позвать, а функцию планировщик к индексу не привязывает, поэтому индекса нет:
  таблица маленькая, фильтр листинговый. Семантика та же — точное совпадение кода, а не подстрока;
  ловушка `varchar[]`, ради которой на колонке стоял `Length.LONG32`, исчезла вместе с колонкой.
- `agent_skill_connections.connector_code` → `connector_key`, ограничение
  `uq_agent_skill_connections_agent_skill_id_connector_key`. Данные не трогаются: у всех существующих
  навыков `key = code`.
- Фолбэк «ключ без своей ссылки» разрешается **по идентичности, когда она есть**: привязанные
  экземпляры кода, чей `sub_code` равен `identifierOf(params)`; без идентичности — все привязанные
  экземпляры кода, как сегодня. Иначе `context7` без ссылки получал бы и сервер GitHub, хотя
  требование знает, какой экземпляр имеет в виду, — план и рантайм отвечали бы на один вопрос по-разному.
- Тул `platform` для мета-агента, который привязывает навыки, продолжает работать: ключ равен коду у
  всех нынешних навыков.

### Почему навык не доехал (2026-09-13)

Признак «удовлетворён» был структурным: экземпляр выбран и привязан. Состояние самого экземпляра в него
не входило, и `findActiveBoundToAgent` смотрит только на `enabled`/`deleted_at` — поэтому экземпляр с
умершим OAuth (`AUTH_EXPIRED`) или недоведённым (`PENDING_AUTH`) проходил гейт: навык доезжал целиком, а
каждый вызов падал 401. Туда же MCP, у которого не удалось открытие тулов: `McpToolDiscoveryListener`
пишет ошибку в лог, в `connection_tools` пусто, тело навыка обещает тулы, которых нет ни одного. Обе
агентские поверхности — `McpToolCatalog.forAgent` и `AgentService.availableNames` — уже фильтровали по
`Connection.isUsable()`; до контекста прогона это решение просто не доехало.

Одновременно причина отсечения выбрасывалась: `complete` хранил `boolean`, и для агента навыка просто не
существовало. Сказать пользователю «я недонастроен» он не мог — ему нечем.

- `boolean complete` → `RequirementState` на ключ требования, считается один раз в
  `AgentSkillService.resolveSkills`. Читателей четыре: гейт прогона, каталог `<skills>`,
  `SkillConnectorStatus.state` (мастер и листинг) и `platform.list_agent_skills`. Листинг именно
  **читает** состояние, а не выводит `satisfied` заново, — расхождение листинга с рантаймом и есть то,
  против чего `resolveSkills` в своё время сводили в одно место.
- **Хватает одного пригодного экземпляра.** Там, где требование называет экземпляр, кандидат и так
  один; там, где не называет, фолбэк означает «любой привязанный экземпляр этого кода» — и требовать
  пригодности от всех значило бы отключать навык из-за одного сломанного телеграма из двух. Тулы при
  этом открываются только у пригодных. Причина, когда пригодных нет, — причина кандидатов, в порядке,
  в котором это чинит пользователь: нет ответа на требование (`NOT_CHOSEN`) → не привязан
  (`NOT_BOUND`) → авторизация мертва (`UNAUTHORIZED`) → экземпляр не принёс ничего (`NO_CAPABILITIES`).
  Сообщать о мёртвом токене на ещё не привязанном экземпляре бессмысленно.
- `NO_CAPABILITIES` — «ни тулов, ни триггеров». Обе половины нужны: `app` тоже DYNAMIC, и приложение,
  которое только шлёт события, не сломано.
- `Connection.isUsable()` применяется поверх `boundIds`, **не** правкой SQL в `findActiveBoundToAgent`:
  сломанную строку нужно загрузить, чтобы про неё рассказать, а джоба обновления токенов обязана видеть
  именно сломанные. В `RunCatalog.collectTools` предиката намеренно **нет**: там проходят коннекции мимо
  гейта навыков (коннекция события при `ownConnectionTools`, канал с тулами), сказать причину там нечем,
  а спрятанный тул уносит с собой единственное, что чинит ситуацию, — мёртвый грант MCP отвечает на
  вызов ссылкой на переавторизацию, которую агент передаёт пользователю.
- В `RunCatalog.Catalog` отсечённые лежат **отдельным полем**, а не состоянием внутри `skills`: все
  прочие читатели `skills()` (в том числе `SkillLoaderToolService`) означают «чем агенту можно
  пользоваться», и забытый там фильтр отдал бы тело отсечённого навыка через `load_skill`.
- Блок `<skills>` дополняется пояснением `run.skills-unavailable.guidance` — оно же говорит, когда об
  этом **не** заговаривать: постоянная заметка про недонастройку превращается в агента, который
  поминает её каждый ход.

Не сделано намеренно: разовые поломки в рантайме (5xx, таймауты) — `tool_call_logs.error` смешивает
деловые ошибки с транспортными, а самый частый случай (401 у MCP) и так становится `AUTH_EXPIRED`;
и уведомление пользователю вне диалога при смене состояния коннекции — оно дополняет, а не заменяет:
агенту в триггерном прогоне рассказать некому. Оба — в `roadmap.md`.

### Как мастер находит уже существующий экземпляр

У части интеграций идентичность экземпляра выводима из параметров без сети: у MCP это URL, у telegram —
нет (username бота узнаётся только у Telegram). Реализация пока одна, и метод в SPI оправдан лишь тем,
что иначе план и фолбэк содержали бы спецкейс `mcp`. В `IntegrationConnectorHandler` добавляется

```java
/** The would-be {@code sub_code} for these params, when it can be told without touching the platform. */
default Optional<String> identifierOf(Map<String, String> params) { return Optional.empty(); }
```

MCP прогоняет `params` через тот же `McpUtils.toServerConfig`, что и `validateCredentials`, и отдаёт
URL — нормализация (сейчас это `trim()`) живёт в одном месте, и сравнение с `sub_code` не разъедется.
Требование с известным идентификатором сопоставляется с коннекциями пользователя по
`(connector_code, sub_code)`; без идентификатора кандидаты — все экземпляры кода, как сегодня.

### Правила доступа: советующая модель

Навык **предлагает** правила, а ставит их пользователь — в момент привязки навыка. Бэкенд применяет
объявленные правила в `POST /agents/{id}/skills/` и `PUT /agents/{id}/skills/{skillId}/connections` (мастер
заканчивается одним из них) — для тех требований, чей экземпляр уже привязан к агенту. Процедура одна:

- желаемые строки выводятся из объявления, `source = skill:<id навыка>` — id, а не имя: имя
  уникально лишь в пределах владельца, и системный `coder` рядом с пользовательским `coder` на одном
  агенте делили бы одну строку `source`;
- строки с этим `source`, которых больше нет в объявлении, удаляются; желаемой строки нет — создаётся;
  есть со своим `source` — обновляется;
- есть с **чужим** `source` (пользовательская, `null`, или другого навыка) — **конфликт**, даже при
  одинаковом эффекте: строка не трогается и возвращается в ответе (`policyConflicts` у требования).
  Одинаковую строку можно было бы молча считать выполненной, но тогда зависимость второго навыка от
  строки первого была бы невидимой: отвязали первый — его binding-wide `DENY` ушёл, у второго остались
  одни `ALLOW`, то есть всё разрешено. Конфликт делает это видимым в момент привязки.

Та же процедура — в `POST /agents/{id}/skills/refresh`, и это меняет его смысл: сегодня он лишь снимает
`needsReinstall`, теперь это **сброс к правилам автора** — удалённая пользователем строка навыка
вернётся. Отвязка навыка удаляет строки с его `source`. `PATCH` правила пользователем **стирает
`source`** — строка стала его, и никакая логика навыка её больше не касается.

Продуктовое следствие, которое мастер должен показывать: `allow` в навыке — это `DENY` на всю
привязку агента к коннекции, и оно ограничит агента на этом сервере и там, где навык ни при чём
(прямой вызов, канал). В мастере это происходит один раз и на глазах у пользователя; именно поэтому
модель советующая, а постоянная реконсиляция — путь наверх, если понадобится.

### Что отдаёт бэкенд мастеру

`GET /manage/agents/{agentId}/skills/plan?skillId=…` — план привязки: по требованию на элемент
`key`, `connectorCode`, `internal`, `title`, `params`, поля формы интеграции (то же, что
`IntegrationMeta.credentialFields`), вычисленный `identity` (или `null`), `matches` — коннекции
пользователя, подходящие под требование, у каждой `boundToAgent`, и `policies` — строки, которые
будут поставлены. «Требование × агент» — одно понятие до и после привязки, поэтому элемент плана и
`SkillConnectorStatus` в листинге привязок — один и тот же record; после привязки у него заполнены
выбранный экземпляр, `satisfied` и `policyConflicts`. Дальше фронт идёт существующими эндпойнтами, и
**порядок обязателен**: создать
коннекцию (`POST /manage/connections/`, форма предзаполнена `params`) → привязать к агенту
(`POST /manage/agents/{id}/connections/`) → привязать навык, `connections` теперь по **ключу**
(`{"context7": "0198…"}`; для старых навыков ключ равен коду, так что нынешний payload фронта верен).
Правила требуют существующей привязки — на это и завязан порядок. Привязка навыка **без** выбора
внешнего экземпляра не ошибка, а неудовлетворённая привязка: так агент создаётся из пресета, у
которого навык требует MCP-сервер, и мастер потом доделывает; фолбэк по идентичности закроет
требование и без `PUT connections`, как только объявленный сервер привязан к агенту, — но правила
лягут только после `PUT connections` или `refresh`, потому что пишутся по ссылке.

Изменения в ответах: `SkillResponse`/`SkillDetailResponse` получают `connectors` (объектная форма),
`SkillConnectorStatus` — `key`, `title`, `policyConflicts`. `PUT /manage/skills/{id}/connectors`
принимает объектную форму. Пресеты ссылаются на навыки по именам; мастер на создании агента из
пресета — тот же план по каждому навыку, отдельной механики не нужно.

## Отвергнутое

- **Реконсиляция правил** — пересчитывать желаемое множество как объединение по всем навыкам агента на
  этой коннекции и применять при каждом bind/unbind, включая привязку коннекции к агенту. Две причины
  против: слой коннекций начинает звать слой навыков (новое направление зависимости, которого в коде
  нет), и binding-wide `DENY` возникал бы молча, всякий раз как появляется привязка, — а не один раз в
  мастере. Остаётся путём наверх.
- **Навык сам создаёт коннекции и привязки.** Инвариант «навыки не привязывают и не отвязывают»
  держит ABAC осмысленным: доступ выдаёт человек. Мастер — это и есть человек, с подсказками.
- **Секреты в SKILL.md.** Навык публичен по замыслу; `params` тоже видны всем читателям навыка —
  адрес приватного сервера в публичном навыке остаётся на совести автора, а токен туда не попадёт по
  формату.
- **Правила навыка в момент вызова.** `ConnectionAccessEvaluator.evaluate(agentId, connectionId, kind,
  name)` не знает, через какой навык тул попал агенту, и узнавать не должен: тул одной коннекции могут
  принести два навыка. Второй механизм рядом с ABAC — гарантированный разъезд.

## Следствия и ловушки

- **Seed-only-if-missing.** На уже засеянных установках системные навыки сохранят старые объявления;
  формат совместим, так что ничего не ломается, но добавленное автором требование MCP до них не
  доедет — известная ловушка SKILL.md, здесь она впервые касается не текста, а поведения мастера.
- Изменение `connectors` поднимает `skills.version` → `needsReinstall` → `refresh` переприменяет
  правила (см. процедуру выше).
