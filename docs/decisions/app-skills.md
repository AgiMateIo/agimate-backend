# Навык, который приносит подключённое приложение

Сегодня `app` — единственный код коннектора для всех приложений: desktop-агент, Android-приложение,
браузерное расширение, сторонний коннектор заводят строку `apps` с одним и тем же
`connector_code = app`. Экземпляр знает про себя только то, что прислал при линковке: `deviceId`,
`deviceName`, `deviceOs`, произвольную карту `deviceFeatures` и объявленный каталог
`tools`/`triggers`. Ни кодового имени приложения (desktop / chromium / photoshop), ни его
человекочитаемого названия, ни версии клиента на бэкенде нет.

При этом тулы попадают в контекст рана только через навыки: `RunCatalog.collectTools` берёт
инструменты коннекшенов, на которые указывают привязанные к агенту навыки (плюс канал и событие
триггера). Системного навыка с `connectors: [app]` не существует, поэтому подключённое приложение
агенту недоступно, пока пользователь не напишет свой навык. Но разные приложения умеют разное, и
один общий текст им не подходит.

Документ о том, как приложение называет себя, приносит свой навык при подключении, и как этот навык
привязывается ровно к своему экземпляру. Текст приложения хранится в `apps.skill` и обновляется до
первой правки пользователя; после правки главнее пользователь. Схема запросов и ответов здесь не
дублируется — точные поля генерируются из кода и видны в OpenAPI (`/control/docs/ui`).

## Что есть сейчас

- `StaticConnector.APP` — единственная строка каталога с кодом `app` и `execution_kind = APP`:
  исполняет само приложение, вызов уходит push-сообщением в канал `app:{appId}`, результат
  приходит отдельным HTTP-запросом. Обработчика у кода нет — это чистая запись каталога.
- Строка `apps` — это ключ доступа, а не описание приложения: `name` и `description` вводит
  пользователь при создании ключа, `deviceId`/`info`/`triggers`/`tools` появляются при линковке.
  Из `name` строится `sub_code`, а из него — `full_code = app_<slug>`: клиентский handle и
  namespace тулов (`app_moy_noutbuk.screenshot`).
- `POST /app/registration/link` объявляет устройство и каталог `tools`/`triggers`; каталог
  заменяется целиком при каждом вызове. Другой `deviceId` для того же ключа — `409`.
- Навык сопоставляется с экземпляром по `code` и открытой части подключения
  (`params ⊆ connections.params`). У `app` открытой части нет, поэтому навык с `connectors: [app]`
  подходил бы к любому приложению — и к desktop, и к chromium. Ссылка
  `agent_skill_connections` уточняет экземпляр, но её ставит пользователь или мастер, а не
  приложение.
- `apps.name` — метка экземпляра, а не идентичность приложения; `deviceOs` — операционная система
  устройства, а не семейство клиента. Различить «desktop» и «chromium» на бэкенде нечем.

## Разбор по ТРИЗ

Документ начат с разбора по ТРИЗ; он изменил исходное предложение в нескольких местах — они собраны
в «Что разбор изменил».

### Идеальный конечный результат

Приложение само приносит навык; платформа не знает его типа; пользователь не пишет текст; навык
привязан ровно к своему экземпляру; текст остаётся свежим, пока пользователь его не правил; правки
пользователя не теряются.

### Ресурсы

| Ресурс | Какую функцию может взять | Использован |
|---|---|---|
| `POST /app/registration/link` | идемпотентная самодекларация при подключении | да |
| `connections.id = app.id` | стабильная идентичность экземпляра | да |
| `connection_tools`/`connection_triggers` | динамический каталог тулов и триггеров | да |
| `skills` + `agent_skill_connections` | гейт «навык → экземпляр» и явная ссылка | да |
| `full_code`/`sub_code` | namespace тулов и клиентский handle | да |
| `Skill.version` + `AgentSkill.installedSkillVersion` | версия текста и `needsReinstall` | да, новое |
| `apps.tools`/`triggers` JSONB | образец хранения объявленного приложением в БД | да, новое: `apps.skill` |
| `apps.version` | версия клиента как источник версии текста | да, метаданные |
| `connections.params` | существующее сопоставление навыка и подключения | нет: синтетический `appId` отвергнут |
| `RunBlock.untrusted` | недоверенный рендер текста приложения | нет: отложено |
| `ContentLanguage` | язык тела навыка | да, метаданные |
| `App.enabled`/`Connection.enabled` | состояние «выключено» | да, синхронизировать |

### Противоречия

**ТП-1. Конкретность против открытости.** Навык должен быть про конкретное приложение, но платформа
не должна вести закрытый перечень приложений: пользователи подключают Photoshop, домашнюю
автоматизацию, что угодно ещё.

Разрешение — **разделить тип и экземпляр** (принципы 1 «дробление», 3 «местное качество»): код
приложения объявляет сам клиент свободной строкой (`apps.code`), экземпляр — это `connection.id`,
а навык привязан к экземпляру через `origin_connection_id`. Платформа не ведёт словарь, клиент
называет себя сам.

**ФП-1. Приложение против пользователя.** Навык должен быть приложением (его текст, его правда) и
должен быть пользователем (владение, правки, удаление).

Разрешение — **разделение во времени** (принцип 10 «предварительное действие»): приложение приносит
текст при линковке, пользователь владеет копией после; первая же правка пользователя останавливает
обновления приложения.

**ФП-2. Экземпляр против лишней связи.** Навык должен выбирать ровно свой экземпляр, но не должен
плодить второй механизм «какой экземпляр».

Разрешение — **пара ссылок на разных уровнях**: `origin_connection_id` — на уровне навыка (кто его
породил), `agent_skill_connections` — на уровне привязки к агенту (кто его использует). Они живут в
разных жизненных циклах; привязка форсирует ссылку на origin, поэтому расходиться им негде.

**ТП-2. Свежесть против стабильности.** Текст должен обновляться вместе с приложением, но правки
пользователя не должны затираться.

Разрешение — **обновление до первой правки**: `apps.skill` хранит последнее объявление приложения;
пока `skills.updated_by = APP`, линковка копирует его в навык и поднимает `Skill.version`; после
первой правки (`updated_by = USER`) приложение пишет только `apps.skill` и не трогает навык.
Принцип 9 «предварительное антидействие»: признак `updated_by` ставится в момент правки, до
следующей линковки.

**ТП-3. Линковка против валидности.** Устройство должно подключиться, а ошибка в тексте навыка
должна быть видна.

Остаётся компромиссом: невалидный блок `skill` блокирует всю линковку. Это осознанно — иначе
приложение молча остаётся без навыка, и причину не видно. Цена названа в «Следствиях»: баг клиента
в тексте отключает приложение до исправления.

**ФП-3. Один язык против локализации.** Текст должен быть один на все каталоги и должен быть на
языке пользователя.

Разрешение — **язык как метаданные, а не фильтр владельца**: приложение объявляет
`skill.language`; бэкенд хранит его в `apps.skill.language`, а `Skill.language` оставляет `NULL`,
чтобы пользователь видел все свои навыки в любом каталоге. Многоязычное приложение присылает тело
на текущем языке; пока навык не правили, копирование обновит его.

**ФП-4. Имя подключения.** Метка пользователя и название приложения — два владельца одного поля.
Принято: `connection.name` следует за `title`, пользовательское переименование перезаписывается при
следующей линковке. Если станет мешать — хранить метку отдельно (вне рамок).

**Доверие к тексту приложения.** Текст приходит от клиента, но `RunContextService` рендерит тело и
описание навыка доверенным блоком. Отдельного недоверенного рендера в первой версии нет; это
осознанное ограничение, вынесенное в «Вне рамок».

## Что разбор изменил

1. **Текст приложения хранится в `apps.skill`, навык — его пользовательская копия.** Пока копию не
   правили, она обновляется с приложением. «Первый текст навсегда» отменён.
2. **`skills.updated_by` вместо boolean-флага.** Значение `APP` или `USER` говорит, кто последним
   менял содержимое; обновление приложения разрешено только при `APP`.
3. **Язык — метаданные.** `apps.skill.language` описывает язык тела; `Skill.language = NULL`, чтобы
   владелец видел навык в любом каталоге.
4. **`apps.name` → `apps.code`.** Код приложения — не метка экземпляра; `Skill.name` остаётся кодом
   навыка и не переименовывается.
5. **`origin` осознанно вместо `params`.** Синтетический `appId` в `connections.params` отвергнут:
   это открытое редактируемое поле учётных данных, а не идентичность.
6. **Нет старых клиентов и нет запасного навыка.** Нет блока `skill` — нет навыка и тулов;
   протокол требует новые блоки.

## Решение

### Идентичность приложения: `code`, `title`, `version`

Кодовое имя приложения объявляет сам клиент при линковке. Никакого закрытого перечня нет:
пользователи подключают свои приложения-коннекторы (Photoshop, домашняя автоматизация, что угодно
ещё), и платформа не должна знать их заранее.

- `apps.code` — код приложения: `desktop`, `chromium`, `photoshop`. Свободная строка в kebab-case
  (`^[a-z0-9]+(-[a-z0-9]+)*$`), до 48 символов, до линковки `NULL`. Это идентичность типа
  приложения, а не метка экземпляра. Поле переименовано из `apps.name`; у строки, подключённой до
  этой работы, там лежит прежняя метка, пока клиент не пришлёт блок `app`.
- `apps.title` — человекочитаемое название (`AgiMate Desktop`), его объявляет клиент.
- `apps.version` — версия клиента. Обязательна вместе с блоком `app` и обновляется каждым линком;
  в первой версии это метаданные для интерфейса и поддержки, логика на них не опирается.
  Обязательность даёт ещё и признак переходной строки: у приложения, которое ещё не присылало блок,
  `title` и `version` пусты.

Пользовательской метки экземпляра больше нет: ключ создаётся без имени, до линковки в списке он
«приложение не подключено», после — `title` + `deviceName`/`deviceOs`. `description` остаётся
заметкой пользователя. Уникальность `apps.code` на пользователя снимается: два desktop-ключа —
нормальный сценарий. Уникальности `apps.name` в БД и не было — её держал только
`AppRepository.existsByUserIdAndName`; проверка удаляется.

Для приложений, подключённых до этой работы, `apps.code` продолжает хранить старую метку, пока
клиент не пришлёт блок `app`. Признак переходной строки — пустые `title` и `version`: первый блок
`app` их ставит и перезаписывает `code`. Это переходное состояние, а не два разных поля: смысл
колонки — код приложения. Если приложений в проде мало и старых клиентов нет, первая миграция может
перенести старую метку в `description`/`title` — решает миграция, не код.

### Namespace: из кода, один раз

`full_code` нового подключения вычисляется при первом линке с блоком `app`:
`app_<slug(code)>`, при коллизии — `app_<slug>_2`; `sub_code` — `slug(code)`. `FullCodes.slug`
заменяет дефисы на подчёркивания, поэтому для кода `my-app` namespace — `app_my_app`, а имя
навыка — `app-my-app`. До линковки у connection стоит placeholder `app_<appId>`: тулов ещё нет,
переименование безопасно.

`AppService.createApp` обязан ставить этот placeholder явно. Если оставить `FullCodes.slug("app",
null)`, он вернёт `"app"`, `full_code` станет `app_app`, и второе неслинкованное приложение упадёт на
уникальности `(full_code, user_id)` среди живых строк.

Существующие подключения свой namespace не меняют. Переименование тулов сломало бы ABAC-правила,
историю вызовов и навыки, которые ссылаются на имена, — цена не оправдана. Смена `apps.code` после
первого линка игнорируется с записью в лог: код запечён в namespace и в имя навыка.

### Приложение приносит навык

Линковка получает два необязательных блока рядом с `tools`/`triggers`:

- `app` — `code`, `title`, `version` (описаны выше);
- `skill` — `title`, `description`, `body`, `starters`, `language`.

Всё в одном вызове, потому что `POST /app/registration/link` уже является самодекларацией
приложения в момент подключения. Вызов идемпотентен и повторяется при каждом старте приложения:
оборвавшаяся связь не теряет навык, следующий старт повторит объявление. Отдельный
`PUT /app/skill` пришлось бы не забыть вызвать, а «бэкенд сам запросит у приложения» не работает:
приложение — клиент за WebSocket и часто офлайн.

`apps.skill` (JSONB) хранит **последнее** объявление приложения — `{title, description, body,
starters, language}`. Это тот же приём, что `apps.tools`/`triggers`: приложение объявляет, бэкенд
хранит. Строка `skills` — пользовательская копия; пока её не правили, она обновляется из
`apps.skill`.

Приложение не объявляет имя навыка, `connectors`, `category`, `is_public` — это решает бэкенд. Иначе
пришлось бы валидировать попытку объявить чужой коннектор (`platform`, `files`) или опубликовать
навык от имени пользователя. Бэкенд ставит:

| Поле | Значение |
|---|---|
| `name` | `app-<code>`, при коллизии с другим навыком пользователя — `app-<code>-2`, затем `-3` |
| `title` | `skill.title`, иначе `app.title`, иначе `app.code` |
| `description` | `skill.description` — обязателен: без него lazy-навык не виден в каталоге |
| `md_content` | `skill.body` — тело инструкции |
| `starters` | `skill.starters`, если пришли (проверяются `StarterTexts`) |
| `connectors` | принудительно `[app]` |
| `category` | `PLATFORM` |
| `disclosure` | `LAZY` — тело не едет в промпт сразу, в каталоге работает описание |
| `language` | `NULL` — пользовательский навык виден владельцу во всех каталогах |
| `is_public` | `false` |
| `user_id` | владелец приложения |
| `origin_connection_id` | id этого подключения |
| `updated_by` | `APP` — текст пришёл от приложения, а не от пользователя |

Счётчик имени — через дефис, не `_2`: имя навыка — kebab-case (`SkillService.NAME_SLUG`),
`app-<code>_2` не пройдёт валидацию. Суффикс остаётся на всю жизнь навыка.

`Skill.language` остаётся `NULL`, а язык тела приложения хранится в `apps.skill.language` как
метаданные. Пользователь видит все свои навыки вне зависимости от выбранного языка интерфейса:
`scope=MINE` и `scope=ALL` не фильтруют свои навыки по языку (`SkillSpecs.visibleTo` — это
`ownedBy(userId) OR public+inCatalogue`); публичным origin-навык не бывает. Многоязычное приложение
присылает тело на текущем языке; пока навык не правили, копирование обновит его.

Навык создаётся **один раз** — на первом линке, несущем блок `skill`, если у подключения ещё нет
навыка с таким origin (включая soft-deleted). Если блока `skill` нет, навык не создаётся и тулы
приложения недоступны, пока пользователь не напишет свой: запасного общего навыка нет.

### Обновление текста: до первой правки

`apps.skill` пишется при каждой линковке с блоком `skill`. Если у подключения есть живой
origin-навык и `updated_by = APP`, бэкенд копирует в него `title`/`description`/`md_content`/
`starters` и поднимает `Skill.version`; `AgentSkill.installedSkillVersion` показывает агенту и
пользователю, что текст обновился (`needsReinstall`). Если `updated_by = USER`, приложение пишет
только `apps.skill` и не трогает навык.

Любая пользовательская правка — полный SKILL.md (`SkillService.update`) или только требования
(`SkillService.updateConnectors`) — ставит `updated_by = USER`. После этого приложение не
перезаписывает навык. Если пользователь удалил навык, приложение его не воскрешает: soft-deleted
строка с тем же origin блокирует повторное создание; `apps.skill` продолжает обновляться, но никем
не читается. Свою инструкцию пользователь может написать отдельным навыком.

### Перелинковка

| Сценарий | Что происходит |
|---|---|
| Тот же `deviceId`, тот же каталог | каталог `tools`/`triggers` заменяется, как сейчас; `title`/`version` освежаются; `apps.skill` обновляется; при `updated_by=APP` навык обновляется, при `USER` — нет |
| Тот же `deviceId`, новый `title`/`version` | метаданные обновляются; каталог заменяется; `apps.skill` обновляется; навык — по `updated_by` |
| Тот же `deviceId`, другой текст навыка | `apps.skill` обновляется; при `updated_by=APP` навык обновляется, при `USER` — игнорируется |
| Блок `skill` не пришёл | `apps.skill` не меняется; существующий навык остаётся |
| `apps.code` изменился | игнорируется с WARN: код уже в namespace и в имени навыка; побеждает первое значение |
| Пользователь удалил навык | не воскрешаем; приложение работает без навыка |
| Другой `deviceId` | `409`, ничего не меняется |
| Перевыпуск ключа | ничего: ключ — только аутентификация |
| Приложение удалено и создано заново | новый `app.id` → новое подключение, новый origin и новый навык; старый уходит вместе с приложением |

### Origin — это выбранный экземпляр

`skills.origin_connection_id` — не только пометка происхождения, а селектор экземпляра. Навык от
app A должен матчиться только к app A: иначе он появится на странице app B и подхватит чужие тулы.

- `AgentSkillService.resolveInstances` разрешает требование такого навыка в **ровно это
  подключение**, как если бы для него была явная ссылка `agent_skill_connections`. Дальше работает
  существующая машина состояний: подключение не привязано — `NOT_BOUND`, выключено или
  авторизация мертва — `UNAUTHORIZED`, ничего не объявило — `NO_CAPABILITIES`.
- `SkillSpecs.fitsConnection` добавляет условие `origin IS NULL OR origin = :connectionId`:
  обратный листинг `?connectionId=` показывает навык приложения только на странице его
  подключения.
- При привязке навыка к агенту (`AgentSkillService.create`/`updateConnectors`) ссылка форсируется
  на origin, как у внутреннего коннектора со строкой-режимом; чужое подключение в `requested` —
  `400`. Это держит в согласии `agent_skill_connections`, счётчик «сколько навыков смотрят на это
  подключение» и правила доступа навыка.
- `AgentSkillService.matches` для origin-навыка сужается до origin: иначе мастер предложит другое
  app-подключение, а привязка ответит `400`.
- Плана мастера это не ломает: origin виден как выбранный экземпляр, а если он не привязан —
  статус говорит `NOT_BOUND` и объясняет, чего не хватает.

`origin` — не новая ось в `ConnectorRequirement`, а парная ссылка к `agent_skill_connections`: одна
на уровне навыка (кто его породил), другая на уровне привязки к агенту (кто его использует).
Вариант с синтетическим `appId` в `connections.params` отвергнут — см. «Отвергнутое».

### Ограничения на origin-навык

Навык лежит в списке пользователя и принадлежит ему, но пришёл от приложения, поэтому заморожены:

- `connectors` — код требования только `app`; правила `tools`/`triggers` внутри требования
  пользователь менять может. Попытка объявить другой коннектор или убрать `app` — `400`. Проверка
  живёт в **обоих** путях: `SkillService.update` и `SkillService.updateConnectors` (отдельный
  `PUT /manage/skills/{id}/connectors` иначе обходит заморозку).
- `name` — `app-<code>` с суффиксом, не меняется: код запечён в имя навыка. Пользователь правит
  заголовок, тело, описание, стартеры, категорию и теги.
- `is_public = true` — `400`: у других пользователей нет этого origin-подключения, публичный навык
  был бы у них сломан.

`disclosure` пользователь может менять; значение по умолчанию — `LAZY`. `language` остаётся `NULL`.

### Удаление приложения

`AppService.deleteApp` после сворачивания подключения soft-delete'ит origin-навык через
`SkillService.delete`: навык отвязывается от агентов, его правила снимаются. Если навык уже
soft-deleted, шаг пропускается — иначе `SkillService.delete` ответит `404` на `findByIdNotDeleted`
и удаление приложения откатится. Отдельной уборки не нужно — это существующий путь удаления
пользовательского навыка.

Уборка живёт в этой одной рутине, и оба эндпоинта должны в неё попадать. Сейчас
`DELETE /manage/connections/{id}` для APP не падает: `integrationHandler` бросает
«Unsupported platform», это ловится в `try/catch` вокруг снятия вебхука, и строка connection
мягко удаляется — а строка `apps` остаётся. С origin-навыком этот путь оставил бы ещё и
осиротевший навык, поэтому для APP общий эндпоинт делегирует в `AppService.deleteApp`
(`connection.appId`): обе поверхности удаляют одно и то же.

### API и миграция

- `POST /manage/apps` (`CreateAppRequest`) теряет `name`: ключ создаётся без имени.
  `PUT`/`PATCH /manage/apps/{id}` (`UpdateAppRequest`) теряет `name` — идентичность приложения
  принадлежит клиенту; остаются `description` и `enabled`.
- `AppResponse`, `UserAppDetailResponse` и `AppCreatedResponse` получают `code` (бывший `name`) и
  `title`/`version`; до линковки `code`/`title`/`version` пусты.
- `SkillResponse` и `SkillDetailResponse` получают необязательный блок `origin`: id подключения, код,
  человекочитаемое имя и версия приложения, `deviceName`. Листинг собирает его пачкой (один запрос
  по connections, один по apps), одиночный ответ — одним.
- `LinkDeviceRequest` получает необязательные `app` и `skill`. Пришёл `skill` без `app` — `400`:
  имени навыка не из чего собрать.
- Миграция `updates/2026/11/01-00-app-skills.xml`: `apps.name` переименовывается в `apps.code` и
  становится nullable, добавляются `apps.title`, `apps.version`, `apps.skill` (JSONB);
  `skills.origin_connection_id` с внешним ключом на `connections(id)` и уникальным индексом;
  `skills.updated_by` (`APP`/`USER`, nullable для не-origin навыков). Уникальность origin включает
  soft-deleted строки — так удалённый навык нельзя создать заново. Backfill не нужен: у
  существующих навыков origin пуст, у существующих приложений старая метка остаётся в `code` до
  первого линка с блоком `app`.

### Валидация

| Поле | Правило |
|---|---|
| `app.code` | обязателен при наличии блока `app`; trim, нижний регистр, kebab-case (`NAME_SLUG`), 1..48 |
| `app.title` | необязателен, до 200 символов |
| `app.version` | обязателен при наличии блока `app`, до 64 символов |
| `skill.title` | необязателен, до 200 символов |
| `skill.description` | обязателен, 1..2000 символов |
| `skill.body` | обязателен, 1..32768 символов |
| `skill.starters` | существующее правило `StarterTexts` (не больше 5) |
| `skill.language` | необязателен, значение `ContentLanguage`; хранится в `apps.skill.language` |

`app.code` длиной до 48, а не 64: `FullCodes.slug` укорачивает до `MAX_SLUG_LENGTH = 48`, и
namespace перестал бы совпадать с кодом. Регулярка `NAME_SLUG` не допускает `desktop-` и `a--b` —
иначе имя навыка `app-<code>` не прошло бы `SkillService.validateName`.

Пришёл, но невалиден — `400` с внятным сообщением: это баг клиента, и молча его проглатывать
нельзя. Цена: невалидный блок `skill` блокирует линковку, приложение не подключается, пока клиент
не исправит. Блоков нет — линковка работает как раньше, но навыка и тулов нет.

Текст навыка — недоверенный ввод клиента. Он ограничен владельцем, принудительным `[app]`, запретом
публикации и origin-привязкой: до агентов, где не привязано это приложение, он не доезжает.
Поверхность prompt-injection здесь того же класса, что у пользовательских навыков и описаний тулов
приложения; пометка происхождения делает авторство видимым. Отдельный недоверенный рендер — вне
рамок первой версии (см. «Следствия и ловушки»).

## Отвергнутое

- **`kind` с закрытым перечнем (`desktop|android|chromium`).** Набор приложений открыт:
  пользователь подключает Photoshop или собственный коннектор, и платформа не может вести
  закрытый словарь. Кодовое имя, которое объявляет клиент, — та же ось, но без перечня.
- **Отдельные коды коннекторов на семейство (`app-desktop`, `app-android`).** Заставляют
  пользователя выбирать «какое у вас приложение» до того, как клиент что-то сказал, и плодят
  строки каталога. Навык теперь всё равно принадлежит экземпляру.
- **`sub_code` как носитель семейства.** `sub_code` — производный handle экземпляра: из него
  считается `full_code` и namespace. `sub_code = desktop` даёт один desktop-ключ на пользователя
  (второй упрётся в коллизию `app_desktop`), а `desktop_<имя>` — разбор строки префиксом; навык
  всё равно не видит `sub_code`.
- **Хранить текст навыка только в клиенте.** Раны асинхронные, приложение часто офлайн;
  `tools`/`triggers` уже копируются при линковке по той же причине. Текст живёт в `apps.skill` в
  БД, а не только в приложении.
- **`apps.skill_id` — обратная ссылка на навык.** `skills.origin_connection_id` уже даёт связь
  «навык → приложение» (уникальный origin). Второй указатель пришлось бы ставить при создании,
  чистить при удалении и держать в согласии; он не даёт ничего, чего не даёт origin.
- **`params` с синтетическим `appId`.** Переиспользует существующее сопоставление
  (`connections.params @> params`), но делает внутреннюю идентичность открытым редактируемым полем:
  `params` — часть формы учётных данных, у `app` формы нет, `SkillService.validateConnectors`
  запрещает там `params`; пользователь или копия навыка могли бы поменять `appId`. `origin` — FK,
  который ставит бэкенд и который пользователь не редактирует.
- **Автопривязка навыка при привязке подключения.** Пользователь привязывает навык сам: платформа
  остаётся с явной моделью «навыки привязок не создают».
- **Обновлять текст навыка, который пользователь уже правил.** Первая правка ставит
  `updated_by = USER`; после неё приложение пишет только `apps.skill`. Обновление до первой правки
  принято — см. «Обновление текста».
- **Отдельный `PUT /app/skill`.** Линковка и так идемпотентная самодекларация; второй вызов можно
  забыть.
- **Публикация origin-навыка.** У других пользователей нет этого origin-подключения — навык был бы
  сломан.
- **Воскрешать удалённый навык при следующем линке.** Удаление — решение пользователя.

## Вне рамок

- Недоверенный рендер текста приложения: сейчас тело и описание рендерятся как доверенный
  пользовательский блок; для приложений третьих сторон нужен отдельный режим или подтверждение.
- Ручной сброс пользовательского навыка к тексту приложения (`updated_by` обратно в `APP`).
- Многоязычное приложение с несколькими телами: сейчас одно тело и метаданные языка.
- Группировка нескольких приложений одного кода в интерфейсе сверх `deviceName`.
- Переименование namespace существующих подключений под новую схему.
- Реализация в самих клиентах (`connector-desktop`, `connector-android`, `connector-chromium`) —
  сначала бэкенд, затем дельта протокола для них в `docs/tmpspec/` и правки в репозиториях
  клиентов.

## Следствия и ловушки

- **Каталог смешанных namespace.** Старые подключения остаются на `app_<метка>`, новые — на
  `app_<slug(code)>`. Имена тулов стабильны для каждого подключения, поэтому это не ломает ABAC и
  историю, но в интерфейсе и логах какое-то время видны оба вида.
- **`apps.code` у старых строк — метка, а не код** до первого линка с блоком `app`. API
  документирует поле как код; переходное расхождение исчезает само после обновления клиента.
- **Origin-навык можно привязать к агенту без привязанного приложения** — он будет `unavailable`
  с причиной `NOT_BOUND`, пока подключение не привязано. Это существующая история мастера, не
  новая ошибка.
- **Приложение не перезаписывает правленный навык.** Неотредактированный обновляется при
  линковке; правленный — нет. После обновления клиента текст остаётся свежим, пока пользователь не
  внёс правку.
- **Один язык тела.** `apps.skill.language` — метаданные; `Skill.language = NULL`, поэтому
  владелец видит навык в любом каталоге. Текст при этом один; многоязычное приложение присылает
  тело на текущем языке, и оно обновляется, пока навык не правили.
- **Имя `app-<code>` может совпасть с навыком пользователя** — создание добавляет суффикс `-2`,
  затем `-3`; суффикс остаётся на всю жизнь навыка. `_2` не подходит: имя навыка — kebab-case.
- **Уникальный origin включает soft-deleted строки**: приложение не сможет создать второй навык
  для того же подключения даже после удаления первого. Пользователь может написать свой.
- **`connections.name` у приложения следует за `title`** и обновляется при линковке; ручное
  переименование на странице подключения будет перезаписано при следующем старте приложения.
  Если это окажется мешающим, имя перестанем синкать и будем собирать в интерфейсе.
- **Строгая валидация блока блокирует линковку.** Это намеренно: иначе приложение молча остаётся
  без навыка, и причину не видно. Цена — баг клиента в тексте отключает приложение до исправления.
- **Общий путь удаления APP-подключения сегодня оставляет строку `apps`**: ошибка «Unsupported
  platform» глотается в `try/catch` вокруг снятия вебхука, и connection мягко удаляется один.
  С origin-навыком этот путь оставил бы и навык; поэтому общий эндпоинт для APP делегирует в
  `AppService.deleteApp`. Если делегирование не сделать, появится второй, неполный путь удаления.
- **`updated_by` — консервативный признак.** Любая правка навыка пользователем, включая правку
  только правил доступа, останавливает обновление текста приложением. Если понадобится обновлять
  текст после правки только правил, нужен отдельный признак — в первой версии не заводим.
- **`App.enabled` и `Connection.enabled` — два флага.** `UpdateAppRequest.enabled` меняет
  `App.enabled`; `RequirementState` смотрит на `Connection.isUsable`. Если их не синхронизировать,
  origin-навык покажет `OK` при выключенном приложении. `AppService.updateApp` должен обновлять и
  `Connection.enabled`, либо состояние origin должно проверять `App.isActive`.
- **`AppService.createApp` без placeholder.** Если не поставить `app_<appId>` явно, два
  неслинкованных приложения получат `full_code = app_app` и второе упадёт на уникальности.
- **`AppCreatedResponse` и `SkillDetailResponse`.** Первый отдаёт `code` (до линковки пустой),
  второй получает `origin`; иначе страница деталей не покажет происхождение.
- **Приложение не знает итоговый namespace при коллизии.** Второе приложение с тем же кодом
  получит `app_<slug>_2`; тело навыка, написанное до линка, может ссылаться на `app_<slug>`. Тело
  должно использовать короткие имена тулов; либо ответ линковки должен возвращать итоговый
  `full_code`.
- **Текст приложения получает доверие пользовательского навыка.** `RunContextService` рендерит
  тело и описание навыка доверенным блоком; отдельного недоверенного рендера для origin-навыков в
  первой версии нет. Пользователь подключил приложение и может прочитать/отредактировать навык,
  поэтому это осознанное решение; для приложений третьих сторон — отдельная задача.
