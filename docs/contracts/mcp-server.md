# MCP-сервер

Платформа отдаёт тулы агента наружу по Model Context Protocol: внешний AI-клиент (Claude Code,
Cursor, свой скрипт) подключается к `https://<host>/mcp` и получает те же инструменты, что есть у
агента, под теми же политиками.

## Модель: MCP-агент — это агент, у которого мозг снаружи

Отдельной сущности «ключ к MCP» нет. Субъектом прав остаётся агент: коннекшены к нему привязаны
(`agent_connections`), политики уточняют доступ (`agent_connection_policies`), а MCP — это
поверхность, на которой его ключ работает. Выбор «какие коннекшены отдать наружу» делается там же,
где и для любого агента, — привязками и политиками.

Тип `MCP` (см. [api-keys.md](api-keys.md)) говорит ровно одно: **push-транспорта нет**. Мозг тянет
работу сам, поэтому триггеров и каналов у такого агента не бывает. Во всём остальном он не отличается
от `CENTRIFUGO` и `WEBHOOK` — и `/mcp` открыт всем трём внешним типам: это один и тот же внешний мозг,
просто с разной дверью для входящих. Закрыт `/mcp` только для `GENERIC`: там цикл уже крутит наш
воркер, и внешний клиент был бы вторым мозгом на одной памяти.

## Ревизия и транспарент

Поддерживается **только `2026-07-28`** и только его stateless-форма.

| | |
|:--|:--|
| Эндпойнт | `POST /mcp` — один JSON-RPC запрос на запрос (батчи из протокола убраны) |
| Аутентификация | `Authorization: Bearer <ключ агента>`; принимается и legacy-заголовок `X-Api-Key` |
| `GET` / `DELETE` | `405` — потоков и сессий нет |
| `Mcp-Session-Id`, `Last-Event-ID` | игнорируются: не выдаются и не отражаются |
| `MCP-Protocol-Version` | если прислан и не равен `2026-07-28` — `400` |
| Методы | `server/discover`, `ping`, `tools/list`, `tools/call`, `tasks/get`, `tasks/update`, `tasks/cancel` |
| `initialize` | оставлен **сверх ревизии**: живые клиенты всё ещё открываются им; отдаёт те же капабилити, что и `server/discover` |
| `resultType` | во всех результатах, всегда `"complete"` — кроме `CreateTaskResult` с `"task"` |
| Нотификации (запрос без `id`) | `202`, без тела |

Ответы **не заворачиваются** в `SuccessResponse` — конверт здесь протокольный. Ошибки уровня
транспорта (401/403/429) остаются HTTP-ответами: клиент читает статус.

Осознанно не поддержано: сессии и возобновляемые SSE (их нет в ревизии), промпты, ресурсы,
пагинация листинга, уведомления `tools/list_changed` и `notifications/tasks` с
`subscriptions/listen` (без канала «сервер → клиент» их некуда послать — поллинг спека разрешает),
`input_required`/MRTR (нет тулов, спрашивающих клиента).

## Имена тулов

Клиент видит плоский список, поэтому имя строится как `<handle>__<тул>`. Хендл тот же, что в
контексте агента (`RunContextService.namespaceOf`): внутренний mode-коннектор называется **кодом**
(`platform__create_agent`, `time__schedule`), внешний экземпляр — `full_code`
(`mcp_context7__resolve-library-id`). Разделитель двойной, потому что одинарный `_` встречается
внутри `full_code`. Для внутренних коннекторов код вместо `code_<userId>`-хендла выбран намеренно:
хендл с uuid съедал бы половину лимита имени, и длинные админ-тулы (`list_llm_provider_models`)
усекались бы хвостом-хэшем.

Символы вне `[a-zA-Z0-9_-]` заменяются на `_` (function-calling API клиентов иначе имя не примут),
имя длиннее 64 символов усекается с хвостом-хэшем. Обратное преобразование не делается: вызов
разрешается через каталог, а не разбором строки. Если два имени схлопнулись в одно, второе в листинг
не попадает — об этом пишется `WARN` с обоими именами.

## tools/call

1. Лимит вызовов по агенту (`INBOUND_RATE_LIMIT_MCP_CALLS_PER_MINUTE`, по умолчанию 120/мин) —
   до обращения к базе; превышение → `429`.
2. Имя ищется в каталоге. Каталога нет — значит тула нет или он запрещён политикой; в обоих случаях
   `-32602 Unknown tool`, без объяснения причины.
3. `AgentToolCallService` создаёт `tool_call_logs` (идемпотентность по `(agent_id, external_id)`,
   `external_id` генерирует сервер) и применяет ABAC вместе с `params_filter`.
4. Бюджет ожидания зависит от клиента. Не объявивший расширение тасков ждёт **60 с**: по таймауту —
   `isError`, исполнение продолжается и дописывает результат в лог (для разговора он потерян).
   Объявивший ждёт **grace 10 с**, дальше вызов отдаётся таском — см. ниже.

Отказ политики на вызове и любая ошибка исполнения возвращаются как `isError: true` в успешном
JSON-RPC ответе: модель должна их увидеть и решить, что делать. Транспортная ошибка спрятала бы это.

Тул с объявленным `outputSchema` получает `structuredContent`; тот же payload дублируется текстом для
клиентов, которые структурированный вывод не читают.

## Таски (расширение `io.modelcontextprotocol/tasks`)

Server-directed, по спеке расширения: клиент объявляет капабилити в `_meta` **каждого** запроса
(`io.modelcontextprotocol/clientCapabilities.extensions`), сервер сам решает, отвечать ли таском.
Не объявившему таск не отдаётся никогда, а его `tasks/*` получают `-32003` с
`requiredCapabilities` в `data`. Почему так устроено — [../decisions/mcp-tasks.md](../decisions/mcp-tasks.md).

- **Таск — это строка `tool_call_logs`**: `taskId` = `external_id`, признак таска — `detached_at`.
  Состояния между запросами нет, отвечает любой узел; `Mcp-Name` принимается и игнорируется.
- **`tools/call`** объявившего клиента ждёт grace **10 с**; не уложившийся вызов отдаётся как
  `CreateTaskResult` (`resultType: "task"`, `status: "working"`, `ttlMs` 24 ч, `pollIntervalMs` 5 с).
  Тул, успевший на границе grace, выигрывает гонку штампа — клиент получает обычный результат.
- **Потолок — 10 живых тасков** на агента (детачнутых, не завершённых, не старше TTL), проверяется
  до старта вызова; превышение — `isError`, вызов не начинается.
- **`tasks/get`**: `working` → `completed` с инлайненным `CallToolResult` (включая `isError: true` —
  это по спеке `completed`, не `failed`; `failed` этот сервер не производит вовсе) или `cancelled`
  без результата. Чужой, неизвестный и не-детачнутый `taskId` неразличимы: `-32602`.
- **`tasks/cancel`** кооперативен: штамп `cancel_requested_at` ложится только пока вызов не
  завершён; исполнение не прерывается, статус остаётся `working` до конца, результат отменённого
  наружу не отдаётся. Отмена завершённого — пустой ack, таск остаётся `completed`.
- **`tasks/update`** отвечает пустым ack: `input_required` не производится.
- **TTL 24 ч**: после срока `tasks/get` отвечает `-32602 expired` (строка остаётся логом). Это
  единственный механизм против сирот — рестарт control-api убивает исполнение в полёте, и такой
  таск иначе вечно отвечал бы `working`.
- **Поллы лимитируются** отдельно от вызовов: `INBOUND_RATE_LIMIT_MCP_TASK_POLLS_PER_MINUTE`,
  по умолчанию 240/мин на агента — вдвое больше, чем даёт честный клиент при полном потолке.

## Администрирование платформы через /mcp

Внутренний коннектор `platform` (мета-агент, см. [../connectors/platform.md](../connectors/platform.md))
доступен и как MCP-поверхность: привяжите навык `platform` к агенту типа `MCP` (готовый набор — пресет `platform-admin`) — его клиент
получит те же тулы `platform`, что и мета-агент в чате, под теми же политиками (имена — по общей
схеме `<handle>__<тул>`, примеры: `platform__list_agents`, `platform__delete_agent`). Caller-
идентичность для этих тулов — `env.userId`, выводимый из владельца ключа агента (владелец ключа =
владелец операций), поэтому поверхность ограничена ресурсами владельца, как и в чате.

ADMIN-поверхность (`/manage/admin`: платформенный LLM-провайдер, create/update пресетов, системные
навыки) через `/mcp` не выставляется — ключ агента не доказывает ADMIN. Секреты через MCP не
ходят ни в одну сторону. Ключ агента, ключи LLM-провайдеров, `webhookAuthHeader` и креды
подключений заводятся и выдаются через deep-link в интерфейс, а не параметром и не в ответе
тула. Наружу отдаются только производные — `apiKeyMask`, `hasWebhookAuth`.

## Что стоит знать

- **Каталог собирается на каждый запрос** — состояния между запросами нет по устройству протокола.
  Дорогая часть (решения политик) закэширована внутри `ConnectionAccessEvaluator`.
- **Тулы с отложенной доставкой бессмысленны.** `time.schedule` и джобы коннекторов адресуют ответ
  агенту вне контекста вызова, а доставлять MCP-агенту некуда — результат будет выброшен в лог
  (таски покрывают только результат самого вызова). Такие коннекторы к MCP-агентам привязывать
  не нужно.
- **App-тулы через MCP не работают.** Вызов диспетчеризуется мимо развилки `execution_kind`
  (`pushToConnector`) — app-тул упадёт, не дойдя до приложения. Воронка результата к таскам уже
  готова, не хватает маршрутизации вызова; см. «отложено» в decision-файле.
- **Петля через собственный mcp-коннектор.** У платформы есть и клиентский коннектор `mcp`; ничто не
  мешает подключить им же наш собственный `/mcp`. `McpTargetGuard` ловит SSRF, но не «сам себя» —
  пока это ограничение договорённости, а не кода.
