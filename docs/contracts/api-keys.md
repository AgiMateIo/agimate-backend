# Формат ключа AGM

Единый позиционный формат для всех ключей, которые платформа выдаёт наружу. Источник истины —
`AppKeyUtils` (`services/control-api/src/main/java/ru/agimate/controlapi/util/AppKeyUtils.java`);
этот документ описывает формат, а не дублирует реализацию.

## Формат

```
agntZ3h5YWJjZGVlxQ8pJvLmN5rT3sU2vWxYzAbCdEfGhIjKlMnOpQrStUvWxYz
└──┘└──────────┘└──────────────────────────────────────────────┘
 4        12                          48
```

Без разделителей, ровно 64 символа, фиксированные позиции.

| Компонент | Описание                             | Длина | Позиция |
|:----------|:-------------------------------------|:------|:--------|
| `prefix`  | Тип ключа, 4 строчные латинские       | 4     | 0–4     |
| `keyid`   | Timestamp + random, для поиска в БД   | 12    | 4–16    |
| `payload` | Закодированные secret + checksum      | 48    | 16–64   |

## Префиксы

| Префикс | Назначение                           | Где хранится                            |
|:--------|:-------------------------------------|:----------------------------------------|
| `agnt`  | Ключ агента (один ключ = один агент)  | `agents.key_id` / `agents.key_hash`     |
| `appk`  | Ключ приложения                      | `apps.key_id` / `apps.key_hash`         |
| `wrkp`  | Authkey пула воркеров                | конфиг `worker-pools.authkeys`, не в БД |

Префиксы объявлены константами: `AgentService.AGENT_KEY_PREFIX`, `AppService.APP_KEY_PREFIX`,
`WorkerPoolRegistry.WORKER_POOL_KEY_PREFIX`. В тестах и javadoc встречаются `apik` и `dvck` —
это следы эпохи device-api, в рабочем коде такие ключи не выдаются.

## Генерация

```
prefix   = "agnt"                                            → 4 символа
keyid    = base64url(unix_timestamp_4b || random_5b)         → 12 символов
secret   = random(32 байта)
checksum = crc32(prefix || keyid || secret)                  → 4 байта
payload  = base64url(secret || checksum)                     → 48 символов

fullKey  = prefix + keyid + payload                          → 64 символа
```

`keyid` — 9 байт, кратно 3, поэтому base64url даёт ровно 12 символов без паддинга. Из него
извлекается время создания (не секрет), и ключи естественно сортируются по нему. Вероятность
коллизии в пределах одной секунды — 1 / 2^40.

## Валидация

1. Длина ровно 64 символа.
2. Разбор по позициям: `prefix` = `[0,4)`, `keyid` = `[4,16)`, `payload` = `[16,64)`.
3. Формат: `prefix` — `^[a-z]{4}$`, `keyid` и `payload` — base64url `^[A-Za-z0-9_-]+$`.
4. `base64url(payload)` → 36 байт: `secret` (32) + `checksum` (4).
5. Пересчитать `crc32(prefix || keyid || secret)`, сравнить с `checksum` — формат валиден.
6. Найти запись по `keyid`.
7. Сравнить `sha256(secret)` с сохранённым хэшем — ключ валиден.

Шаг 7 идёт через `MessageDigest.isEqual`: сравнение хэшей не должно течь по таймингу.

## Хранение

В БД лежат только `key_id` (для поиска) и `key_hash` — SHA-256 hex от `secret`. Сам ключ
показывается пользователю один раз при создании и больше нигде не восстановим.

## Поверхности ключа агента

Ключ `agnt` один на агента, но открывает не одну и ту же поверхность. Решает тип агента, а тип
говорит **ровно одно: как до мозга доходят события**.

| Тип         | Мозг               | Push-транспорт | Что открывает ключ            |
|:------------|:-------------------|:---------------|:------------------------------|
| `CENTRIFUGO`| снаружи            | websocket      | `/agent/**`, `/acp`, `/mcp`   |
| `WEBHOOK`   | снаружи            | HTTP callback  | `/agent/**`, `/acp`, `/mcp`   |
| `MCP`       | снаружи, тянет сам | нет            | `/agent/**`, `/acp`, `/mcp`   |
| `GENERIC`   | наш `agent-worker` | DBOS-очередь   | только `/acp`                 |

У трёх внешних типов поверхности одинаковые: это один и тот же внешний мозг, и разница между ними
только в двери для входящих. Какую из поверхностей клиент реально умеет позвать — его дело:
MCP-клиент говорит только на MCP, самописный агент на n8n — только по REST.

`GENERIC` — исключение не по степени, а по существу: его мозг это наш воркер на gRPC, и у HTTP-поверхности
мозга нет ни одного законного вызывающего. Остаётся `/acp` — направление обратное, IDE разговаривает
**с** агентом, а не за него.

**Ключей LLM наружу не выдаётся никому.** Единственное место, где ключи расшифровываются, —
`LlmCredentialsResolver`, и он обслуживает воркер по gRPC, где проверяется квота и возвращается расход.
`/agent/llm/` отдаёт только метаданные привязки (провайдер, модель): внешний мозг работает на своей
копии ключа. Платформенные модели внешним агентам — это [прокси инференса](../decisions/deferred/llm-inference-proxy.md),
а не выдача ключа.

Маппинг типа на authority живёт в `AgentAuthFilter#authorities`, пути — в `SecurityConfig`
(цепочка api-key). Валидный ключ на чужой поверхности даёт **403**, а не 401: ключ настоящий,
поверхность не его.

## Отдельный случай: authkey пула воркеров

Ключи `wrkp` не хранятся в базе — control-api сверяет их с конфигом. Поэтому у них есть вторая
сериализация, **authkey**, где вместо payload стоит хэш секрета:

```
authkey = prefix + keyid + sha256Hex(secret)      → 80 символов
```

Предъявителю уходит обычный 64-символьный `fullKey`, а в конфиг проверяющего кладётся
80-символьный authkey. Собирается это в `ParsedAuthkey.build` (`libs/common`), генерируется гейтед-тестами:

| Ключ | Кто предъявляет | Генератор |
|:-----|:----------------|:----------|
| `wrkp` | agent-worker, Bearer в gRPC (`agent.grpc.auth-token` → `worker-pools.authkeys`) | `--tests "*WorkerAuthkeyGeneratorTest" -Dgenerate.worker.authkey=true` |

Для локального стенда ключ генерит `ops/dev-init.sh` — руками собирать его не нужно.

**Вызовы между нашими сервисами этот формат не используют.** control-api зовёт user-api с общим
секретом в заголовке `X-S2S-Key` (`APP_S2S_KEY`, `openssl rand -hex 32`), который проверяющая сторона
хранит как есть. Асимметрии, ради которой у `wrkp` заведён хэш, там нет: держателей двое, секрет один,
и конфиг, который для этого должен утечь, содержит секреты OAuth и пароль от базы.

## Свойства формата

- Парсится через `substring()`, без `split()` — разделителей нет.
- Всегда 64 символа, фиксированная длина.
- Тип ключа виден глазами по префиксу.
- CRC32 покрывает все части, включая префикс и keyid, — подменить тип ключа не получится.
- Утечка базы не компрометирует ключи: SHA-256 от 256-битного секрета не перебирается.
