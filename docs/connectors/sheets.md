# Sheets — таблицы агента

Internal-коннектор `sheets`: табличные данные пользователя с объявленной схемой — фильтры и сводки
по любой колонке, PNG-графики, импорт и выгрузка `xlsx`/`csv`.

Закрывает класс сценариев «веду табличку»: дневник давления, показания счётчиков, выручка точки,
бюджет по категориям, юнит-экономика селлера.

## Модель

**Лист** (`sheets`) — объявленная схема колонок. **Строка** (`sheet_rows`) — значения ячеек в JSONB.

```
sheets      id, scope_id, user_id, name, title, columns JSONB   UNIQUE (scope_id, name)
sheet_rows  id, sheet_id, user_id, data JSONB                   INDEX (sheet_id)
```

Колонка: `{name, title, type, unit}`, где `type` ∈ `number | text | date | bool`. `name` — латинский
snake_case-slug (машинный код, уходит в SQL ключом JSONB), `title` — дисплейное имя. Та же пара
name-как-код / title-как-дисплей, что у скиллов и пресетов.

Порядок строк не хранится: в Excel он значим, здесь сортировку задаёт запрос. Колонка БД называется
`data`, а не `values` — `VALUES` зарезервировано в PostgreSQL; в JSON-выдаче тулов ключ остаётся
`values`.

**Владелец — AGENT scope**: `scope_id` = `env.agentId()`, как у persistent memory. Листы личные;
`user_id` — сквозная граница доступа. FK на `agents` с `ON DELETE CASCADE`; удаление агента мягкое,
поэтому строки переживают его и при необходимости переносятся миграцией.

## Почему схема объявляется, а не выводится

Объявленная схема — единственное отличие от свободной сетки ячеек Excel, и оно несущее:

- **тип колонки известен заранее** → каст `(data->>'col')::numeric` в агрегации детерминирован;
- **имя колонки резолвится по whitelist** → аргумент от LLM не может стать инъекцией;
- **агент видит схему в prompt-блоке** → не заводит дубль листа и не выдумывает имена колонок.

## DSL запроса вместо SQL

Фильтр — структура, не строка:

```json
[{"column": "category", "op": "eq",  "value": "продукты"},
 {"column": "amount",   "op": "gte", "value": "100"}]
```

Операции: `eq, ne, gt, gte, lt, lte, contains, in, between, is_null, not_null`; соединяются через
AND (OR не поддержан осознанно — редко нужен модели, а стоимость выразительности высокая). Скалярные
операции берут `value`, `in`/`between` — список `values`.

**Почему не дать LLM писать SQL.** Прямой SQL пришлось бы валидировать, чтобы модель не дотянулась до
чужих таблиц, не выполнила DDL и не уронила базу тяжёлым запросом, — а валидация SQL это парсер SQL.
DSL даёт защиту структурно: имя колонки резолвится по схеме листа, значение всегда уходит
bind-параметром. Инъекции нет по построению, а не по фильтрации (`SheetQueryBuilder`).

**Инвариант записи → безопасность чтения.** Значение попадает в JSONB только через
`SheetSchema.coerceCell`, поэтому в числовой колонке лежит JSON-число либо ключа нет вовсе. Пустая
строка не пишется никогда — иначе `::numeric` падал бы на ней. `NULL::numeric` — это NULL, не ошибка.

`groupBy` по текстовой колонке даёт разбивку по категориям, по колонке-дате — отчёт по периодам
(`bucket`: `day`, `week`, `month`, `year`).

## Ввод значений

Пользователь диктует голосом, поэтому приём мягкий, а хранение — нормализованное:

- числа: `1200`, `"1200"`, `"1 200,50"` → BigDecimal;
- даты: `2026-07-24`, `2026-07-24T08:30`, `24.07.2026` → всегда `yyyy-MM-ddTHH:mm:ss`;
- bool: `да`/`нет`, `yes`/`no`, `1`/`0`.

## График

`render_chart` возвращает `{file, sheet, summary}`, где `summary` — count/min/max/avg/sum по каждой
серии. Это не удобство: **агент не видит собственный PNG**, и без чисел рядом он комментировал бы
картинку по памяти о том, что в неё отправлял. Сводка O(колонок), а не O(строк).

Типы: `line` (X — дата или число), `bar` (X — категории), `pie` (требует `aggregate` и одну Y-колонку).
Сырой график капнут 2000 точками, число групп — 200.

Файл кладётся в файловый слой (`origin = sheets:chart`), агент прикладывает его маркером
`[[attach:agf_…]]` — см. `docs/connectors/files.md`.

> **Требование к образу:** кириллица в подписях рендерится через fontconfig. В «голом» JRE-образе без
> `fontconfig` и шрифтов (например DejaVu) подписи выйдут квадратами. Headless Spring Boot включает сам.

## Импорт и экспорт

Файл — это **края потока, а не его середина**: истина живёт в БД (быстрые агрегаты, детерминированные
метрики), а `xlsx`/`csv` нужен на входе («у меня уже всё в табличке») и на выходе («отдай бухгалтеру»).
Хранить живую таблицу файлом мешало бы всё сразу: TTL файлового слоя 7 дней, каждая правка порождает
новый `agf_`-id, а любой вопрос требовал бы парсинга всего файла.

- **Импорт** (`import_file`): первая строка — заголовки. Заголовок → `title`, транслит-slug → `name`
  (`SheetSlugs`), тип выводится по первым 50 непустым значениям колонки. Формат определяется по
  сигнатуре (ZIP → xlsx, иначе csv; разделитель csv детектируется). Кап 5000 строк.
- **Экспорт** (`export`): `csv` — UTF-8 **с BOM и разделителем `;`**, иначе русский Excel показывает
  кракозябры и склеивает всё в одну колонку. `xlsx` — через fastexcel.

Библиотека — `org.dhatim:fastexcel` (Apache 2.0, стриминговая), а не Apache POI: POI тянет `xmlbeans`
и десятки мегабайт ради формата, нужного только на краях.

## Prompt-блок

SYSTEM-блок `sheets` со схемой листов:

```
household_budget «Бюджет семьи» (128 rows): date:date, amount:number ₽, category:text
```

Снимает главный риск модели: не увидев своих таблиц, агент завёл бы дубль вместо записи в
существующую. Инвариант «O(1) от объёма данных» соблюдён (строка на лист, не на запись), плюс кап
8 листов × 12 колонок — полный листинг живёт в туле `list_sheets`, а не в промпте.

## Что не делаем

- **Формулы Excel** (ссылки на ячейки, диапазоны) — никогда. Дешёвая честная половина — вычисляемая
  колонка (`formula: "price - cost"`, вычислитель на `+ - * / ()`): добавляется полем в `columns`
  JSONB без миграции, когда понадобится юнит-экономика селлера.
- **Совместное редактирование человеком** — база его не даёт в принципе. Это отдельный
  integration-коннектор (Google Sheets / Яндекс Документы) поверх той же доменной модели: колонки и
  строки ложатся на внешний лист один в один. Перед выбором Google стоит сверить доступность
  сервисов с RU-аудиторией продукта.
- **OR в фильтре, join между листами, произвольный SQL** — см. выше.
