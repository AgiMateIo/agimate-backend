# Файлы в коннекторном слое (control-api)

Единый файловый слой для бинарных артефактов коннекторов: скриншоты и файлы от device-apps,
вложения внешних MCP-серверов, отправка медиа в каналы (Telegram-фото/документы/видео).

## Проблема и принцип

Результат тула — плоская строка `output`, которая целиком уезжает в LLM-контекст агента
(и режется трункейтом воркера). Байты через этот путь ходить не могут: base64-скриншот сжигает
контекст и упирается в лимиты.

**Принцип: pass-by-reference на тул-слое.** Файл — сущность коннекторного слоя, адресуемая
`fileId`; байты живут в объектном хранилище и покидают его только на краях (загрузка с устройства,
multipart в Telegram). Агент — курьер ссылок: получает `fileId` в результате одного тула и передаёт
его параметром в другой. Протокол воркера (v2.1) не меняется — для модели `fileId` это короткая
строка в обычных tool-ходах.

Файлы **не** ходят через канальный ответ (`Part`/`OutboundMessage.parts`) — тот слой остаётся
зарезервированным под входящие медиа каналов (юзер прислал фото боту), это отдельная фаза.

## Хранилище

Таблица `files` + `FileStorageService` (пакет `controlapi/storage`), backend — S3-совместимый
(MinIO локально, любой S3 в проде).

| колонка      | тип       | назначение |
|--------------|-----------|------------|
| `id`         | UUID      | `UUIDUtils.generateUuidV8()`; наружу — `agf_<uuid>` |
| `user_id`    | UUID      | владелец; граница доступа (ABAC) |
| `mime`       | TEXT      | MIME-тип |
| `size`       | BIGINT    | байты |
| `sha256`     | TEXT      | контроль целостности / дедуп |
| `origin`     | TEXT      | провенанс: `connector_code` / tool / connection, породившие файл |
| `status`     | TEXT enum | `UPLOADING` / `READY` |
| `expires_at` | TIMESTAMP | TTL по происхождению (скриншот — короткий, прочее — длиннее) |

- **Ownership**: файл принадлежит `user_id`; коннектор исполняется в `ConnectorEnv` с caller
  identity — резолв чужого `fileId` невозможен по построению.
- **Lifecycle**: чистка просроченных строк + блобов — фоновая задача на существующем scheduler'е.
- **Квоты**: bytes stored / bytes per day на пользователя — рядом с `InboundRateLimiter`,
  проверка на путях загрузки.

## Контракт fileId

- Идентификатор: `agf_<uuid>` — узнаваем в параметрах и логах, не конфликтует с URL/чужими id.
- **В результате тула** — маленький JSON вместо байтов:
  `{"file": {"id": "agf_…", "mime": "image/png", "size": 384211}}`. Никаких контент-блоков в
  протоколе воркера: модель получает текст, конвенция живёт на уровне JSON-выхода тула.
- **В параметре тула** — Java-тип `FileRef` в `@ToolParam`; `ToolSchemaReflector` рендерит его как
  `string` с `format: "x-agimate-file"` (+ описание, что сюда подставляется `id` из результата
  предыдущего тула).
- MCP-совместимость: наружный формат сознательно конвертируем в/из MCP-блоков —
  `resource_link` ↔ `{"file": …}`, `image`/`embedded resource` (base64 от внешнего MCP-сервера) →
  байты в storage → `{"file": …}`. Конверсия — на границе mcp-коннектора, не в ядре.

## Продюсеры

- **Серверные коннекторы** (locus BACKEND): пишут в `FileStorageService` напрямую, байты не
  покидают control-api.
- **Device-apps** (locus DELEGATED×INBOUND): `POST /app/files` — multipart под тем же app-ключом,
  ответ — `fileId`; тул устройства (скриншот и т.п.) кладёт в `output` `{"file": …}` вместо base64.
  Presigned-URL напрямую в S3 — оптимизация позже, если трафик через control-api станет узким местом.
- **mcp-коннектор**: бинарные блоки ответа внешнего сервера → storage (см. выше).

## Потребители

- **Резолв на краю диспатча**: `BaseConnectorHandler` при биндинге аргументов видит параметр типа
  `FileRef` → проверяет ownership по `ConnectorEnv` → отдаёт тулу lazy-handle со стримом из storage.
  Невалидный/чужой/просроченный `fileId` → `ConnectorException` (агент видит причину).
- **Telegram**: multipart-загрузка в `TelegramApiClient`; `send_photo` принимает URL / telegram
  file_id / `agf_…` (обратная совместимость), новые тулы `send_document`, `send_video`
  (Bot API: до 50 MB от бота).
- **Device-apps как приёмник**: `GET /app/files/{id}` под app-ключом — когда файл нужно доставить
  на устройство (аргумент-`FileRef` app-тула прокидывается устройству ссылкой, скачивание — по этому
  endpoint'у).
- **Webchat/UI**: короткоживущий signed URL (`GET /files/{id}?sig=…`) для отображения в истории —
  отдельная фаза.

## Порядок работ

1. `files` + `FileStorageService` + TTL/квоты/чистка;
2. app upload/download endpoints; скриншот-тул возвращает `{"file": …}`;
3. `FileRef` в reflector/handler; multipart + `send_document`/`send_video` в Telegram.

Вне скоупа документа (следующие фазы): коннекторы-генераторы изображений/видео, «зрение» агента
(инжект картинки в LLM-контекст — единственное место, где потребуется расширение протокола
воркера), signed URL для webchat, входящие медиа каналов через `InboundMessage.parts`.
