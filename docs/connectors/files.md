# Файлы в коннекторном слое (control-api)

Единый файловый слой для бинарных артефактов коннекторов: скриншоты и файлы от подключённых приложений,
вложения внешних MCP-серверов, отправка медиа в каналы (Telegram-фото/документы/видео).

## Проблема и принцип

Результат тула — плоская строка `output`, которая целиком уезжает в LLM-контекст агента
(и режется трункейтом воркера). Байты через этот путь ходить не могут: base64-скриншот сжигает
контекст и упирается в лимиты.

**Принцип: pass-by-reference на тул-слое.** Файл — сущность коннекторного слоя, адресуемая
`fileId`; байты живут в объектном хранилище и покидают его только на краях (загрузка из приложения,
multipart в Telegram). Агент — курьер ссылок: получает `fileId` в результате одного тула и передаёт
его параметром в другой. Протокол воркера (v2.1) не меняется — для модели `fileId` это короткая
строка в обычных tool-ходах.

Файловых полосы **две**, и они не конкурируют:

- **тул-слой** (эта часть документа): файл — вход/выход тулов, агент — курьер `fileId` между
  вызовами (переслать в конкретный чат, доставить в приложение, приложить к board-задаче);
- **канальный ответ** (`OutboundMessage.parts`, см. «Вложения в ответе» ниже): файл — часть
  ответа пользователю; адресацию и транспорт выбирает channel handler, агент не знает ни
  chatId, ни имени тула.
- **входящее вложение** (`InboundMessage.parts`, см. «Входящие вложения» ниже): юзер прислал
  файл/фото; control-api материализует его в файловый слой на ingest'е, а воркер подтягивает
  байты изображения при LLM-вызове («зрение»).

## Хранилище

Таблица `files` + `FileStorageService` (пакет `controlapi/storage`); блобы — за интерфейсом
`BlobStore`: `local` (диск, дефолт — разработка/single-node, корень `app.files.local-dir`,
пусто = `~/.agimate/files`) или `s3` (AWS S3 / MinIO), переключается `app.files.backend`.

| колонка      | тип       | назначение |
|--------------|-----------|------------|
| `id`         | UUID      | `UUIDUtils.generateUuidV8()`; наружу — `agf_<uuid>` |
| `user_id`    | UUID      | владелец; граница доступа (ABAC) |
| `agent_id`   | UUID      | агент-производитель; провенанс, **не** граница доступа. nullable |
| `mime`       | TEXT      | MIME-тип |
| `size`       | BIGINT    | байты |
| `name`       | TEXT      | имя файла, каким его знал производитель. nullable |
| `sha256`     | TEXT      | контроль целостности / дедуп |
| `origin`     | TEXT      | провенанс: `connector_code` / tool / connection, породившие файл |
| `status`     | TEXT enum | `UPLOADING` / `READY` |
| `expires_at` | TIMESTAMP | TTL по происхождению (скриншот — короткий, прочее — длиннее) |

Строка собирается через `NewFile` (билдер) — `origin`, `name` и `mime` идут тремя подряд
строковыми полями, и позиционная путаница между ними всплыла бы только испорченной строкой в БД.

Объект заливается **вместе со своим представлением**: `BlobStore.put` принимает пару
`Content-Type`/`Content-Disposition` от того же `FileContentHeaders`, что и подписанная ссылка.
Ключ (`user_id/agf_<id>`) расширения не несёт, и хранилище, которое проигнорирует `response-*`
в подписи, отдало бы браузеру именно ключ вместо имени; у локального бэкенда представления нет —
всё, что он отдаёт, идёт через control-api и заголовки собираются по строке.

- **Ownership**: файл принадлежит `user_id`; коннектор исполняется в `ConnectorEnv` с caller
  identity — резолв чужого `fileId` невозможен по построению.
- **`agent_id` — только провенанс.** Доступ намеренно остаётся пользовательским: агенты одного
  владельца передают друг другу `agf_`-ссылки через комментарии board'а и ячейки sheets, и
  поагентный гейт сломал бы этот поток. Заполняется там, где производитель известен из
  `ConnectorEnv` (media, экспорт и графики sheets); пусто на ingest-путях — вебхук скачивает медиа
  **до** того, как маршрутизация выбрала получателей (а их может быть несколько), а приложение и
  webchat-UI грузят файл вне рана.
- **`name`** — то, что видит человек: `Content-Disposition` при скачивании (`FileHttpResponses`),
  имя multipart-части при отправке в Telegram (`TelegramToolService`, приоритет: явный параметр тула
  → то, как файл назвался бы при скачивании), подпись вложения в истории webchat. Пусто там, где
  имени нет в природе (фото в Telegram, сгенерированная картинка) — выдуманное имя было бы
  неотличимо от настоящего. Санитизация в `NewFile`: срезается путь, вырезаются кавычки и
  управляющие символы (значение уезжает в HTTP-заголовок), длина — до 255.
- **Имя на выдаче считает `FileNames.forDownload`** — единственное место, где решается, как файл
  назовётся человеку. Сохранённое имя отдаётся **дословно**, включая имя без расширения: как файл
  назвал производитель (или прислал пользователь), так он и скачается. Пустое имя даёт
  `<вид>-<хвост id>.<расширение>` — `image-5f2a3c44.png` вместо нечитаемого `agf_<uuid>` без
  расширения. Имя — чистая функция строки `files` (`name`, `mime`, `id`), поэтому один и тот же файл
  скачивается под одним и тем же именем на всех путях и при каждой попытке. Расширение — по таблице
  в `FileNames` с фолбэком на подтип; подтип берётся из разобранного `MediaType`, потому что загрузка
  кладёт в `mime` заголовок клиента дословно (`text/plain;charset=UTF-8`).
- **Lifecycle**: чистка просроченных строк + блобов — фоновая задача на существующем scheduler'е.
- **Срок жизни зависит от происхождения**: `app.files.default-ttl` (7 дней) — то, что произвёл
  коннектор, `app.files.user-ttl` (90 дней) — то, что пользователь загрузил сам. Скриншот — леса
  одного рана, а принесённый человеком файл принадлежит ему; на недельном окне вопрос «покажи файл,
  который я тебе присылал» отвечался бы только про последнюю неделю.
- **Квоты**: bytes stored / bytes per day на пользователя — рядом с `InboundRateLimiter`,
  проверка на путях загрузки.

## Контракт fileId

- Идентификатор: `agf_<uuid>` — узнаваем в параметрах и логах, не конфликтует с URL/чужими id.
- **В результате тула** — маленький JSON вместо байтов:
  `{"file": {"id": "agf_…", "mime": "image/png", "size": 384211}}`. Никаких контент-блоков в
  протоколе воркера: модель получает текст, конвенция живёт на уровне JSON-выхода тула.
- **В параметре тула** — Java-тип `FileRef` в `@ToolParam`; `ToolSchemaReflector` рендерит его как
  `string` с `format: "x-agimate-file"` (+ описание, что сюда подставляется `id` из результата
  предыдущего тула).
- MCP-совместимость: наружный формат сознательно конвертируем в/из MCP-блоков —
  `resource_link` ↔ `{"file": …}`, `image`/`embedded resource` (base64 от внешнего MCP-сервера) →
  байты в storage → `{"file": …}`. Конверсия — на границе mcp-коннектора, не в ядре.

## Продюсеры

- **Серверные коннекторы** (`execution_kind = BACKEND`): пишут в `FileStorageService` напрямую,
  байты не покидают control-api.
- **Подключённые приложения** (`execution_kind = APP`): `POST /app/files` — multipart под тем же
  app-ключом, ответ — `fileId`; тул приложения (скриншот и т.п.) кладёт в `output` `{"file": …}`
  вместо base64.
  Presigned-URL напрямую в S3 — оптимизация позже, если трафик через control-api станет узким местом.
- **mcp-коннектор**: бинарные блоки ответа внешнего сервера → storage (см. выше).

## Потребители

- **Резолв на краю диспатча**: `BaseConnectorHandler` при биндинге аргументов видит параметр типа
  `FileRef` → проверяет ownership по `ConnectorEnv` → отдаёт тулу lazy-handle со стримом из storage.
  Невалидный/чужой/просроченный `fileId` → `ConnectorException` (агент видит причину).
- **Telegram**: multipart-загрузка в `TelegramApiClient`; `send_photo` принимает URL / telegram
  file_id / `agf_…` (обратная совместимость), новые тулы `send_document`, `send_video`
  (Bot API: до 50 MB от бота).
- **Подключённые приложения как приёмник**: `GET /app/files/{id}` под app-ключом — когда файл нужно
  доставить в приложение (аргумент-`FileRef` app-тула прокидывается ему ссылкой, скачивание — по
  этому endpoint'у).
- **Webchat/UI**: вложения ответа приходят фронту `parts`'ами webchat-сообщения (событие + история)
  со свежим подписанным URL содержимого — `GET /files/{fileId}?exp&sig` (публичный endpoint,
  HMAC-SHA256 по `fileId|exp` секретом `app.files.url-secret`, TTL `app.files.url-ttl`, дефолт
  15 мин). `Authorization`-заголовок в `<img src>` не подставить, поэтому доступ авторизуется
  capability-ссылкой; владение проверяется при выдаче (parts видит только владелец сессии). В строке
  `webchat_messages.parts` URL не хранится (протухает) — каждая выдача подписывает заново.
  Изображения отдаются inline (рендер в чате), прочее — attachment; активный контент —
  octet-stream + nosniff + CSP-sandbox. При включённом presign та же выдача возвращает абсолютную
  ссылку прямо в хранилище — см. «Прямая ссылка в хранилище».

## Прямая ссылка в хранилище (presign)

При `app.files.backend=s3` и `app.files.presign=true` `SignedFileUrlService` отдаёт не `/files/…`,
а presigned URL (SigV4 в query-строке, тот же TTL `url-ttl`): байты едут из хранилища в браузер
мимо control-api. Выигрыш не столько в трафике, сколько в том, чего наш стриминг не умеет вовсе —
Range-запросы: перемотка видео и докачка на `/files/…` не работают, объект отдаётся целиком.

- **Форма ссылки выбирает хранилище, а не вызывающий.** `BlobStore.presignGet` возвращает пустой
  `Optional` — «этот бэкенд ссылок не подписывает» (диск) или «не настроен подписывать», и выдача
  откатывается на HMAC-ссылку. Сбой подписи — тоже откат, а не ошибка: хуже прежнего не станет.
- **Представление общее.** `Content-Type`/`Content-Disposition`/`Cache-Control` уезжают в подпись
  как `response-*`, значения считает `FileContentHeaders` — тот же код, что и на стриминге и при
  заливке объекта, поэтому правило «активный контент деградирует до octet-stream» и имя файла
  держатся на всех путях. Часть без `mime`
  (в `parts` он представим) не подписывается вовсе: угаданное представление превратило бы картинку
  в скачивание, а наш путь возьмёт настоящий mime из строки `files`.
  `nosniff` и CSP-sandbox выставить нечем — на прямой ссылке их заменяет то, что бакет живёт на
  чужом origin. **Хост хранилища не должен попадать в cookie-домен приложения**
  (`app.oauth.cookie-domain`): иначе аргумент «чужой origin» перестаёт работать, и остаётся голая
  подстановка `octet-stream`.
- **Отзыв слабее, и не только отзыв.** Presigned-ссылка не проходит через строку `files` **ни при
  выдаче, ни при скачивании**, поэтому мимо неё проходят все три фильтра `findLive` — владение,
  `READY` и TTL. Практическое следствие: удалённый (`DELETE /manage/files/{id}` = проставить
  `expires_at`) или протухший файл остаётся читаемым до ближайшей чистки блобов — до минуты, — а
  когда блоб уже сметён, браузер получит XML-ошибку хранилища вместо нашего 403. Это цена, ради
  которой фича сделана opt-in.
- **В ключе — `userId`**, а значит, он виден в адресной строке и уезжает вместе со скопированной
  ссылкой. Внутренний идентификатор аккаунта наружу лучше не отдавать: перед включением presign в
  проде ключ стоит сделать непрозрачным (формат живёт в одном месте — `FileLink.blobKey`).
  Отдельно из этого следует, что владельца для ключа вебчат берёт **из сессии**, а не из строки
  `files` (иначе листинг истории стоил бы чтения на вложение); держится это тем, что вложение в
  сессию попадает только через владельца канала. Если у агента появятся несколько участников
  (`docs/decisions/`), инвариант надо будет пересмотреть — ссылка сломается молча.
- **Адрес для подписи — `public-endpoint`** (пусто = `endpoint`): адрес, по которому SDK ходит
  изнутри кластера, браузеру может быть недоступен (MinIO во внутренней сети).
- **Контракт с фронтом**: URL в `parts` и в листинге `/manage/files/` становится абсолютным —
  использовать как есть, не приклеивая origin; бакету нужен CORS, фронтовому CSP — хост хранилища
  в `img-src`/`connect-src`. Пока фронт этого не умеет, флаг держать выключенным.
- **cloud.ru S3**: регион `ru-central-1`, access key вида `<tenant_id>:<key_id>`, `X-Amz-Expires`
  до 7 суток (наши 15 минут проходят). Поддержка `response-content-*` в их документации не описана;
  если хранилище их игнорирует, отдаётся записанное при PUT — `Content-Type` там проставлен, а имя
  файла в `Content-Disposition` теряется (браузер возьмёт имя из ключа, `agf_…`).

## Просмотр и удаление (manage)

`ManageFilesController` (`/manage/files`, JWT) — собственный слой пользователя над его файлами:
загрузка, список, удаление. `UserFileService` держит эту логику отдельно от `FileStorageService`,
потому что ей нужны HTTP-DTO и подписанные ссылки, а слой байтов и владения про них знать не должен.
Схемы запроса/ответа — в OpenAPI (`/control/docs/ui`).

- **`POST /manage/files`** — multipart-загрузка под своим именем (rate-limit `FILE_UPLOAD` по
  пользователю). `agent_id` пуст: загрузка не входит в ран, а получателя выбирают позже — когда файл
  прикрепляют к сообщению. `origin` = `user`, а с необязательным полем формы `origin` —
  `user:<метка>`: клиент называет место в своём UI (`chat`, `board`), но **только суффикс**.
  Префикс здесь не украшение: серверный провенанс (`telegram:<connId>`, `media:<model>`,
  `app:<id>`) лежит в той же колонке, и без пространства имён загрузка смогла бы представиться
  коннектором. Метка проверяется по `[a-z0-9][a-z0-9_-]{0,31}`, иначе 400 — молча переписать
  значение хуже, чем отказать. Ответ — то же представление, что и в листинге, вместе
  со свежей подписанной ссылкой: у файла одна форма, а не две. Раньше эндпойнт жил как шаг сценария
  вебчата (`POST /manage/webchat/files`) — вебчат-специфичного в нём не было ничего, кроме `origin`,
  и он **удалён**, а не оставлен алиасом.
- **`GET /manage/files/`** — свои файлы, свежайшие первыми, постранично. Выборка идёт по тем же трём
  условиям, что и `findReadable` (свой + `READY` + не протух): список не должен предлагать файл,
  который откажется открыться. Фильтры — `sessionId` (разговор), `agentId` и `name` (подстрока,
  регистронезависимо). Контекстные фильтры идут через `EXISTS` по `file_references`, а не джойном:
  файл, засветившийся в разговоре дважды, должен появиться в странице один раз. Каждая строка несёт
  **свежую** подпись `GET /files/{fileId}?exp&sig`; URL нигде не хранится, как и в вебчате.
- **`agentId` — это «связан с агентом», а не «произведён им»**: агент произвёл файл (`files.agent_id`)
  **или** видел его (`file_references`). Буквальный провенанс никуда не делся — он в самой строке
  ответа, полями `agentId` и `origin`. Смысл выбран под фронт: листинг, отфильтрованный по агенту,
  должен содержать и то, что пользователь этому агенту прислал.
- **`DELETE /manage/files/{fileId}`** — удаление раньше TTL. Реализовано **проставлением
  `expires_at = now()`**, а не удалением на месте: блоб трогает ровно один код —
  `purgeExpiredBatch`, — операция идемпотентна под ретраем, а из листинга файл исчезает сразу
  (фильтр по `expires_at`). Цена — байты живут ещё до минуты, до ближайшего тика чистки.
- **Следствие**: после удаления `agf_`-ссылки в истории вебчата, комментариях board и ячейках sheets
  перестают резолвиться — ровно то же, что происходит при протухании по TTL.
- Сознательно нет: фильтра по типу (`image`/`video`/…), выдачи метаданных одного файла и счётчика
  занятой квоты — добавим, когда у них появится потребитель во фронте.

## Контекст файла (`file_references`)

Где файл засветился: разговор, к которому его приложили, и агент, который его видел. До этой таблицы
связь жила только внутри `webchat_messages.parts` (JSONB) — неиндексируемая, нефильтруемая и
недоступная ни одному каналу, кроме вебчата.

Таблица, а не колонка `session_id` в `files`, потому что связь честно множественная: одно входящее
фото разъезжается по всем получателям триггера, а тот же файл переприкладывается к более поздним
ответам. Колонка удержала бы только первое из этого и молча врала бы про остальное.

| колонка | назначение |
|---|---|
| `file_id` | FK на `files`, `ON DELETE CASCADE` — чистка блобов уносит ссылки за собой |
| `session_id` | разговор; пусто у файла, произведённого вне канального потока |
| `agent_id` | агент; nullable — `ConnectorEnv.agentId` пуст вне tool-use flow |
| `kind` | `INBOUND` (принёс пользователь) / `OUTBOUND` (отдал агент) / `TOOL` (произвёл тул) |

- **`user_id` намеренно нет**: владение живёт в `files.user_id` и остаётся единственным источником
  (ABAC). Любое чтение всё равно джойнит `files` — за именем и mime.
- **Ключ идемпотентности** `uq_file_references_file_session_kind` — `(file_id, session_id, kind)`
  **`NULLS NOT DISTINCT`**: доставка ретраится, стиринг переигрывает ран, а обычный UNIQUE считает
  NULL'ы различными и пропускал бы дубли у безсессионных строк. Такое написание невыразимо ни в
  `<addUniqueConstraint>`, ни в `@Table(uniqueConstraints)`, поэтому оно живёт в миграции, а на
  сущности вместо привычного дубликата стоит комментарий.
- **Две правды разведены явно**: `file_references` — источник для **навигации и поиска**,
  `webchat_messages.parts` — для **отображения сообщения**. При расхождении прав `parts`.

**Пишут воронки, а не листья** — иначе таблица врёт молча, стоит новому коннектору забыть про запись:

| воронка | что покрывает |
|---|---|
| `TriggerRouterService.dispatch` | всё входящее (`INBOUND`): только здесь известна сессия каждого получателя, и только здесь fan-out превращается в строку на разговор. Пишется **после** доставки: файл побывал в разговоре, только если сообщение дошло |
| `ChannelMessageOutboundService.send` | всё исходящее (`OUTBOUND`): единственный путь ответа во все каналы, `parts` уже разобраны из `[[attach:…]]`, а отброшенные (хендлер без вложений, progress-стрим) до записи не доходят |
| `FileStorageService.store` | продюсеры тул-слоя (`TOOL`), когда `NewFile.sessionId` назван. Провенанс сессии едет в спеке рядом с `agentId`, а строку пишет одно место — продюсеру нечего забыть |

Запись — best-effort по контракту: ссылка это навигация, и её потеря не должна стоить доставки.
Поэтому вставка идёт `ON CONFLICT DO NOTHING` в `REQUIRES_NEW`-транзакции, а сбой логируется, а не
поднимается наверх.

**Загрузка (`POST /manage/files`) строк не пишет**: положить файл в слой — ещё не воспользоваться им.
Контекст появляется, когда файл прикладывают к сообщению.

**Читает** её листинг `/manage/files/` (фильтры `sessionId` и `agentId`) и тул `list_files`
платформенного коннектора: агент находит файл, чей `agf_`-идентификатор уже вышел из его контекста,
и передаёт id дальше — параметром другого тула или маркером `[[attach:…]]`. По умолчанию тул сужен до
текущего разговора; в ране без канала сессии нет, и поиск идёт по всему аккаунту — отказ оставил бы
агента без доступа к собственным файлам вовсе.

> Аудитория тула пока узкая: `platform` привязан только к пресету `platform-admin`. Обычному агенту
> «покажи файл, который я тебе присылал» недоступно — для этого капабилити нужен отдельный внутренний
> коннектор `files`, привязываемый пресетами наравне с `time` и `persist-memory`.

**Чего таблица не знает** (границы, а не недоделки):

- *Потребление* файла тулом. `FileRef` из раздела «Контракт fileId» — описанный, но не
  реализованный тип: тулы принимают обычную строку, единой точки связывания нет.
- Файлы приложений (`POST /app/files`): грузятся вне рана, инициатор невосстановим по построению.
  Если агент передаст такой файл дальше параметром тула, а не приложит к ответу, ссылок у файла не
  будет.
- Прошлое канальных сессий. Перенос при миграции идёт из `webchat_messages.parts` — единственного
  места, где история вложений записана; у телеграм-разговора своего лога сообщений нет, и его файлы
  старше миграции остаются без ссылок. Честный пробел лучше выдуманного.

## Вложения в ответе канала (attach-конвенция)

Ответ агента может нести файлы без знания адресата и транспорта:

- **Маркер в тексте ответа**: `[[attach:agf_<uuid>]]`. Семантику объясняет system-блок
  `RunContextService.ATTACHMENT_GUIDANCE` — добавляется только в DIALOGUE-ранах, чей prompt-канал
  умеет вложения (`ChannelHandler.supportsOutboundAttachments()`).
- **Парсинг на границе control-api** (`OutboundAttachmentParser`, вызывается из
  `ChannelMessageOutboundService`): маркеры вырезаются из текста всегда; `Part` создаётся только
  для файла, читаемого владельцем канала (`FileStorageService.findReadable`) — галлюцинированный
  или чужой id молча отбрасывается. Парсится только текст агента (доверенный автор), не
  tool-результаты. Протокол воркера не затронут: конвенция целиком серверная.
- **Доставка**: `ChannelHandler.handleOutput` возвращает список `ToolCallRequest`; Telegram мапит
  part по типу (`image` → `send_photo`, `video` → `send_video`, иначе `send_document`), каждая
  часть — отдельным сообщением с контентным ключом идемпотентности
  (`messageId:fileId` — устойчив к изменению состава parts между ретраями); резолв `agf_` → байты
  уже в тул-слое. Webchat доставляет parts прямо в webchat-сообщении (подписанные ссылки, см.
  «Потребители»). Handler'ы без поддержки вложений
  получают сообщение с очищенным текстом и без parts.
- **Parts несёт только answer-стрим**: маркер, упомянутый агентом в progress-выводе, вырезается из
  текста, но вложением не доставляется — иначе файл уехал бы дважды (progress + финальный ответ).
- Структурные parts в протоколе воркера (v2.x) — отложенная фаза: конвенция маркеров
  конвертируема в неё без изменения этого слоя.

## Входящие вложения (зрение)

Пользователь присылает файл/фото → агент «видит» изображение. Тракт (webchat + Telegram):

- **Ingest → материализация**. Файл кладётся в файловый слой ОДИН раз на ingest-границе:
  - **webchat**: `POST /manage/files` (multipart, JWT, см. «Просмотр и удаление») → `id`; фронт
    передаёт его в `parts: [{"fileId": "agf_…"}]` при отправке сообщения. `WebchatService`
    валидирует каждый (`findReadable`: свой + READY + не протух, ≤ 5) и кладёт `parts` в data триггера.
    Имя берётся из строки `files` (фронт его не присылает) и едет в data/`webchat_messages.parts`
    полем `name` — как у Telegram-документа.
  - **Telegram**: `TelegramMediaService` на webhook/long-poll качает крупнейший `PhotoSize`
    (или документ) через Bot API `getFile`+download, сохраняет в файловый слой и заменяет сырой
    `photo`/`document` в data триггера на `parts`. Сбой скачивания → деградация к прежней
    текст-заглушке, триггер не теряется. Токен в логи/исключения не попадает.
- **Канонизация**. `ChannelHandler.handleInput` маппит `data.parts` → `InboundMessage.parts` и строит
  текст с «описанием загруженного файла» на каждое вложение (`MediaStubs`): `[Описание загруженного
  файла: изображение, уже приложено к этому сообщению — ты видишь его напрямую, image/jpeg, 18 KB.
  id: agf_…. Файл уже доступен, скачивать по id не нужно; id — только чтобы сослаться на файл.]`.
  Рамка намеренная: сырой `[… agf_…]` сбивал модель — она принимала инлайн-картинку за «файл по id,
  который надо достать» и игнорировала зрение. id в описании даёт модели переиспользовать файл
  (`[[attach:agf_…]]`, см. `ATTACHMENT_GUIDANCE` — расширен на inbound-файлы). Это одновременно
  плейсхолдер в истории (протокол текстовый). `InboundTextResolver` возвращает полное
  `InboundMessage`; `RunContextService` кладёт ссылки в `RunContextView.inboundParts`.
- **Протокол v2**. `RunContext.inbound_parts` (`repeated FilePart` — только `agf_`-ссылки, без байтов:
  в чекпоинт уезжает ссылка, содержимое — никогда). Новый RPC `AgentContext.GetFile` (server-streaming
  чанки 128 KB) отдаёт содержимое воркеру с ownership-гейтом `file.user_id == agent.user_id`.
- **Воркер → LLM**. `inbound_parts` доезжают до `AgentChatMessage.parts` (только ссылки). Байты
  image-вложений воркер тянет `GetFile`'ом **inline при llm_call** — как `api_key`, вне чекпоинта —
  и подаёт в модель через Spring AI `Media` (`LlmMessageMapper`). Недоступный файл (NOT_FOUND/сбой) →
  без Media, текст со стабом (деградация, ран не падает). Не-image (pdf/zip…) в модель не подаётся —
  только стаб; агент может переслать его attach-конвенцией.
- **История — плейсхолдеры**: картинка видна только в ране, куда пришла; в истории следующих ранов —
  текст-стаб. Реприкрепление изображений из истории — возможная следующая фаза.

## Порядок работ

1. `files` + `FileStorageService` + TTL/квоты/чистка;
2. app upload/download endpoints; скриншот-тул возвращает `{"file": …}`;
3. `FileRef` в reflector/handler; multipart + `send_document`/`send_video` в Telegram;
4. входящие вложения: `RunContext.inbound_parts` + `GetFile`, webchat-upload, Telegram-download,
   `Media` в воркере (см. «Входящие вложения»).

Вне скоупа документа (следующие фазы): коннекторы-генераторы изображений/видео, реприкрепление
изображений из истории, транскрибация аудио, входящие вложения в ACP-канале.
