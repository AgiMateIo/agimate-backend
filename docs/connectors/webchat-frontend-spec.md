# Webchat — спека для фронта (временная)

> Черновик под первую реализацию UI; контракт может уточняться. Бэкенд-архитектура: `webchat.md`.

Чат пользователя с его агентами прямо из дашборда. Пользователь выбирает агента, ведёт **сессии**
(новую можно начать в любой момент), сообщения агента (включая прогресс работы) прилетают в
реальном времени через **Centrifugo**.

Все REST-эндпоинты — под `/manage/**` (context path `/control`), авторизация — **пользовательский
JWT** (`Authorization: Bearer <jwt>`, как у остального дашборда).

## Конверты ответа

Успех:
```json
{ "response": <payload> }
```
Ошибка (HTTP 4xx/5xx):
```json
{ "error": { "message": "..." } }
```
Коды: `400` (закрытая сессия, вложения, валидация), `401` (нет/протух JWT), `403` (чужая сессия),
`404` (сессия/агент не найдены).

---

## Рекомендуемый флоу UI

```
[1] Новая сессия (или выбор из списка)  →  [2] Токены Centrifugo  →  [3] Подписка на webchat:{sessionId}
                                                                              ↓
[6] История (при открытии существующей)  ←  [5] События: echo / progress / answer  ←  [4] Отправка сообщения
```

Ничего настраивать заранее не нужно: первый `POST /sessions` для агента сам подключает webchat
к агенту и создаёт канал (лениво, на бэке).

---

## [1] Новая сессия

`POST /manage/webchat/sessions`

```json
{ "agentId": "0197..." }
```

```json
{ "response": {
  "sessionId": "0197...",
  "channelId": "0197...",
  "agentId": "0197...",
  "title": null,
  "lastMessageAt": "2026-07-08T12:00:00",
  "closedAt": null,
  "createdAt": "2026-07-08T12:00:00"
} }
```

Каждый вызов создаёт **новую** сессию. `title` появится после первого сообщения (первые 80 символов).

## [2] Список сессий

`GET /manage/webchat/sessions/` (опционально `?agentId=`)

```json
{ "response": [ <WebchatSessionResponse>, ... ] }
```

Отсортированы по `lastMessageAt` desc. `closedAt != null` — сессия закрыта (читать историю можно,
писать нельзя). Live-обновлений списка нет — обновляйте его при получении событий активной
сессии / по фокусу вкладки.

## [3] Токены Centrifugo

`POST /manage/webchat/sessions/{sessionId}/token` (без тела)

```json
{ "response": {
  "connectionToken": "<jwt>",
  "subscriptionToken": "<jwt>",
  "channel": "webchat:0197...",
  "wsUrl": "wss://.../connection/websocket"
} }
```

С centrifuge-js:

```js
const c = new Centrifuge(wsUrl, { getToken: fetchConnectionToken }); // re-fetch при протухании
const sub = c.newSubscription(channel, { getToken: fetchSubscriptionToken });
sub.on("publication", ({ data }) => { /* data = { type, payload } */ });
sub.subscribe(); c.connect();
```

TTL токенов — 1 час; `getToken`-коллбэки должны заново дёргать эндпоинт. У namespace включены
history + recovery — при реконнекте SDK сам доставит пропущенные публикации.

## [4] Отправка сообщения

`POST /manage/webchat/sessions/{sessionId}/messages`

```json
{ "text": "Привет! Что в бэклоге?" }
```

```json
{ "response": { "sessionId": "0197...", "messageId": "b3f0..." } }
```

- Ответ — подтверждение приёма; сам ответ агента прилетит событиями в Centrifugo.
- Рендерите своё сообщение оптимистично сразу, `messageId` из ответа — ключ для сверки с echo-событием.
- Поле `parts` зарезервировано под вложения (файлы/картинки) — сейчас **не передавать** (непустое → 400).
- В закрытую сессию → 400.
- Сообщение в сессию, где агент ещё работает, — допустимо: бэкенд поставит его в очередь
  (или подмешает в активный запуск — политика воркера), ничего не теряется.

## [5] События `webchat_message`

Публикация в `webchat:{sessionId}`:

```json
{ "type": "webchat_message",
  "payload": {
    "sessionId": "0197...",
    "channelId": "0197...",
    "agentId": "0197...",
    "messageId": "b3f0...",
    "direction": "USER",          // USER | AGENT
    "stream": null,               // null (USER) | "progress" | "answer" | "error"
    "text": "Привет! Что в бэклоге?",
    "parts": null,                // вложения ответа агента, см. [5.1]; null — их нет
    "createdAt": "2026-07-08T12:00:01Z"
  } }
```

Правила обработки:

| Случай | Что делать |
|---|---|
| `direction=USER` | Echo своего (или из другой вкладки) сообщения. Если `messageId` уже отрисован оптимистично — пометить доставленным, не дублировать. |
| `AGENT` + `stream=progress` | Промежуточный шаг работы агента (строка, не токен-стрим). Показывать как «агент работает: …» / свёрнутые шаги. |
| `AGENT` + `stream=answer` | Финальный ответ — основной пузырь. После него можно скрыть индикатор работы. |
| `AGENT` + `stream=error` | Ошибка запуска — показать как системное сообщение. |

**Дедупликация обязательна**: доставка at-least-once (ретраи бэка могут повторить событие) —
игнорируйте `messageId`, который уже отображён. На один вопрос может прийти несколько
progress-событий и одно answer; у answer и progress разные `messageId`.

Между отправкой и ответом показывайте индикатор «агент думает…» (первое событие обычно
progress). Таймаут индикатора — на усмотрение UI; сообщения в любом случае попадут в историю.

## [5.1] Вложения ответа агента (`parts`)

Ответ агента (`stream=answer`) может нести файлы — чаще всего изображения (скриншоты):

```json
"parts": [
  { "type": "image",            // image | video | audio | file
    "fileId": "agf_0197...",
    "mime": "image/png",
    "size": 384211,
    "url": "/files/agf_0197...?exp=1789000000&sig=Ab12..." }
]
```

- `url` — подписанный URL содержимого, **относительный к context path** (как все пути этого
  документа): префиксуйте `{origin}/control`. Работает в `<img src>` без Authorization-заголовка.
- `type=image` → рендерить инлайном (`<img>`); остальные типы — карточкой-ссылкой на скачивание
  (сервер отдаст их `Content-Disposition: attachment`).
- Ссылка живёт ~15 минут. 403 на ссылке из старого события — перечитать историю ([6]): каждая
  выдача подписывает `url` заново. 404 — файл удалён по TTL хранилища, показать заглушку.
- `parts` приходят только с `stream=answer`; в `progress` их не бывает.

## [6] История сессии

`GET /manage/webchat/sessions/{sessionId}/messages/?page=0&size=50`

```json
{ "response": {
  "content": [
    { "id": "0197...", "messageId": "c1a2...", "direction": "AGENT",
      "stream": "answer", "text": "В бэклоге 3 задачи: ...", "parts": null,
      "createdAt": "2026-07-08T12:00:05" },
    { "id": "0197...", "messageId": "b3f0...", "direction": "USER",
      "stream": null, "text": "Привет! Что в бэклоге?", "createdAt": "2026-07-08T12:00:01" }
  ],
  "totalElements": 2, "totalPages": 1, "number": 0, "size": 50, "...": "стандартный Spring Page, как у /manage/skills/"
} }
```

**Новые сначала** (`page=0` — свежие): для отрисовки разверните страницу; подгрузка вверх
(infinite scroll) — следующие страницы. Это та же лента, что и события, — можно восстановить чат
после перезагрузки и досклеить live-события поверх (дедуп по `messageId`).

## [7] Закрыть сессию

`DELETE /manage/webchat/sessions/{sessionId}` → `{ "response": <WebchatSessionResponse c closedAt> }`

Мягкое закрытие: история остаётся читаемой, отправка в неё вернёт 400. «Продолжить разговор» —
просто новая сессия с тем же агентом.

---

## Ограничения текущей версии

- **Файлы — только от агента.** Вложения ответа агента работают ([5.1]); `parts` в *отправке*
  пользователя по-прежнему зарезервирован — не передавать (непустое → 400).
- **Нет токен-стриминга** ответа: `progress` — это строки-шаги работы агента, `answer` приходит целиком.
- **Список сессий не live** (подписка — per-session). Обновлять по событиям/фокусу.
- `stream=error` и тексты ошибок пока не локализованы.
